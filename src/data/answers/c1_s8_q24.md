# HikariCP: Các tham số Tuning hiệu năng thực chiến

## ⚡ Tóm tắt ngắn (30s)
Để tinh chỉnh **HikariCP** đạt hiệu suất tối ưu và hoạt động ổn định ở môi trường High Traffic, bạn cần tập trung vào 4 nhóm cấu hình cốt lõi:
1. **Fixed-Size Pool**: Luôn đặt `minimum-idle` bằng `maximum-pool-size` để loại bỏ chi phí giãn nở pool cục bộ.
2. **Fail Fast (Chặn lỗi nhanh)**: Giảm `connection-timeout` xuống mức 2s - 5s (mặc định là 30s - quá lâu cho người dùng).
3. **Ngăn lỗi Broken Pipe**: Đảm bảo `max-lifetime` ngắn hơn timeout của DB (như `wait_timeout` của MySQL) ít nhất 30 giây.
4. **Prepared Statement Caching (Bật bộ đệm câu lệnh)**: Kích hoạt cache câu lệnh SQL ở phía driver (đặc biệt là MySQL JDBC Driver) để tiết kiệm thời gian phân tích cú pháp SQL.

## 🔍 Chi tiết bản chất thực chiến các tham số Tuning

### 1. Triết lý "Fixed-Size Pool" (Kích thước cố định)
* **Tham số**: `minimum-idle = maximum-pool-size` (Ví dụ: đều đặt bằng 30).
* **Bản chất**: Nếu bạn đặt `minimum-idle = 10` và `maximum-pool-size = 50`. Khi traffic tăng đột biến, HikariCP sẽ cuống cuồng thực hiện các bắt tay TCP/IP, TLS và xác thực để mở thêm 40 kết nối mới dưới DB. Quá trình này cực kỳ chậm và gây trồi sụt độ trễ API (Latency Spikes).
* **Best Practice**: Việc giữ các kết nối luôn mở (Fixed-Size) giúp loại bỏ hoàn toàn chi phí khởi tạo kết nối trên đường đi của request người dùng.

### 2. Ngăn ngừa kết nối "Chết ngầm" (Connection Eviction & Max Lifetime)
* **Vấn đề**: Database Engine luôn có một cấu hình tự động đóng các kết nối rảnh rỗi sau một thời gian (ví dụ: `wait_timeout` của MySQL mặc định là 8 tiếng, nhưng các DBA thường hạ xuống 5-10 phút để tiết kiệm tài nguyên). Nếu kết nối trong HikariCP đã rảnh quá 5 phút nhưng HikariCP vẫn nghĩ nó còn sống và bàn giao cho ứng dụng, ứng dụng sẽ quăng ra lỗi `Communications link failure` hoặc `Broken pipe`.
* **Tham số**: `max-lifetime`
* **Best Practice**:
  * Đặt `max-lifetime` ngắn hơn `wait_timeout` của DB ít nhất 30 giây đến 1 phút.
  * *Ví dụ*: Nếu MySQL `wait_timeout` là 120 giây (2 phút), thì hãy đặt `max-lifetime = 90000` (90 giây).

### 3. Fail-Fast (connection-timeout)
* **Vấn đề**: Khi pool hết kết nối sạch sẽ do DB bị khóa (Lock) hoặc quá tải, luồng request của người dùng mặc định sẽ xếp hàng chờ **30 giây** (`connection-timeout = 30000ms`). 30 giây là khoảng thời gian quá dài, làm treo toàn bộ các Thread của Web Server (như Tomcat), dẫn đến sập dây chuyền toàn bộ hệ thống (Cascading Failure).
* **Best Practice**: Hạ thấp `connection-timeout` xuống từ **2000ms đến 5000ms (2s - 5s)**. Nếu hệ thống quá tải, ta chấp nhận báo lỗi nhanh (Fail-Fast) hoặc kích hoạt Circuit Breaker trả về kết quả fallback cho người dùng, giải phóng thread Web Server lập tức.

### 4. Leak Detection (Phát hiện rò rỉ kết nối)
* **Vấn đề**: Các lập trình viên vô tình viết code quên giải phóng kết nối, làm pool cạn kiệt dần.
* **Tham số**: `leak-detection-threshold`
* **Best Practice**: Đặt từ **2000 đến 5000** (độ trễ 2s - 5s). Nếu bất kỳ luồng nào giữ kết nối lâu hơn ngưỡng này mà không gọi `close()`, HikariCP sẽ in ra một stack trace chi tiết kèm theo vị trí dòng code chính xác đang gây rò rỉ.
  * *Chú ý*: Không đặt quá thấp (ví dụ: < 1000ms) vì có thể gây ra các cảnh báo giả (false alarm) khi DB chạy các câu lệnh batch job hợp lệ nhưng nặng.

## 💻 Cấu hình thực chiến: Tối ưu kết hợp giữa HikariCP và MySQL Driver

MySQL JDBC Driver mặc định tắt toàn bộ cơ chế lưu đệm câu lệnh đã chuẩn bị (Prepared Statement Cache). Để tối ưu tối đa hiệu năng, bạn bắt buộc phải bật cấu hình này thông qua các tham số mở rộng `data-source-properties`:

```yaml
spring:
  datasource:
    url: jdbc:mysql://db-prod.internal:3306/sales_db?rewriteBatchedStatements=true
    username: production_app
    password: secure_pass
    hikari:
      pool-name: OptimizedHikariPool
      maximum-pool-size: 32
      minimum-idle: 32
      connection-timeout: 3000   # 3 giây timeout (Fail fast)
      max-lifetime: 600000       # 10 phút (Đảm bảo nhỏ hơn wait_timeout của MySQL)
      idle-timeout: 300000
      leak-detection-threshold: 2000 # Cảnh báo rò rỉ sau 2 giây giữ kết nối
      
      # 🚀 Tinh chỉnh tối ưu hóa Prepared Statement phía MySQL Driver
      data-source-properties:
        cachePrepStmts: true             # Bật bộ nhớ đệm Prepared Statements phía Client
        prepStmtCacheSize: 250           # Số lượng câu lệnh SQL được phép cache (Khuyên dùng từ 250 - 500)
        prepStmtCacheSqlLimit: 2048      # Độ dài tối đa của câu SQL được cache (2KB)
        useServerPrepStmts: true         # Ép buộc driver sử dụng Prepared Statements phía Server
        useLocalSessionState: true       # Tránh việc truy vấn lại DB chỉ để kiểm tra trạng thái Session
        useLocalTransactionState: true   # Tương tự cho trạng thái Transaction
```

## 📊 Bảng tra cứu thông số Tuning HikariCP thực chiến

| Tham số | Giá trị mặc định | Giá trị đề xuất (Production) | Mục tiêu thiết kế |
| :--- | :--- | :--- | :--- |
| **`maximum-pool-size`**| 10 | **20 - 50** (Tùy theo số Cores của DB CPU) | Tối ưu hóa năng lực xử lý vật lý của DB |
| **`minimum-idle`** | 10 | **Bằng `maximum-pool-size`** | Giảm thiểu độ trễ co giãn pool ngầm |
| **`connection-timeout`**| 30000 (30s) | **2000 - 5000** (2s - 5s) | Tránh treo luồng Web Server khi DB nghẽn |
| **`max-lifetime`** | 1800000 (30m) | **Ngắn hơn DB Timeout 30s** | Triệt tiêu lỗi kết nối chết ngầm (Broken Pipe) |
| **`leak-detection-threshold`**| 0 (Tắt) | **2000 - 5000** (2s - 5s) | Sớm phát hiện rò rỉ kết nối từ code |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Lỗi "HikariPool-1 - Connection is not available, request timed out after X ms"
Đây là lỗi kinh điển nhất trên Production. Khi gặp lỗi này, bạn cần tiến hành phân tích theo 3 bước sau:
1. **Kiểm tra Slow Queries**: Sử dụng APM (như NewRelic, Datadog) hoặc Slow Query Log để xem có câu lệnh nào chạy mất vài giây không. Nếu một câu lệnh chạy quá lâu, nó sẽ giữ chặt kết nối, làm cạn kiệt pool cực kỳ nhanh.
2. **Kiểm tra Connection Leak**: Xem trong file log có thông báo `Apparent connection leak detected` từ `leak-detection-threshold` hay không.
3. **Tải tăng đột biến (CPU DB Spike)**: CPU của Database Server chạm ngưỡng 100%, khiến thời gian xử lý mọi truy vấn bị kéo dài, dẫn đến hàng đợi mượn kết nối bị ùn ứ.
   * *Giải pháp khắc phục*: Tuyệt đối **không tự ý tăng `maximum-pool-size`** lên quá lớn vì nó sẽ chỉ làm CPU DB bị nghẽn nặng hơn do đổi ngữ cảnh luồng. Thay vào đó, hãy tập trung thêm Index, phân tách Read/Write hoặc nâng cấp cấu hình phần cứng DB Server.
