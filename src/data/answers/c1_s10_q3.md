# Monolith Modular và Microservices khác nhau thế nào?

## ⚡ Tóm tắt ngắn (30s)
*   **Bản chất**: Cả hai kiến trúc đều hướng tới mục tiêu phân rã hệ thống thành các khối độc lập có tính bao đóng cao (High Cohesion, Low Coupling). Sự khác biệt cốt lõi là **Ranh giới vật lý (Physical & Runtime Boundaries)**:
    *   **Modular Monolith**: Các mô-đun được tách biệt về mặt cấu trúc mã nguồn (Logic) nhưng chạy chung một tiến trình xử lý dưới RAM, dùng chung bộ nhớ JVM và giao tiếp thông qua các cuộc gọi phương thức trực tiếp (**In-memory calls**, < 1 microsecond).
    *   **Microservices**: Các mô-đun được phân tách vật lý hoàn toàn. Mỗi dịch vụ chạy trên một tiến trình riêng biệt (Docker container), sở hữu Database riêng đĩa vật lý và bắt buộc phải giao tiếp qua giao thức mạng (**Network hops**: HTTP, gRPC, Message Queue, từ 5 - 50 miliseconds).
*   **Các điểm nhấn thực chiến**:
    1.  **Hiệu năng & Độ trễ**: Modular Monolith nhanh hơn Microservices gấp hàng vạn lần do không tốn chi phí tuần tự hóa (Serialization) và truyền tin qua card mạng.
    2.  **Độ nhất quán dữ liệu**: Modular Monolith xử lý giao dịch vô cùng đơn giản bằng cơ chế ACID của Database cục bộ. Microservices bắt buộc phải dùng Giao dịch phân tán (Saga, Outbox) phức tạp và tiềm ẩn rủi ro sai lệch dữ liệu.
    3.  **Chi phí vận hành**: Modular Monolith chỉ cần một vài server và 1 DB, chi phí vận hành cực rẻ. Microservices yêu cầu cả một hệ sinh thái DevOps (K8s, API Gateway, Distributed Tracing, Kafka) khổng lồ.
*   **Quyết định Senior**: Modular Monolith là giải pháp tối ưu cho hầu hết các doanh nghiệp vừa và lớn khi nghiệp vụ phức tạp nhưng quy mô team chưa vượt quá 30 người. Nó cho phép thiết kế hệ thống sạch sẽ, bảo vệ cấu trúc miền (Domain boundaries), và sẵn sàng tách lên Microservices bất kỳ lúc nào mà không phải gánh chịu chi phí vận hành quá sớm.

## 🔍 Chi tiết bản chất thực chiến

### Ranh giới Logical vs Ranh giới Vật lý

Sự khác biệt lớn nhất giữa hai kiến trúc được thể hiện qua sơ đồ dòng chảy thực thi:

```mermaid
graph TD
    subgraph Modular Monolith (Single Process)
        OrderModule[Order Module] -->|In-memory Call <1ms| PaymentModule[Payment Module]
        OrderModule -->|Local JDBC TX| DBShared[(Single Database - Separate Schemas)]
        PaymentModule -->|Local JDBC TX| DBShared
    end

    subgraph Microservices (Multi-Process via Network)
        OrderService[Order Service] -->|REST/gRPC Call 10ms-50ms| PaymentService[Payment Service]
        OrderService -->|JDBC TX| DBOrder[(Order DB)]
        PaymentService -->|JDBC TX| DBPayment[(Payment DB)]
    end

    style OrderModule fill:#dff,stroke:#388,stroke-width:2px
    style PaymentModule fill:#dff,stroke:#388,stroke-width:2px
    style OrderService fill:#dfd,stroke:#3c3,stroke-width:2px
    style PaymentService fill:#dfd,stroke:#3c3,stroke-width:2px
```

*   **Modular Monolith**: Ranh giới chỉ mang tính **bao đóng mã nguồn** (Logical Boundary). Khi `OrderModule` gọi `PaymentModule`, hệ thống thực thi một lệnh gọi phương thức trên luồng Stack của JVM. Nếu xảy ra lỗi, giao dịch cơ sở dữ liệu chung sẽ tự động rollback nhờ JDBC Connection duy nhất.
*   **Microservices**: Ranh giới mang tính **phân tách mạng** (Network Boundary). `OrderService` và `PaymentService` chạy ở hai server khác nhau. Để gọi nhau, dữ liệu phải được convert thành JSON/Protobuf, đẩy qua card mạng và xử lý bất đồng bộ. Việc Rollback dữ liệu khi có lỗi yêu cầu viết code nghiệp vụ bù trừ (Compensating Transactions) vô cùng phức tạp.

## 💻 Code thực chiến: BAD vs GOOD

###  Modular Monolith: Giao tiếp bộ nhớ phi liên kết (Decoupled In-Memory Communication)
Trong Modular Monolith, để tránh việc `OrderModule` gọi trực tiếp đến class thực thi của `InventoryModule` gây liên kết cứng (Tight Coupling), chúng ta sử dụng cơ chế Sự kiện Nội bộ của Spring Framework. Cuộc gọi diễn ra hoàn toàn trên RAM nhưng các mô-đun độc lập nhau 100%.

```java
// --- PACKAGE: com.company.app.order ---
package com.company.app.order;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final ApplicationEventPublisher eventPublisher;

    public OrderService(OrderRepository orderRepository, ApplicationEventPublisher eventPublisher) {
        this.orderRepository = orderRepository;
        this.eventPublisher = eventPublisher;
    }

    @Transactional
    public void completeOrder(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.setStatus("COMPLETED");
        orderRepository.save(order);

        // Đúng đắn 1: Phát sự kiện trên RAM của JVM. Không có mạng, cực kỳ nhanh!
        eventPublisher.publishEvent(new OrderCompletedEvent(order.getId(), order.getProductId(), order.getQuantity()));
    }
}

// --- PACKAGE: com.company.app.inventory ---
package com.company.app.inventory;

import com.company.app.order.OrderCompletedEvent;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class InventoryService {
    private final InventoryRepository inventoryRepository;

    public InventoryService(InventoryRepository inventoryRepository) {
        this.inventoryRepository = inventoryRepository;
    }

    @EventListener // Đúng đắn 2: Lắng nghe sự kiện đồng bộ trong cùng Transaction vật lý của luồng hiện tại
    @Transactional
    public void handleOrderCompleted(OrderCompletedEvent event) {
        Inventory inventory = inventoryRepository.findByProductId(event.getProductId());
        inventory.setStock(inventory.getStock() - event.getQuantity());
        inventoryRepository.save(inventory);
    }
}
```

###  Microservices: Giao tiếp vật lý qua Message Broker (Kafka Event Driven)
Khi hệ thống phình to và được tách thành hai microservices chạy trên hai Kubernetes Pod khác nhau, luồng xử lý trên RAM sẽ được thay thế bằng hạ tầng Kafka Message Broker để giao tiếp xuyên suốt mạng.

**1. Order Service đẩy sự kiện lên mạng:**
```java
package com.company.app.orderservice;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public OrderService(OrderRepository orderRepository, KafkaTemplate<String, OrderEvent> kafkaTemplate) {
        this.orderRepository = orderRepository;
        this.kafkaTemplate = kafkaTemplate;
    }

    public void completeOrder(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.setStatus("COMPLETED");
        orderRepository.save(order);

        // Bắt buộc 1: Chuyển đổi dữ liệu (Serialize) và đẩy qua mạng đến Kafka cluster
        kafkaTemplate.send("order-completed-topic", new OrderEvent(order.getId(), order.getProductId(), order.getQuantity()));
    }
}
```

**2. Inventory Service nhận sự kiện, bắt buộc phải xử lý Idempotency chống trùng lặp tin nhắn:**
```java
package com.company.app.inventoryservice;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Service;

@Service
public class InventoryListener {
    private final InventoryService inventoryService;
    private final IdempotencyTokenRepository tokenRepository;

    @KafkaListener(topics = "order-completed-topic", groupId = "inventory-group")
    public void consumeOrderCompleted(OrderEvent event) {
        // Bắt buộc 2: Kiểm tra chống xử lý trùng lặp (Idempotent check) vì mạng có thể retry tin nhắn
        if (tokenRepository.existsById(event.getOrderId())) {
            return; // Đã xử lý rồi, bỏ qua
        }

        inventoryService.deductStock(event.getProductId(), event.getQuantity());
        tokenRepository.save(new IdempotencyToken(event.getOrderId()));
    }
}
```

## 📊 Bảng so sánh chi tiết toàn diện

| Đặc tính kiến trúc | Modular Monolith | Microservices |
| :--- | :--- | :--- |
| **Độ trễ giao tiếp (Network Latency)** | **Bằng không** (< 1 $\mu s$, trực tiếp trên RAM). | **Cao** (5 - 50ms tùy giao thức HTTP/gRPC). |
| **Khả năng tách nhóm (Team Autonomy)** | Khá cao. Các nhóm sở hữu module mã nguồn riêng. | **Tuyệt đối**. Các nhóm tự quyết định lịch release và stack. |
| **Tính toàn vẹn giao dịch (ACID)** | **Nhất quán tức thời** (Local Transaction). | **Eventual Consistency** (Saga, Outbox, Reconciliation). |
| **Cơ chế gọi API lỗi (Failure Handling)**| Gọi phương thức thông thường, không lo sập mạng. | **Bắt buộc** có Retry, Circuit Breaker, Fallback. |
| **Tách biệt Database vật lý** | Không bắt buộc (chỉ cần phân rã Logical schema). | **Bắt buộc** (mỗi service 1 database vật lý). |
| **Chi phí cơ sở hạ tầng (Hạ tầng Cloud)** | Rất thấp. Chạy trên 1 cụm server nhỏ. | **Cực kỳ tốn kém** do sự bùng nổ của số lượng container. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy phá vỡ tính bao đóng (Modular Leakage) trong Modular Monolith
*   **Vấn đề thực tế**: Trong một Modular Monolith viết bằng Java, lập trình viên của `OrderModule` vô tình import một class mang tính chất nội bộ (internal) của `InventoryModule` (ví dụ: `InventoryEntity` hoặc `InventoryServiceImpl`) chỉ để lấy dữ liệu nhanh hơn, thay vì gọi qua Interface API công khai.
*   **Hậu quả**: Thiết kế bị suy thoái thành Monolith đống mì Spaghetti truyền thống. Khi cần tách module thành Microservice, bạn không thể bóc tách vì mã nguồn đã bị dính chặt vào nhau.
*   **Giải pháp**: Sử dụng thư viện **ArchUnit** trong các Unit Test để tự động kiểm tra và ngăn chặn các lập trình viên import sai cấu trúc mô-đun quy định.

### 2. Sự ngộ nhận về ranh giới Module bằng Package
*   **Vấn đề**: Nhiều người nghĩ chỉ cần chia folder (package) là đã có Modular Monolith.
*   **Hậu quả**: Nếu các bảng database của các package vẫn `JOIN` chéo nhau vô tội vạ trong code SQL, thì việc chia folder Java hoàn toàn vô nghĩa. Ranh giới database logical mới là thứ quan trọng nhất quyết định khả năng tách dịch vụ.

### 3. Câu hỏi đào sâu từ interviewer
*   **Q: Làm thế nào để tự động hóa việc kiểm tra ranh giới giữa các mô-đun trong Modular Monolith bằng code, ngăn chặn tuyệt đối tình trạng lập trình viên phá vỡ cấu trúc một cách vô ý?**
    *   *Trả lời*: Cách chuyên nghiệp nhất để bảo vệ ranh giới kiến trúc của Modular Monolith là sử dụng thư viện **ArchUnit** tích hợp trực tiếp vào quy trình chạy Unit Test của CI/CD:
        1.  **ArchUnit** là một thư viện Java mã nguồn mở chuyên dùng để kiểm tra cấu trúc kiến trúc của mã nguồn Java (phân tích bytecode).
        2.  Ta viết một Unit Test đặc biệt để định nghĩa các quy tắc phụ thuộc giữa các package:
        ```java
        @AnalyzeClasses(packages = "com.company.app")
        public class ArchitectureTest {

            @ArchTest
            public static final ArchRule order_module_should_not_access_inventory_internals = 
                noClasses().that().resideInAPackage("..order..")
                .should().accessClassesThat().resideInAPackage("..inventory.internal..");

            @ArchTest
            public static final ArchRule database_entities_should_be_private_to_modules = 
                classes().that().areAnnotatedWith(Entity.class)
                .should().onlyBeAccessed().byClassesThat().resideInAnyPackage("..internal..", "..repository..");
        }
        ```
        3.  Khi bất kỳ lập trình viên nào cố tình import một class cấm, Unit Test này sẽ bị fail lập tức trên máy local hoặc trên luồng CI/CD, ngăn chặn pull request được merge và bảo vệ tính toàn vẹn của cấu trúc mô-đun 100%.
