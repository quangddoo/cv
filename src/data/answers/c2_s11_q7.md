# Race condition tạo double booking. Bạn fix thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Lỗi đặt trùng (Double Booking) là một dạng lỗ hổng đồng thời cực kỳ phổ biến thuộc nhóm **"Đọc rồi mới Ghi" (Check-then-Act Vulnerability)**. Khi hai luồng xử lý song song cùng đọc thấy trạng thái "Ghế/Phòng còn trống" và cùng ra quyết định chèn bản ghi đặt chỗ, hệ thống sẽ tạo ra hai lượt đặt chỗ cho cùng một tài nguyên duy nhất.
* **Thảm họa thực chiến được giải quyết**:
  1. **Đặt trùng ghế xem phim/máy bay**: Khách hàng A và B cùng chọn ghế `G12`. Cả hai request kiểm tra thấy ghế trống ở tầng ứng dụng và tiến hành thanh toán thành công. Kết quả: Hai khách hàng đến rạp phim cầm hai vé cùng số ghế, nhân viên rạp phải đền bù voucher VIP và xin lỗi trong sự phẫn nộ của khách.
  2. **Vỡ trận đặt phòng khách sạn (Overbooking)**: Khách sạn chỉ còn 1 phòng Deluxe. Hai trang OTA (như Agoda, Booking.com) cùng gọi API đặt phòng đồng thời. Do thiếu cơ chế khóa đồng thời, cả hai khách hàng đều nhận được email xác nhận đặt phòng thành công, buộc khách sạn phải chuyển khách sang cơ sở khác xa hơn với chi phí gấp đôi.
* **Quyết định Senior**:
  1. **Tạo Unique Constraint / Composite Index vật lý**: Đây là chốt chặn cuối cùng bắt buộc phải có. Ví dụ: `UNIQUE INDEX (seat_id, showtime_id)` hoặc `UNIQUE INDEX (room_id, booking_date)`.
  2. **Sử dụng Khóa phân tán Redis (Distributed Lock - Redlock) cho hệ thống Scale lớn**: Nhằm chặn đứng request trùng lặp ngay tại cửa ngõ API, giảm tải tối đa cho Database khỏi các câu lệnh ghi chắc chắn sẽ thất bại.
  3. **Pessimistic Lock (SELECT FOR UPDATE) cho hệ thống RDBMS truyền thống**: Thích hợp khi lượng request không quá khổng lồ và muốn tận dụng tính toàn vẹn ACID của DB để xử lý đặt chỗ một cách tuyệt đối an toàn.

## 🔍 Chi tiết bản chất thực chiến: Tại sao xảy ra & Luồng xử lý lỗi

### Kịch bản "Check-then-Act" điển hình tàn phá hệ thống:

```java
public void bookSeat(Long seatId) {
    // Bước 1: Đọc DB kiểm tra trạng thái ghế
    Seat seat = seatRepository.findById(seatId).get();
    if (seat.isBooked()) { 
        throw new SeatAlreadyBookedException(); 
    }
    
    // Bước 2: Thanh toán & Đổi trạng thái ghế
    seat.setBooked(true);
    seatRepository.save(seat); // Ghi đè song song phá hủy logic!
}
```

Khi luồng A và luồng B chạy song song, cả hai luồng cùng chạy xong Bước 1 trước khi bất kỳ luồng nào kịp chạy Bước 2. Cả hai đều đọc thấy `isBooked = false` và tự tin ghi đè trạng thái thành `true`, dẫn đến thảm họa Double Booking.

        ▼                                     ▼

 │ Lấy Lock    │                       │ Lấy Lock    │

        │                               └─────────────┘
        ▼
  [Giải phóng Lock]

## 💻 Code thực chiến: Giải pháp Đặt ghế an toàn bằng Redisson (Redis Lock) trong Java

Dưới đây là mã nguồn sử dụng thư viện **Redisson** để lấy khóa phân tán. Khóa phân tán đảm bảo rằng tại một thời điểm, chỉ có duy nhất một máy chủ trong cụm Microservices được quyền kiểm tra và đặt một số ghế cụ thể.

### 1. Cấu hình Unique Index dưới DB (Lá chắn vật lý tối thượng)
Trước khi viết code, bắt buộc phải đảm bảo DB có ràng buộc vật lý để không bao giờ có thể chèn trùng:
```sql
ALTER TABLE ticket_bookings ADD CONSTRAINT uq_seat_showtime UNIQUE (seat_id, showtime_id);
```

### 2. Code Java xử lý đặt vé an toàn với Redis Lock và Database Transaction

```java
package com.example.booking;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.concurrent.TimeUnit;

@Service
@RequiredArgsConstructor
@Slf4j
public class BookingService {

    private final RedissonClient redissonClient;
    private final SeatRepository seatRepository;
    private final BookingRepository bookingRepository;

    public BookingResponse bookSeatSecure(Long seatId, Long showtimeId, Long userId) {
        // Tạo key lock duy nhất cho từng chiếc ghế trong suất chiếu cụ thể
        String lockKey = String.format("lock:seat:%d:showtime:%d", seatId, showtimeId);
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // Cố gắng lấy lock trong vòng 3 giây, tự động giải phóng lock sau 10 giây nếu crash
            boolean isLocked = lock.tryLock(3, 10, TimeUnit.SECONDS);
            
            if (!isLocked) {
                log.warn("User {} could not acquire lock for seat {} during showtime {}", userId, seatId, showtimeId);
                return BookingResponse.fail("Seat is currently being locked by another user. Please try again.");
            }

            // Gọi phương thức chứa Transaction để xử lý nghiệp vụ ghi DB
            return executeBookingTransaction(seatId, showtimeId, userId);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return BookingResponse.fail("Request interrupted due to high traffic.");
        } finally {
            // Luôn luôn giải phóng lock ở khối finally
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.info("Successfully released lock for key: {}", lockKey);
            }
        }
    }

    // Phương thức Transaction phải để ở tầng Service và gọi qua Proxy
    @Transactional
    public BookingResponse executeBookingTransaction(Long seatId, Long showtimeId, Long userId) {
        // 1. Kiểm tra trạng thái ghế trực tiếp trong DB
        Seat seat = seatRepository.findBySeatIdAndShowtimeId(seatId, showtimeId)
                .orElseThrow(() -> new IllegalArgumentException("Seat not found"));

        if (seat.isBooked()) {
            return BookingResponse.fail("This seat has already been booked by someone else.");
        }

        try {
            // 2. Cập nhật trạng thái ghế
            seat.setBooked(true);
            seat.setBookedByUserId(userId);
            seatRepository.saveAndFlush(seat);

            // 3. Tạo bản ghi hóa đơn đặt vé
            TicketBooking booking = new TicketBooking();
            booking.setSeatId(seatId);
            booking.setShowtimeId(showtimeId);
            booking.setUserId(userId);
            booking.setStatus("PENDING_PAYMENT");
            bookingRepository.save(booking);

            return BookingResponse.success(booking.getId(), "Seat reserved successfully!");

        } catch (DataIntegrityViolationException e) {
            // Bắt lỗi Unique Constraint từ DB phòng trường hợp hiếm hoi bị lọt lưới
            log.error("Database constraint hit! Duplicate booking prevented for seat {} - showtime {}", seatId, showtimeId, e);
            return BookingResponse.fail("This seat is already booked (Database Constraint).");
        }
    }
}
```

## 📊 Bảng so sánh các giải pháp phòng chống Double Booking

| Phương pháp | Độ an toàn | Hiệu năng hệ thống | Ưu điểm | Nhược điểm | Chi phí triển khai |
| :--- | :---: | :---: | :--- | :--- | :--- |
| **Database Unique Index** | **100% Tuyệt đối** | Tốt | Lá chắn vật lý cuối cùng, cực kỳ nhẹ và đơn giản. | Chỉ chặn được lúc chèn mới (`INSERT`), khó áp dụng cho luồng cập nhật trạng thái (`UPDATE`). | Rất rẻ (Miễn phí) |
| **Pessimistic Write Lock (`FOR UPDATE`)** | **100% Tuyệt đối** | Kém khi scale ngang | Tận dụng an toàn ACID của DB, không cần hạ tầng ngoài. | Gây giữ Connection Pool lâu, dễ dẫn đến nghẽn cổ chai nếu hệ thống có traffic lớn. | Rẻ |
| **Optimistic Lock (`@Version`)** | **Cao** | Rất tốt khi ít xung đột | Hiệu năng siêu cao vì không khóa tài nguyên trước. | Tỉ lệ lỗi ném ra cao khi có tranh chấp lớn, bắt buộc tầng ứng dụng phải tự viết cơ chế Retry phức tạp. | Trung bình |
| **Distributed Lock (Redis Redlock)** | **Rất cao** | **Siêu cao** | Chặn lỗi từ tầng nhớ tạm, giảm tải hoàn toàn cho DB. Phù hợp tuyệt đối với Microservices. | Cực kỳ phức tạp khi cấu hình (cần cụm Redis Cluster), rủi ro "Split-brain" hoặc hết hạn khóa sớm. | Cao |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Hết hạn Lock trước khi DB kịp Commit" (The Lock-Commit Race Condition)
* **Vấn đề nguy hiểm**: Nhìn vào đoạn code trên, nếu ta cấu hình thời gian giữ lock tự động quá ngắn (ví dụ 2 giây), trong khi DB đang bị chậm (quá tải CPU) và Transaction cần tới 3 giây để thực hiện `COMMIT`. 
  * Lúc này, ở giây thứ 2, Lock trong Redis bị giải phóng. Luồng B nhảy vào lấy Lock thành công, chèn dữ liệu. Sau đó luồng A mới thực hiện commit thành công. Kết quả: **Vẫn bị double booking dù đã dùng Lock!**
* **Cách khắc phục**:
  1. Sử dụng tính năng **Redisson RedLock Watchdog**. Watchdog sẽ tự động gia hạn thời gian khóa (Lock renewal) liên tục mỗi khi khóa sắp hết hạn, và chỉ dừng gia hạn khi Transaction đã hoàn tất và phương thức `unlock()` được gọi một cách chủ động.
  2. Bắt buộc đặt thời gian khóa (Lease time) lớn hơn đáng kể so với Transaction timeout.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Nếu hệ thống của tôi là rạp phim bán vé siêu hot (như vé concert Taylor Swift), hàng chục ngàn người cùng tranh nhau 100 chiếc ghế VIP trong 1 giây. Việc dùng Redis Distributed Lock cho từng ghế có làm sập hệ thống Redis không? Bạn tối ưu thế nào?"**
* **Trả lời**:
  * Khi hàng chục ngàn người cùng tranh mua số lượng ghế giới hạn, việc dùng Redis Lock trên từng `seat_id` vẫn chịu tải rất tốt vì Redis có thể xử lý tới 100,000+ ops/sec.
  * Tuy nhiên để tối ưu vượt trội, Senior sẽ áp dụng giải pháp **"Phân mảnh tồn kho ảo" (Virtual Inventory Partitioning / Redis Token Bucket)**:
    1. Đưa toàn bộ trạng thái ghế lên bộ nhớ đệm Redis (ví dụ lưu dưới dạng Bitmap hoặc Set).
    2. Request của người dùng chỉ cần gọi lệnh `SPOP` hoặc kiểm tra nhanh trên Redis. Nếu lấy được ghế thành công trên Redis, mới cho phép đi tiếp vào luồng thanh toán và ghi xuống DB.
    3. DB lúc này chỉ đóng vai trò ghi nhận kết quả cuối cùng (Asynchronous Write-behind) thông qua Kafka, loại bỏ hoàn toàn hiện tượng nghẽn cổ chai ghi trực tiếp vào DB.
