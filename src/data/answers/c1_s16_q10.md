# Thiết kế dịch vụ Tải lên tệp tin dung lượng lớn (Resumable File Upload Service)

## ⚡ Tóm tắt ngắn (30s)
* **Mục tiêu**: Thiết kế dịch vụ tải lên tệp tin lớn (hàng chục GB như video 4K, tệp zip) ổn định, hỗ trợ tạm dừng và tải lên tiếp tục (Resumable Upload), bảo mật cao, tối ưu hóa băng thông cho Backend và phân phối tệp tải xuống toàn cầu với độ trễ thấp thông qua CDN.
* **Core Logic**:
  * **Tải lên phân đoạn (Chunked Upload)**: Client chia tệp lớn thành các phần nhỏ (Chunks) khoảng 5-10MB, tính mã băm MD5/SHA-256 cho từng phần. Các phần được tải lên song song và độc lập. Nếu mất mạng giữa chừng, hệ thống chỉ cần tải lên tiếp tục các phần bị lỗi (Resumable).
  * **Tải lên trực tiếp qua Presigned URL (AWS S3 / GCS)**: Tránh để dữ liệu nhị phân chạy qua Backend để tránh nghẽn CPU và băng thông. Backend chỉ đóng vai trò điều phối điều khiển (Control Plane), sinh mã **Presigned URL** bảo mật để Client đẩy trực tiếp luồng dữ liệu (Data Plane) lên Object Storage.
  * **Phân phối qua CDN & Cache Eviction**: Đặt CDN (Cloudflare/CloudFront) phía trước Object Storage để tăng tốc độ tải xuống. Cấu hình cơ chế ký URL tải xuống (Signed URLs) để bảo mật nội dung trả phí.

## 🔍 Yêu cầu hệ thống (Requirements)

### 1. Functional Requirements
* **Khởi tạo phiên tải lên (Initiate Session)**: Bắt đầu phiên tải lên, đăng ký dung lượng và băm toàn bộ tệp.
* **Tải lên phân đoạn**: Cho phép Client đẩy từng phân đoạn (Chunk) của tệp lên.
* **Resumable (Tải lên tiếp tục)**: Truy vấn xem các phân đoạn nào đã tải lên thành công để bỏ qua và chỉ gửi tiếp các phần còn thiếu.
* **Ghép tệp (Assemble File)**: Sau khi tải lên đủ các phân đoạn, hệ thống thực hiện ghép chúng lại thành tệp hoàn chỉnh và kiểm tra tính toàn vẹn.
* **Phân phối qua CDN**: Tải xuống tệp nhanh chóng thông qua các máy chủ bộ đệm ở biên (Edge Servers).

### 2. Non-Functional Requirements
* **Tối ưu hóa băng thông Backend**: Tuyệt đối không để Backend xử lý hoặc lưu tạm (buffer) dữ liệu nhị phân thô của tệp tin.
* **Khả năng chịu lỗi cao (Resilience)**: Đảm bảo luồng tải lên không bị hủy bỏ hoàn toàn khi mạng chập chờn hoặc thay đổi IP (WiFi $\rightarrow$ 4G).
* **Bảo mật và an toàn**: Đảm bảo tệp tin được quét virus trước khi đưa vào sử dụng, kiểm tra tính toàn vẹn bằng Hash MD5/SHA-256.

## 💾 Thiết kế Database & Cơ chế Chunking

### 1. Schema Database (PostgreSQL - Lưu trữ thông tin trạng thái)
Lưu trữ siêu dữ liệu (Metadata) và tiến độ tải lên của từng phần tệp để phục vụ tính năng Resumable.

```sql
CREATE TABLE file_uploads (
    id VARCHAR(64) PRIMARY KEY,
    user_id BIGINT NOT NULL,
    filename VARCHAR(255) NOT NULL,
    file_size BIGINT NOT NULL, -- Kích thước tệp tính bằng bytes
    file_hash VARCHAR(64) NOT NULL, -- SHA-256 hoặc MD5 của toàn bộ tệp
    status VARCHAR(30) NOT NULL DEFAULT 'UPLOADING', -- UPLOADING, COMPLETED, FAILED
    upload_id VARCHAR(255), -- ID Multipart Session từ Object Storage (AWS S3)
    storage_path VARCHAR(512),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE file_chunks (
    id BIGSERIAL PRIMARY KEY,
    file_upload_id VARCHAR(64) REFERENCES file_uploads(id) ON DELETE CASCADE,
    chunk_index INT NOT NULL, -- Số thứ tự phân đoạn (1-indexed)
    chunk_size INT NOT NULL,
    chunk_hash VARCHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING', -- PENDING, COMPLETED
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Index tối ưu hóa luồng kiểm tra tiến độ Resume
CREATE UNIQUE INDEX idx_file_chunks_index ON file_chunks(file_upload_id, chunk_index);
```

## 💻 Code Example: Spring Boot & AWS SDK sinh Presigned URL cho Multipart Upload

Dưới đây là mã nguồn Spring Boot điều phối luồng **Multipart Upload của AWS S3**. Thay vì gửi file thô về Spring Boot, Backend chỉ gọi AWS SDK để khởi tạo session và sinh ra các đường dẫn Presigned URL cho Client tự tải lên S3.

### 1. Service khởi tạo Session và sinh Presigned URL
```java
@Service
public class FileUploadService {

    @Autowired
    private AmazonS3 s3Client;

    @Value("${aws.s3.bucket}")
    private String bucketName;

    /**
     * Bước 1: Khởi tạo Multipart Upload và sinh danh sách Presigned URLs cho từng phân đoạn
     */
    public InitiateUploadResponse initiateMultipartUpload(String filename, int totalChunks) {
        String s3Key = "uploads/" + UUID.randomUUID().toString() + "_" + filename;

        // 1. Gửi lệnh lên S3 khởi tạo Multipart Session
        InitiateMultipartUploadRequest initRequest = new InitiateMultipartUploadRequest(bucketName, s3Key);
        InitiateMultipartUploadResult initResult = s3Client.initiateMultipartUpload(initRequest);
        String uploadId = initResult.getUploadId();

        List<String> presignedUrls = new ArrayList<>();
        
        // 2. Với mỗi chunk_index, sinh ra một Presigned URL riêng biệt
        for (int i = 1; i <= totalChunks; i++) {
            GeneratePresignedUrlRequest generateUrlRequest = new GeneratePresignedUrlRequest(bucketName, s3Key)
                    .withMethod(HttpMethod.PUT)
                    .withExpiration(new Date(System.currentTimeMillis() + 3600 * 1000)); // Hết hạn trong 1 giờ

            // Thêm các tham số Query cho AWS S3 để nhận diện phân đoạn
            generateUrlRequest.addRequestParameter("uploadId", uploadId);
            generateUrlRequest.addRequestParameter("partNumber", String.valueOf(i));

            URL url = s3Client.generatePresignedUrl(generateUrlRequest);
            presignedUrls.add(url.toString());
        }

        // Trả về cho Client: UploadId, S3Key và Danh sách các URL để Client PUT trực tiếp
        return new InitiateUploadResponse(uploadId, s3Key, presignedUrls);
    }
}
```

### 2. Service xác nhận hoàn tất và ghép tệp trên S3
Sau khi Client tải lên thành công toàn bộ các phần, nó sẽ gửi danh sách mã băm ETag (mã định danh phân đoạn trả về từ S3) về cho Backend để gọi lệnh ghép tệp.

```java
@Service
public class FileAssemblyService {

    @Autowired
    private AmazonS3 s3Client;

    @Autowired
    private FileUploadRepository fileUploadRepository;

    @Value("${aws.s3.bucket}")
    private String bucketName;

    /**
     * Bước 2: Gọi S3 thực hiện ghép các phân đoạn thành tệp hoàn chỉnh
     */
    public void completeMultipartUpload(String uploadId, String s3Key, List<PartETag> partETags) {
        // 1. Gửi yêu cầu ghép tệp lên S3
        CompleteMultipartUploadRequest compRequest = new CompleteMultipartUploadRequest(
                bucketName, s3Key, uploadId, partETags);

        CompleteMultipartUploadResult result = s3Client.completeMultipartUpload(compRequest);

        // 2. Cập nhật trạng thái tệp trong DB thành COMPLETED
        String fileUrl = result.getFileRedirectLocation(); // Hoặc URL S3 vật lý
        fileUploadRepository.updateStatusToCompleted(s3Key, fileUrl);
        
        System.out.println("✅ Tệp tin " + s3Key + " đã được ghép thành công trên Object Storage.");
    }
}
```

## 📊 Trade-off Analysis: Các mô hình tải lên tệp tin lớn

| Tiêu chí | Tải trực tiếp qua Backend (Direct to Backend) | Tải qua Backend theo Chunk (Chunked to Backend) | Tải trực tiếp lên S3 qua Presigned URL |
| :--- | :--- | :--- | :--- |
| **Băng thông Backend** | **Tệ nhất**. Backend gánh toàn bộ luồng IO nhị phân, dễ gây nghẽn cổ chai mạng. | Kém. Vẫn phải đi qua Backend nhưng giảm thiểu nguy cơ quá tải bộ nhớ đệm nhờ chia nhỏ. | **Tốt nhất (Khuyên dùng)**. Backend chỉ truyền nhận JSON Metadata siêu nhẹ, băng thông dành trọn cho Object Storage. |
| **Khả năng Resumable** | Không thể. Đứt mạng giữa chừng $\rightarrow$ Tải lại từ 0%. | Có thể. Backend nhận và lưu tạm từng chunk trên đĩa cứng, sau đó ghép lại. | **Có thể (Khuyên dùng)**. Client tự theo dõi tiến độ và đẩy tiếp các chunk bị lỗi lên S3 thông qua các URL tương ứng. |
| **Độ trễ và Tải hệ thống** | Tải CPU và RAM của Backend tăng vọt khi nhiều người cùng upload. | Trung bình. Backend tốn IO đĩa cứng để lưu tạm và ghép các file phân đoạn. | **Không đáng kể**. Backend hầu như rảnh tay, Object Storage tự động scale không giới hạn. |
| **Độ phức tạp code** | Đơn giản nhất. | Phức tạp trung bình. Backend tự xử lý ghép file. | Phức tạp cao. Đòi hỏi cấu hình CORS an toàn trên S3/GCS và quản lý ETag ở Client. |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

1. **Làm sao ngăn chặn người dùng tải lên các tệp độc hại (Virus, Malware, Ransomware) làm hỏng hệ thống và ảnh hưởng đến người dùng khác?**
   * *Trả lời*: Ta xây dựng **Luồng xử lý bất đồng bộ sau khi Upload (Async Post-Processing Pipeline)**:
     * Tuyệt đối không cho phép người dùng tải xuống hoặc xem trực tiếp các tệp vừa upload lên ngay lập tức. Sau khi ghép file thành công, S3 sẽ gửi một sự kiện (S3 Event Notification) vào Kafka/RabbitMQ.
     * Một Worker Pool sẽ tiêu thụ event này, tải file xuống trong môi trường Sandbox cô lập và chạy qua bộ quét virus **ClamAV** hoặc các dịch vụ quét chuyên dụng của cloud.
     * Chỉ khi quét virus thành công, Worker mới cập nhật cờ `is_safe = true` trong DB và di chuyển tệp từ Bucket nháp (Inbound Bucket) sang Bucket sản xuất (Production Bucket) để cho phép phân phối qua CDN.

2. **Làm thế nào để giải quyết vấn đề "Orphaned Chunks" (các phân đoạn tải lên bị bỏ dở giữa chừng làm tốn dung lượng và chi phí Object Storage)?**
   * *Trả lời*: Khi người dùng đang upload tệp lớn được một nửa thì tắt trình duyệt hoặc hủy tải lên, các phân đoạn đã tải lên S3 vẫn sẽ nằm ở đó và bị nhà cung cấp tính phí lưu trữ vĩnh viễn nếu không xử lý.
   * Giải pháp: Cấu hình **S3 Lifecycle Rules** trên AWS S3. Ta thiết lập quy tắc tự động xóa (AbortIncompleteMultipartUpload) đối với toàn bộ các session multipart upload dở dang có tuổi thọ quá 7 ngày. AWS S3 sẽ tự động quét, hủy phiên và giải phóng toàn bộ các chunk thừa này hoàn toàn miễn phí.

3. **Thiết kế luồng phân phối video qua CDN thế nào để không bị nghẽn băng thông và tối ưu hóa trải nghiệm người dùng (HLS/DASH Streaming)?**
   * *Trả lời*: Với tệp video lớn, không bao giờ được phép cho người dùng tải trực tiếp tệp MP4 thô vì sẽ gây trễ lớn (phải tải xong mới xem được) và tốn băng thông CDN cực lớn khi user chỉ xem vài giây rồi tắt.
   * Giải pháp là áp dụng **Transcoding sang định dạng HLS/DASH**:
     * Sau khi video tải lên thành công, Media Worker (sử dụng FFmpeg hoặc AWS Elemental MediaConvert) sẽ chia nhỏ video thành các phân đoạn dài 2-5 giây (tệp `.ts`) ở nhiều độ phân giải khác nhau (360p, 720p, 1080p) và tạo ra tệp danh mục quản lý `.m3u8` (Playlist file).
     * Toàn bộ các file `.ts` này được cache trên CDN. Client khi xem video sẽ chỉ tải tệp `.m3u8` về trước, sau đó phát đến đâu thì CDN tải các phân đoạn `.ts` siêu nhẹ tương ứng đến đó. Cơ chế này cũng tự động phát hiện tốc độ mạng của client để chuyển đổi mượt mà giữa các chất lượng video khác nhau (Adaptive Bitrate Streaming).
