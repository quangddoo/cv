# Một request đi qua 5 service, lỗi xảy ra ở service thứ 4. Bạn trace thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Trong hệ thống microservices đa tầng, việc tìm lỗi bằng cách truy cập từng máy chủ để đọc log thủ công là nhiệm vụ bất khả thi. Để trace được lỗi, hệ thống phải triển khai **Distributed Tracing (Giám sát phân tán)** dựa trên cơ chế truyền ngữ cảnh (**Context Propagation**) thông qua tiêu chuẩn **W3C Trace Context**.
* **Thảm họa thực chiến được giải quyết**:
  1. **Lỗi mù trung gian (Blind Spots)**: Một request từ client bị lỗi 500. Log ở Gateway chỉ ghi nhận lỗi generic `500 Internal Server Error` từ Service 1 gửi về. Service 1 báo lỗi từ Service 2... Bạn hoàn toàn mù thông tin về việc Service 4 bị lỗi thực tế là do nghẽn SQL hay OOM, làm tê liệt quá trình debug sự cố khẩn cấp.
  2. **Tranh cãi trách nhiệm giữa các team (Finger-pointing)**: Khi không có dữ liệu truy vết trực quan, các đội ngũ vận hành từng service sẽ đổ lỗi cho nhau. Tracing cung cấp bằng chứng rõ ràng bằng hình ảnh về vị trí và thời điểm chính xác lỗi xảy ra.
* **Quyết định Senior**:
  1. **Áp dụng OpenTelemetry**: Tự động sinh ra một **Trace ID** duy nhất tại điểm đầu vào (API Gateway) và truyền tải Trace ID này xuyên suốt qua 5 service bằng HTTP Header (`traceparent`) hoặc Metadata (gRPC, Kafka).
  2. **Cấu hình MDC Logging**: Đẩy Trace ID vào **MDC (Mapped Diagnostic Context)** của Logback để mọi dòng log in ra console đều tự động đính kèm Trace ID này.
  3. **Sử dụng Jaeger / Grafana Tempo**: Gom toàn bộ trace dữ liệu về một công cụ tập trung. Chỉ cần gõ Trace ID trên Jaeger, hệ thống sẽ vẽ ra sơ đồ cây luồng gọi trực quan, chỉ rõ Service 4 bị đỏ (lỗi) kèm theo stack trace chi tiết.

## 🔍 Chi tiết bản chất thực chiến: Cơ chế Hoạt động của Distributed Tracing

Mô hình lan truyền ngữ cảnh (Context Propagation) đi qua 5 service hoạt động dựa trên cấu trúc W3C như sau:

```
[Client] ──> [API Gateway] ──> [Service 1] ──> [Service 2] ──> [Service 3] ──> [Service 4 (💥 Lỗi)] ──> [Service 5]
                  │               │               │               │               │
            (Sinh TraceID)  (Nhận TraceID)  (Nhận TraceID)  (Nhận TraceID)  (💥 Ghi nhận lỗi)
                  │               │               │               │               │
                  └───────────────┴───────────────┴───────────────┴───────────────┘
                                                  │
                                                  ▼
                                    [Jaeger / Grafana Tempo UI]
```

### 1. Phân tích cấu trúc W3C Trace Context Header (`traceparent`)
Khi Service A gọi HTTP sang Service B, thư viện Tracing (như OpenTelemetry) sẽ tự động inject vào HTTP Header một tham số có tên `traceparent` với định dạng chuẩn hóa:
```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └──────────────────────────────┘ └──────────────┘ └─┘
           Version          Trace ID                 Span ID      Flags
```
* **Trace ID (128-bit)**: ID duy nhất đại diện cho toàn bộ hành trình đi qua 5 service của request. Giá trị này **giữ nguyên không đổi** trong suốt vòng đời của request.
* **Span ID (64-bit)**: ID đại diện cho một phân đoạn công việc nhỏ tại một service cụ thể. Khi đi qua mỗi service mới, một Span ID mới sẽ được sinh ra, và Span ID của service phía trước sẽ trở thành `Parent Span ID`.
* **Flags**: Trạng thái lấy mẫu (Sampling flag), ví dụ `01` là ghi nhận dữ liệu trace này (sampled).

### 2. Sự kết hợp hoàn hảo: Distributed Tracing & Centralized Logging
* Khi bạn phát hiện Trace ID bị lỗi trên Jaeger UI, bạn sao chép (copy) Trace ID đó.
* Truy cập vào hệ thống log tập trung (Elasticsearch / Grafana Loki) và tìm kiếm theo truy vấn: `traceId="4bf92f3577b34da6a3ce929d0e0e4736"`.
* Toàn bộ log của cả 5 service liên quan đến request này sẽ được hiển thị theo trình tự thời gian chi tiết, giúp bạn cô lập lỗi chỉ trong 10 giây.

## 💻 Code thực chiến: Tự động truyền Trace ID qua WebClient & in log MDC

Trong Spring Boot 3 (sử dụng Micrometer Tracing và OpenTelemetry), việc tự động truyền ngữ cảnh qua HTTP Client (WebClient) được thiết lập như sau:

### 1. Cấu hình in Trace ID ra log thông qua Logback Pattern
Chỉnh sửa file `logback-spring.xml` hoặc `application.yml` để inject thông số `traceId` và `spanId` lấy từ MDC (Mapped Diagnostic Context) vào console log:
```yaml
logging:
  pattern:
    # ✅ [%X{traceId}] sẽ tự động in Trace ID nếu có trong Context
    console: "%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{traceId:-},%X{spanId:-}] %logger{36} : %msg%n"
```

### 2. Triển khai cấu hình tự động Propagation cho WebClient
```java
import io.micrometer.observation.ObservationRegistry;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.reactive.function.client.WebClient;

@Configuration
public class TracingWebClientConfig {

    /**
     * ✅ Sử dụng WebClient.Builder được Spring Boot cấu hình sẵn.
     * Builder này đã được tích hợp sẵn Micrometer ObservationRegistry ngầm,
     * tự động bốc Trace Context từ luồng hiện tại và inject vào header của HTTP request tiếp theo.
     */
    @Bean
    public WebClient tracingWebClient(WebClient.Builder webClientBuilder, ObservationRegistry observationRegistry) {
        return webClientBuilder
                .observationRegistry(observationRegistry) // ✅ Kích hoạt Auto-Tracing Propagation
                .baseUrl("http://service-4.internal-api")
                .build();
    }
}
```

### 3. Service nghiệp vụ in log lỗi kèm Trace ID tự động
```java
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

@Slf4j
@Service
@RequiredArgsConstructor
public class TransactionService {

    private final WebClient tracingWebClient;

    public Mono<String> processPayment(String orderId) {
        // ✅ Log này sẽ tự động được in kèm Trace ID duy nhất của request hiện tại
        log.info("💳 Đang chuẩn bị gửi yêu cầu thanh toán cho đơn hàng: {}", orderId);

        return tracingWebClient.post()
                .uri("/payments")
                .bodyValue(new PaymentRequest(orderId))
                .retrieve()
                .bodyToMono(String.class)
                .doOnError(throwable -> {
                    // ✅ Khi lỗi xảy ra, log ERROR này đính kèm Trace ID giúp debug lập tức trên Elasticsearch
                    log.error("🚨 GIAO DỊCH THẤT BẠI. Nguyên nhân: {}", throwable.getMessage(), throwable);
                });
    }
}
```

| :--- | :--- | :--- | :--- |
| **Bản chất dữ liệu** | Log text dạng thô (Raw string/JSON). | Metric tổng quan (CPU, RAM, Error Rate). | Sơ đồ cây biểu diễn quan hệ nhân quả của cuộc gọi. |
| **Khả năng trace lỗi qua nhiều Service** | Khó khăn (Phải dùng script để grep Trace ID thủ công). | Trung bình (Chỉ thấy được quan hệ cấp độ service high-level). | **Hoàn hảo** (Thấy chi tiết từng microsecond đi qua từng node). |
| **Dung lượng lưu trữ yêu cầu** | Cực kỳ tốn kém (In log tràn lan). | Thấp (Chỉ lưu metric tổng hợp). | Trung bình (Tối ưu được nhờ cấu hình Sampling). |
| **Chi phí triển khai** | Miễn phí (Tự dựng ELK) hoặc trung bình. | Cực kỳ đắt đỏ (Trả phí theo lượng tài nguyên/host). | Miễn phí (Tự dựng Jaeger + Tempo). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Mất dấu vết khi xử lý Bất đồng bộ (Async Thread Loss)"
* **Vấn đề**: Khi request đi vào Service 3, luồng xử lý chính chuyển giao tác vụ cho một Thread Pool ngầm để chạy bất đồng bộ (`@Async` hoặc `CompletableFuture.runAsync`). Do thread mới không kế thừa ngữ cảnh MDC của thread cũ, Trace ID bị biến mất hoàn toàn kể từ bước này. Các log phía sau bị rỗng Trace ID, làm gãy toàn bộ chuỗi Tracing.
* **Giải pháp khắc phục**: Cấu hình Spring TaskExecutor sử dụng **MDC Task Decorator** hoặc **ContextPropagatingExecutorService** để tự động copy toàn bộ ngữ cảnh Tracing từ Thread cha sang Thread con khi chuyển giao tác vụ.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Làm sao để cấu hình Sampling (Lấy mẫu) cho Tracing để không làm sập dung lượng đĩa cứng lưu trữ khi hệ thống có hàng tỷ request/ngày?**
  * *Trả lời*:
    * Ta áp dụng hai chiến lược Sampling tiên tiến:
      1. **Adaptive/Probabilistic Sampling (Lấy mẫu xác suất)**: Chỉ lấy mẫu ngẫu nhiên ví dụ `1%` hoặc `5%` đối với các request thành công (HTTP 2xx).
      2. **Tail-Based Sampling (Lấy mẫu ở điểm cuối)**: Đây là kỹ thuật tối ưu nhất. Thư viện tracing sẽ giữ lại toàn bộ trace tạm thời trong bộ nhớ đệm. Khi request kết thúc, nếu phát hiện có lỗi (HTTP 5xx, Exception, Latency > 2s), hệ thống sẽ **bắt buộc lưu trữ 100% dữ liệu trace** đó. Nếu request hoàn toàn thành công và chạy nhanh, hệ thống sẽ loại bỏ nó để tiết kiệm dung lượng.
