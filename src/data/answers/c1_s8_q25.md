# Quy trình Debug và Tối ưu hóa Slow Query thực chiến

## ⚡ Tóm tắt ngắn (30s)
Quy trình debug slow query chuẩn chỉnh của một Senior Engineer gồm 4 bước khoa học:
1. **Phát hiện (Detect)**: Sử dụng **Slow Query Log** (DB Level), bật **APM** (Datadog, NewRelic) hoặc truy vấn trực tiếp bảng thống kê hệ thống (như `pg_stat_statements` trong Postgres).
2. **Phân tích (Analyze)**: Chạy lệnh **`EXPLAIN`** hoặc **`EXPLAIN ANALYZE`** để đọc Kế hoạch thực thi (Execution Plan) của Database Engine.
3. **Chẩn đoán (Diagnose)**: Xác định nguyên nhân chính:
    * Quét toàn bảng (Full Table Scan / Seq Scan) do thiếu Index.
    * Index bị vô hiệu hóa (do dùng hàm bao bọc cột index, implicit type casting, hoặc wildcard đứng đầu `%abc`).
    * Bùng nổ dữ liệu đọc do lạm dụng Offset quá lớn (`LIMIT ... OFFSET ...`).
4. **Sửa đổi (Fix)**: Thêm Index phù hợp (Composite Index, Covering Index), sửa lại câu lệnh SQL chuẩn, hoặc áp dụng các kỹ thuật kiến trúc (Caching, Denormalization, Partitioning).

## 🔍 Chi tiết bản chất thực chiến

### Bước 1: Phát hiện Slow Query bằng Công cụ Hệ thống

Không nên đợi đến khi user báo lỗi mới đi tìm slow query. Ta có thể chủ động truy quét:
* **MySQL**: Bật cấu hình ghi nhận các query chạy lâu hơn 1 giây:
  ```ini
  slow_query_log = 1
  long_query_time = 1.0 # đơn vị giây
  log_queries_not_using_indexes = 1
  ```
* **PostgreSQL**: Kích hoạt extension thần thánh `pg_stat_statements` để thống kê toàn bộ lịch sử query:
  ```sql
  SELECT query, calls, total_exec_time, mean_exec_time 
  FROM pg_stat_statements 
  ORDER BY total_exec_time DESC LIMIT 10;
  ```

### Bước 2: Phân tích Kế hoạch Thực thi với `EXPLAIN`

Đặt từ khóa `EXPLAIN` (hoặc `EXPLAIN ANALYZE` để DB chạy thực tế và đo đạc chính xác thời gian từng bước) phía trước câu truy vấn.

```sql
EXPLAIN ANALYZE 
SELECT * FROM orders WHERE user_id = 99999 AND status = 'COMPLETED';
```

#### 🌟 Các chỉ số "Báo động đỏ" cần chú ý trong kết quả EXPLAIN:

#### Trong MySQL:
* **`type`**: Thể hiện cách DB quét bảng.
  * **❌ Cực tệ**: `ALL` (Full Table Scan - Quét toàn bảng vật lý), `index` (Full Index Scan - Quét toàn bộ cây index).
  * **✅ Cực tốt**: `const`, `eq_ref` (đọc bằng Khóa chính), `ref` (dùng index thường), `range` (quét trong khoảng index).
* **`key`**: Chỉ ra index thực tế được chọn. Nếu là `NULL`, DB đang chạy chay không có index!
* **`rows`**: Số lượng dòng dữ liệu DB ước lượng phải duyệt qua. Nếu con số này lên hàng triệu, chắc chắn query sẽ chậm.
* **`Extra`**:
  * **❌ Cảnh báo**: `Using filesort` (phải sắp xếp dữ liệu ngoài đĩa đắt đỏ), `Using temporary` (phải tạo bảng tạm trên bộ nhớ).

#### Trong PostgreSQL:
* **❌ Cần tránh**: `Seq Scan` (Sequential Scan - quét tuần tự toàn bảng), `Filter` (lọc sau khi quét).
* **✅ Ưu tiên**: `Index Scan` (Tìm trên index và trỏ về bảng), `Index Only Scan` (Chỉ đọc trên index - cực nhanh), `Bitmap Index Scan`.

### Bước 3: 4 Nguyên nhân kinh điển làm vô hiệu hóa Index

Ngay cả khi bạn đã tạo Index trên cột `created_at`, câu lệnh của bạn vẫn có thể chạy chậm thê thảm nếu mắc phải các lỗi thiết kế sau:

#### 1. Dùng hàm bao bọc cột Index (Function wrapping)
* **❌ BAD (Index bị bỏ qua)**:
  ```sql
  SELECT * FROM users WHERE YEAR(created_at) = 2026;
  -- DB buộc phải quét từng dòng dữ liệu, chạy hàm YEAR() cho từng dòng rồi mới so sánh.
  ```
* **✅ GOOD (Tận dụng Index)**:
  ```sql
  SELECT * FROM users WHERE created_at >= '2026-01-01 00:00:00' AND created_at <= '2026-12-31 23:59:59';
  ```

#### 2. Ép kiểu ngầm định (Implicit Type Casting)
* **❌ BAD**: Cột `phone` được định nghĩa kiểu `VARCHAR`, nhưng bạn lại so sánh với kiểu số `INT`:
  ```sql
  SELECT * FROM users WHERE phone = 0987654321; -- DB buộc phải cast toàn bộ cột VARCHAR sang INT để so sánh.
  ```
* **✅ GOOD**:
  ```sql
  SELECT * FROM users WHERE phone = '0987654321';
  ```

#### 3. Wildcard (ký tự đại diện `%`) đặt ở đầu chuỗi tìm kiếm
* **❌ BAD**:
  ```sql
  SELECT * FROM products WHERE code LIKE '%PROD123'; -- B-Tree không thể tìm kiếm tiền tố ngẫu nhiên, buộc phải quét toàn bảng.
  ```
* **✅ GOOD**:
  ```sql
  SELECT * FROM products WHERE code LIKE 'PROD123%'; -- Tìm kiếm đúng tiền tố, tối ưu hóa B-Tree index.
  ```

#### 4. Phân trang bằng `OFFSET` quá lớn
* **❌ BAD**:
  ```sql
  SELECT * FROM orders ORDER BY id DESC LIMIT 10 OFFSET 1000000;
  -- DB buộc phải đọc 1.000.010 bản ghi, sắp xếp chúng, lấy ra 10 bản ghi cuối cùng và vứt bỏ 1.000.000 bản ghi trước đó. Cực kỳ lãng phí I/O!
  ```
* **✅ GOOD (Cursor Pagination / Keyset Pagination)**:
  Sử dụng giá trị ID của bản ghi cuối cùng của trang trước làm điểm neo (Cursor) để nhảy trực tiếp:
  ```sql
  SELECT * FROM orders WHERE id < 998877 ORDER BY id DESC LIMIT 10;
  ```

## 💻 Code thực chiến: Sử dụng Covering Index để tăng tốc độ 100 lần

**Covering Index (Chỉ mục bao phủ)** là kỹ thuật tối ưu hóa đỉnh cao. Ta tạo một Composite Index chứa toàn bộ các trường cần hiển thị trong câu `SELECT`. Lúc này, DB Engine chỉ việc đọc dữ liệu từ cây Index nằm sẵn trên RAM và trả kết quả luôn cho ứng dụng, không cần tốn thêm một bước đọc vật lý vào bảng chính trên ổ đĩa cứng (**Index Only Scan / Avoid Table Lookup**).

### Minh họa thực tế:

Yêu cầu: Lấy ra danh sách mã đơn hàng (`code`) và ngày tạo (`created_at`) của một `user_id` cụ thể.

```sql
-- Tạo Composite Index chứa cả 3 trường
CREATE INDEX idx_orders_user_covering 
ON orders (user_id, created_at, code);

-- Câu truy vấn:
SELECT code, created_at 
FROM orders 
WHERE user_id = 12345 
ORDER BY created_at DESC;

-- Giải thích vật lý:
-- DB chỉ cần quét cây Index idx_orders_user_covering trên RAM, 
-- lấy ra dữ liệu của code và created_at đã được sắp xếp sẵn. Tốc độ nhanh tiệm cận tức thời!
```

## 📊 Bảng tra cứu chẩn đoán lỗi Slow Query

| Triệu chứng | Nguyên nhân khả dĩ | Phương pháp khắc phục |
| :--- | :--- | :--- |
| **`EXPLAIN` thấy `Seq Scan` / `ALL`** | Thiếu index hoặc DB đánh giá quét toàn bảng nhanh hơn | Tạo Index trên cột trong `WHERE`. Chạy `ANALYZE TABLE` để DB cập nhật lại thông số thống kê dữ liệu. |
| **`Using filesort` ở cột `Extra`** | Sắp xếp dữ liệu (`ORDER BY`) trên cột không có index | Thêm cột cần `ORDER BY` vào làm cột tiếp theo của Composite Index. |
| **Query chạy chậm lúc cao điểm** | Connection pool bị nghẽn, khóa hàng (Row Lock / Table Lock) | Sử dụng `SELECT ... FOR UPDATE SKIP LOCKED` cho async workers để tránh tranh chấp luồng ghi. |
| **Truy vấn JOIN chạy rất chậm** | Thiếu index ở các cột khóa ngoại liên kết | Bắt buộc phải tạo Index cho toàn bộ các cột tham chiếu khóa ngoại (`foreign key`). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Sự sai lệch của Query Planner do số liệu thống kê (Stale Statistics)
Database Engine (Query Optimizer) hoạt động dựa trên các ước lượng thống kê của dữ liệu (ví dụ: bảng này có bao nhiêu dòng, tỷ lệ phân bổ giá trị ở cột này ra sao). Nếu dữ liệu của bạn vừa tăng vọt gấp 10 lần (hoặc sau khi import lô dữ liệu lớn), số liệu thống kê bị cũ (Stale Statistics). DB Engine sẽ đưa ra quyết định sai lầm: Chọn nhầm Index, hoặc từ chối dùng Index để quay sang quét toàn bảng.
* **Giải pháp thực chiến**: Định kỳ chạy lệnh dọn dẹp và cập nhật chỉ số thống kê của DB vào khung giờ thấp điểm ban đêm:
  * Trong PostgreSQL: `ANALYZE orders;` (hoặc cấu hình Auto-vacuum hoạt động mạnh hơn).
  * Trong MySQL: `ANALYZE TABLE orders;`.

### 2. Câu hỏi đào sâu từ interviewer: "Nếu một câu lệnh JOIN 5 bảng bị chậm, bạn sẽ tối ưu hóa theo thứ tự nào?"
* **Trả lời**:
  1. Sử dụng `EXPLAIN` để xác định bảng nào đang bị quét toàn bảng (`type = ALL`).
  2. Đảm bảo tất cả các cột dùng làm điều kiện JOIN (các cặp `ON a.id = b.foreign_id`) đều đã được đánh chỉ mục (Index).
  3. Kiểm tra xem có thể lọc bớt dữ liệu ở các bảng con trước khi thực hiện JOIN hay không (chuyển bớt điều kiện lọc từ `HAVING` hoặc sau `JOIN` vào trực tiếp mệnh đề `WHERE` của bảng chính).
  4. Nếu dữ liệu quá lớn và truy vấn chạy quá nhiều trên luồng realtime, đề xuất kiến trúc **Phi chuẩn hóa (Denormalization)** để gom bớt dữ liệu hiển thị về một bảng chính duy nhất, triệt tiêu bớt số lượng phép JOIN.
