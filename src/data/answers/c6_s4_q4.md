# Edge cases và test case — Test từ contract, không test ngẫu nhiên
## ⚡ Tóm tắt ngắn (30s)
* Nhóm test theo boundary của contract: empty, min/max, duplicate, no-solution và malformed input.
* Trace một case bằng tay; dùng brute-force oracle/property khi hữu ích.
* Tách algorithm bug khỏi assumption về input validation.

---

## 🔍 Cách trả lời từng bước
### 1. Đọc contract như test spec
Tôi xác định input hợp lệ, output khi không có đáp án, có duplicate hay không, ordering có quan trọng không và có overflow/Unicode/timezone không. Nếu contract chưa nói, tôi hỏi thay vì tự đoán.

### 2. Tạo boundary matrix
Nhóm thường có: rỗng, một phần tử, tất cả giống nhau, đã sort/ngược, giá trị biên, nhiều đáp án, không có đáp án, input lớn nhất và structure bị lệch/cycle. Mỗi nhóm đại diện một failure mode khác nhau.

### 3. Test correctness và performance
Tôi trace case nhỏ; với solution tối ưu, dùng brute-force làm oracle trên random input nhỏ để so sánh. Với performance, tạo input worst-case như cùng prefix, graph chain hoặc duplicate lớn. Tôi không phụ thuộc chỉ vào coverage line.

### 4. Nêu hành vi invalid
Nếu input violation, solution có thể throw, return error hoặc assume precondition; tôi nói rõ theo đề bài.

---

## 💻 Ví dụ trả lời / worked example
Với LRU cache, ngoài get/put bình thường, tôi test capacity 1, capacity 0 theo contract, get key không tồn tại, update key đã tồn tại, eviction đúng key cũ nhất và sequence làm key vừa đọc trở thành most-recent.

Tôi trace sequence: put(A), put(B), get(A), put(C). Kỳ vọng B bị evict, không phải A. Tôi cũng test nhiều put cùng key để chắc size không tăng, và nếu implementation dùng doubly linked list + map thì kiểm tra head/tail khi xóa node duy nhất.

Nếu code production, tôi thêm concurrency contract riêng; không giả định thread-safe nếu bài không yêu cầu.

## 📊 Follow-up interviewer có thể hỏi
| Follow-up | Hướng trả lời mạnh |
| :--- | :--- |
| Edge case nào quan trọng nhất? | Case có thể phá invariant hoặc tạo boundary behavior. |
| Random test có đủ không? | Không; cần deterministic boundary và oracle. |
| Test performance thế nào? | Worst-case input, time budget, memory và complexity claim. |
| Input invalid xử lý sao? | Theo contract; nếu chưa rõ, hỏi interviewer. |

---

## ⚠️ Common Mistakes & Pro Tips
1. **Không liệt kê test nhưng không nói expected output.**
2. **Không chỉ test happy path.**
3. **Không dùng coverage làm proxy duy nhất của correctness.**
4. **Không thêm behavior ngoài contract mà không nói.**

**Mục tiêu của câu trả lời:** cho thấy cách suy nghĩ có cấu trúc, ownership cá nhân, khả năng định lượng impact và sự trung thực về trade-off cũng như giới hạn của solution.
