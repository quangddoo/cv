# Tại sao gọi nội bộ phương thức @Transactional trong cùng Class lại thất bại?

## ⚡ Tóm tắt ngắn (30s)
Đây là một trong những câu hỏi phỏng vấn kinh điển nhất để kiểm tra hiểu biết thực tế về Spring Framework của các ứng viên Senior.
*   **Nguyên nhân trực tiếp**: Spring AOP mặc định hoạt động dựa trên cơ chế **Proxy-based (Lớp bọc động)**. Khi một phương thức bên ngoài gọi vào Bean, cuộc gọi sẽ đi qua lớp bọc Proxy để Spring kích hoạt tính năng mở Transaction. Tuy nhiên, khi phương thức A gọi phương thức B **trong cùng một Class**, cuộc gọi được thực hiện trực tiếp thông qua con trỏ tham chiếu **`this`** nội bộ của đối tượng gốc (Target Object).
*   **Hậu quả**: Do cuộc gọi nội bộ bypass (vượt mặt) hoàn toàn lớp bọc Proxy, **`TransactionInterceptor`** không có cơ hội đánh chặn (intercept) cuộc gọi này. Kết quả là transaction trên phương thức B **hoàn toàn không được khởi tạo**, khiến dữ liệu không được rollback nếu xảy ra lỗi.
*   **Giải pháp tốt nhất**: **Tách Service (Refactoring)**. Phân rã logic sang một Spring Bean độc lập khác để bắt buộc mọi cuộc gọi phải đi qua Proxy của Spring.

## 🔍 Chi tiết bản chất thực chiến

### Sơ đồ cơ chế Bypass Proxy khi tự gọi nội bộ (`this`)

Hãy xem sơ đồ luồng dữ liệu dưới đây để hiểu tại sao Spring AOP hoàn toàn bất lực khi bạn gọi nội bộ:

```text
1. Cuộc gọi từ Client (Thành công):
Client ──> [ Proxy Lớp Bọc ] ──(Đánh chặn & Mở Transaction)──> [ Target Object (Service Gốc) ]
                                                                        │
2. Cuộc gọi nội bộ (Thất bại):                                           │
                                                                   methodA() (Không Transaction)
                                                                        │
                                                                 (Gọi trực tiếp: this.methodB())
                                                                        │
                                                                        ▼
                                                                   methodB() (Gắn @Transactional)
                                                                 ❌ BYPASS HOÀN TOÀN PROXY!
                                                                 ❌ KHÔNG CÓ TRANSACTION NÀO MỞ!
```

Khi Client gọi `methodA()`, nó gọi thông qua đối tượng Proxy được Spring tiêm vào. Nhưng khi đang ở trong `methodA()` của đối tượng gốc, câu lệnh gọi `methodB()` thực chất là `this.methodB()`. Con trỏ `this` lúc này chính là đối tượng vật lý thô (Target Object) chứ không phải đối tượng Proxy. Do đó, logic mở transaction bị bỏ qua hoàn toàn.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Gọi trực tiếp phương thức `@Transactional` từ phương thức thường cùng Class
Lập trình viên muốn thực hiện thanh toán trong transaction, nên tách riêng logic ghi DB vào method `processPaymentDb()` và đánh dấu `@Transactional`. Nhưng họ lại gọi chéo trực tiếp từ method `checkout()` không có transaction.

```java
package com.example.service;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderServiceBad {

    public void checkout() {
        System.out.println("Step 1: Validate cart...");
        
        // ⚠️ Lỗi nghiêm trọng: Tự gọi nội bộ qua con trỏ 'this' ngầm định!
        // bypass hoàn toàn Proxy của Spring!
        processPaymentDb(); 
    }

    @Transactional // ⚠️ Vô tác dụng! Không có transaction nào được mở cho method này!
    public void processPaymentDb() {
        System.out.println("SQL: Update user balance");
        System.out.println("SQL: Insert payment invoice");
        // Nếu lỗi xảy ra ở đây, DB hoàn toàn KHÔNG rollback!
        throw new RuntimeException("Payment API Timeout!");
    }
}
```

###  GOOD (Cách 1 - Khuyên dùng): Tách class theo nguyên tắc Single Responsibility (SRP)
Tách riêng logic nghiệp vụ điều phối (`OrderService`) độc lập với logic thao tác dữ liệu DB có chứa transaction (`PaymentDbService`). Đây là giải pháp sạch sẽ nhất về mặt kiến trúc.

```java
package com.example.service;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PaymentDbService { // ✅ Service độc lập chịu trách nhiệm ghi DB

    @Transactional // ✅ OK: Sẽ chạy hoàn hảo vì được gọi từ bên ngoài thông qua Proxy!
    public void processPaymentDb() {
        System.out.println("SQL: Update user balance");
        System.out.println("SQL: Insert payment invoice");
        throw new RuntimeException("Payment API Timeout! Rollback activated!");
    }
}

@Service
public class OrderServiceGood {

    private final PaymentDbService paymentDbService;

    // Tiêm Bean PaymentDbService (thực chất là đối tượng Proxy) vào
    public OrderServiceGood(PaymentDbService paymentDbService) {
        this.paymentDbService = paymentDbService;
    }

    public void checkout() {
        System.out.println("Step 1: Validate cart...");
        // ✅ OK: Gọi qua Bean được tiêm giúp đi qua Proxy và kích hoạt Transaction thành công!
        paymentDbService.processPaymentDb(); 
    }
}
```

###  GOOD (Cách 2 - Giải pháp tình thế): Tự tiêm chính mình (Self-Injection Proxy)
Nếu vì lý do nào đó bạn không muốn tạo thêm Class mới, bạn có thể tự tiêm chính Proxy của mình vào Class thông qua cơ chế `@Autowired` trễ (Sử dụng `@Lazy` để tránh lỗi phụ thuộc vòng).

```java
package com.example.service;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderServiceSelfInject {

    private OrderServiceSelfInject selfProxy;

    // ✅ Tiêm chính bản thân mình dưới dạng Proxy bằng cách dùng @Lazy
    @Autowired
    public void setSelfProxy(@Lazy OrderServiceSelfInject selfProxy) {
        this.selfProxy = selfProxy;
    }

    public void checkout() {
        System.out.println("Step 1: Validate cart...");
        // ✅ OK: Gọi thông qua đối tượng selfProxy được tiêm thay vì gọi trực tiếp!
        selfProxy.processPaymentDb(); 
    }

    @Transactional // ✅ Hoạt động hoàn hảo!
    public void processPaymentDb() {
        System.out.println("SQL: Writing to DB...");
        throw new RuntimeException("Error! Database rolled back!");
    }
}
```

## 📊 Trade-off: So sánh các giải pháp khắc phục tự gọi nội bộ

| Phương pháp | Độ phức tạp code | Đánh giá kiến trúc | Ưu điểm | Nhược điểm |
| :--- | :--- | :--- | :--- | :--- |
| **1. Tách Class (Refactoring)** | Trung bình |  **Xuất sắc (Clean Code)** | Phù hợp nguyên tắc SRP, code decoupling, cực kỳ dễ viết Unit Test độc lập. | Tạo thêm class phụ trong project. |
| **2. Tự tiêm chính mình (Self-injection)** | Thấp |  **Tạm chấp nhận** | Giải quyết lỗi cực nhanh mà không cần tạo thêm file class mới. | Nhìn hơi kỳ lạ (code smell nhẹ), dễ gây bối rối cho junior. |
| **3. Dùng `TransactionTemplate`** | Thấp |  **Rất tốt** | Kiểm soát transaction ở mức block dòng code cực kỳ linh hoạt. | Phải viết code lồng trong callback (Boilerplate code). |
| **4. Dùng AspectJ Weaving** | Cực cao |  **Xuất sắc** | Phá vỡ hoàn toàn lỗi tự gọi bằng cách sửa bytecode trực tiếp. | Cấu hình Java Agent/Maven Plugin phức tạp, nặng máy khi dev. |

## ⚠️ Common Gotchas & Questions follow-up

### Câu hỏi phỏng vấn hóc búa: *"Nếu tôi đặt @Transactional trên method public B, nhưng method A gọi nó là protected hoặc private thì sao?"*
*   **Trả lời**: 
    1.  Nếu phương thức B là `private`, Spring AOP mặc định sẽ **bỏ qua hoàn toàn** vì cơ chế Proxy (cả JDK và CGLIB) chỉ hỗ trợ ghi đè các `public` methods.
    2.  Nếu phương thức B là `protected` hoặc `package-private` (default visibility), mặc dù về mặt lý thuyết CGLIB có thể kế thừa và ghi đè được, nhưng cấu hình mặc định của Spring Transaction Manager (`TransactionAttributeSource`) vẫn **chỉ chấp nhận các public methods**. Bất kỳ phương thức phi-public nào gắn `@Transactional` đều bị bỏ qua âm thầm.
    *   *Kết luận:* Phương thức được gắn `@Transactional` **bắt buộc phải là `public`** và **phải được gọi từ bên ngoài Class** thì tính năng quản lý transaction mới hoạt động đúng thiết kế.
