# Stack trace bị swallow, không thấy root cause. Bạn xử lý thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Lỗi xảy ra nhưng log chỉ còn một dòng cụt lủn như `"Có lỗi xảy ra"` hoặc `"Error: null"` — **stack trace và chuỗi nguyên nhân (cause chain) bị nuốt mất**. Gần như luôn do anti-pattern code: bắt exception rồi log thiếu, hoặc bọc lại exception mà **đánh rơi `cause`**. Hậu quả: biết "có lỗi" nhưng không biết lỗi *ở dòng nào, do đâu* → điều tra production bế tắc.
* **Nguyên nhân gốc thường gặp**:
  1. `catch (Exception e) { log.error("Error"); }` — **không truyền `e`** nên không in stack trace.
  2. `log.error("Failed: " + e.getMessage())` — chỉ lấy message, **mất stack trace và cause**.
  3. `throw new MyException(e.getMessage())` — bọc lại nhưng **không truyền `e` làm cause** → đứt chuỗi, mất root cause gốc.
  4. `catch (Exception e) {}` — nuốt trọn, không log không ném.
* **Quyết định Senior**: luôn **truyền throwable làm tham số cuối** (`log.error("msg id={}", id, e)`), luôn **giữ cause** khi bọc exception (`new X("...", e)`), và **log đúng một lần ở biên** thay vì nuốt giữa chừng.

## 🔍 Chi tiết bản chất thực chiến

### 1. Quy tắc throwable của SLF4J — điểm mấu chốt hay sai
* SLF4J coi **tham số cuối cùng là `Throwable`** nếu nó *không* được tiêu thụ bởi một placeholder `{}`. Khi đó nó in **đầy đủ stack trace**:
  ```java
  log.error("Xử lý order thất bại orderId={}", orderId, ex); // ✅ in cả message lẫn stack trace
  ```
* Ngược lại, nếu bạn **nhét exception vào `{}`** thì nó chỉ gọi `toString()` (mất stack):
  ```java
  log.error("Lỗi: {}", ex);            // ❌ chỉ in ex.toString(), KHÔNG có stack trace
  log.error("Lỗi: " + ex.getMessage()); // ❌ mất cả stack lẫn cause
  ```

### 2. Giữ cause chain khi bọc exception
* Khi chuyển exception kỹ thuật thành exception nghiệp vụ, **luôn truyền nguyên nhân gốc**:
  ```java
  throw new OrderProcessingException("Không tạo được order", e); // ✅ giữ cause
  ```
* Nếu chỉ `new OrderProcessingException(e.getMessage())`, log sẽ in stack trace của exception *mới* (trỏ về dòng `throw`), còn **root cause thật** (ví dụ `SQLException` ở tầng DB) biến mất. Cause chain (`Caused by: ...`) chính là sợi dây dẫn tới gốc.

### 3. Log đúng một lần, ở đúng chỗ
* **Nuốt giữa chừng là tệ nhất**: tầng dưới `catch` rồi nuốt (hoặc chỉ log message) khiến tầng trên tưởng mọi thứ ổn. Nguyên tắc: tầng dưới **giữ nguyên/bọc-kèm-cause rồi ném tiếp**; chỉ **biên ngoài cùng** (global `@ExceptionHandler`/`@ControllerAdvice`, hoặc error handler của message listener) **log một lần với stack trace đầy đủ**.

### 4. Không để khung che mất lỗi
* Cẩn thận với `try-with-resources`/`finally` ném exception mới → **che lấp (suppress)** exception gốc. Dùng `Throwable.addSuppressed()`/để nguyên cơ chế của try-with-resources thay vì nuốt. Tránh `catch (Throwable t)` quá rộng nuốt cả `Error`.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: nuốt stack trace và đứt cause chain
```java
public Order create(OrderRequest req) {
    try {
        return repository.save(map(req));
    } catch (DataAccessException e) {
        // ❌ Chỉ lấy message: mất stack trace + mất cause gốc
        log.error("Tạo order lỗi: " + e.getMessage());
        // ❌ Bọc lại nhưng đánh rơi e → root cause SQLException biến mất
        throw new OrderProcessingException("Tạo order thất bại");
    }
}
```

### ✅ GOOD: truyền throwable + giữ cause + log một lần ở biên
```java
public Order create(OrderRequest req) {
    try {
        return repository.save(map(req));
    } catch (DataAccessException e) {
        // ✅ Bọc kèm cause để giữ root cause; KHÔNG log ở đây (tránh log nhiều lần)
        throw new OrderProcessingException("Tạo order thất bại orderRef=" + req.getRef(), e);
    }
}
```
```java
// ✅ Biên ngoài cùng log đúng MỘT lần, truyền e làm tham số cuối → full stack + Caused by
@RestControllerAdvice
public class GlobalExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(OrderProcessingException.class)
    public ResponseEntity<ApiError> handle(OrderProcessingException e) {
        log.error("Xử lý order thất bại [{}]", MDC.get("traceId"), e); // ✅ e ở cuối, không nằm trong {}
        return ResponseEntity.status(500).body(ApiError.of("ORDER_FAILED", e.getMessage()));
    }
}
```

## 📊 Bảng so sánh: các cách log exception

| Cách viết | Stack trace? | Cause chain? | Đánh giá |
| :--- | :--- | :--- | :--- |
| `log.error("msg")` | ❌ Không | ❌ Không | Vô dụng khi debug |
| `log.error("msg: " + e.getMessage())` | ❌ Không | ❌ Không | Mất root cause |
| `log.error("msg {}", e)` | ❌ Không (chỉ toString) | ❌ Không | Sai cách dùng SLF4J |
| `log.error("msg id={}", id, e)` | ✅ Có | ✅ Có | **Đúng chuẩn** |
| `throw new X(msg)` (không cause) | — | ❌ Đứt | Mất root cause khi log ở trên |
| `throw new X(msg, e)` | — | ✅ Giữ | **Đúng chuẩn** |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "đặt exception vào placeholder `{}`"
* Nhiều người viết `log.error("Lỗi {}", e)` tưởng sẽ in stack trace, nhưng placeholder `{}` **tiêu thụ** `e` và chỉ gọi `e.toString()` → ra một dòng `...Exception: message`, **không có stack trace**. Đúng là để `e` làm tham số **dư ra ngoài** mọi `{}`: `log.error("Lỗi xử lý id={}", id, e)`. Quy tắc vàng: *throwable luôn là tham số cuối và không có `{}` dành cho nó*.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Production chỉ thấy `OrderProcessingException: Tạo order thất bại`, không có `Caused by`. Bạn lần ra root cause kiểu gì và sửa code ra sao?"**
* **Trả lời**: Thiếu `Caused by` nghĩa là khi bọc exception, người viết đã **không truyền nguyên nhân gốc** vào constructor (`new X(msg)` thay vì `new X(msg, e)`), nên chuỗi cause bị đứt ngay tại điểm bọc — stack trace chỉ trỏ về dòng `throw` chứ không về `SQLException`/IO thật. Trước mắt, tôi sẽ dựa vào **traceId trong MDC** để gom toàn bộ log của request đó, lần ngược qua các tầng tìm log gần nhất còn giữ ngữ cảnh, và nếu cần thì bật DEBUG có kiểm soát ở tầng nghi ngờ để tái hiện. Về lâu dài, sửa tận gốc bằng hai nguyên tắc: (1) **mọi chỗ bọc exception phải truyền cause** (`new X("...", e)`) để giữ `Caused by`; (2) **log đúng một lần ở biên** với `log.error("...", e)` (throwable ở cuối) thay vì rải `getMessage()` khắp các tầng. Như vậy một lần log ở `@ControllerAdvice` là đủ thấy toàn bộ chuỗi từ exception nghiệp vụ xuống tận root cause kỹ thuật.
