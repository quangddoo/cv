# Authentication vs. Authorization: Sự khác biệt & Phân quyền thực chiến trong Spring Boot

## ⚡ Tóm tắt ngắn (30s)
*   **`Authentication (Xác thực - Bạn là ai?)`**: Là quá trình xác minh danh tính của một thực thể truy cập hệ thống (ví dụ: đăng nhập bằng Username/Password, quét vân tay, kiểm tra JWT). Kết quả thành công là hệ thống biết được danh tính chính xác của bạn.
*   **`Authorization (Phân quyền - Bạn được làm gì?)`**: Là quá trình kiểm tra thực thể đã được xác thực có quyền thực hiện một hành động cụ thể hay truy cập một tài nguyên nào đó hay không (ví dụ: User thường không được vào trang quản trị Admin, chỉ Quản trị viên mới được xóa dữ liệu).
*   **Spring Security**:
    *   Authentication được quản lý bởi **`AuthenticationManager`** và đại diện bởi đối tượng **`Authentication`** chứa thông tin danh tính (`Principal`) trong **`SecurityContext`**.
    *   Authorization được quyết định bởi **`AuthorizationManager`** dựa trên danh sách quyền hạn (**`GrantedAuthority`**) được đính kèm trong đối tượng `Authentication` của người dùng.

## 🔍 Chi tiết bản chất thực chiến

### 1. Bảng đối chiếu so sánh bản chất

| Tiêu chí | Authentication (Xác thực) | Authorization (Phân quyền) |
| :--- | :--- | :--- |
| **Câu hỏi cốt lõi** | Bạn là ai? (Who are you?) | Bạn được phép làm gì? (What can you do?) |
| **Thời điểm chạy** | Chạy **trước** (Phải biết danh tính trước khi cấp quyền). | Chạy **sau** (Dựa trên danh tính đã xác định). |
| **Đầu vào phổ biến** | Credentials: Username/Password, Token (JWT), OTP, Client Certificate. | Authorities/Roles: `ROLE_ADMIN`, `READ_PRIVILEGE`, `write:order`. |
| **Component Spring** | `AuthenticationManager`, `AuthenticationProvider`, `UserDetailsService`. | `AuthorizationManager`, `@PreAuthorize`, `SecurityExpressionHandler`. |
| **Trạng thái lỗi** | **401 Unauthorized** (Chưa xác thực hoặc xác thực sai). | **403 Forbidden** (Đã xác thực nhưng không đủ quyền). |

### 2. Sự liên kết trong Spring Security Lifecycle
```text
[ Client Request ]
       │
┌──────▼────────────────────────────────────────────────────────┐
│ 1. Authentication Phase (Xác thực)                            │
│  - Filter trích xuất Credentials                              │
│  - Gửi tới AuthenticationManager -> Xác thực thành công       │
│  - Tạo đối tượng Authentication chứa UserDetails & Authorities│
│  - Nạp Authentication vào SecurityContextHolder              │
└──────┬────────────────────────────────────────────────────────┘
       │
┌──────▼────────────────────────────────────────────────────────┐
│ 2. Authorization Phase (Ủy quyền)                             │
│  - Request tiếp tục đi tới AuthorizationFilter                │
│  - Hệ thống kiểm tra: "Đường dẫn /api/admin có yêu cầu gì?"   │
│  - Đọc Authorities từ SecurityContext và đối chiếu           │
│  - Đủ quyền -> Đi tiếp. Thiếu quyền -> Ném AccessDenied       │
└───────────────────────────────────────────────────────────────┘
```

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Tự viết logic phân quyền thủ công bằng code if-else trong Service/Controller
Việc kiểm tra quyền truy cập bị trộn lẫn trực tiếp vào logic nghiệp vụ của Controller hoặc Service, khiến mã nguồn rối rắm, lặp đi lặp lại và cực kỳ khó bảo trì hay mở rộng khi thay đổi cấu trúc phân quyền.

```java
package com.example.controller;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.example.service.UserService;
import com.example.model.User;

@RestController
@RequestMapping("/api/v1/users")
public class UserControllerBad {

    private final UserService userService;

    public UserControllerBad(UserService userService) {
        this.userService = userService;
    }

    // ❌ BAD: Tự check quyền thủ công bằng logic thô
    @DeleteMapping("/{id}")
    public ResponseEntity<String> deleteUser(@PathVariable Long id, @RequestHeader("X-User-Role") String role) {
        if (!"ADMIN".equals(role)) {
            // ❌ Trả về lỗi 403 thủ công, code bị phân mảnh và dễ sót lọt bảo mật
            return ResponseEntity.status(HttpStatus.FORBIDDEN).body("Only admin can delete user!");
        }
        
        userService.deleteById(id);
        return ResponseEntity.ok("Deleted successfully");
    }
}
```

### ✅ GOOD: Sử dụng Phân quyền khai báo (Declarative Security) với `@PreAuthorize`
Tách biệt hoàn toàn bảo mật phân quyền ra khỏi mã nghiệp vụ bằng các công cụ mạnh mẽ và tiêu chuẩn của Spring Security.

```java
package com.example.controller;

import org.springframework.http.ResponseEntity;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.*;
import com.example.service.UserService;

@RestController
@RequestMapping("/api/v1/users")
public class UserControllerGood {

    private final UserService userService;

    public UserControllerGood(UserService userService) {
        this.userService = userService;
    }

    // ✅ GOOD: Phân quyền khai báo ở mức Method
    // Chỉ cho phép người dùng có Role ADMIN được xóa
    @DeleteMapping("/{id}")
    @PreAuthorize("hasRole('ADMIN')")
    public ResponseEntity<String> deleteUser(@PathVariable Long id) {
        userService.deleteById(id);
        return ResponseEntity.ok("Deleted successfully");
    }

    // ✅ Phân quyền động nâng cao (Instance-level authorization)
    // Người dùng chỉ được sửa thông tin của CHÍNH HỌ hoặc là ADMIN
    @PutMapping("/{id}")
    @PreAuthorize("hasRole('ADMIN') or #id == authentication.principal.id")
    public ResponseEntity<String> updateUser(@PathVariable Long id, @RequestBody UserDto dto) {
        userService.update(id, dto);
        return ResponseEntity.ok("Updated successfully");
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Phân biệt `Role` và `Authority` trong Spring Security
Đây là chi tiết cực kỳ hay bị nhầm lẫn và hỏi sâu trong phỏng vấn:
*   **`Authority (Quyền hạn - Dạng hạt mịn)`**: Đại diện cho một hành động cụ thể mà người dùng có thể thực hiện. Ví dụ: `write:order`, `read:user`.
    *   Sử dụng: `hasAuthority('write:order')`.
    *   Spring Security đối chiếu chính xác ký tự chuỗi khớp 100%.
*   **`Role (Vai trò - Dạng thô)`**: Đại diện cho một nhóm các quyền hạn. Ví dụ: `ADMIN`, `USER`.
    *   Sử dụng: `hasRole('ADMIN')`.
    *   *Bản chất dưới mui xe*: Spring Security tự động bổ sung tiền tố **`ROLE_`** vào trước tên role bạn khai báo. Lệnh `hasRole('ADMIN')` thực chất sẽ tìm quyền **`ROLE_ADMIN`** trong danh sách Authorities của người dùng.
    *   *Cạm bẫy*: Nếu trong cơ sở dữ liệu hoặc JWT bạn lưu quyền là `ADMIN`, khi dùng `hasRole('ADMIN')` sẽ luôn bị lỗi 403 vì Spring mong muốn tìm chuỗi `ROLE_ADMIN`.

### 2. Cạm bẫy bỏ qua bảo mật khi gọi phương thức nội bộ (AOP Proxy Self-Invocation Gotcha)
*   **Vấn đề**: Bạn chú thích `@PreAuthorize("hasRole('ADMIN')")` ở phương thức `deleteSensitiveData()` trong `ProductService`. Tại một phương thức public khác là `executeBatchJobs()` cùng nằm trong `ProductService`, bạn gọi trực tiếp `this.deleteSensitiveData()`. Một người dùng có quyền `USER` gọi vào `executeBatchJobs()`, hệ thống vẫn cho phép xóa dữ liệu nhạy cảm mà không quăng lỗi bảo mật!
*   **Nguyên nhân**: `@PreAuthorize` hoạt động dựa trên cơ chế **Spring AOP Proxy**. Khi một bean khác gọi vào `ProductService`, cuộc gọi đi qua Proxy và Proxy sẽ chặn lại để kiểm tra quyền bảo mật. Tuy nhiên, khi gọi nội bộ (`self-invocation`), từ khóa `this` trỏ thẳng tới đối tượng đích (Target Object) thay vì đi qua Proxy, dẫn đến việc bỏ qua hoàn toàn bước kiểm tra phân quyền!
*   **Giải pháp**: Thiết kế lại kiến trúc, chuyển các phương thức cần bảo mật sang một class Service độc lập để bắt buộc các cuộc gọi phải đi qua Spring AOP Proxy.
