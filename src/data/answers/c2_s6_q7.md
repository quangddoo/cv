# CompletableFuture dùng sai có thể gây issue gì?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: `CompletableFuture` là một công cụ lập trình phản ứng (Reactive/Async) vô cùng mạnh mẽ của Java. Tuy nhiên, việc sử dụng sai cách sẽ biến nó thành "quả bom nổ chậm". Sai lầm cốt lõi thường nằm ở việc **lạm dụng tài nguyên ngầm định**: Sử dụng Thread Pool mặc định (`commonPool`) cho các tác vụ nghẽn I/O chậm, gọi lệnh nhận kết quả (`get`/`join`) mà không đặt thời gian chờ, hoặc sử dụng sai các chuỗi xử lý làm nghẽn luồng xử lý chính.
* **Các thảm họa thực chiến được giải quyết**:
    1. **Thảm họa cạn kiệt luồng Docker Container (Common Pool Starvation)**: Ứng dụng chạy trên Kubernetes Pod (thường chỉ được cấp 2 Cores CPU). Do không truyền Thread Pool tùy biến, `CompletableFuture` mặc định dùng `ForkJoinPool.commonPool()` (chỉ có duy nhất 1 luồng trên hệ thống 2 Cores) để gọi HTTP API bên ngoài. Chỉ cần 1 request bị lag, toàn bộ các luồng con chạy ngầm của dự án và các thư viện khác dùng chung commonPool đều bị treo cứng hoàn toàn.
* **Quyết định Senior**: Cấu hình quy chuẩn sử dụng an toàn:
    1. **Luôn truyền Custom Executor**: Tuyệt đối không gọi `supplyAsync(supplier)` mà bắt buộc phải truyền Thread Pool chuyên biệt: `supplyAsync(supplier, customIoExecutor)`.
    2. **Đặt chốt chặn thời gian**: Bắt buộc xích thêm `.orTimeout(timeout, unit)` cho mọi pipeline để giải phóng tài nguyên khi xảy ra sự cố.
    3. **Phân biệt rạch ròi sync/async**: Sử dụng các phương thức có hậu tố `Async` (như `thenApplyAsync`) khi bước tiếp theo chứa logic tính toán nặng hoặc nghẽn I/O.

## 🔍 Chi tiết bản chất thực chiến: 4 Sai lầm chí mạng khi dùng CompletableFuture

Senior Engineer nắm lòng cơ chế vận hành của `ForkJoinPool` và mô hình Non-blocking để tránh các cạm bẫy hiệu năng sau:

### 1. Thảm họa dùng chung `ForkJoinPool.commonPool()` cho tác vụ I/O
* **Cơ chế mặc định**: Khi gọi `CompletableFuture.supplyAsync(() -> { ... })` không truyền tham số thứ hai, JVM tự động đẩy task vào `ForkJoinPool.commonPool()`.
* **Cạm bẫy**: `commonPool` được tối ưu hóa cho các tác vụ **CPU-bound** (tính toán thuần túy, chạy nhanh). Kích thước mặc định của nó bằng $\text{Số CPU cores} - 1$.
  * Trên các container Kubernetes (ví dụ: limit 2 Cores), pool này chỉ có đúng **1 luồng làm việc**.
  * Nếu ta dùng nó để gọi HTTP API ngoài (I/O-bound) mất 5 giây, thì duy nhất 1 luồng này bị khóa cứng. Toàn bộ các tác vụ bất đồng bộ khác sử dụng CompletableFuture trong hệ thống sẽ bị dồn ứ xếp hàng, gây nghẽn toàn cục.

### 2. Treo luồng vô hạn do gọi `.get()` hoặc `.join()` thiếu Timeout
* **Cạm bẫy**: Hàm `join()` hoặc `get()` là các hàm chặn (blocking calls). Nếu tác vụ chạy ngầm bị rơi vào vòng lặp vô hạn, deadlock dưới DB, hoặc treo I/O mạng, luồng gọi chính (như luồng xử lý request HTTP) sẽ xếp hàng chờ đợi vĩnh viễn, ăn mòn toàn bộ năng lực chịu tải của web server.

### 3. Hiểu sai sự khác biệt giữa `thenApply` và `thenApplyAsync`
* **`thenApply(Function)`**: Bước tiếp theo này sẽ được chạy bởi **chính luồng vừa hoàn thành tác vụ trước đó**, hoặc luồng gọi chính nếu tác vụ trước đã hoàn thành xong.
  * **Hậu quả**: Nếu bên trong `thenApply` chứa logic ghi file nặng hoặc gọi API tiếp theo, nó sẽ vô tình block luôn luồng worker của pool trước đó, làm giảm throughput nghiêm trọng.
* **`thenApplyAsync(Function, Executor)`**: Bước tiếp theo bắt buộc được tách ra và đẩy vào một luồng hoàn toàn mới thuộc Pool được chỉ định, giúp giải phóng ngay lập tức luồng worker trước đó.

## 💻 Code thực chiến / Cấu hình thực tế: BAD vs GOOD

### ❌ BAD: Viết code bất đồng bộ mù quáng phá hủy hệ thống dưới tải cao
Sử dụng Thread Pool mặc định, gọi các bước tiếp theo trong chuỗi mà không tách luồng chuyên biệt, và chặn luồng chính vô hạn.

```java
import java.util.concurrent.CompletableFuture;

public class BadAsyncPipeline {

    public String processOrderBad(String orderId) {
        // ❌ TỒI 1: Dùng commonPool cho tác vụ I/O chậm (gọi DB)
        return CompletableFuture.supplyAsync(() -> {
            return queryDatabaseForOrder(orderId); 
        })
        // ❌ TỒI 2: Dùng thenApply cho tác vụ ghi file I/O nặng
        // Việc này sẽ block luồng commonPool vừa chạy ở bước trên
        .thenApply(orderData -> {
            return writeOrderToFileSystem(orderData); 
        })
        // ❌ TỒI 3: Gọi join() không có Timeout làm treo cứng luồng chính vĩnh viễn nếu lỗi
        .join(); 
    }

    private String queryDatabaseForOrder(String id) { return "OrderData"; }
    private String writeOrderToFileSystem(String data) { return "FilePath"; }
}
```

### ✅ GOOD: Cấu hình Custom Thread Pool, sử dụng Fluent API bất đồng bộ an toàn
Senior tách biệt rạch ròi Thread Pool xử lý I/O, cấu hình các bước tiếp theo chạy bất đồng bộ trên luồng mới, và thiết lập chốt chặn thời gian `orTimeout`.

```java
import java.util.concurrent.*;
import lombok.extern.slf4j.Slf4j;

@Slf4j
public class OptimizedAsyncPipeline {

    // ✅ TỐT: Khởi tạo Thread Pool riêng biệt chuyên xử lý các tác vụ I/O nặng
    private static final ExecutorService dbExecutor = Executors.newFixedThreadPool(20, new ThreadFactory() {
        private int count = 1;
        @Override
        public Thread newThread(Runnable r) {
            return new Thread(r, "db-worker-" + count++);
        }
    });

    private static final ExecutorService fileExecutor = Executors.newFixedThreadPool(10, new ThreadFactory() {
        private int count = 1;
        @Override
        public Thread newThread(Runnable r) {
            return new Thread(r, "file-worker-" + count++);
        }
    });

    public String processOrderOptimized(String orderId) {
        return CompletableFuture.supplyAsync(() -> {
            // ✅ Chạy trên luồng DB chuyên dụng
            return queryDatabaseForOrder(orderId); 
        }, dbExecutor)
        // ✅ TỐT: Chuyển tiếp sang luồng File chuyên dụng bất đồng bộ, giải phóng ngay luồng DB
        .thenApplyAsync(orderData -> {
            return writeOrderToFileSystem(orderData); 
        }, fileExecutor)
        // ✅ TỐT: Thiết lập giới hạn thời gian chờ tối đa 3 giây
        .orTimeout(3, TimeUnit.SECONDS)
        .exceptionally(ex -> {
            log.error("Hệ thống xử lý đơn hàng quá thời gian chờ!", ex);
            return "Fallback_Error_Processing";
        })
        .join(); // Giải phóng luồng an toàn
    }

    private String queryDatabaseForOrder(String id) { return "OrderData"; }
    private String writeOrderToFileSystem(String data) { return "FilePath"; }
}
```

## 📊 Bảng so sánh các phương thức chuỗi xử lý của CompletableFuture

| Phương thức | Luồng thực thi | Use Case phù hợp | Rủi ro hiệu năng |
| :--- | :--- | :--- | :--- |
| **`thenApply`** | Luồng vừa chạy xong tác vụ trước đó (hoặc luồng main). | Các tác vụ biến đổi dữ liệu cực nhanh trong bộ nhớ (CPU-bound siêu nhẹ). | Dễ gây block nhầm luồng worker của pool trước nếu xử lý logic nặng. |
| **`thenApplyAsync`** | Luồng hoàn toàn mới được mượn từ Pool chỉ định. | Tác vụ bước tiếp theo chứa logic tính toán nặng hoặc gọi I/O tiếp. | Tốn tài nguyên chuyển ngữ cảnh luồng (Context Switch) nếu tác vụ quá nhẹ. |
| **`thenCompose`** | Luồng của tác vụ trước đó. | Gom/phẳng hóa (flatten) 2 CompletableFuture lồng nhau (trả về Future khác). | Treo luồng nếu Future con không có timeout. |
| **`thenCombine`** | Luồng hoàn thành tác vụ thứ hai. | Kết hợp kết quả của 2 CompletableFuture độc lập chạy song song. | Block luồng nếu 1 trong 2 Future bị lag vô hạn. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Spring `@Async` trả về `CompletableFuture` nhưng lại dùng thread pool mặc định của Spring"
* **Vấn đề**: Nếu ta viết `@Async public CompletableFuture<String> run()` mà không định nghĩa rõ cấu hình Thread Pool trong annotation `@Async("customExecutor")`.
* **Hậu quả**: Spring sẽ sử dụng Thread Pool mặc định là `SimpleAsyncTaskExecutor`. Thư viện này có hành vi cực kỳ nguy hiểm: **Nó tạo mới 1 luồng vật lý OS cho mỗi request và hủy luồng khi chạy xong**. Dưới tải cao, việc tạo hàng nghìn luồng vật lý sẽ băm nát CPU hệ thống do Context Switching và nhanh chóng làm sập tiến trình với lỗi `OutOfMemoryError: unable to create new native thread`.
* **Khắc phục**: Luôn khai báo tường minh tên Bean Thread Pool khi dùng `@Async`, ví dụ: `@Async("taskExecutor")`.

### 2. Câu hỏi đào sâu từ interviewer

* **Q1: Tại sao việc gọi `.join()` trên CompletableFuture lại thường được ưa chuộng hơn `.get()`, mặc dù cả hai đều dùng để chặn luồng lấy kết quả?**
  * *Trả lời*: Đây là vấn đề về thiết kế cú pháp và xử lý ngoại lệ:
    1. **`get()`**: Định nghĩa trong giao diện `Future` truyền thống. Phương thức này bắt buộc lập trình viên phải bắt các checked exception là `InterruptedException` và `ExecutionException` trong khối `try-catch`. Việc này làm code bị rườm rà (boilerplate code) khi viết theo phong cách functional/reactive.
    2. **`join()`**: Định nghĩa riêng trong `CompletableFuture`. Nó chỉ ném ra unchecked exception (`CompletionException` bọc ngoài lỗi gốc). Điều này cho phép sử dụng mượt mà trong Java Streams API hoặc các chuỗi lambda mà không cần viết khối `try-catch` lồng ghép phức tạp.

* **Q2: Lệnh `CompletableFuture.allOf()` giúp giải quyết bài toán chạy song song nhiều task như thế nào? Cần lưu ý gì về hiệu năng và bẫy lỗi khi dùng hàm này?**
  * *Trả lời*: 
    * `CompletableFuture.allOf(f1, f2, f3)` trả về một Future mới và chỉ hoàn thành khi **tất cả** các Future truyền vào đều hoàn thành. Nó giúp tối ưu hóa thời gian chạy song song nhiều API độc lập.
    * **Lưu ý chí mạng về bẫy lỗi**:
      1. **Bẫy nuốt lỗi**: Nếu có nhiều Future bị lỗi, `allOf().join()` chỉ ném ra exception của Future đầu tiên thất bại. Các exception của các Future thất bại khác sẽ bị che giấu hoàn toàn.
      2. **Khắc phục**: Tôi luôn duyệt qua danh sách các Future ban đầu để kiểm tra `.isCompletedExceptionally()` và chủ động thu thập toàn bộ các lỗi riêng lẻ để ghi log chính xác, thay vì chỉ tin tưởng vào exception ném ra từ `allOf`.
