# Cơ Chế Chốt Chặn Chất Lượng (Quality Gates) Trong CI/CD: Chống Triển Khai Code Lỗi Lên Production

## ⚡ Tóm tắt ngắn (30s)
Để tuyệt đối ngăn chặn code lỗi tiếp cận người dùng trên Production, hệ thống CI/CD cần thiết lập một chuỗi **Chốt chặn chất lượng (Quality Gates)** tự động và nghiêm ngặt qua 4 lớp bảo vệ:
1. **Lớp 1: Branch Protection & PR Validation (Cửa ngõ)**: Bắt buộc code phải chạy qua pipeline CI thành công trên nhánh feature và được duyệt thủ công bởi tối thiểu 2 Seniors trước khi merge vào `main`.
2. **Lớp 2: Kiểm thử tự động & Ngưỡng bao phủ (Test Coverage Threshold)**: Ép kiểm tra độ bao phủ test (ví dụ: **JaCoCo > 80% coverage**). Nếu test coverage tụt giảm, pipeline lập tức báo đỏ.
3. **Lớp 3: SonarQube Quality Gate & Security Check**: Chặn đứng các bản build có chứa "lỗ hổng bảo mật mới" hoặc "nợ kỹ thuật" (technical debt) vượt ngưỡng cho phép.
4. **Lớp 4: Triển khai Canary/Blue-Green & Smoke Test tự động**: Deploy thử nghiệm trên 5% lượng traffic, chạy kịch bản giả lập gọi API thực tế (Smoke Test). Nếu phát hiện tỷ lệ lỗi HTTP 5xx tăng vọt, hệ thống **tự động Rollback trong vòng 60 giây**.

---

## 🔍 Chi tiết bản chất kỹ thuật & Các lớp chốt chặn

### 1. Ngưỡng chất lượng tĩnh (SonarQube & JaCoCo Quality Gates)
* **JaCoCo (Java Code Coverage)**: Không chỉ đo lượng dòng code được chạy qua test, JaCoCo còn kiểm tra **Branch Coverage** (độ bao phủ của các rẽ nhánh `if-else`). Nếu một developer viết thêm code logic phức tạp mà không bổ sung unit test tương ứng, JaCoCo sẽ đánh sập pipeline trước khi đóng gói Docker.
* **SonarQube Quality Gate**: Định nghĩa một bộ quy tắc cứng. Ví dụ:
  * Số lượng lỗi bảo mật mới (New Vulnerabilities) = `0`.
  * Tỷ lệ trùng lặp code mới (New Duplicated Lines) < `3%`.
  * Điểm đánh giá độ tin cậy (Reliability Rating) đạt mức `A`.

### 2. Kịch bản Smoke Test sau Deploy (Kiểm thử khói)
Sau khi deploy ứng dụng lên Staging hoặc Canary Production, pipeline không được phép coi là hoàn thành ngay lập tức.
* Một kịch bản **Smoke Test** độc lập sẽ được kích hoạt để thực hiện một loạt các API call cốt lõi (như Login, Get Profile, Healthcheck).
* Nếu Smoke Test trả về HTTP Status `200` và độ trễ dưới ngưỡng quy định (ví dụ: `< 200ms`), đợt deploy mới được chấp thuận hoàn tất.

## 💻 Cấu hình Thực chiến: Thiết lập Chốt chặn

### 1. Cấu hình JaCoCo chặn build nếu Coverage < 80% (`pom.xml`):
```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.8</version>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
        <!-- ✅ Thiết lập Chốt chặn Check Coverage -->
        <execution>
            <id>jacoco-check</id>
            <goals>
                <goal>check</goal>
            </goals>
            <configuration>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>LINE</counter>
                                <value>COVEREDRATIO</value>
                                <minimum>0.80</minimum> <!-- Bắt buộc phủ tối thiểu 80% dòng code -->
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

### 2. Kịch bản Smoke Test tự động trong Pipeline CD (Shell script):
```bash
#!/bin/bash
echo "🚀 Khởi động Smoke Test cho dịch vụ mới deploy..."

TARGET_URL="https://staging.myapi.com"
MAX_ATTEMPTS=6
WAIT_SECONDS=10
SUCCESS=false

# 🔄 Vòng lặp kiểm tra sức khỏe của dịch vụ trong tối đa 1 phút
for ((i=1; i<=MAX_ATTEMPTS; i++)); do
  # Gọi API healthcheck lấy HTTP status code
  STATUS=$(curl -o /dev/null -s -w "%{http_code}" --max-time 5 "${TARGET_URL}/actuator/health")
  
  if [ "$STATUS" -eq 200 ]; then
    echo "✅ [Lần thử $i] Dịch vụ HOẠT ĐỘNG KHỎE MẠNH! (HTTP 200)"
    SUCCESS=true
    break
  else
    echo "⚠️ [Lần thử $i] Dịch vụ chưa sẵn sàng, trả về HTTP $STATUS. Thử lại sau ${WAIT_SECONDS}s..."
    sleep $WAIT_SECONDS
  fi
done

if [ "$SUCCESS" = false ]; then
  echo "❌ SMOKE TEST THẤT BẠI sau 1 phút! Lập tức dừng pipeline và báo động đỏ!"
  exit 1 # Báo lỗi để kích hoạt rollback tự động trong CI/CD tool
fi
```

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. "Làm sao để chúng ta chạy thử nghiệm tích hợp (Integration Tests) gọi tới các API của bên thứ ba (như Cổng thanh toán Stripe, SendGrid) trong pipeline CI/CD mà không làm phát sinh chi phí thực tế hoặc bị block do giới hạn mạng bảo mật?"
* **Trả lời**: Chúng ta tuyệt đối không bao giờ gọi tới API Production hoặc Sandbox của đối tác trong quá trình chạy tự động của pipeline CI vì 3 lý do: Mạng chập chờn gây lỗi build oan, tốn chi phí, và giới hạn rate limiting.
* **Các giải pháp thực chiến**:
  1. **API Mocking (WireMock)**: Khởi chạy một container **WireMock** giả lập trong pipeline. Ta cấu hình cho WireMock trả về đúng các mẫu HTTP Response (thành công, thất bại, timeout) giống hệt Stripe khi nhận được yêu cầu. Từ đó, ta có thể test toàn bộ logic xử lý của App một cách độc lập tuyệt đối.
  2. **Contract Testing (Pact / Spring Cloud Contract)**: Định nghĩa một "hợp đồng" cấu trúc dữ liệu giữa App và Bên thứ ba. Pipeline sẽ kiểm tra xem code của ta có vi phạm cấu trúc hợp đồng đó hay không mà không cần gọi mạng thực tế.

### 2. "Nếu Smoke Test báo thành công (Green) nhưng ứng dụng bị rò rỉ bộ nhớ (Memory Leak) âm thầm và bị sập hoàn toàn sau 2 tiếng chạy thực tế, làm sao để phát hiện và ngăn chặn thảm họa này?"
* **Trả lời**: Đây là lỗi thuộc về hành vi runtime dài hạn, Smoke Test chạy trong 1 phút đầu không thể phát hiện được.
* **Giải pháp khắc phục**:
  1. **Kubernetes Liveness & Readiness Probes**: Cấu hình K8s liên tục ping cổng `/actuator/health` cứ 10 giây một lần. Nếu Pod bị đơ (Deadlock) hoặc ngốn RAM không phản hồi, K8s sẽ **tự động khởi động lại (restart)** pod đó để cứu hệ thống tạm thời.
  2. **APM Alerts (Grafana / Prometheus)**: Thiết lập cảnh báo dựa trên tỷ lệ lỗi (Error Rate) và mức tiêu thụ RAM. Nếu RAM của Pod tăng tiến liên tục không giảm (Pattern của Memory Leak), Grafana sẽ gửi tin nhắn khẩn cấp về Slack/Telegram để Senior Engineer vào can thiệp, chủ động chạy hotfix trước khi toàn bộ hệ thống bị sập.
