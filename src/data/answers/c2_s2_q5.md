# Làm sao xác định lỗi đến từ version mới hay dependency bên ngoài?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Đây là bài toán **Cô lập và Phân bổ lỗi (Error Attribution)** trong hệ thống phân tán. Để xác định thủ phạm gây lỗi 5xx là do mã nguồn phiên bản mới vừa deploy hay do lỗi của các dịch vụ liên kết bên ngoài (Database, Redis, Downstream Microservice, Third-party API), kỹ sư cần phân tích các biểu đồ **Distributed Tracing (Spans)** và phân loại ngoại lệ (Exception Classification) trong log.
* **Các thảm họa thực chiến được giải quyết**:
    1. **Rollback oan uổng (Unnecessary Rollback)**: Hệ thống sập do cổng thanh toán đối tác bị nghẽn, nhưng vì không phân tích sâu, đội ngũ lầm tưởng lỗi do bản deploy mới và thực hiện rollback, làm mất thời gian mà không giải quyết được sự cố.
    2. **Đổ lỗi chéo giữa các bên (Finger-pointing)**: Thiếu dữ liệu quan trắc khiến team phát triển ứng dụng và team hạ tầng đổ lỗi cho nhau khi hệ thống chậm, kéo dài thời gian downtime vô ích.
* **Quyết định Senior**: Xem biểu đồ **Trace Timeline** trên hệ thống APM. Nếu Span nội bộ bị đánh dấu đỏ (lỗi) nhưng các Span con gọi ra ngoài (Outbound HTTP/SQL) vẫn xanh (thành công), lỗi chắc chắn nằm ở code mới. Ngược lại, nếu Span gọi ra ngoài bị đỏ hoặc trả về thời gian phản hồi quá lâu (Timeout), lỗi thuộc về Dependency bên ngoài. Phân loại log lỗi rõ ràng thành nhóm lỗi nghiệp vụ nội bộ (Local Exception) và lỗi giao tiếp mạng (Integration/Client Exception).

## 🔍 Chi tiết bản chất thực chiến

Để xác định chính xác nguồn gốc lỗi sau khi deploy, kỹ sư Senior sẽ thực hiện quy trình phân tích cô lập 3 bước sau:

### Bước 1: Phân tích Trace Spans trên APM (Phương pháp nhanh nhất)
Hệ thống Distributed Tracing tự động phân rã một request thành các phân đoạn (Spans) tương ứng với từng tác vụ.
* **Trường hợp A: Thủ phạm là Code mới (Local Bug)**
  * **Dấu hiệu**: APM cho thấy Span gốc (ví dụ: `POST /api/v1/checkout`) bị lỗi (màu đỏ), nhưng tất cả các Span con như `SQL SELECT`, `HTTP POST stripe-api` đều xanh (thành công). Điều này chứng tỏ code mới đã nhận dữ liệu thành công từ ngoài, nhưng gặp lỗi logic khi xử lý dữ liệu đó (như NullPointerException, Parse error).
* **Trường hợp B: Thủ phạm là Dependency bên ngoài (External Bug)**
  * **Dấu hiệu**: Span con gọi ra ngoài bị đánh dấu lỗi đỏ (HTTP 502/503/504) hoặc kéo dài quá thời gian quy định (Timeout), dẫn đến sập Span gốc của ứng dụng.

### Bước 2: Phân loại Ngoại lệ (Exception Classification) trong Log
Đọc stack trace để xác định loại thư viện hoặc lớp (Class) ném ra ngoại lệ:
* Nếu ngoại lệ xuất phát từ các gói code dự án (ví dụ: `com.company.project.service.OrderService.process`), đây là lỗi của Code mới.
* Nếu ngoại lệ xuất phát từ Client giao tiếp (ví dụ: `feign.FeignException$InternalServerError`, `org.springframework.web.client.HttpServerErrorException`, `com.mongodb.MongoTimeoutException`), đây là lỗi do dịch vụ bên ngoài phản hồi lỗi hoặc không thể kết nối.

### Bước 3: So sánh tương quan thời gian (Time-series Correlation)
* Sử dụng Grafana để so sánh thời điểm tỷ lệ lỗi bắt đầu tăng vọt với thời điểm bản deploy mới hoàn tất.
* Nếu lỗi tăng vọt *trước* khi deploy, hoặc chỉ tăng vọt khi một đối tác bên ngoài gửi cảnh báo bảo trì, lỗi thuộc về bên ngoài.

## 🎨 Sơ đồ trực quan (Trace Spans: Code mới lỗi vs Dependency lỗi)

### Kịch bản 1: Lỗi do CODE MỚI vừa deploy (Local Bug)
```mermaid
gantt
    title Checkout Request: Lỗi do Code mới (Internal Error)
    dateFormat  X
    axisFormat %s ms
    
    Gateway: POST /checkout (500 Internal Error)  :active, span1, 0, 100
    App: CheckoutService.process() (Lỗi Logic!)     :crit, span2, 10, 100
    App: Call Database (Thành công)                 :active, span3, 15, 30
    App: Call Payment API (Thành công)              :active, span4, 35, 75
```
*(Giải thích: Các kết nối ngoại vi đều thành công, nhưng ứng dụng vẫn trả về lỗi 500 do lỗi logic xử lý dữ liệu sau đó).*

### Kịch bản 2: Lỗi do DEPENDENCY bên ngoài (External Bug)
```mermaid
gantt
    title Checkout Request: Lỗi do Dịch vụ Thanh toán sập (External Error)
    dateFormat  X
    axisFormat %s ms
    
    Gateway: POST /checkout (500 Internal Error)  :active, span1, 0, 2050
    App: CheckoutService.process() (Bị ảnh hưởng)    :active, span2, 10, 2050
    App: Call Database (Thành công)                 :active, span3, 15, 30
    App: Call Payment API (TIMEOUT / ERROR!)        :crit, span4, 35, 2035
```
*(Giải thích: Lỗi trực tiếp do cuộc gọi cổng thanh toán bị treo 2s rồi trả về lỗi/timeout).*

## 💻 Code thực chiến / Cấu hình thực tế: BAD vs GOOD

### ❌ BAD: Bắt tất cả lỗi thành một đống hỗn độn, không thể phân biệt nguồn gốc
Khi gọi dịch vụ bên ngoài, nếu bắt lỗi chung chung (`Exception`) và trả về 500, log ghi nhận sẽ rất mập mờ, không thể biết hệ thống sập do code của mình chạy sai hay do đối tác trả về lỗi.

```java
@Service
public class OrderServiceBad {
    @Autowired
    private RestTemplate restTemplate;

    public OrderResponse createOrder(OrderRequest request) {
        try {
            // ❌ Gọi API ngoài, nếu đối tác trả về 500 hoặc bị timeout, 
            // RestTemplate sẽ ném ra Exception chung chung.
            Object paymentResult = restTemplate.postForObject(
                "http://external-payment/pay", request, Object.class);
                
            return new OrderResponse("SUCCESS");
        } catch (Exception e) {
            // ❌ Log nghèo nàn, không phân biệt được lỗi kết nối mạng, lỗi 500 đối tác, hay lỗi NullPointer nội bộ
            logger.error("Order processing failed", e);
            throw new RuntimeException("System error");
        }
    }
}
```

---

### ✅ GOOD: Tách biệt Exception Handler rõ ràng và phân loại mã lỗi
Sử dụng các Exception đặc thù cho từng loại tích hợp và ghi log với mã nhận diện rõ ràng (Error Codes).

```java
@Service
public class OrderServiceGood {
    private static final Logger logger = LoggerFactory.getLogger(OrderServiceGood.class);

    @Autowired
    private RestTemplate restTemplate;

    public OrderResponse createOrder(OrderRequest request) {
        try {
            Object paymentResult = restTemplate.postForObject(
                "http://external-payment/pay", request, Object.class);
            return new OrderResponse("SUCCESS");
            
        } catch (HttpStatusCodeException e) {
            // ✅ ĐÚNG: Bắt riêng lỗi HTTP từ phía đối tác trả về (4xx, 5xx)
            logger.error("Dependency Error: Payment service returned HTTP {}. Body: {}", 
                e.getStatusCode(), e.getResponseBodyAsString());
            throw new DependencyFailureException("Payment service failed with status " + e.getStatusCode(), e);
            
        } catch (ResourceAccessException e) {
            // ✅ ĐÚNG: Bắt riêng lỗi kết nối mạng (Timeout, DNS, Connection Refused)
            logger.error("Infrastructure Error: Network connection to Payment service failed. Reason: {}", 
                e.getMessage());
            throw new InfrastructureFailureException("Unable to reach Payment service", e);
            
        } catch (NullPointerException | IllegalArgumentException e) {
            // ✅ ĐÚNG: Bắt riêng lỗi code logic nội bộ để phân loại mức độ cảnh báo cao
            logger.error("Local Code Error: Bug found in order processing logic", e);
            throw e;
        }
    }
}
```

## 📊 Bảng so sánh phương thức cô lập lỗi

| Tiêu chí | Sử dụng Distributed Tracing | Kiểm tra Log Exception Class | Phân tích Thống kê mã lỗi Gateway | Chạy kiểm thử tự động (Smoke Test) |
| :--- | :--- | :--- | :--- | :--- |
| **Độ chính xác** | Tuyệt đối (Định vị chính xác từng mili-giây và trạng thái Span) | Rất cao (Đọc được chính xác dòng code và thư viện lỗi) | Trung bình (Chỉ thấy mã lỗi tổng quan ở ngoài biên) | Thấp (Chỉ biết hệ thống có lỗi hay không) |
| **Thời gian thực hiện**| Ngay lập tức (Nhìn biểu đồ APM trong 10 giây) | Nhanh (Mất 1–2 phút lọc log Kibana) | Nhanh (Xem dashboard Grafana trong 30 giây) | Chậm (Mất 5-10 phút để chạy bộ test) |
| **Yêu cầu hệ thống** | Phải cấu hình APM Agent (Jaeger/Datadog) trước. | Phải có hệ thống Log tập trung. | Phải có Metric Monitor tại Gateway (Kong, Prometheus). | Phải viết sẵn kịch bản test tích hợp tự động. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Lỗi 200 giả mạo" (HTTP 200 with Error Payload)
* **Vấn đề**: Rất nhiều dịch vụ bên ngoài (hoặc code cũ) khi bị lỗi hệ thống vẫn trả về HTTP Status Code `200 OK`, nhưng trong Body chứa JSON lỗi dạng: `{"success": false, "errorCode": "SYSTEM_BUSY"}`.
* **Hậu quả**: APM Spans sẽ hiển thị màu xanh lá cây (thành công) vì tầng mạng HTTP không phát hiện lỗi. Nhưng ứng dụng của bạn sẽ bị sập (lỗi 500) khi cố gắng parse dữ liệu trống. Kỹ sư phân tích APM sẽ bị đánh lạc hướng, lầm tưởng lỗi do code mới parse sai.
* **Giải pháp**: Phải viết interceptor hoặc bộ lọc tại client để kiểm tra nội dung phản hồi (Response Body) và chủ động đánh dấu Span đó là lỗi (Set Span Status to Error) nếu chứa payload thất bại nghiệp vụ.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Nếu cả APM và hệ thống Log của bạn đều bị nghẽn và ngừng hoạt động đúng vào lúc xảy ra sự cố lỗi 5xx tăng cao sau deploy, bạn sẽ dùng lệnh hạ tầng Linux nào để xác định xem ứng dụng có đang kết nối thành công tới Database hay không?**
  * *Trả lời*: Đây là kịch bản mất hoàn toàn công cụ giám sát cao cấp. Tôi sẽ truy cập SSH trực tiếp vào máy chủ ứng dụng và sử dụng các công cụ dòng lệnh cấp thấp sau:
    1. Kiểm tra trạng thái socket mạng vật lý bằng lệnh:
       `netstat -antp | grep 3306` (hoặc cổng 5432 của Postgres). Nếu thấy trạng thái là `ESTABLISHED` với số lượng lớn, kết nối mạng vật lý vẫn ổn. Nếu thấy `SYN_SENT` hoặc `TIME_WAIT` quá cao, kết nối đang bị nghẽn mạng hoặc cạn kiệt socket.
    2. Sử dụng lệnh `tcpdump -i any port 3306 -A -c 10` để xem trực tiếp các gói tin truyền qua cổng DB dưới dạng văn bản thô. Nếu thấy gói tin gửi đi mà không có phản hồi về, hoặc phản hồi chậm > 2s, thủ phạm chắc chắn là Database quá tải.
    3. Kiểm tra log hệ thống cục bộ trong container bằng lệnh `docker logs <container_id>` hoặc `kubectl logs <pod_name>` để tìm các lỗi kết nối DB trực tiếp được ghi ra file.
