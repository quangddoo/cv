# Khi nào nên phi chuẩn hóa (Denormalize) cơ sở dữ liệu?

## ⚡ Tóm tắt ngắn (30s)
Chỉ thực hiện **phi chuẩn hóa (Denormalization)** khi hệ thống gặp các vấn đề nghiêm trọng về hiệu năng đọc mà không thể giải quyết bằng các phương pháp tối ưu hóa thông thường (indexing, query tuning, caching). Các chỉ dấu chính để áp dụng bao gồm:
* **Tần suất Đọc gấp nhiều lần Ghi (Read-Heavy workloads)**: Tỷ lệ Read/Write tối thiểu từ 100:1 trở lên.
* **JOIN quá phức tạp và tốn tài nguyên**: Truy vấn cần JOIN nhiều bảng lớn (ví dụ: > 3-4 bảng có kích thước hàng triệu bản ghi) trên luồng realtime của người dùng.
* **Tính toán Aggregation lặp đi lặp lại**: Các thao tác tính toán như `COUNT`, `SUM`, `AVG` cần thực thi liên tục trên các dữ liệu lịch sử khổng lồ.
* **Yêu cầu độ trễ cực thấp (Sub-millisecond Latency)**: Nơi các API cốt lõi bắt buộc phải trả về kết quả tức thì dưới dạng các Flat Object (như Feed, Dashboard).

## 🔍 Chi tiết bản chất thực chiến

Phi chuẩn hóa không phải là việc thiết kế DB cẩu thả, mà là một **quyết định kiến trúc có tính toán (Calculated Architectural Decision)** dựa trên việc đánh đổi bộ nhớ đĩa và hiệu năng ghi để đổi lấy hiệu năng đọc tối đa.

### 4 Tiêu chí cốt lõi để quyết định Denormalize:

#### 1. Workload Pattern (Đọc vượt trội Ghi)
Nếu hệ thống của bạn có tỷ lệ ghi cao (Write-Heavy) như hệ thống log, IoT telemetry, việc phi chuẩn hóa sẽ làm **giảm sút nghiêm trọng** hiệu năng hệ thống vì mỗi lần ghi bạn phải cập nhật dữ liệu ở nhiều bảng/cột trùng lặp, gây ra hiện tượng lock và nghẽn ghi. Ngược lại, ở các hệ thống như E-commerce (xem sản phẩm), Social Network (đọc feed), tin tức, tỷ lệ đọc/ghi thường là 1000:1 hoặc cao hơn. Đây là thánh địa của phi chuẩn hóa.

#### 2. Query Complexity (Nghẽn CPU do JOIN bảng lớn)
Khi dữ liệu phình to lên hàng chục triệu bản ghi, việc thực thi `JOIN` đòi hỏi DB Engine phải thực hiện Nested Loops, Hash Joins hoặc Merge Joins trên bộ nhớ RAM. Nếu CPU của Database Server liên tục chạm ngưỡng 90-100% chỉ để giải quyết các phép JOIN của trang chủ, đã đến lúc đưa dữ liệu cần thiết của bảng liên kết vào trực tiếp bảng chính.

#### 3. Phép toán Aggregate đắt đỏ
Các trang Dashboard hoặc trang cá nhân của user thường yêu cầu hiển thị các chỉ số tổng hợp như: *Tổng số đơn hàng*, *Tổng tiền tích lũy*, *Số lượng follower*. 
* **Nếu chuẩn hóa**: DB phải thực hiện `COUNT(*)` hoặc `SUM(amount)` trên hàng triệu dòng dữ liệu lịch sử mỗi khi user tải trang.
* **Nếu phi chuẩn hóa**: Dữ liệu này được tính toán trước và cộng dồn trực tiếp vào 1 cột trong bảng `users` hoặc `shops`.

#### 4. Khả năng chịu đựng sự bất nhất dữ liệu (Inconsistency Tolerance)
* **Strong Consistency**: Nếu hệ thống yêu cầu dữ liệu phải đồng nhất tuyệt đối trong mọi tích tắc (như số dư tài khoản ngân hàng), phi chuẩn hóa đòi hỏi quản lý transaction cực kỳ phức tạp để tránh lệch dữ liệu.
* **Eventual Consistency**: Nếu ứng dụng chấp nhận dữ liệu có thể bị lệch pha trong vài trăm mili-giây đến vài giây (ví dụ: số lượng like của một bài viết, tổng số view của video), phi chuẩn hóa kết hợp với đồng bộ bất đồng bộ (Async Event) là giải pháp tối ưu hàng đầu.

## 💻 Thiết kế thực chiến: BAD vs GOOD

### ❌ BAD: Thực hiện JOIN và Aggregation đắt đỏ trên luồng mua hàng realtime
Hệ thống hiển thị thông tin đơn hàng của người dùng, yêu cầu hiển thị cả tên khách hàng (`user_name`) và tổng giá trị đơn hàng được tính toán từ bảng chi tiết đơn hàng (`order_items`).

```sql
-- Mỗi khi khách hàng xem danh sách lịch sử đơn hàng:
-- Hệ thống phải thực hiện quét index và JOIN 3 bảng lớn, cộng với tính SUM vật lý.
-- Dẫn đến nghẽn CPU database khi traffic tăng đột biến!
SELECT 
    o.id AS order_id,
    o.created_at,
    u.name AS user_name,
    SUM(oi.quantity * oi.price) AS total_amount
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN order_items oi ON o.id = oi.order_id
WHERE u.id = 12345
GROUP BY o.id, o.created_at, u.name;
```

### ✅ GOOD: Phi chuẩn hóa thông tin hiển thị trực tiếp vào bảng Orders
Chúng ta đưa thẳng trường `user_name` (giả định tên user rất ít khi thay đổi) và `total_amount` (tính toán một lần lúc tạo đơn hàng và không bao giờ thay đổi nữa) vào bảng `orders`.

```sql
-- Cấu trúc bảng Orders sau khi phi chuẩn hóa
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    user_name VARCHAR(100) NOT NULL,     -- Phi chuẩn hóa tên user
    total_amount DECIMAL(15, 2) NOT NULL, -- Phi chuẩn hóa tổng tiền đơn hàng
    created_at TIMESTAMP NOT NULL
);

-- Khi user xem danh sách đơn hàng:
-- Không cần JOIN, không cần SUM! Câu truy vấn cực kỳ đơn giản và tốc độ phản hồi < 1ms.
SELECT id, created_at, user_name, total_amount 
FROM orders 
WHERE user_id = 12345;
```

## 📊 Quyết định Kiến trúc: Khi nào dùng giải pháp gì?

| Phương án thay thế | Chi phí triển khai | Hiệu quả giảm tải DB | Khi nào nên dùng thay vì Denormalization? |
| :--- | :--- | :--- | :--- |
| **Database Indexing** | Thấp | Trung bình | Khi query chậm do quét toàn bảng (Full Table Scan), chưa liên quan đến JOIN phức tạp hoặc Aggregate. |
| **Application Caching (Redis)** | Trung bình | Rất cao | Khi dữ liệu ít thay đổi nhưng tần suất đọc siêu cao. Tuy nhiên, nếu dữ liệu thay đổi liên tục, cache invalidation sẽ trở thành ác mộng. |
| **Materialized Views** | Trung bình | Cao | Phù hợp khi dùng PostgreSQL hoặc Oracle, tự động refresh định kỳ hoặc qua trigger mà không cần viết logic ở tầng ứng dụng. |
| **Denormalization (Flat Tables)** | Cao | Cực kỳ cao | Khi cấu trúc dữ liệu bắt buộc phải phẳng để phục vụ truy vấn phức tạp realtime, dữ liệu thay đổi liên tục nhưng cần ghi nhận tức thì. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. "Write Amplification" (Khuếch đại ghi)
Khi bạn lưu thông tin `user_name` ở bảng `orders`, nếu user đổi tên thì sao? Bạn phải quét toàn bộ bảng `orders` chứa hàng triệu bản ghi của user đó để `UPDATE` lại toàn bộ cột `user_name`.
* **Kinh nghiệm thực chiến**: Chỉ phi chuẩn hóa các thông tin **Immutability** (không bao giờ thay đổi như giá mua lúc tạo đơn hàng) hoặc **Rarely Changed** (cực kỳ ít khi thay đổi như tên khách hàng). Nếu dữ liệu thay đổi liên tục (như trạng thái online của user), tuyệt đối không phi chuẩn hóa vào các bảng nghiệp vụ khác.

### 2. Câu hỏi đào sâu từ interviewer: "Nếu bắt buộc phải đồng bộ dữ liệu phi chuẩn hóa khi bản gốc thay đổi, bạn sẽ implement như thế nào ở môi trường High Concurrency?"
* **Trả lời**: Có 2 pattern chính tương ứng với yêu cầu nghiệp vụ:
  1. **Đồng bộ qua Eventual Consistency (Khuyến nghị)**: Sử dụng mô hình **Transactional Outbox Pattern** kết hợp Debezium (CDC - Change Data Capture) để lắng nghe sự thay đổi ở bảng `users`, đẩy event đổi tên vào Kafka, sau đó một service worker tiêu thụ event và cập nhật ngầm (background update) bảng `orders` theo lô (batch update) để tránh gây nghẽn DB.
  2. **Đồng bộ đồng thì thông qua Application Transaction**: Thực hiện cập nhật cả hai bảng trong cùng một `@Transactional` của Spring. Chỉ áp dụng khi bảng bị phi chuẩn hóa có lượng ghi cực thấp để tránh giữ Lock quá lâu làm sập hệ thống.
