# Thiết kế hàng đợi ưu tiên có giới hạn kích thước (Design Bounded Priority Queue)

## ⚡ Tóm tắt ngắn (30s)
* **Bài toán**: Hàng đợi ưu tiên mặc định trong Java (`PriorityQueue`) là **không giới hạn dung lượng** (unbounded) - nó sẽ phình to RAM liên tục khi có thêm phần tử. Trong thực tế hệ thống (ví dụ: bộ lập lịch tác vụ, tìm kiếm Top $K$ dữ liệu lớn, quản lý tài nguyên giới hạn), ta cần một **Bounded Priority Queue** (Hàng đợi ưu tiên giới hạn kích thước tối đa là $K$).
* **Giải pháp cốt lõi**:
  1. **Nguyên lý hoạt động (Top K lớn nhất)**: Sử dụng cấu trúc **Min-Heap** kích thước $K$. Khi thêm phần tử mới vào hàng đợi đã đầy: so sánh nó với phần tử có độ ưu tiên thấp nhất hiện tại (đỉnh của Min-Heap). Nếu phần tử mới lớn hơn, loại bỏ đỉnh heap và chèn phần tử mới vào. Ngược lại, bỏ qua phần tử mới.
  2. **Đồng bộ hóa luồng (Thread-Safety)**: Sử dụng khóa nâng cao `ReentrantLock` kết hợp với biến điều kiện `Condition` để hỗ trợ cơ chế chặn luồng (Blocking Operations) khi hàng đợi trống hoặc đầy (tương tự `LinkedBlockingQueue` nhưng có tính năng ưu tiên).
* **Độ phức tạp**: Thao tác chèn/xóa mất thời gian $O(\log K)$, dung lượng bộ nhớ cố định $O(K)$.

## 🔍 Phân tích yêu cầu (Requirements)

### 1. Functional Requirements (Yêu cầu chức năng)
* Khởi tạo hàng đợi với kích thước giới hạn tối đa `capacity` và một bộ so sánh `Comparator`.
* Thao tác cơ bản:
  * `offer(element)`: Thêm phần tử. Nếu đầy, tự động loại bỏ phần tử có độ ưu tiên thấp nhất (đối với bài toán lọc lấy top), hoặc chặn luồng ghi (đối với bài toán Block Producer).
  * `poll()`: Lấy ra và xóa phần tử có độ ưu tiên cao nhất.
  * `peek()`: Xem phần tử đầu hàng đợi.
* Hỗ trợ hai chế độ hoạt động:
  * **Trục xuất tự động (Eviction mode)**: Phục vụ bài toán tìm Top K. Tự động loại bỏ phần tử "kém ưu tiên" hơn khi bị tràn dung lượng.
  * **Chặn luồng (Blocking mode)**: Phục vụ bài toán Producer-Consumer. Chặn luồng ghi nếu hàng đợi đầy cho đến khi luồng đọc giải phóng chỗ trống.

### 2. Non-Functional Requirements (Yêu cầu phi chức năng)
* **Thread-Safety**: Bảo vệ an toàn toàn vẹn dữ liệu khi nhiều luồng thực hiện đọc/ghi đồng thời.
* **Không tràn bộ nhớ**: Đảm bảo kích thước hàng đợi không bao giờ vượt quá dung lượng $K$ đã định trong bất kỳ tình huống tranh chấp dữ liệu nào.

## 🎨 Sơ đồ trực quan & Bản chất toán học

### Bài toán tìm Top K lớn nhất bằng Min-Heap giới hạn kích thước K

```
          [ Phần tử mới: V = 45 ]
                     │
                     ▼
             ┌───────────────┐
             │   Min-Heap    │   (Kích thước tối đa K = 3)
             │   [Đỉnh = 10] │
             └───────┬───────┘
                     │
         ┌───────────┴───────────┐
         │ V (45) > Đỉnh (10)?  │
         └───────────┬───────────┘
                     │
             ┌───────┴───────┐
          NO │           YES │
             ▼               ▼
        [ Bỏ qua 45 ]   [ Xóa đỉnh 10 ]
                        [ Đưa 45 vào Heap ]
                             │
                             ▼
                     ┌───────────────┐
                     │   Min-Heap    │   (Sau khi cập nhật: [20, 30, 45])
                     │   [Đỉnh = 20] │
                     └───────────────┘
```
> [!NOTE]
> **Quy tắc vàng**: Để tìm $K$ phần tử **lớn nhất**, ta dùng **Min-Heap**. Để tìm $K$ phần tử **nhỏ nhất**, ta dùng **Max-Heap**.

## 💻 Code Example: Hiện thực hóa cấu trúc Bounded Priority Queue bằng Java

Dưới đây là phiên bản hiện thực hóa cấu trúc dữ liệu Bounded Priority Queue hoàn chỉnh bằng Java, hỗ trợ cả cơ chế đồng bộ hóa luồng nâng cao (`ReentrantLock`), chặn luồng an toàn (Blocking mode) và trục xuất tự động cho bài toán lọc dữ liệu:

```java
import java.util.Comparator;
import java.util.PriorityQueue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class BoundedPriorityQueue<E> {

    private final PriorityQueue<E> queue;
    private final int capacity;
    private final Comparator<? super E> comparator;
    
    // Đồng bộ hóa luồng sử dụng khóa nâng cao
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    public BoundedPriorityQueue(int capacity, Comparator<? super E> comparator) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("Dung lượng hàng đợi phải lớn hơn 0!");
        }
        this.capacity = capacity;
        this.comparator = comparator;
        // Khởi tạo PriorityQueue nội bộ
        this.queue = new PriorityQueue<>(capacity, comparator);
    }

    /**
     * Chế độ 1: Thêm phần tử tự động TRỤC XUẤT (Không chặn luồng)
     * Thích hợp cho bài toán tìm Top K.
     * Trả về phần tử bị loại bỏ (nếu có), hoặc null.
     */
    public E offerWithEviction(E element) {
        if (element == null) throw new NullPointerException();
        
        lock.lock();
        try {
            if (queue.size() < capacity) {
                queue.offer(element);
                notEmpty.signal(); // Báo thức cho các luồng đọc đang chờ
                return null;
            }

            // So sánh phần tử mới với phần tử ở đỉnh hàng đợi (độ ưu tiên thấp nhất trong heap)
            E leastPriority = queue.peek();
            
            // Nếu phần tử mới có độ ưu tiên cao hơn phần tử thấp nhất trong heap hiện tại
            if (comparator.compare(element, leastPriority) > 0) {
                queue.poll(); // Loại bỏ phần tử kém nhất
                queue.offer(element); // Thêm phần tử mới xịn hơn vào
                return leastPriority; // Trả về phần tử bị loại bỏ để theo dõi
            }

            // Phần tử mới không đủ điều kiện lọt vào nhóm Top, bỏ qua
            return element;
        } finally {
            lock.unlock();
        }
    }

    /**
     * Chế độ 2: Thêm phần tử CHẶN LUỒNG (Blocking write)
     * Thích hợp cho bài toán lập lịch đa luồng giới hạn tài nguyên.
     * Sẽ block luồng ghi nếu hàng đợi đã đạt công suất tối đa.
     */
    public void put(E element) throws InterruptedException {
        if (element == null) throw new NullPointerException();
        
        lock.lockInterruptibly();
        try {
            // Chờ cho đến khi hàng đợi có chỗ trống
            while (queue.size() == capacity) {
                notFull.await();
            }
            queue.offer(element);
            notEmpty.signal(); // Đánh thức luồng đọc
        } finally {
            lock.unlock();
        }
    }

    /**
     * Lấy và xóa phần tử có độ ưu tiên cao nhất (Chặn luồng nếu rỗng)
     */
    public E take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            // Chờ cho đến khi hàng đợi có dữ liệu
            while (queue.isEmpty()) {
                notEmpty.await();
            }
            E element = queue.poll();
            notFull.signal(); // Đánh thức luồng ghi
            return element;
        } finally {
            lock.unlock();
        }
    }

    /**
     * Lấy và xóa phần tử không chặn luồng (trả về null nếu rỗng)
     */
    public E poll() {
        lock.lock();
        try {
            E element = queue.poll();
            if (element != null) {
                notFull.signal();
            }
            return element;
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return queue.size();
        } finally {
            lock.unlock();
        }
    }

    // --- Demo chạy thử bài toán lọc Top K ---
    public static void main(String[] args) {
        // Bài toán: Tìm Top 3 số lớn nhất trong danh sách dữ liệu đầu vào
        // Sử dụng Min-Heap (Để phần tử bé hơn nổi lên đầu và bị trục xuất trước)
        Comparator<Integer> minHeapComparator = Integer::compareTo;
        
        BoundedPriorityQueue<Integer> topKQueue = new BoundedPriorityQueue<>(3, minHeapComparator);

        int[] dataStream = {5, 20, 1, 40, 30, 2, 50};
        
        System.out.println("Đang gửi luồng dữ liệu vào hàng đợi giới hạn (K = 3)...");
        for (int num : dataStream) {
            Integer evicted = topKQueue.offerWithEviction(num);
            if (evicted != null) {
                if (evicted == num) {
                    System.out.printf("Nhập: %-2d | Trạng thái: Bỏ qua (không đủ điều kiện vào Top)\n", num);
                } else {
                    System.out.printf("Nhập: %-2d | Trạng thái: Thêm thành công. Trục xuất phần tử kém nhất: %d\n", num, evicted);
                }
            } else {
                System.out.printf("Nhập: %-2d | Trạng thái: Thêm thành công (chưa đầy dung lượng)\n", num);
            }
        }

        System.out.println("\n--- KẾT QUẢ TOP 3 SỐ LỚN NHẤT THU ĐƯỢC ---");
        while (topKQueue.size() > 0) {
            System.out.println(topKQueue.poll()); // Sẽ in ra: 20, 30, 40 (sắp xếp tăng dần từ heap)
        }
    }
}
```

## 📊 Phân tích độ phức tạp & Trade-offs

### So sánh các giải pháp lấy Top K phần tử lớn nhất

| Phương pháp | Sắp xếp mảng thô (Sort Array) | Sử dụng PriorityQueue không giới hạn kích thước | Sử dụng Bounded PriorityQueue (Min-Heap tối ưu) |
| :--- | :--- | :--- | :--- |
| **Độ phức tạp thời gian** | $O(N \log N)$ do phải sắp xếp toàn bộ tập dữ liệu gốc. | $O(N \log N)$ do chèn toàn bộ $N$ phần tử vào cây nhị phân heap. | **$O(N \log K)$** cực kỳ tối ưu, vì chiều cao của heap chỉ tối đa là $\log K$ ($K \ll N$). |
| **Độ phức tạp bộ nhớ (RAM)** | $O(N)$ yêu cầu lưu giữ toàn bộ mảng dữ liệu trong RAM. Dễ gây OOM. | $O(N)$ lưu toàn bộ các phần tử trong heap. Rủi ro OOM cao. | **$O(K)$** bộ nhớ không đổi (hằng số), cực kỳ an toàn cho dù dữ liệu đầu vào lớn vô tận (infinite stream). |
| **Ứng dụng Real-time** | Không thể. Bắt buộc phải có đầy đủ bộ dữ liệu tĩnh mới sắp xếp được. | Kém. Vẫn phải giữ toàn bộ lịch sử trong RAM. | **Tuyệt vời**. Thích hợp cho luồng dữ liệu trôi nổi (Streaming Data) liên tục 24/7. |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

### 1. Tại sao để tìm Top K phần tử LỚN NHẤT ta lại bắt buộc phải sử dụng một bộ so sánh Min-Heap chứ không phải Max-Heap?
* **Trả lời**: Đây là lỗi logic cực kỳ kinh điển của các kỹ sư khi đi phỏng vấn:
  * **Tại sao không dùng Max-Heap**: Trong Max-Heap, phần tử lớn nhất luôn nằm ở đỉnh heap. Khi hàng đợi đầy (kích thước là $K$), nếu ta muốn thêm phần tử mới, ta chỉ có thể so sánh phần tử mới với đỉnh (phần tử lớn nhất). Việc so sánh này không đem lại giá trị, vì ta cần trục xuất phần tử **bé nhất** ra khỏi nhóm Top K chứ không phải trục xuất phần tử lớn nhất.
  * **Tại sao phải dùng Min-Heap**: Trong Min-Heap, phần tử bé nhất trong số $K$ phần tử hiện tại luôn nằm ở đỉnh heap. Khi có phần tử mới xuất hiện, ta so sánh nó với đỉnh heap (thằng yếu nhất hiện tại). Nếu phần tử mới lớn hơn thằng yếu nhất này, chứng tỏ thằng yếu nhất kia không còn tư cách nằm trong Top $K$ nữa. Ta trục xuất đỉnh heap và đưa phần tử mới vào. Điều này giúp duy trì chính xác nhóm $K$ phần tử tinh anh nhất.

### 2. Làm thế nào để đảm bảo tính an toàn chống ngập lụt bộ nhớ (Memory Exhaustion) khi luồng ghi (Producer) chạy nhanh gấp 100 lần luồng đọc (Consumer)?
* **Trả lời**: 
  * Nếu dùng `PriorityQueue` nguyên bản, luồng ghi sẽ liên tục nhồi dữ liệu làm RAM tăng đột biến cho tới khi sập ứng dụng.
  * **Cách xử lý**: Áp dụng cơ chế **Chặn luồng với biến điều kiện (Blocking with Conditions)** như đã triển khai trong hàm `put()` và `take()` của code mẫu.
  * Khi kích thước hàng đợi chạm ngưỡng `capacity`, luồng ghi gọi lệnh `notFull.await()`. Lệnh này sẽ tạm dừng thực thi luồng ghi đó và nhường hoàn toàn CPU cho luồng đọc làm việc. Chỉ khi luồng đọc lấy bớt dữ liệu ra thông qua lệnh `take()`, nó mới phát tín hiệu `notFull.signal()` để đánh thức luồng ghi tiếp tục hoạt động. Cơ chế điều khiển dòng chảy này gọi là **Backpressure** tự nhiên trong lập trình đa luồng.

### 3. Giải thuật này có đảm bảo tính ổn định (Stable Priority) không? Nếu hai phần tử có độ ưu tiên bằng nhau, phần tử nào vào trước có chắc chắn ra trước không?
* **Trả lời**:
  * Cấu trúc dữ liệu Heap nhị phân của `PriorityQueue` **không đảm bảo tính ổn định (Unstable)**. Khi hai phần tử có cùng giá trị so sánh ưu tiên, thứ tự ra của chúng là không xác định (phụ thuộc vào cấu trúc tái cân bằng cây nhị phân).
  * **Cách giải quyết để đạt Stable Priority**:
    * Ta thiết lập một lớp bọc phần tử bổ sung chỉ số thứ tự tuần tự (Sequence Number) tăng dần cho mỗi phần tử khi đưa vào hàng đợi: `class SequenceElement<E> { E value; long sequenceNumber; }`.
    * Bộ so sánh `Comparator` sẽ được nâng cấp: Nếu mức độ ưu tiên bằng nhau, ta tiến hành so sánh chỉ số `sequenceNumber`. Phần tử nào có chỉ số nhỏ hơn (đến trước) sẽ có độ ưu tiên cao hơn, đảm bảo tính chất FIFO chuẩn xác tuyệt đối!
