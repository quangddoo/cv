# System Design theo Domain Công ty Phỏng vấn

## ⚡ Tóm tắt ngắn (30s)
* **Strategy**: research domain phỏng vấn → ôn 3-5 system design phổ biến trong domain đó.
* **Map domain → designs**:
  - **Fintech**: payment processing, fraud detection, ledger, KYC.
  - **E-commerce**: catalog search, cart, checkout, inventory, recommendation.
  - **SaaS B2B**: multi-tenancy, billing, integration platform.
  - **Social/Media**: feed, notification, messaging, moderation.
  - **Logistics**: order, route optimization, tracking.

---

## 🔍 Process

### Step 1: Identify domain
- Job description.
- Company products.
- Glassdoor interview reports.

### Step 2: Map common designs
Each domain has 3-5 "system design classics":

**Fintech**:
1. Design payment processing (ledger, idempotency, reconcile).
2. Design fraud detection (real-time score, ML model serving).
3. Design KYC pipeline (document upload, OCR, verification).
4. Design transaction history with reporting.

**E-commerce**:
1. Design checkout flow (cart, payment, inventory).
2. Design product search (filter + facets + search).
3. Design recommendation engine.
4. Design flash sale (high concurrent, anti-bot).
5. Design inventory management across warehouses.

**SaaS**:
1. Design multi-tenant database/schema.
2. Design subscription billing.
3. Design webhook delivery (retry, signed).
4. Design audit log.

### Step 3: Practice each design

Standard framework:
1. **Requirements** (functional + non-functional).
2. **Estimate scale** (QPS, storage).
3. **High-level architecture**.
4. **Components detail**.
5. **Database schema**.
6. **Data flow**.
7. **Failures + trade-offs**.

### Step 4: Practice presenting
- Draw on whiteboard or virtual.
- 45-60 min target.
- Talk while drawing.

## 💻 Example outline: Payment Processing

```
1. Requirements:
   - 10k TPS peak.
   - <500ms p99 latency.
   - Strong consistency.
   - PCI-DSS compliant.

2. High-level:
   API Gateway → Payment Service → Risk Service → Payment Provider
                       ↓
                   Ledger DB

3. Components:
   - Idempotency: idempotency_key UUID per request.
   - Saga: reserve → charge → ship; compensations.
   - Ledger: double-entry accounting; Postgres + replication.
   - Risk: real-time score from ML model + rules.
   - Webhook handler: PSP callbacks signed.

4. Data flow:
   - Client → Gateway → Auth → Risk → Reserve → Charge → Ledger → Response.

5. Failures:
   - Payment provider down → fallback or queue.
   - Network timeout → idempotency on retry.
   - Database split-brain → only primary writes.

6. Trade-offs:
   - Sync vs async confirm.
   - Strong vs eventual consistency.
```

## ⚠️ Common Mistakes & Pro Tips

1. **Don't memorize**: interviewer asks follow-ups, you'll get lost.
2. **Stuck on tech**: focus on requirements & trade-offs.
3. **Skip non-functional**: scale, latency, consistency critical.
4. **No fail handling**: every component fails, design for it.
5. **Numbers lacking**: estimate QPS, storage, throughput.
6. **Show your thinking**: ask clarifying questions, walk through trade-offs.
