# Quản lý Database Migration như thế nào trong môi trường Enterprise?

## ⚡ Tóm tắt ngắn (30s)
* **Nguyên tắc bất di bất dịch**: **Tuyệt đối không chạy tay SQL DDL** trên môi trường Staging/Production. Mọi sự thay đổi Schema bắt buộc phải được mã hóa thành các file script có đánh số phiên bản (Versioned Scripts) và lưu trữ trong Git.
* **Công cụ khuyên dùng**: **Flyway** (phù hợp với các script SQL thuần túy, trực quan, dễ viết) hoặc **Liquibase** (phù hợp với các cấu trúc phức tạp cần chạy trên nhiều loại DBMS khác nhau nhờ định dạng XML/YAML/JSON).
* **Quy trình Zero-Downtime**: Áp dụng mẫu thiết kế **Expand/Contract Pattern (Song song thay đổi)**. Một sự thay đổi Schema (ví dụ: đổi tên cột) phải được chia thành 3 bước nhỏ qua nhiều đợt deploy để đảm bảo phiên bản ứng dụng cũ và mới hoạt động song song mà không làm gián đoạn người dùng.

## 🔍 Chi tiết bản chất thực chiến

### 1. Zero-Downtime Migration: Expand/Contract Pattern (Mẫu Mở rộng và Thu hẹp)

Khi triển khai các đợt cập nhật lớn (như Blue-Green Deployment hoặc Kubernetes Rolling Update), sẽ có thời điểm phiên bản Code cũ (v1) và phiên bản Code mới (v2) cùng kết nối vào một Cơ sở dữ liệu duy nhất. Nếu bạn chạy một câu lệnh sửa trực tiếp cấu trúc DB (ví dụ: đổi tên cột `phone` thành `phone_number`), Code v1 đang chạy sẽ lập tức bị crash hàng loạt do không tìm thấy cột `phone`.

Để tránh thảm họa này, ta phải thực hiện quy trình **Expand/Contract**:

```mermaid
graph TD
    subgraph Bước 1: EXPAND (Mở rộng)
        B1["Thêm cột mới: phone_number<br/>(Giữ nguyên cột cũ: phone)"]
        B1_Code["Code v2 ghi song song vào cả 2 cột.<br/>Đọc từ cột cũ."]
    end

    subgraph Bước 2: MIGRATE (Chuyển dịch)
        B2["Chạy Batch Job ngầm dưới DB<br/>Copy toàn bộ dữ liệu từ phone -> phone_number"]
    end

    subgraph Bước 3: CONTRACT (Thu hẹp)
        B3["Deploy Code v3:<br/>Chỉ đọc và ghi trên phone_number"]
        B3_DDL["Xóa bỏ (DROP) cột cũ: phone"]
    end

    Bước 1 --> Bước 2 --> Bước 3
```

#### Ví dụ chi tiết các bước:
1. **Bước 1 (Expand)**: Deploy DB Script thêm cột `phone_number`. Deploy Code v2: Khi ghi nhận thông tin, Code sẽ ghi vào cả `phone` và `phone_number`. Nhưng khi Đọc, vẫn đọc từ `phone` (đảm bảo Code v1 cũ chỉ biết cột `phone` vẫn chạy bình thường).
2. **Bước 2 (Migrate)**: Chạy một background script chuyển đổi dữ liệu lịch sử từ `phone` sang `phone_number` cho những dòng chưa được cập nhật.
3. **Bước 3 (Contract)**: Deploy Code v3: Chuyển hoàn toàn việc Đọc và Ghi sang `phone_number`. Sau khi kiểm tra hệ thống chạy ổn định và không còn instance cũ nào kết nối, chạy script DDL cuối cùng để `DROP COLUMN phone`.

### 2. Lựa chọn Công cụ: Flyway vs Liquibase

| Tiêu chí | Flyway (Khuyên dùng cho Startups/SMEs) | Liquibase (Khuyên dùng cho Enterprise lớn) |
| :--- | :--- | :--- |
| **Định dạng Script** | Viết bằng file SQL thuần túy (ví dụ: `V1__init.sql`) | XML, YAML, JSON hoặc SQL |
| **Khả năng Cross-DB**| Thấp (Script viết cho MySQL không chạy được trên Postgres) | Rất cao (Liquibase tự dịch XML sang SQL tương ứng của từng DB) |
| **Độ dốc học tập** | Cực thấp, chỉ cần biết SQL | Trung bình (cần học cú pháp tag của Liquibase) |
| **Cơ chế Rollback** | Chỉ hỗ trợ ở bản Enterprise (Trả phí) | Hỗ trợ Rollback tự động rất tốt (Miễn phí) |

## 💻 Code thực chiến: Cấu hình Flyway trong Spring Boot

Flyway cực kỳ dễ tích hợp vào Spring Boot. Nó sẽ tự động quét thư mục `src/main/resources/db/migration`, so sánh bảng lịch sử `schema_version` dưới DB để chạy các script mới nhất ngay khi ứng dụng khởi động.

### 🛠️ File cấu hình `pom.xml` (Maven)
```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

### 🛠️ Đặt tên Script theo đúng quy chuẩn Flyway
Thư mục: `src/main/resources/db/migration/`
* `V1__create_users_table.sql`: Script khởi tạo.
* `V2__add_index_on_email.sql`: Script thêm Index.
* `V3_1__add_phone_number_to_users.sql`: Script cập nhật cấu trúc.

*Lưu ý*: Sử dụng **2 dấu gạch dưới (`__`)** sau số phiên bản.

```sql
-- Nội dung file V3_1__add_phone_number_to_users.sql
ALTER TABLE users ADD COLUMN phone_number VARCHAR(20) DEFAULT NULL;
```

## 📊 Quy tắc vàng khi viết Migration Script

1. **Một script không được thay đổi (Immutable)**: Sau khi script `V1__...sql` đã được merge và chạy trên Production, tuyệt đối không được chỉnh sửa nội dung file đó. Nếu muốn sửa đổi, bắt buộc phải tạo một file mới là `V2__...sql`. Flyway sẽ kiểm tra checksum, nếu phát hiện file cũ bị sửa, ứng dụng sẽ crash lập tức để bảo vệ tính toàn vẹn.
2. **Mỗi file chỉ làm một nhiệm vụ (Granular Migrations)**: Tránh viết một file SQL khổng lồ chứa hàng chục câu lệnh tạo bảng, tạo index, insert dữ liệu. Nên tách nhỏ ra. Nếu một câu lệnh ở giữa bị lỗi, bạn sẽ dễ dàng debug và rollback hơn.
3. **Mọi câu lệnh DDL phải an toàn (Idempotent DDL)**: Luôn sử dụng cú pháp an toàn như `CREATE TABLE IF NOT EXISTS` hoặc `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (nếu DBMS hỗ trợ) để tránh lỗi khi script vô tình bị chạy lại.

## ⚠️ Common Gotchas & Questions follow-up

### 1. Table Lock do chạy DDL trên bảng hàng trăm triệu dòng
Trong các DB truyền thống như MySQL cũ, việc chạy câu lệnh `ALTER TABLE orders ADD COLUMN status VARCHAR(20) NOT NULL;` trên một bảng chứa 100 triệu dòng sẽ kích hoạt cơ chế **Table Lock (Khóa toàn bảng)** để copy dữ liệu sang bảng tạm mới. Mọi request Ghi của người dùng lúc này sẽ bị xếp hàng chờ (Queue), dẫn đến nghẽn connection pool và sập toàn bộ hệ thống API (Downtime).
* **Giải pháp thực chiến**:
  1. Từ PostgreSQL 11+ và MySQL 8.0.12+, việc thêm cột với giá trị mặc định `NULL` hoặc có `DEFAULT` đã được tối ưu hóa thành thao tác **Instant DDL** (chỉ thay đổi metadata trong vài mili-giây). Do đó, hãy luôn thêm cột mới ở chế độ **Nullable** trước.
  2. Với các phiên bản DB cũ hơn, bắt buộc phải sử dụng các công cụ thay đổi cấu trúc trực tuyến (Online Schema Change Tools) như **gh-ost** hoặc **pt-online-schema-change** của Percona. Các công cụ này sẽ tạo bảng phụ, đồng bộ dữ liệu ngầm và tráo đổi bảng (swap table) mà không hề gây khóa bảng chính.

### 2. Câu hỏi đào sâu từ interviewer: "Nếu chạy Migration bị lỗi giữa chừng trên Production, bạn xử lý thế nào?"
* **Trả lời**:
  * **Phòng bệnh**: Luôn bao bọc các câu lệnh migration trong một **Database Transaction** (PostgreSQL hỗ trợ Transactional DDL hoàn hảo, nếu lỗi sẽ tự động rollback toàn bộ. Rất tiếc MySQL không hỗ trợ Transactional DDL).
  * **Chữa bệnh (Với MySQL)**: Nếu một script Flyway bị lỗi giữa chừng, trạng thái của nó dưới bảng `flyway_schema_history` sẽ được đánh dấu là `FAILED` (success = 0). 
    1. Đầu tiên, ta phải kiểm tra thủ công dưới DB xem những câu lệnh nào trong script đã được thực thi để tiến hành dọn dẹp (ví dụ: drop các bảng vừa tạo dở).
    2. Sử dụng lệnh `flyway repair` (hoặc xóa dòng log lỗi trực tiếp trong bảng `flyway_schema_history` bằng SQL).
    3. Sửa lỗi trong file script, đóng gói và redeploy lại ứng dụng.
