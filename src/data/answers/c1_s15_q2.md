# Structured Logging là gì?

## ⚡ Tóm tắt ngắn (30s)
* **Structured Logging (Ghi log có cấu trúc)** là kỹ thuật ghi nhật ký ứng dụng dưới một định dạng dữ liệu chuẩn hóa, có thể đọc và phân tích tự động bằng máy (thường là **JSON**) thay vì dạng chuỗi văn bản tự do (Plain Text / Free-form text).
* **Mục tiêu**: Giúp các hệ thống quản lý log tập trung (như Elasticsearch, Grafana Loki, Splunk) dễ dàng tự động **phân tích (parse), lập chỉ mục (index), và truy vấn (query)** dữ liệu log tốc độ cao mà không cần viết các bộ lọc Regex (Grok patterns) phức tạp, dễ lỗi và tốn CPU.
* **Cấu trúc**: Mỗi dòng log là một JSON object chứa các trường cố định (`timestamp`, `level`, `logger`, `message`, `thread`, `trace_id`) và các trường tùy biến nghiệp vụ (`user_id`, `duration_ms`, `http_status`).

## 🔍 Chi tiết bản chất thực chiến

### 1. Vấn đề của Plain Text Logging truyền thống
Trong quá khứ, dev thường ghi log dạng text như sau:
```text
2026-05-23 07:39:17 [Thread-5] INFO c.e.s.OrderService - User USR-123 created order ORD-9988 successfully in 120ms
```
* **Khó khăn khi phân tích tự động**: Để trích xuất thông tin `user_id` hay `duration_ms` để vẽ biểu đồ, DevOps bắt buộc phải viết biểu thức chính quy (Regex/Grok) để bóc tách chuỗi.
* **Dễ gãy (Fragile)**: Nếu lập trình viên chỉ cần thay đổi nhẹ format log (ví dụ đổi chữ `successfully` thành `done` hoặc đổi vị trí `in 120ms`), bộ parser Regex trên server log tập trung sẽ bị lỗi ngay lập tức.
* **Tốn tài nguyên**: Chạy Regex parse hàng triệu dòng log mỗi giây cực kỳ ngốn CPU của các log shipper (Logstash, Fluentd).

### 2. Sức mạnh của Structured Logging (JSON)
Với Structured Logging, dòng log trên được ghi lại dưới dạng JSON:
```json
{
  "@timestamp": "2026-05-23T00:39:17.001Z",
  "level": "INFO",
  "thread": "Thread-5",
  "logger": "com.example.service.OrderService",
  "message": "Order created successfully",
  "trace_id": "8bfa51c8a14e9b92",
  "user_id": "USR-123",
  "order_id": "ORD-9988",
  "duration_ms": 120
}
```
* **Lập chỉ mục thông minh**: Elasticsearch có thể trực tiếp index trường `"user_id"` và `"duration_ms"` dưới dạng trường số/chuỗi thực thụ.
* **Truy vấn cực mạnh**: Bạn có thể viết câu lệnh tìm kiếm chính xác: *“Tìm tất cả các log có `level = ERROR` và `duration_ms > 500` của `user_id = USR-123`”*.

## 💻 Code thực chiến: Cấu hình JSON Structured Logging trong Spring Boot

Để ghi log dạng JSON trong Java, best practice là kết hợp **SLF4J**, **Logback** và thư viện **`logstash-logback-encoder`**.

### 1. Thêm Dependency vào `pom.xml` (Maven)
```xml
<dependency>
    <groupId>net.logstash.logback</groupId>
    <artifactId>logstash-logback-encoder</artifactId>
    <version>7.4</version> <!-- ✅ Thư viện chuẩn để mã hóa log sang JSON -->
</dependency>
```

### 2. Cấu hình file `logback-spring.xml`
Ta sẽ cấu hình xuất log ra Console dưới dạng JSON khi chạy trên môi trường Production (`prod`).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <include resource="org/springframework/boot/logging/logback/defaults.xml"/>

    <!-- Appender ghi log JSON ra Console -->
    <appender name="JSON_CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder class="net.logstash.logback.encoder.LoggingEventCompositeJsonEncoder">
            <providers>
                <timestamp>
                    <timeZone>UTC</timeZone>
                </timestamp>
                <pattern>
                    <!-- ✅ Định nghĩa các trường JSON chuẩn hóa và ánh xạ trường tự động -->
                    <pattern>
                        {
                        "severity": "%level",
                        "service": "${spring.application.name:-}",
                        "trace": "%X{traceId:-}",
                        "span": "%X{spanId:-}",
                        "pid": "${PID:-}",
                        "thread": "%thread",
                        "class": "%logger",
                        "message": "%message",
                        "exception": "%ex"
                        }
                    </pattern>
                </pattern>
                <!-- ✅ Tự động nhúng mọi biến trong MDC (Mapped Diagnostic Context) vào JSON -->
                <mdc/> 
            </providers>
        </encoder>
    </appender>

    <!-- Kích hoạt cấu hình theo Profile -->
    <springProfile name="prod">
        <root level="INFO">
            <appender-ref ref="JSON_CONSOLE" />
        </root>
    </springProfile>
    
    <springProfile name="dev">
        <!-- Môi trường Dev vẫn dùng Console Plain Text truyền thống cho lập trình viên dễ đọc -->
        <appender name="TEXT_CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
            <encoder>
                <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n</pattern>
            </encoder>
        </appender>
        <root level="INFO">
            <appender-ref ref="TEXT_CONSOLE" />
        </root>
    </springProfile>
</configuration>
```

### 3. Viết Code Java sử dụng MDC để tiêm ngữ cảnh động vào JSON Log
**MDC (Mapped Diagnostic Context)** của SLF4J cho phép lưu trữ thông tin dạng Key-Value trong ThreadLocal và tự động nhúng vào mọi dòng log phát sinh từ thread đó.

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

@Service
public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void processOrder(OrderRequest req) {
        try {
            // ✅ Đặt các trường ngữ cảnh nghiệp vụ vào MDC
            MDC.put("user_id", req.getUserId());
            MDC.put("order_id", req.getOrderId());
            MDC.put("ip_address", req.getClientIp());

            log.info("Starting order processing"); // Line 1

            long start = System.currentTimeMillis();
            // Xử lý logic...
            long duration = System.currentTimeMillis() - start;

            MDC.put("duration_ms", String.valueOf(duration));
            log.info("Order processed successfully"); // Line 2

        } finally {
            // ⚠️ LUÔN LUÔN clean MDC ở khối finally để tránh rò rỉ bộ nhớ (Memory Leak) trong Thread Pool!
            MDC.clear();
        }
    }
}
```

**Kết quả output JSON log dòng "Order processed successfully" thực tế**:
```json
{
  "timestamp": "2026-05-23T00:39:17.452Z",
  "severity": "INFO",
  "service": "order-service",
  "trace": "8bfa51c8a14e9b92",
  "span": "416b2cfd29c8e9b2",
  "pid": "8450",
  "thread": "http-nio-8080-exec-3",
  "class": "com.example.service.OrderService",
  "message": "Order processed successfully",
  "user_id": "USR-123",
  "order_id": "ORD-9988",
  "ip_address": "192.168.1.50",
  "duration_ms": "45"
}
```

## 📊 So sánh Plain Text vs Structured Logging

| Tiêu chí | Plain Text Logging | Structured Logging (JSON) |
| :--- | :--- | :--- |
| **Đối tượng đọc chính** | Con người (Lập trình viên khi dev) | Máy móc (Log Indexer, ELK, Grafana Loki) |
| **Cách phân tích tự động** | Dùng Grok/Regex rất tốn CPU | Parse JSON trực tiếp cực nhanh |
| **Khả năng mở rộng** | Kém (thêm trường mới làm gãy regex parser) | Cực tốt (chỉ cần thêm key-value mới vào JSON) |
| **Dung lượng lưu trữ** | Nhỏ hơn một chút | Lớn hơn (do lặp lại các JSON key ở mỗi dòng) |
| **Độ phức tạp khi code** | Đơn giản (system.out hoặc log thông thường) | Phải định hình cấu trúc, dùng MDC, cấu hình logback |

## ⚠️ Common Gotchas & Questions follow-up

### 1. "Lưu log dạng JSON có làm chậm ứng dụng Java không?"
* **Trả lời**: **Có, một chút**. Việc chuyển đổi đối tượng log thành chuỗi JSON (Serialization) sử dụng thư viện Jackson tiêu tốn CPU nhiều hơn so với việc ghi log text thông thường.
* **Cách khắc phục**:
  * Luôn sử dụng **`AsyncAppender`** trong Logback. Ghi log bất đồng bộ giúp luồng xử lý chính (Request Thread) không bị chặn (Blocked) bởi thao tác I/O ghi log và serialization.
  * Chỉ bật JSON log ở môi trường **Production**. Ở Local Dev, hãy dùng định dạng Plain Text truyền thống có tô màu (Colorized Output) để dễ quan sát bằng mắt thường.

### 2. "Ghi log JSON trùng lặp các Key (ví dụ dòng nào cũng có chữ `timestamp`, `level`...) có gây lãng phí dung lượng không?"
* **Trả lời**: Đúng là file log thô dạng JSON sẽ nặng hơn file log text khoảng 1.5 - 2 lần.
* **Tuy nhiên**: Trong thực tế, các Log Shipper (Fluentd, Vector, Filebeat) hoặc các hệ thống lưu trữ (Elasticsearch) đều áp dụng cơ chế nén dữ liệu cực mạnh (Gzip, LZ4). Sự trùng lặp của các key tĩnh trong JSON là mục tiêu lý tưởng của các thuật toán nén, giúp dung lượng thực tế lưu trữ đĩa cứng co lại rất nhiều, gần như tương đương với log text.
