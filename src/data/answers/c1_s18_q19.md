# Mô hình Tên miền Thiếu máu là gì? (Anemic Domain Model)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **Anemic Domain Model** (Mô hình miền thiếu máu) là một mùi code (Code Smell) hoặc một **Anti-Pattern** trong lập trình hướng đối tượng. Nó mô tả tình trạng các lớp đối tượng Domain (như `User`, `Order`) chỉ chứa **dữ liệu thô** (trường dữ liệu và getter/setter) mà hoàn toàn **không có bất kỳ hành vi hay logic nghiệp vụ nào**.
* **Đặc điểm**: Toàn bộ logic nghiệp vụ (Business Rules) bị đẩy hết ra các lớp dịch vụ thủ tục (như `UserService`, `OrderService`).
* **Hệ quả**: Biến kiến trúc hướng đối tượng (OOP) thành **lập trình thủ tục tuần tự (Procedural Programming)** trá hình, phá vỡ tính đóng gói (Encapsulation).
* **Giải pháp đối nghịch**: **Rich Domain Model** (Mô hình miền giàu sinh lực) - nơi mà các Entities tự quản lý và bảo vệ trạng thái của chính nó thông qua các phương thức nghiệp vụ đóng gói.

## 🔍 Phân tích chuyên sâu: Anemic vs Rich Domain Model

Martin Fowler đã gọi tên Anemic Domain Model là một hiện tượng phổ biến nhưng cực kỳ nguy hại trong thiết kế phần mềm doanh nghiệp:

### 1. Cách vận hành của Anemic Domain Model (Lập trình thủ tục)
Trong mô hình này, các Domain class thực chất chỉ là các **Cấu trúc dữ liệu thô (Data Holders)** hoạt động như các DTO.
* Lớp Service lấy dữ liệu thô từ Entity qua `getter`.
* Lớp Service tự thực hiện kiểm tra logic nghiệp vụ.
* Lớp Service ghi đè dữ liệu mới vào Entity qua `setter`.
* **Vấn đề**: Đối tượng Entity không hề có tiếng nói hay quyền tự quyết bảo vệ dữ liệu của nó. Bất kỳ ai ở bên ngoài cũng có thể gọi `order.setStatus("CANCELLED")` mà không cần kiểm tra xem đơn hàng đã được giao hay chưa.

### 2. Cách vận hành của Rich Domain Model (Lập trình hướng đối tượng thực thụ)
Trong DDD, mô hình Domain phải là **Rich Domain Model**.
* Entity đóng gói cả **Dữ liệu** và **Hành vi (Behavior)**.
* **Constructor private/protected** bắt buộc phải truyền đầy đủ tham số hợp lệ mới khởi tạo được đối tượng.
* **Không có Setters tùy tiện**. Muốn thay đổi trạng thái, bắt buộc phải gọi phương thức nghiệp vụ tự giải thích (ví dụ: `order.cancel()`).
* Entity tự kiểm tra tính hợp lệ (Invariant) của chính nó. Nếu vi phạm, tự động ném ra Exception lập tức.

## 💻 Code Example: Thiết kế Đơn hàng (Order)

### ❌ Vi phạm thiết kế (Anemic Domain Model - Thiếu máu)

```java
// Lớp Entity rỗng tuếch, chỉ có data (Anemic)
public class Order {
    private String id;
    private String status; // "CREATED", "SHIPPED", "CANCELLED"
    
    // Chỉ có Getter & Setter tự động sinh ra
    public String getStatus() { return status; }
    public void setStatus(String status) { this.status = status; }
}

// Lớp Service gánh vác toàn bộ logic (Procedural)
@Service
public class OrderService {
    @Autowired private OrderRepository repository;

    public void cancelOrder(String orderId) {
        Order order = repository.findById(orderId);
        
        // VI PHẠM: Logic nghiệp vụ bị phơi bày ra Service
        if ("SHIPPED".equals(order.getStatus())) {
            throw new IllegalStateException("Không thể hủy đơn hàng đã giao!");
        }
        
        order.setStatus("CANCELLED"); // Thay đổi trạng thái tùy tiện
        repository.save(order);
    }
}
```
* **Hậu quả**: Một lập trình viên mới hoàn toàn có thể viết code ở một file khác gọi `order.setStatus("CANCELLED")` mà không biết đến luật kiểm tra `SHIPPED` ở trên, dẫn đến rò rỉ và mất tính nhất quán dữ liệu.

### ✔️ Áp dụng Rich Domain Model (Đóng gói tuyệt đối)

```java
// Lớp Entity tự quản lý hành vi và bảo vệ trạng thái của mình (Rich)
public class Order {
    private final String id;
    private OrderStatus status; // Sử dụng Enum an toàn

    public enum OrderStatus { CREATED, SHIPPED, CANCELLED }

    // Constructor kiểm soát tính hợp lệ ngay khi khởi tạo
    public Order(String id) {
        this.id = id;
        this.status = OrderStatus.CREATED;
    }

    public OrderStatus getStatus() { return status; }

    // HÀNH VI NGHIỆP VỤ ĐÓNG GÓI: Không có setStatus()!
    public void cancel() {
        if (this.status == OrderStatus.SHIPPED) {
            // Tự bảo vệ ràng buộc nghiệp vụ (Invariant)
            throw new IllegalStateException("Không thể hủy đơn hàng đã được giao đi!");
        }
        this.status = OrderStatus.CANCELLED;
    }
}

// Lớp Service cực kỳ ngắn gọn, đóng vai trò điều phối (Orchestration)
@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void cancelOrder(String orderId) {
        Order order = repository.findById(orderId)
                .orElseThrow(() -> new IllegalArgumentException("Không tìm thấy đơn hàng!"));
        
        order.cancel(); // Ủy thác hoàn toàn logic cho Domain Object tự quyết!
        repository.save(order);
    }
}
```

## 🎨 Sơ đồ so sánh luồng xử lý dữ liệu

```
[ANEMIC DOMAIN MODEL (Lập trình thủ tục)]
┌──────────────┐   1. Lấy trạng thái   ┌──────────────┐
│              │ ────────────────────► │              │
│ OrderService │                       │    Order     │
│ (Nắm Logic)  │ ◄──────────────────── │ (Chỉ có Data)│
│              │   2. Kiểm tra logic   └──────────────┘
│              │ ────────────────────► 
│              │   3. Set status mới
└──────────────┘

[RICH DOMAIN MODEL (Lập trình hướng đối tượng)]
┌──────────────┐     Gọi hàm cancel()  ┌──────────────┐
│ OrderService │ ────────────────────► │    Order     │
│ (Điều phối)  │                       │ (Nắm cả Data │
│              │                       │  và Logic)   │
└──────────────┘                       └──────────────┘
                                         (Tự kiểm tra
                                          và cập nhật)
```

## 📊 Phân tích Trade-offs: Anemic vs Rich Domain Model

| Tiêu chí | Anemic Domain Model (Anti-pattern) | Rich Domain Model (OOP chuẩn) |
| :--- | :--- | :--- |
| **Bảo vệ tính Đóng gói** | **Tồi tệ**: Các biến có thể bị sửa đổi bất cứ lúc nào qua hàm set. | **Tuyệt vời**: Trạng thái chỉ được thay đổi thông qua các phương thức hành vi hợp lệ. |
| **Độ trùng lặp code** | **Cao**: Một luật kiểm tra dữ liệu dễ bị copy rải rác ở 3-4 Services khác nhau. | **Không xảy ra**: Luật nghiệp vụ tập trung duy nhất bên trong lớp Entity. |
| **Khả năng tự tài liệu** | **Kém**: Đọc file Entity chỉ thấy các trường thô, không hiểu nghiệp vụ hoạt động ra sao. | **Tuyệt vời**: Các phương thức tự giải thích (như `cancel()`, `ship()`, `applyDiscount()`). |
| **Tương thích ORM Framework**| **Tuyệt đối**: Hibernate cực kỳ thích các class getter/setter thô sơ này. | Cần một chút nỗ lực cấu hình (như chỉ định JPA truy cập trực tiếp qua Fields thay vì Properties). |
| **Độ phức tạp ban đầu** | Thấp, phù hợp viết code nhanh ăn xổi. | Cao hơn, đòi hỏi tư duy thiết kế hướng đối tượng tốt. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Tại sao Anemic Domain Model bị coi là một Anti-Pattern nhưng nó lại cực kỳ phổ biến và chiếm tới 90% số lượng dự án Spring Boot thực tế hiện nay?
* **Trả lời**: Đây là câu hỏi thực chiến sâu sắc. Có 3 nguyên nhân cốt lõi giải thích cho nghịch lý này:
  1. **Ảnh hưởng của Framework**: Spring Boot khuyến khích phân tách rạch ròi: `@Repository` lo DB, `@Service` lo Transaction và Logic, còn Entity chỉ là JPA ánh xạ bảng. Cấu trúc này vô tình hướng lập trình viên đi theo con đường "Anemic" một cách tự nhiên.
  2. **Tính chất của dự án (Simple CRUD)**: Đa số ứng dụng thực tế chỉ là CRUD đơn giản (Đọc dữ liệu lên hiển thị, cho sửa rồi lưu xuống). Chúng không hề có các quy tắc nghiệp vụ phức tạp. Khi đó, Anemic Model đi kèm Service thô sơ lại là lựa chọn tối ưu chi phí và tốc độ phát triển.
  3. **Rào cản tư duy**: Viết Rich Domain Model đòi hỏi trình độ thiết kế hướng đối tượng cao, thống nhất Ubiquitous Language chặt chẽ. Đa số dev quen với lối tư duy tuần tự (mở database lên ngắm bảng rồi viết code insert/update) nên dễ trượt theo Anemic.

### 2. Làm sao để sử dụng Dependency Injection (tiêm các dịch vụ bên ngoài như EmailService, DatabaseQuery) vào bên trong một Rich Domain Entity? Entity là đối tượng do ta tự khởi tạo bằng `new`, không phải Spring Bean!
* **Trả lời**:
  * **Quy tắc DDD**: Tuyệt đối **không được tiêm** các Service cơ sở hạ tầng (như EmailService, HttpClient) trực tiếp vào trong Entity. Entity phải hoàn toàn tinh khiết, độc lập với hạ tầng ngoài.
  * **Giải pháp chuẩn**:
    1. **Double Dispatch Pattern**: Chuyển giao trách nhiệm bằng cách truyền Service đó vào phương thức của Entity dưới dạng một tham số (Interface):
       ```java
       public class Order {
           // Truyền Interface kiểm tra từ bên ngoài vào lúc chạy
           public void ship(DeliveryService deliveryService) {
               if (!deliveryService.canDeliverTo(this.address)) {
                   throw new IllegalStateException("Không hỗ trợ giao hàng tới địa chỉ này!");
               }
               this.status = OrderStatus.SHIPPED;
           }
       }
       ```
    2. **Domain Service**: Nếu một nghiệp vụ đòi hỏi sự kết hợp phức tạp của nhiều Services hạ tầng và nhiều thực thể, hãy viết một **Domain Service** ở giữa để điều phối, giữ cho Entity không bị nhiễm bẩn code hạ tầng.
