# Request Validation trong Spring Boot: Kỹ thuật phân lớp & Custom Validator thực chiến

## ⚡ Tóm tắt ngắn (30s)
Xác thực dữ liệu đầu vào (**Request Validation**) trong Spring Boot chủ yếu dựa trên chuẩn **Jakarta Bean Validation (JSR-380)**, được hiện thực hóa bởi **Hibernate Validator**.
*   **Thực thi**: Sử dụng các annotation chuẩn trên DTO (như `@NotNull`, `@NotBlank`, `@Size`, `@Email`, `@Pattern`).
*   **Kích hoạt**:
    *   Dùng **`@Valid`** (chuẩn Jakarta) đặt trước `@RequestBody` trong Controller để tự động validate đối tượng đầu vào.
    *   Dùng **`@Validated`** (chuẩn Spring) ở mức Class của Controller/Service để validate các `@PathVariable`, `@RequestParam`, hoặc dùng tính năng **Validation Groups** (phân nhóm xác thực cho các luồng Create/Update khác nhau).
*   **Ngoại lệ trả về**: Khi validate thất bại, Spring sẽ ném ra **`MethodArgumentNotValidException`** (đối với `@RequestBody`) hoặc **`ConstraintViolationException`** (đối với Path/Query Param).

## 🔍 Chi tiết bản chất thực chiến

### 1. Phân biệt sâu sắc `@Valid` và `@Validated`
Đây là câu hỏi phân biệt kinh điển để đánh giá mức độ am hiểu công nghệ của ứng viên:

| Đặc điểm | `@Valid` (Jakarta Bean Validation) | `@Validated` (Spring Framework) |
| :--- | :--- | :--- |
| **Nguồn gốc** | Chuẩn Java EE / Jakarta EE (`jakarta.validation.Valid`). | Lớp hỗ trợ của Spring (`org.springframework.validation.annotation.Validated`). |
| **Vị trí áp dụng** | Tham số phương thức, Thuộc tính trường (Fields). | Mức Class (Controller/Service), Tham số phương thức. |
| **Nested Validation**| **Có hỗ trợ**. Bắt buộc phải dùng `@Valid` trên các thuộc tính đối tượng con để validate lồng nhau. | **Không hỗ trợ** validate lồng nhau trực tiếp. |
| **Validation Groups**| Không hỗ trợ phân nhóm trực tiếp. | **Có hỗ trợ**. Cho phép chỉ định Group cụ thể sẽ validate (ví dụ: `OnCreate.class`, `OnUpdate.class`). |

### 2. Cách xây dựng Custom Constraint Validator chuẩn chỉnh
Khi các annotation mặc định không đáp ứng được quy tắc nghiệp vụ phức tạp (ví dụ: kiểm tra định dạng số điện thoại Việt Nam, kiểm tra trùng lặp email từ DB), chúng ta tự xây dựng Custom Validator gồm 2 phần:
1.  **Annotation**: Định nghĩa interface annotation mới chú thích bởi `@Constraint(validatedBy = MyValidator.class)`.
2.  **Validator Class**: Implement interface `ConstraintValidator<MyAnnotation, MyFieldType>`. Class này hoàn toàn có thể sử dụng cơ chế Dependency Injection để inject các Spring Beans khác (như `UserRepository`) nhằm kiểm tra nghiệp vụ thực tế.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Viết code kiểm tra thủ công trong Controller và thiếu xác thực lồng nhau (Nested Validation)
Việc validate bị trộn lẫn vào Controller, đồng thời quên đánh dấu `@Valid` ở đối tượng con khiến dữ liệu bên trong các danh sách hoặc đối tượng lồng nhau hoàn toàn bị bỏ qua, dẫn tới lỗi NullPointerException ở tầng Service.

```java
package com.example.controller;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.example.model.OrderDto;
import com.example.model.OrderItemDto;

@RestController
@RequestMapping("/api/orders")
public class OrderControllerBad {

    @PostMapping
    public ResponseEntity<String> createOrder(@RequestBody OrderDto orderDto) {
        // ❌ Lỗi 1: Tự viết code validate thủ công làm phình to Controller
        if (orderDto.getCustomerName() == null || orderDto.getCustomerName().trim().isEmpty()) {
            return ResponseEntity.badRequest().body("Customer name is required!");
        }

        // ❌ Lỗi 2: Thiếu cơ chế validate các OrderItemDto nằm bên trong OrderDto.
        // Nếu client gửi OrderItemDto có price = -100, hệ thống vẫn chấp nhận!
        
        return ResponseEntity.ok("Order created successfully");
    }
}
```

### ✅ GOOD: Sử dụng khai báo Annotation, Custom Validator và hỗ trợ Nested Validation hoàn chỉnh
Tách biệt hoàn toàn việc xác thực dữ liệu ra khỏi Controller bằng cách sử dụng các Annotation khai báo mạnh mẽ và thiết lập Custom Validator kiểm tra số điện thoại Việt Nam chuẩn chỉnh.

#### Bước 1: Tạo Custom Annotation & Validator kiểm tra Số điện thoại Việt Nam
```java
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = VietnamesePhoneValidator.class) // ✅ Liên kết tới lớp xử lý logic
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
public @interface VietnamesePhone {
    String message() default "Số điện thoại Việt Nam không đúng định dạng!";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

```java
package com.example.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import java.util.regex.Pattern;

public class VietnamesePhoneValidator implements ConstraintValidator<VietnamesePhone, String> {

    // ✅ Regex kiểm tra số điện thoại Việt Nam chuẩn (bắt đầu bằng 03, 05, 07, 08, 09 và gồm 10 chữ số)
    private static final String PHONE_REGEX = "^(0|\\+84)(3|5|7|8|9)[0-9]{8}$";
    private static final Pattern PHONE_PATTERN = Pattern.compile(PHONE_REGEX);

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) {
            return true; // Để mặc cho @NotNull hoặc @NotBlank xử lý nếu trường này bắt buộc
        }
        return PHONE_PATTERN.matcher(value).matches();
    }
}
```

#### Bước 2: Thiết kế DTO tối ưu với Nested Validation
```java
package com.example.dto;

import com.example.validation.VietnamesePhone;
import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import java.util.List;

public class OrderDto {

    @NotBlank(message = "Tên khách hàng không được để trống!")
    @Size(max = 100, message = "Tên không được vượt quá 100 ký tự!")
    private String customerName;

    @NotBlank(message = "Số điện thoại không được để trống!")
    @VietnamesePhone // ✅ Áp dụng Custom Validator vừa viết
    private String phoneNumber;

    @NotEmpty(message = "Đơn hàng phải có ít nhất 1 sản phẩm!")
    @Valid // ✅ QUAN TRỌNG: Kích hoạt Nested Validation để duyệt tiếp vào trong từng phần tử của List
    private List<OrderItemDto> items;

    // Getters, Setters, Constructors
}
```

```java
package com.example.dto;

import jakarta.validation.constraints.*;

public class OrderItemDto {

    @NotBlank(message = "Mã sản phẩm không được trống!")
    private String productId;

    @NotNull(message = "Số lượng không được để trống!")
    @Min(value = 1, message = "Số lượng tối thiểu phải là 1!")
    private Integer quantity;

    @NotNull(message = "Đơn giá không được để trống!")
    @DecimalMin(value = "0.0", inclusive = false, message = "Đơn giá phải lớn hơn 0!")
    private Double price;

    // Getters, Setters, Constructors
}
```

#### Bước 3: Triển khai Controller tinh gọn
```java
package com.example.controller;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import jakarta.validation.Valid;
import com.example.dto.OrderDto;

@RestController
@RequestMapping("/api/v1/orders")
public class OrderControllerGood {

    @PostMapping
    // ✅ Dùng @Valid để kích hoạt chuỗi kiểm tra tự động trên OrderDto
    public ResponseEntity<String> createOrder(@Valid @RequestBody OrderDto orderDto) {
        // Luồng chạy chỉ đi vào đây khi dữ liệu đã hoàn toàn sạch sẽ và hợp lệ!
        return ResponseEntity.ok("Order created successfully");
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy cực kỳ hay gặp: Quên đặt `@Valid` cho các thuộc tính đối tượng con (Nested Objects)
*   **Hiện tượng**: Bạn viết các annotation kiểm tra dữ liệu rất đầy đủ trong lớp con `OrderItemDto`, nhưng khi Client gửi lên dữ liệu sai định dạng ở trường con, Spring Boot vẫn chấp nhận lưu trữ mà không quăng lỗi!
*   **Nguyên nhân**: Spring Boot không tự động quét đệ quy (recursive scan) các thuộc tính là đối tượng lồng nhau của DTO chính.
*   **Giải pháp**: Bạn **bắt buộc** phải đặt annotation `@Valid` phía trước khai báo thuộc tính đối tượng con hoặc danh sách đối tượng con trong DTO cha (như đã minh họa ở `private List<OrderItemDto> items` trong ví dụ GOOD).

### 2. Sự khác biệt thực tiễn giữa DTO Validation và Entity Database Validation
Nhiều lập trình viên lạm dụng các annotation validation đặt trực tiếp lên lớp **Entity JPA** (`@Table`) thay vì **DTO** (`@RestController`).
*   **Nhược điểm của Entity Validation**:
    1.  *Lỗi phát hiện quá muộn*: Request lỗi đi qua Controller, vượt qua Service, thực thi các câu lệnh xử lý trung gian rồi chỉ bị chặn lại khi JPA chuẩn bị ghi xuống Database (ném ra `ConstraintViolationException`). Điều này làm lãng phí năng lực tính toán của CPU và tốn Connection Pool vật lý.
    2.  *Thiếu linh hoạt*: Một Entity có thể dùng cho nhiều luồng nghiệp vụ khác nhau (ví dụ: Đăng ký thành viên yêu cầu nhập Email, nhưng Cập nhật thông tin nội bộ không cho phép thay đổi Email). Việc đặt cứng annotation trên Entity làm hạn chế tính tùy biến của nghiệp vụ.
*   *Lời khuyên thực chiến*: **Luôn luôn validate dữ liệu sớm nhất có thể** ngay tại tầng Controller bằng cách sử dụng **DTO**. Chỉ sử dụng Entity Validation như một chốt chặn bảo mật cuối cùng để đảm bảo tính toàn vẹn của dữ liệu ở mức Database.
