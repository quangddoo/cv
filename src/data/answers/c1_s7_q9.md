# Thiết kế API Filtering, Sorting, và Searching chuẩn Enterprise

## ⚡ Tóm tắt ngắn (30s)
Thiết kế các tính năng bộ lọc (Filtering), sắp xếp (Sorting), và tìm kiếm (Searching) cho một API danh sách tài nguyên yêu cầu sự cân bằng tinh tế giữa **trải nghiệm dễ sử dụng của Client (UX/API Design)** và **hiệu năng thực thi dưới Database**.
*   **Filtering**: Thiết kế dạng query param rõ ràng. Sử dụng các hậu tố toán tử như `price[gte]=100` hoặc biểu thức RSQL/FIQL `/products?search=price>100;status==active` đối với các bộ lọc phức tạp.
*   **Sorting**: Tiêu chuẩn hóa theo định dạng `sort=column,direction` (ví dụ: `sort=createdAt,desc&sort=price,asc`).
*   **Searching**: Sử dụng query param `q` (hoặc `query`) cho việc tìm kiếm từ khóa chung trên nhiều cột.
*   **Giải pháp kỹ thuật**: Sử dụng **JPA Specification** hoặc **QueryDSL** trong Spring Boot để sinh câu SQL động một cách an toàn, tránh SQL Injection và tránh viết code "Spaghetti" với hàng chục khối `if-else`.

## 🔍 Chi tiết bản chất thực chiến

### 1. So sánh các phong cách thiết kế URI bộ lọc (Filter Styles)

Khi xây dựng bộ lọc phức tạp (lớn hơn, nhỏ hơn, nằm trong khoảng), có 3 trường phái thiết kế phổ biến:

#### 🔹 Cách 1: Sử dụng Hậu tố (LHS Brackets - Khuyên dùng)
*   *Định dạng*: `GET /api/v1/products?price[gte]=100&price[lte]=500&status[in]=ACTIVE,PENDING`
*   *Ưu điểm*: Cực kỳ rõ ràng, dễ phân tích (parse) ở cả Client và Server. Cho phép nhóm các điều kiện cùng cột dễ dàng.
*   *Thực tế*: Được các ông lớn như Stripe, Shopify áp dụng triệt để.

#### 🔹 Cách 2: Sử dụng Tiền tố (RHS Colon)
*   *Định dạng*: `GET /api/v1/products?price=gte:100&status=eq:ACTIVE`
*   *Ưu điểm*: Đơn giản hơn về mặt cấu trúc cú pháp URI.
*   *Nhược điểm*: Phức tạp hơn khi parse chuỗi giá trị ở backend (phải split dấu `:`).

#### 🔹 Cách 3: Sử dụng RSQL / FIQL (Dành cho truy vấn siêu phức tạp)
*   *Định dạng*: `GET /api/v1/products?search=price>=100;status==ACTIVE,(category==shoes;price<50)`
*   *Đặc điểm*: Dùng dấu `;` thay cho phép `AND`, dấu `,` thay cho phép `OR` cùng dấu đóng mở ngoặc để tạo ra một ngôn ngữ truy vấn hoàn chỉnh truyền qua URI.
*   *Ưu điểm*: Cực kỳ mạnh mẽ và linh hoạt tối đa.
*   *Nhược điểm*: Rất khó viết đối với Frontend. Cần cài đặt thư viện parser chuyên dụng ở Server.

## 💻 Code thực chiến: Sử dụng JPA Specification thiết kế bộ lọc động chuẩn Enterprise

Để giải quyết bài toán lọc động nhiều trường mà không bị lỗi SQL Injection và tránh viết code thủ công lặp đi lặp lại, **JPA Specification** phối hợp với các Criteria API là lựa chọn chuẩn chỉnh nhất trong hệ sinh thái Java.

### Implementation: Bộ lọc động sản phẩm nâng cao

```java
// 1. Định nghĩa đối tượng DTO chứa bộ lọc nhận từ Client
public class ProductFilterCriteria {
    private String q;             // Từ khóa tìm kiếm chung
    private Double priceGte;      // Giá lớn hơn hoặc bằng
    private Double priceLte;      // Giá nhỏ hơn hoặc bằng
    private String status;        // Trạng thái sản phẩm
    
    // Getters và Setters...
}

// 2. Định nghĩa Specification Builder để tự động sinh câu truy vấn SQL động
public class ProductSpecifications {

    public static Specification<Product> build(ProductFilterCriteria criteria) {
        return (root, query, cb) -> {
            List<Predicate> predicates = new ArrayList<>();

            // A. Xử lý Lọc theo trạng thái (Exact Match)
            if (criteria.getStatus() != null && !criteria.getStatus().isBlank()) {
                predicates.add(cb.equal(root.get("status"), criteria.getStatus()));
            }

            // B. Xử lý Lọc theo khoảng giá (Range Match)
            if (criteria.getPriceGte() != null) {
                predicates.add(cb.greaterThanOrEqualTo(root.get("price"), criteria.getPriceGte()));
            }
            if (criteria.getPriceLte() != null) {
                predicates.add(cb.lessThanOrEqualTo(root.get("price"), criteria.getPriceLte()));
            }

            // C. Xử lý Tìm kiếm từ khóa chung trên nhiều cột (Full text / Like search)
            if (criteria.getQ() != null && !criteria.getQ().isBlank()) {
                String pattern = "%" + criteria.getQ().toLowerCase() + "%";
                Predicate nameLike = cb.like(cb.lower(root.get("name")), pattern);
                Predicate descLike = cb.like(cb.lower(root.get("description")), pattern);
                predicates.add(cb.or(nameLike, descLike)); // Khớp tên HOẶC mô tả
            }

            return cb.and(predicates.toArray(new Predicate[0]));
        };
    }
}

// 3. Sử dụng Specification trong Service và Controller kết hợp phân trang + sắp xếp tự động
@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    private final ProductRepository productRepository;

    public ProductController(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    // Client gọi: GET /api/v1/products?q=shoe&priceGte=100&status=ACTIVE&sort=price,desc&page=0&size=20
    @GetMapping
    public ResponseEntity<Page<ProductDto>> getProducts(
            ProductFilterCriteria criteria,
            @PageableDefault(size = 20) Pageable pageable
    ) {
        // JPA Specification tự động sinh câu query WHERE động an toàn
        Specification<Product> spec = ProductSpecifications.build(criteria);
        
        Page<Product> productPage = productRepository.findAll(spec, pageable);
        
        Page<ProductDto> dtoPage = productPage.map(p -> 
            new ProductDto(p.getId(), p.getName(), p.getPrice(), p.getStatus())
        );
        
        return ResponseEntity.ok(dtoPage);
    }
}
```

## 📊 Trade-off: So sánh các công cụ truy vấn động ở Backend

| Tiêu chí | Spring Data JPA Specification | QueryDSL | Raw SQL / String Concatenation |
| :--- | :--- | :--- | :--- |
| **Tính an toàn Type-safety** | Khá tốt. Tuy nhiên vẫn phải chỉ định tên cột dưới dạng chuỗi (ví dụ: `root.get("price")`), dễ viết sai chính tả. | **Tuyệt đối**. Sử dụng cơ chế code generator sinh ra các lớp `QProduct` giúp check lỗi gõ sai tên cột ngay từ lúc compile. | Rất kém. Dễ gõ sai cú pháp SQL. |
| **Nguy cơ SQL Injection** | **Không có**. Cơ chế của Criteria API tự động tham số hóa (Parameterized Queries) hoàn toàn. | **Không có**. Tự động hóa hoàn toàn. | **Cực kỳ cao** nếu dev lười và cộng chuỗi SQL trực tiếp. |
| **Độ phức tạp thiết lập ban đầu** | Thấp. Không cần cài thêm thư viện ngoài, có sẵn trong Spring Data JPA. | Trung bình. Yêu cầu cấu hình Maven/Gradle plugin để sinh mã nguồn Q-classes. | Thấp nhất. |
| **Hiệu năng thực thi** | Tốt, tuy nhiên Criteria API sinh SQL tự động đôi khi hơi dài dòng so với SQL tối ưu bằng tay. | Tương đương JPA Specification. | Tối ưu tuyệt đối nếu dev viết SQL tay cực tốt. |

## ⚠️ Common Gotchas & Questions follow-up

* **Cạm bẫy "Mất index do viết câu query sai cách (SARGable queries)"**:
  Khi bạn viết logic tìm kiếm từ khóa dạng không phân biệt chữ hoa chữ thường: `cb.like(cb.lower(root.get("name")), "%keyword%")`.
  * *Hệ quả:* Việc bọc hàm `LOWER()` lên cột `name` sẽ vô hiệu hóa hoàn toàn chỉ mục (Index) thông thường của cột này trên PostgreSQL/MySQL, ép database phải chạy quét toàn bảng (Full Table Scan). Kết hợp với ký tự `%` nằm ở đầu từ khóa tìm kiếm (`%keyword%`), DB bắt buộc phải quét thủ công từng dòng dữ liệu cực kỳ chậm chạp.
  * *Khắc phục:*
    1. Tránh bọc hàm `LOWER()` lên cột DB, thay vào đó hãy cấu hình collation của cột trong database mặc định là Case-Insensitive (ví dụ: `utf8mb4_unicode_ci` trong MySQL hoặc `citext` trong PostgreSQL).
    2. Nếu dữ liệu tìm kiếm cực kỳ lớn, tuyệt đối không dùng toán tử `LIKE %keyword%` của RDBMS. Hãy chuyển đổi nghiệp vụ tìm kiếm này sang một công cụ Full-Text Search chuyên dụng như **Elasticsearch** hoặc **Meilisearch** để đạt hiệu năng O(1).

* **Câu hỏi đào sâu từ interviewer**: *Nếu API của tôi cho phép client tự do sắp xếp (Sort) theo bất kỳ cột nào họ truyền lên (ví dụ: `sort=anyField,asc`), hệ thống có rủi ro gì không và cách phòng ngừa?*
  * *(Trả lời: Có hai rủi ro cực lớn:
    1. **Hiệu năng**: Nếu client chọn sắp xếp theo một cột không được đánh chỉ mục (Index) và bảng có hàng triệu dòng, Database sẽ phải thực hiện thuật toán Filesort (sắp xếp trên đĩa tạm thời), gây nghẽn đĩa và timeout hệ thống.
    2. **SQL Injection thông qua Sorting**: Nhiều thư viện ORM cũ nếu không kiểm tra kỹ chuỗi tên cột có thể bị chèn mã độc hại vào mệnh đề `ORDER BY`.
    *Biện pháp phòng ngừa:* Bắt buộc phải triển khai một **Whitelisting** (Danh sách trắng các cột cho phép sắp xếp) ngay tại lớp Controller/Service. Chỉ cho phép sắp xếp theo các cột đã được đánh chỉ mục sẵn như `id`, `createdAt`, `price`. Nếu client truyền lên một cột lạ, lập tức từ chối bằng lỗi `400 Bad Request`).*
