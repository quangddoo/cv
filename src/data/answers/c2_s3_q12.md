# Deadlock trong database xảy ra thường xuyên. Bạn tìm và fix ra sao?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Deadlock (Khóa chết) xảy ra khi hai hoặc nhiều transaction giữ các khóa dữ liệu mà transaction kia cần, tạo ra một vòng lặp phụ thuộc vô tận (Dependency Cycle). RDBMS có bộ phát hiện deadlock tự động (**Deadlock Detector**). Khi phát hiện, nó sẽ hy sinh một transaction (Victim), tự động hủy bỏ (Rollback) và trả về mã lỗi (`409 Conflict` hoặc `Deadlock detected`) để giải cứu các transaction còn lại. Deadlock xảy ra thường xuyên là dấu hiệu của lỗi thiết kế thứ tự truy cập dữ liệu hoặc thiếu index.
* **Các thảm họa thực chiến được giải quyết**:
    1. **Thảm họa chuyển tiền chéo gây treo giao dịch**: Người dùng A chuyển tiền cho B, đồng thời B chuyển tiền cho A. Code hệ thống khóa tài khoản A rồi khóa B ở luồng 1; luồng 2 khóa tài khoản B rồi khóa A. Hai luồng chạy song song tự chặn nhau ở bước 2, kích hoạt deadlock liên tục làm sụt giảm nghiêm trọng tỷ lệ giao dịch thành công.
    2. **Lỗi Deadlock do Gap Lock trên dữ liệu không tồn tại**: Thực hiện câu lệnh cập nhật hoặc chọn khóa (`SELECT ... FOR UPDATE`) trên một dải dữ liệu không tồn tại để kiểm tra trùng lặp. Database tự động khóa luôn các khoảng trống (Gap Lock), chặn đứng và gây deadlock chéo với các luồng INSERT dữ liệu thật mới.
* **Quyết định Senior**:
    1. **Chẩn đoán**: Đọc log hệ thống DB (Postgres tự động in vết deadlock rất chi tiết; với MySQL, chạy lệnh `SHOW ENGINE INNODB STATUS` để xem khối `LATEST DEADLOCK DETECTED`).
    2. **Khắc phục tận gốc - Đồng nhất thứ tự khóa (Consistent Ordering)**: Bắt buộc sắp xếp danh sách thực thể cần cập nhật theo một thứ tự cố định (ví dụ: sắp xếp ID tài khoản tăng dần) trước khi thực hiện truy vấn khóa (`FOR UPDATE`).
    3. **Lưới bảo hiểm ứng dụng**: Cài đặt cơ chế tự động thử lại (**Automatic Retry** với Exponential Backoff) ở tầng ứng dụng khi gặp lỗi deadlock để nâng cao trải nghiệm người dùng.

## 🔍 Chi tiết bản chất thực chiến: Cơ chế sinh Deadlock và giải pháp

### 1. Kịch bản Deadlock điển hình (Chuyển tiền song song)
* **Luồng 1 (A chuyển cho B)**:
  * Bước 1: Khóa dòng của khách hàng A (`SELECT ... WHERE id = A FOR UPDATE`). -> THÀNH CÔNG.
  * Bước 2: Khóa dòng của khách hàng B (`SELECT ... WHERE id = B FOR UPDATE`). -> PHẢI CHỜ (vì Luồng 2 đang giữ B).
* **Luồng 2 (B chuyển cho A)**:
  * Bước 1: Khóa dòng của khách hàng B (`SELECT ... WHERE id = B FOR UPDATE`). -> THÀNH CÔNG.
  * Bước 2: Khóa dòng của khách hàng A (`SELECT ... WHERE id = A FOR UPDATE`). -> PHẢI CHỜ (vì Luồng 1 đang giữ A).
* **Kết quả**: Hai luồng rơi vào trạng thái chờ đợi lẫn nhau vô hạn. DB phát hiện vòng lặp khóa và chủ động kill luồng 2, rollback transaction để giải cứu luồng 1.

## 🎨 Sơ đồ trực quan (Mô hình vòng lặp khóa gây Deadlock)

```mermaid
stateContext
    state "Transaction 1 (A -> B)" as T1
    state "Transaction 2 (B -> A)" as T2
    state "Tài khoản A" as A
    state "Tài khoản B" as B

    T1 -->|1. Đã khóa (FOR UPDATE)| A
    T2 -->|2. Đã khóa (FOR UPDATE)| B
    
    T1 -->|3. Đang chờ khóa| B
    T2 -->|4. Đang chờ khóa| A

    Note over T1, T2: ❌ HÀNG ĐỢI VÒNG TRÒN VÔ HẠN!<br/>DB Detector tự động KILL & ROLLBACK Transaction 2
```

## 💻 Code thực chiến / Cấu hình thực tế: BAD vs GOOD

### ❌ BAD: Viết code nghiệp vụ cập nhật hàng loạt không sắp xếp gây Deadlock
Lập trình viên thực hiện cập nhật giỏ hàng hoặc giao dịch chuyển tiền trực tiếp theo thứ tự ngẫu nhiên đầu vào của API, tạo cơ hội cho deadlock chéo xảy ra.

* **Code Java Spring Boot tồi**:
```java
@Service
public class TransferService {
    @Autowired
    private AccountRepository accountRepository;

    @Transactional
    public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
        // ❌ NGUY HIỂM: Khóa tài khoản gửi trước
        Account fromAccount = accountRepository.findByIdForUpdate(fromId); 
        // ❌ Sau đó khóa tài khoản nhận
        Account toAccount = accountRepository.findByIdForUpdate(toId); 
        
        fromAccount.subtract(amount);
        toAccount.add(amount);
        
        accountRepository.save(fromAccount);
        accountRepository.save(toAccount);
    }
}
```

---

### ✅ GOOD: Đồng nhất thứ tự khóa và tích hợp cơ chế Tự động Thử lại (Retry)
Sắp xếp thứ tự ID khóa tăng dần trước khi truy vấn để đảm bảo các luồng luôn khóa theo cùng một chiều, đồng thời tích hợp cơ chế tự động thử lại khi có va chạm deadlock.

* **Code Java Spring Boot chuẩn Senior**:
```java
@Service
public class TransferService {
    @Autowired
    private AccountRepository accountRepository;

    // ✅ GIẢI PHÁP 2: Tích hợp cơ chế tự động thử lại ở tầng ứng dụng
    // Khi có deadlock xảy ra, Spring sẽ tự động chạy lại hàm này tối đa 3 lần với thời gian chờ tăng dần
    @Retryable(
        retryFor = {DeadlockLoserDataAccessException.class, CannotAcquireLockException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 100, multiplier = 2) // Thử lại sau 100ms, 200ms
    )
    @Transactional
    public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
        // ✅ GIẢI PHÁP 1: Đồng nhất thứ tự khóa (Sắp xếp ID tăng dần)
        Long firstLockId = Math.min(fromId, toId);
        Long secondLockId = Math.max(fromId, toId);

        // Luôn luôn khóa tài khoản có ID nhỏ hơn trước
        Account firstAccount = accountRepository.findByIdForUpdate(firstLockId);
        // Sau đó mới khóa tài khoản có ID lớn hơn
        Account secondAccount = accountRepository.findByIdForUpdate(secondLockId);

        // Xác định chính xác vai trò sau khi đã khóa an toàn
        Account fromAccount = (fromId.equals(firstLockId)) ? firstAccount : secondAccount;
        Account toAccount = (toId.equals(firstLockId)) ? firstAccount : secondAccount;

        fromAccount.subtract(amount);
        toAccount.add(amount);
        
        accountRepository.save(fromAccount);
        accountRepository.save(toAccount);
    }
}
```

* **Câu truy vấn khóa an toàn (Spring Data JPA)**:
```java
public interface AccountRepository extends JpaRepository<Account, Long> {
    // Sử dụng PESSIMISTIC_WRITE để phát ra câu lệnh SELECT ... FOR UPDATE dưới SQL
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = :id")
    Account findByIdForUpdate(@Param("id") Long id);
}
```

## 📊 Bảng so sánh các phương pháp xử lý và phòng tránh Deadlock

| Tiêu chí | Đồng nhất thứ tự khóa (Lock Ordering) | Tự động Thử lại (App Retry) | Hạ Isolation Level (Read Committed) | Sử dụng Lock phân tán (Redis Lock) |
| :--- | :--- | :--- | :--- | :--- |
| **Bản chất** | Thiết kế logic code để triệt tiêu hoàn toàn vòng lặp khóa. | Chấp nhận lỗi xảy ra và xử lý êm đẹp ở hậu trường. | Giảm thiểu các loại khóa trung gian (như Gap Lock). | Khóa tài nguyên từ tầng ứng dụng trước khi gọi DB. |
| **Ưu điểm** | **Hiệu quả tuyệt đối**, không tốn tài nguyên chạy lại. | Cực kỳ cần thiết cho các hệ thống tải cao, dễ tích hợp. | Tăng đáng kể throughput, tránh deadlock do Gap Lock. | Tránh hoàn toàn va chạm khóa trực tiếp dưới DB. |
| **Nhược điểm** | Đòi hỏi thiết kế logic cẩn thận, khó áp dụng cho quan hệ nhiều bảng phức tạp. | Làm tăng nhẹ latency của request bị lỗi lúc thử lại. | Có thể gặp hiện tượng đọc không nhất quán (Non-repeatable read). | Tăng độ phức tạp hệ thống, tốn thêm 1 network round-trip tới Redis. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Gap Locks và Next-Key Locks" trong MySQL InnoDB
* **Vấn đề**: Bảng `orders` chỉ có các ID `1, 5, 10`. Luồng 1 chạy lệnh: `SELECT * FROM orders WHERE id = 3 FOR UPDATE;` (ID 3 không tồn tại). Luồng 2 chạy lệnh: `SELECT * FROM orders WHERE id = 4 FOR UPDATE;` (ID 4 cũng không tồn tại). Sau đó cả hai luồng cùng chạy `INSERT` dòng ID 3 và ID 4. Lập tức xảy ra deadlock!
* **Nguyên nhân**: Ở mức cô lập mặc định `Repeatable Read` của MySQL, khi tìm kiếm một giá trị không tồn tại bằng `FOR UPDATE`, InnoDB sẽ khóa toàn bộ khoảng trống xung quanh giá trị đó (khoảng từ ID 1 đến 5) - gọi là **Gap Lock**. Cả hai luồng cùng giữ chung Gap Lock trên khoảng này, sau đó cùng muốn ghi dữ liệu vào khoảng đó nên tự chặn nhau gây deadlock.
* **Giải pháp**:
  1. Hạ Isolation Level của MySQL từ `Repeatable Read` xuống **`Read Committed`** (loại bỏ hoàn toàn Gap Lock). Đây là cấu hình chuẩn được khuyên dùng cho hầu hết các dịch vụ Web tải cao hiện đại.
  2. Sử dụng Distributed Lock bằng Redis để kiểm soát trùng lặp ở tầng ứng dụng trước khi ghi vào DB.

### 2. Câu hỏi đào sâu từ interviewer

* **Q1: Làm thế nào bạn chẩn đoán được nguyên nhân gây ra deadlock trên MySQL Production khi log ứng dụng chỉ báo chung chung lỗi `Lock wait timeout exceeded` hoặc `Deadlock found`?**
  * *Trả lời*: 
    1. Lỗi `Lock wait timeout` và `Deadlock` là hai cơ chế khác nhau. Lỗi deadlock được DB phát hiện và kill lập tức, còn lock wait timeout là do đợi khóa quá lâu mà DB không phát hiện được vòng lặp.
    2. Để chẩn đoán chính xác nguyên nhân gây deadlock trên **MySQL (InnoDB)**, tôi sẽ truy cập trực tiếp vào DB và chạy lệnh:
       `SHOW ENGINE INNODB STATUS;`
    3. Trong kết quả đầu ra, tôi sẽ tìm đến khối thông tin **`LATEST DEADLOCK DETECTED`**. Khối này chứa vết ghi chép chi tiết của đợt deadlock gần nhất:
       * Chỉ rõ **Transaction 1** đang giữ khóa gì, chạy câu SQL nào và đang chờ khóa nào.
       * Chỉ rõ **Transaction 2** đang giữ khóa gì, chạy câu SQL nào và đang chờ khóa nào.
       * Chỉ rõ câu lệnh nào đã bị chọn làm nạn nhân (rollback).
    4. Dựa vào thông tin hai câu SQL và kiểu khóa tranh chấp (ví dụ: `lock_mode X locks rec but not gap waiting`), tôi sẽ định vị được chính xác đoạn code nghiệp vụ nào đang xung đột để tiến hành sắp xếp lại thứ tự khóa hoặc thêm index thích hợp.

* **Q2: Có nên tắt tính năng tự động phát hiện deadlock (`innodb_deadlock_detect = OFF`) trong MySQL để tăng hiệu năng hệ thống không?**
  * *Trả lời*: 
    1. **Mặc định**: Lệnh phát hiện deadlock chạy liên tục dưới nền DB. Khi có hàng ngàn truy vấn đồng thời tranh chấp khóa, thuật toán quét đồ thị vòng lặp khóa (Wait-for Graph) của DB sẽ ngốn cực kỳ nhiều tài nguyên CPU, làm DB bị đơ CPU 100% chỉ để đi tìm deadlock.
    2. **Khi nào nên tắt**: Đối với các hệ thống có lưu lượng giao dịch cực khủng (High-throughput), việc tắt `innodb_deadlock_detect` là một lựa chọn tối ưu hiệu năng hợp lý.
    3. **Điều kiện đi kèm**: Khi tắt detector, hệ thống bắt buộc phải dựa hoàn toàn vào cơ chế **Lock Wait Timeout** để tự động giải phóng các kết nối bị kẹt. Vì vậy, tôi phải hạ cấu hình `innodb_lock_wait_timeout` xuống mức rất thấp (ví dụ: từ mặc định 50 giây xuống còn **1-2 giây**) để đảm bảo các luồng bị kẹt khóa được giải phóng nhanh nhất có thể, tránh làm treo connection pool của ứng dụng.
