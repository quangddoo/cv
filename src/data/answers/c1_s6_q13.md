# Spring Boot Profiles: Giải pháp cô lập cấu hình đa môi trường chuyên nghiệp

## ⚡ Tóm tắt ngắn (30s)
`Spring Boot Profiles` cung cấp giải pháp mạnh mẽ để **cô lập các phần cấu hình** của ứng dụng và chỉ cho phép chúng khả dụng trong các môi trường chạy cụ thể (như `dev`, `test`, `staging`, `prod`).
*   **Tác dụng chính**:
    1.  Tách biệt thông tin kết nối hạ tầng (Database URL, Redis port, Kafka bootstrap servers) giữa môi trường phát triển và môi trường Production thực tế.
    2.  Kích hoạt hoặc vô hiệu hóa các Spring Beans/Services có chọn lọc (ví dụ: chỉ gửi SMS thực tế trên Production, còn Dev thì chỉ in ra console log).
*   **Cách thức kích hoạt**: 
    *   Truyền JVM Argument khi chạy ứng dụng: `-Dspring.profiles.active=prod`
    *   Hoặc set Biến môi trường hệ điều hành: `SPRING_PROFILES_ACTIVE=prod`
*   **Best Practice**: Luôn thiết lập một Profile mặc định (`default`) an toàn cho môi trường Dev local và tuyệt đối không bao giờ hardcode các thông tin nhạy cảm (password, api key) của Prod vào file cấu hình, thay vào đó hãy dùng các biến môi trường thay thế dạng placeholder `${DB_PASSWORD}`.

## 🔍 Chi tiết bản chất thực chiến

### 1. Cơ chế ghi đè cấu hình đa file của Spring Boot
Spring Boot tìm kiếm và tải cấu hình theo thứ tự ưu tiên nhất định:

```text
Thứ tự ưu tiên nạp file cấu hình (Càng ở dưới càng có quyền đè cấu hình ở trên):

1. application.yaml (Cấu hình chung mặc định cho mọi môi trường)
      ↓ (Ghi đè bởi)
2. application-dev.yaml (Cấu hình riêng cho dev)
      ↓ (Ghi đè bởi)
3. Biến môi trường hệ điều hành / JVM Arguments khi deploy (Đè mọi file cấu hình vật lý)
```
Nếu thuộc tính `spring.datasource.url` có mặt ở cả `application.yaml` và `application-prod.yaml`, khi chạy với profile `prod`, giá trị trong `application-prod.yaml` sẽ được chọn.

### 2. Sử dụng Profile Expression mạnh mẽ (Spring 5.3+)
Bạn có thể kết hợp các toán tử logic như `&` (AND), `|` (OR), và `!` (NOT) để kiểm soát việc tải các Bean cực kỳ tinh vi:
*   `@Profile("prod & cloud")`: Chỉ tải Bean nếu đồng thời kích hoạt cả profile `prod` và profile `cloud`.
*   `@Profile("dev | staging")`: Tải Bean nếu chạy một trong hai môi trường `dev` hoặc `staging`.
*   `@Profile("!prod")`: Tải Bean ở bất kỳ môi trường nào ngoại trừ `prod`.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Dùng Hardcoded If-Else để kiểm tra môi trường trong code nghiệp vụ
Lập trình viên viết các câu lệnh rẻ nhánh rườm rà ngay trong lớp nghiệp vụ để chọn Service gửi tin nhắn. Code trở nên cực kỳ khó đọc, vi phạm nguyên tắc Open-Closed (OCP) của SOLID.

```java
package com.example.service;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

@Service
public class BadNotificationService {

    @Value("${spring.profiles.active:dev}")
    private String activeProfile;

    public void sendNotification(String message) {
        if ("prod".equals(activeProfile)) {
            System.out.println("AWS SES Engine: Sending real SMS with content: " + message);
        } else if ("staging".equals(activeProfile)) {
            System.out.println("Sendgrid Engine: Sending mock Email: " + message);
        } else {
            System.out.println("Console Engine [DEV]: " + message);
        }
    }
}
// ⚠️ Tác hại: Cực kỳ khó viết Unit Test độc lập. Khi thêm một môi trường mới (như UAT), ta buộc phải vào đây sửa code và re-deploy!
```

###  GOOD: Tách biệt Interface và các Implementation sử dụng `@Profile`
Phân rã nghiệp vụ thành một interface chung, các implementation cụ thể cho từng môi trường sẽ tự động đăng ký và tự động tiêm (di) vào lớp xử lý thông qua cơ chế lọc của `@Profile`.

**Bước 1: Định nghĩa Interface**
```java
package com.example.service;

public interface NotificationService {
    void send(String message);
}
```

**Bước 2: Cài đặt Service cho môi trường Dev (Chỉ in Log)**
```java
package com.example.service;

import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Service;

@Service
@Profile({"dev", "default"}) // ✅ Kích hoạt khi chạy local hoặc không set profile nào
public class DevNotificationService implements NotificationService {
    @Override
    public void send(String message) {
        System.out.println("[DEV LOG ONLY] - Skip sending SMS: " + message);
    }
}
```

**Bước 3: Cài đặt Service cho môi trường Production (Gửi thật qua AWS SES)**
```java
package com.example.service;

import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Service;

@Service
@Profile("prod") // ✅ Chỉ nạp Bean này lên RAM khi ứng dụng được kích hoạt profile 'prod'
public class ProdNotificationService implements NotificationService {
    @Override
    public void send(String message) {
        // Thực hiện kết nối API mạng viễn thông thật
        System.out.println("AWS SES API: SMS sent successfully! Content: " + message);
    }
}
```

**Bước 4: Sử dụng Clean Injection trong Controller**
```java
package com.example.controller;

import com.example.service.NotificationService;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class NotificationController {

    private final NotificationService notificationService;

    // Spring sẽ tự động tìm Bean phù hợp với Profile đang chạy để tiêm vào đây!
    public NotificationController(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    @PostMapping("/notify")
    public void notifyUser(@RequestBody String msg) {
        notificationService.send(msg);
    }
}
```

## 📊 Trade-off: So sánh các phương án lưu trữ cấu hình nhạy cảm

| Giải pháp | Độ an toàn bảo mật | Độ phức tạp vận hành | Tốc độ truy xuất | Sử dụng khi nào |
| :--- | :--- | :--- | :--- | :--- |
| **Hardcode trực tiếp vào `application-prod.yaml`** | ❌ **Cực kỳ nguy hiểm** | Rất thấp | Cực nhanh | Không bao giờ được phép dùng trên dự án thực tế. |
| **Nạp từ Environment Variables qua Spring Profiles** |  **Cao** | Thấp | Cực nhanh | Hoàn hảo cho các dự án chạy Docker/Kubernetes vừa và nhỏ. |
| **Sử dụng Centralized Vault (HashiCorp Vault, AWS Secrets Manager)** |  **Tuyệt đối** | Cao | Chậm hơn một chút (truy vấn qua API/Agent) | Bắt buộc đối với các hệ thống Microservices doanh nghiệp lớn, ngân hàng, fintech. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy vô ý chạy nhầm Profile hoặc không nạp được Bean nào
*   **Vấn đề**: Bạn khai báo `@Profile("prod")` cho Bean A, và `@Profile("dev")` cho Bean B. Khi deploy lên server UAT, bạn quên không khai báo tham số `-Dspring.profiles.active`. Ứng dụng sẽ khởi chạy với profile `default`. Cả A và B đều không được nạp, dẫn đến lỗi crash hệ thống: `NoSuchBeanDefinitionException`.
*   **Khắc phục**: Luôn luôn thiết kế một class fallback dự phòng (như class `DevNotificationService` phía trên có gắn `@Profile("default")`) hoặc định nghĩa rõ ràng cấu hình mặc định trong file `application.yaml` để đảm bảo hệ thống luôn khởi động an toàn.

### 2. Làm thế nào để config Spring Boot tự động kích hoạt một group các profiles liên đới?
*   **Trả lời**: Sử dụng thuộc tính `spring.profiles.group` trong file `application.yaml` để gom nhóm các profile nhỏ lại với nhau.
    ```yaml
    spring:
      profiles:
        group:
          production:
            - prod-database
            - prod-security
            - aws-cloud
    ```
    Khi bạn khởi chạy ứng dụng với duy nhất tham số `--spring.profiles.active=production`, Spring Boot sẽ tự động kích hoạt cả 3 profile thành phần: `prod-database`, `prod-security`, và `aws-cloud` giúp quản lý kiến trúc đa môi trường cực kỳ nhàn nhã.
