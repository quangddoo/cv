# Spring Security Filter Chain: Kiến trúc & Cơ chế hoạt động thực chiến

## ⚡ Tóm tắt ngắn (30s)
**Spring Security Filter Chain** là xương sống của hệ thống bảo mật trong Spring Boot, hoạt động dựa trên cơ chế chuỗi các bộ lọc (**Servlet Filters**).
*   Kiến trúc cốt lõi hoạt động thông qua cơ chế ủy quyền: **`DelegatingFilterProxy`** (Servlet Filter chuẩn) đón request -> Ủy quyền xử lý cho **`FilterChainProxy`** (Spring Bean quản lý) -> Duyệt qua danh sách **`SecurityFilterChain`** chứa hàng loạt các bộ lọc bảo mật con (như kiểm tra CORS, CSRF, Authentication, Authorization).
*   Nếu request đi qua toàn bộ các bộ lọc thành công, nó mới tiếp cận được tới `DispatcherServlet` và đi vào Controller của bạn. Nếu bất kỳ filter nào từ chối (ném Exception), chuỗi sẽ dừng lại lập tức và trả về mã lỗi (như 401 Unauthorized hoặc 403 Forbidden).

## 🔍 Chi tiết bản chất thực chiến

### 1. Sơ đồ kiến trúc luồng đi của Request

```text
               [ Servlet Container (e.g. Tomcat) ]
                               │
                        ┌──────▼──────┐
                        │ Servlet     │ (Standard Filters)
                        │ Filter Chain│
                        └──────┬──────┘
                               │
                  ┌────────────▼────────────┐
                  │ DelegatingFilterProxy   │ (Servlet Filter cầu nối)
                  └────────────┬────────────┘
                               │
               [ Spring Application Context ]
                               │
                  ┌────────────▼────────────┐
                  │ FilterChainProxy        │ (Spring Bean quản lý các chain)
                  └────────────┬────────────┘
                               │
                 ┌─────────────▼─────────────┐
                 │ SecurityFilterChain       │ (Danh sách các Security Filter)
                 │  - CorsFilter             │
                 │  - CsrfFilter             │
                 │  - BearerTokenAuthFilter  │
                 │  - AuthorizationFilter    │
                 └─────────────┬─────────────┘
                               │
                        ┌──────▼──────┐
                        │ Dispatcher  │ (Spring MVC Entry Point)
                        │ Servlet     │
                        └──────┬──────┘
                               │
                        ┌──────▼──────┐
                        │ Controller  │ (Mã nguồn nghiệp vụ của bạn)
                        └─────────────┘
```

### 2. Các bộ lọc (Security Filters) quan trọng nhất và thứ tự chạy
Trong danh sách `SecurityFilterChain`, Spring Security sắp xếp thứ tự các filter rất chặt chẽ. Dưới đây là các filter then chốt:
1.  **`DisableEncodeUrlFilter`**: Ngăn chặn encode Session ID trên URL (tránh rò rỉ session).
2.  **`WebAsyncManagerIntegrationFilter`**: Đồng bộ SecurityContext khi xử lý request bất đồng bộ (Async requests).
3.  **`SecurityContextHolderFilter`** (Thay thế `SecurityContextPersistenceFilter` cũ): Nạp và lưu trữ `SecurityContext` từ Session hoặc token vào `SecurityContextHolder`.
4.  **`CorsFilter`**: Xử lý request pre-flight CORS.
5.  **`CsrfFilter`**: Chống tấn công giả mạo yêu cầu chéo trang.
6.  **`UsernamePasswordAuthenticationFilter`** / **`BasicAuthenticationFilter`**: Thực hiện xác thực người dùng dựa trên Form Login hoặc HTTP Basic Auth.
7.  **`ExceptionTranslationFilter`**: Bắt các lỗi bảo mật (`AuthenticationException`, `AccessDeniedException`) của các filter phía sau để chuyển đổi thành HTTP Response phù hợp (401/403).
8.  **`AuthorizationFilter`** (Thay thế `FilterSecurityInterceptor` cũ): Bộ lọc cuối cùng đưa ra quyết định người dùng hiện tại có đủ quyền truy cập tài nguyên hay không.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Sử dụng cấu hình cũ (Deprecated) và thứ tự Filter thủ công không chuẩn
Khai báo cấu hình kế thừa `WebSecurityConfigurerAdapter` (Đã bị loại bỏ hoàn toàn kể từ Spring Security 6) và tự viết cấu hình bảo mật bằng chuỗi xích không an toàn, không tối ưu cho Spring Boot 3.

```java
package com.example.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.WebSecurityConfigurerAdapter; // ❌ Deprecated / Removed!

@Configuration
public class SecurityConfigBad extends WebSecurityConfigurerAdapter {

    // ❌ Thiết kế kế thừa này cồng kềnh và đã bị Spring Security 6 loại bỏ
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .csrf().disable() // Vô hiệu hóa CSRF không an toàn mà không phân tích
            .authorizeRequests() // ❌ Cú pháp cũ, nên dùng authorizeHttpRequests
            .antMatchers("/api/public/**").permitAll() // ❌ Cú pháp cũ
            .anyRequest().authenticated()
            .and()
            .httpBasic();
    }
}
```

### ✅ GOOD: Cấu hình hiện đại dựa trên Bean Component (Spring Security 6 / Spring Boot 3)
Sử dụng mô hình cấu hình hướng Component (`SecurityFilterChain` Bean) với cú pháp Lambda DSL rõ ràng, mạch lạc và tối ưu hóa việc quản lý Filter.

```java
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;
import com.example.filter.JwtAuthenticationFilter;

@Configuration
@EnableWebSecurity // ✅ Kích hoạt Spring Security
public class SecurityConfigGood {

    private final JwtAuthenticationFilter jwtAuthenticationFilter;

    public SecurityConfigGood(JwtAuthenticationFilter jwtAuthenticationFilter) {
        this.jwtAuthenticationFilter = jwtAuthenticationFilter;
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // ✅ Cấu hình CORS và CSRF thông qua Lambda DSL hiện đại
            .cors(Customizer.withDefaults())
            .csrf(AbstractHttpConfigurer::disable) // Chỉ tắt khi làm API Stateless (JWT)
            
            // ✅ Định nghĩa quyền truy cập cụ thể cho các endpoint
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**", "/swagger-ui/**", "/v3/api-docs/**").permitAll() // Public
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN") // Admin only
                .anyRequest().authenticated() // Còn lại bắt buộc đăng nhập
            )
            
            // ✅ Đăng ký Custom Filter (JWT) vào đúng vị trí của chuỗi
            // Đặt JWT Filter chạy trước UsernamePasswordAuthenticationFilter
            .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build(); // ✅ Trả về Bean SecurityFilterChain
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy kinh điển: Custom Filter chạy 2 lần (Double Invocation Gotcha)
*   **Hiện tượng**: Bạn tự viết một `JwtAuthenticationFilter` kế thừa từ `OncePerRequestFilter`. Bạn đánh dấu lớp này là **`@Component`** để Spring tự động quản lý và inject các repository cần thiết. Sau đó bạn đăng ký filter này vào Security Chain bằng lệnh `http.addFilterBefore(jwtAuthenticationFilter, ...)`. Kết quả là filter của bạn chạy tới **2 lần** trên mỗi request!
*   **Nguyên nhân dưới mui xe**: Spring Boot tự động phát hiện tất cả các Spring Beans kế thừa từ Servlet `Filter` (bao gồm `OncePerRequestFilter`) và đăng ký chúng trực tiếp vào **Servlet Container** chuẩn. Đồng thời, Spring Security lại đăng ký filter đó vào **SecurityFilterChain** của nó. Do đó request đi qua Servlet Container Filter trước (lần 1), sau đó đi tiếp vào Security Filter Chain (lần 2).
*   **Giải pháp**:
    1.  **Không đánh dấu `@Component`** trên Custom Filter của bạn. Hãy tạo mới nó trực tiếp thông qua constructor (`new JwtAuthenticationFilter(...)`) trong class SecurityConfig.
    2.  Nếu bắt buộc phải dùng `@Component` để inject dependencies, hãy đăng ký một **`FilterRegistrationBean`** để vô hiệu hóa việc tự động đăng ký của Servlet Container:
        ```java
        @Bean
        public FilterRegistrationBean<JwtAuthenticationFilter> registration(JwtAuthenticationFilter filter) {
            FilterRegistrationBean<JwtAuthenticationFilter> registration = new FilterRegistrationBean<>(filter);
            registration.setEnabled(false); // ✅ Ngăn cản Spring Boot tự động đăng ký vào Servlet Container
            return registration;
        }
        ```

### 2. Phân biệt `http.authorizeHttpRequests()` `.permitAll()` vs `web.ignoring()`
Đây là câu hỏi đào sâu cực kỳ phổ biến để đánh giá tư duy tối ưu hóa hiệu năng:
*   **`http.authorizeHttpRequests().requestMatchers("/public/**").permitAll()`**: Request gửi tới các URL này **vẫn phải đi qua toàn bộ Security Filter Chain**. Hệ thống vẫn quét qua CORS, CSRF, Sessions và nạp thông tin người dùng vô danh (Anonymous User) vào `SecurityContext`. Đây là lựa chọn an toàn khi bạn vẫn muốn endpoint public được bảo vệ bởi CORS hoặc ghi log người dùng nếu họ đã đăng nhập.
*   **`webSecurityCustomizer -> web.ignoring().requestMatchers("/static/**")`**: Request gửi tới **bỏ qua hoàn toàn Security Filter Chain**. Nó đi thẳng tới Servlet đích mà không tốn một chút tài nguyên nào cho bảo mật.
*   *Lời khuyên thực chiến*: Dùng `web.ignoring()` cho các tài nguyên tĩnh (Static assets, Images, CSS, JS) hoặc API tài liệu (Swagger/OpenAPI UI). Dùng `.permitAll()` cho các API nghiệp vụ thông thường (như API xem danh sách sản phẩm công khai).
