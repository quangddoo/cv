# Mẫu thiết kế Observer và Kiến trúc hướng Sự kiện (Observer Pattern vs Event-Driven Architecture)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **Observer Pattern** là mẫu thiết kế hành vi cho phép một đối tượng (Subject) tự động thông báo và cập nhật trạng thái cho nhiều đối tượng khác đang theo dõi nó (Observers) khi có sự thay đổi.
* **Mối quan hệ**: **Observer Pattern là nền tảng triết lý và là phiên bản thu nhỏ (Micro) chạy trong bộ nhớ của Kiến trúc hướng sự kiện (Event-Driven Architecture - EDA ở mức Macro).**
* **Sự khác biệt cốt lõi**:
  * **Observer Pattern (Local)**: Chạy trên **cùng một vùng nhớ (In-Memory)** của một tiến trình duy nhất. Subject trực tiếp nắm giữ con trỏ/tham chiếu đến danh sách Observers và gọi hàm cập nhật (thường là đồng bộ - synchronous).
  * **Event-Driven Architecture (Distributed)**: Hoạt động ở mức **hệ thống phân tán (Distributed System)**. Người gửi (Publisher) và người nhận (Subscriber) hoàn toàn không biết nhau, giao tiếp bất đồng bộ (Asynchronous) thông qua một kênh trung gian như Message Broker (Kafka, RabbitMQ).

## 🔍 Phân tích mối liên hệ từ Vi mô đến Vĩ mô

Để hiểu sâu, hãy so sánh cách luồng thông tin vận hành từ mức độ thiết kế mã nguồn (In-Memory) đến thiết kế hệ thống lớn (System Design):

### 1. Góc nhìn Vi mô: Observer Pattern (Thiết kế mã nguồn)
* **Mô hình**: Gồm hai thành phần chính là `Subject` (Đối tượng bị theo dõi) và `Observer` (Đối tượng theo dõi).
* **Cơ chế**: Subject duy trì một `List<Observer>` trong bộ nhớ RAM. Khi trạng thái của Subject thay đổi (ví dụ: có đơn hàng mới), nó duyệt vòng lặp qua danh sách này và gọi trực tiếp phương thức cập nhật của từng Observer:
  ```java
  for (Observer observer : observers) {
      observer.update(data); // Gọi hàm trực tiếp (Direct Call)
  }
  ```
* **Độ kết dính**: Tuy đã giảm thiểu nhờ interface, nhưng Subject vẫn phải chủ động quản lý danh sách Observers, đăng ký (`register`) và hủy đăng ký (`unregister`).

### 2. Góc nhìn Vĩ mô: Event-Driven Architecture (Thiết kế hệ thống phân tán)
* **Mô hình**: Gồm `Publisher` (Người phát sự kiện), `Event Broker` (Bộ điều phối sự kiện - Kafka/RabbitMQ), và `Subscriber` (Người đăng ký).
* **Cơ chế**: Publisher phát ra một gói tin (Event Message) lên Broker rồi lập tức kết thúc nhiệm vụ. Nó hoàn toàn không quan tâm ai sẽ nhận, nhận khi nào hay nhận như thế nào. Event Broker sẽ chịu trách nhiệm định tuyến, lưu trữ tạm thời và đẩy dữ liệu tới các Subscriber đăng ký tương ứng.
* **Độ kết dính (Decoupling) tuyệt đối**: Publisher và Subscriber không dùng chung vùng nhớ, không chạy trên cùng một máy chủ, và có thể viết bằng hai ngôn ngữ lập trình hoàn toàn khác nhau.

## 💻 Code Example: Hiện thực hóa mô hình Đơn hàng (Order)

### 1. Hiện thực hóa bằng Observer Pattern (In-Memory Java)

```java
import java.util.ArrayList;
import java.util.List;

// Interface người theo dõi
interface OrderObserver {
    void onOrderCreated(String orderId);
}

// Các người theo dõi cụ thể
class InventoryService implements OrderObserver {
    @Override
    public void onOrderCreated(String orderId) {
        System.out.println("[Inventory] Giữ chỗ hàng trong kho cho đơn: " + orderId);
    }
}

class EmailService implements OrderObserver {
    @Override
    public void onOrderCreated(String orderId) {
        System.out.println("[Email] Gửi thư xác nhận đơn hàng: " + orderId);
    }
}

// Đối tượng bị theo dõi (Subject)
class OrderSubject {
    private final List<OrderObserver> observers = new ArrayList<>();

    public void registerObserver(OrderObserver observer) {
        observers.add(observer);
    }

    public void createOrder(String orderId) {
        System.out.println("--- ĐÃ TẠO ĐƠN HÀNG " + orderId + " ---");
        // Duyệt danh sách để notify (Đồng bộ)
        for (OrderObserver observer : observers) {
            observer.onOrderCreated(orderId);
        }
    }
}
```

### 2. Mô phỏng luồng Event-Driven (Distributed System với Message Broker)

Trong hệ thống lớn, mã nguồn sẽ chuyển hóa thành việc đẩy thông điệp lên hàng đợi:

```java
// Publisher: Đơn giản là push event lên Kafka topic 'order-events'
public class OrderPublisher {
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void createOrder(OrderEvent event) {
        System.out.println("Tạo đơn hàng vĩ mô. Phát tán sự kiện lên Kafka...");
        kafkaTemplate.send("order-events", event.getOrderId(), event);
        // Hoàn thành lập tức, không đợi các dịch vụ khác xử lý xong!
    }
}

// Dịch vụ Kho tự độc lập lắng nghe sự kiện
@Component
public class InventoryConsumer {
    @KafkaListener(topics = "order-events", groupId = "inventory-group")
    public void handleOrderEvent(OrderEvent event) {
        System.out.println("[Inventory Service] Nhận từ Kafka, xử lý tồn kho...");
    }
}
```

## 📊 Bảng so sánh chi tiết: Observer Pattern vs EDA

| Tiêu chí | Observer Pattern (Micro) | Event-Driven Architecture (Macro) |
| :--- | :--- | :--- |
| **Môi trường hoạt động** | **Đơn tiến trình**: Cùng chạy trên một máy ảo JVM, dùng chung bộ nhớ Heap. | **Đa tiến trình / Phân tán**: Chạy trên nhiều máy chủ vật lý khác nhau. |
| **Phương thức giao tiếp**| **Đồng bộ (Synchronous) mặc định**: Subject phải chờ từng Observer xử lý xong mới tiếp tục chạy. | **Bất đồng bộ (Asynchronous)**: Publisher gửi tin lên Broker là xong nhiệm vụ, hoàn toàn không bị chặn. |
| **Mức độ kết dính** | **Thấp (Loose Coupling)**: Tương tác thông qua Interface chung. | **Tuyệt đối không kết dính (Zero Coupling)**: Không hề biết sự tồn tại của nhau. |
| **Độ tin cậy (Resilience)**| **Lập tức đổ vỡ**: Nếu một Observer gặp exception làm sập luồng, luồng chính của Subject cũng sập theo. | **Rất cao**: Nếu Subscriber sập, tin nhắn vẫn được Broker lưu trữ an toàn, khi sống lại sẽ tiêu thụ tiếp. |
| **Khôi phục lỗi** | Không hỗ trợ tự động gửi lại (Retry) hay lưu trữ thư mục rác (DLQ). | Hỗ trợ tuyệt vời các tính năng: Retry, Backpressure, Dead Letter Queue (DLQ). |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Trong Observer Pattern truyền thống, nếu một Observer thực hiện tác vụ cực nặng (như gọi API ngoài, ghi DB lớn) và bị treo, làm thế nào để tránh việc nó block toàn bộ luồng chính của Subject?
* **Trả lời**: Mặc định, vòng lặp notify của Observer Pattern chạy tuần tự trên luồng chính (Main Thread). Nếu một Observer bị đơ, toàn bộ ứng dụng sẽ bị treo. Có 3 cách xử lý thực chiến:
  * **Sử dụng ExecutorService (Multi-threading)**: Thay vì gọi trực tiếp phương thức của Observer trên luồng hiện tại, ta ném công việc xử lý đó vào một Thread Pool xử lý bất đồng bộ:
    ```java
    for (OrderObserver observer : observers) {
        executorService.submit(() -> observer.onOrderCreated(orderId));
    }
    ```
  * **Sử dụng Spring Event `@EventListener` kết hợp `@Async`**: Trong Spring Framework, ta chỉ cần đánh dấu phương thức lắng nghe sự kiện bằng `@Async` để Spring tự động đẩy nó sang luồng khác thực thi.
  * **Áp dụng Lập trình phản ứng (Reactive Programming)**: Sử dụng các thư viện như RxJava hay Project Reactor để tạo ra các luồng dữ liệu (Data Streams) bất đồng bộ và quản lý cơ chế Backpressure an toàn.

### 2. Vấn đề "Lapsed Listener" (Rò rỉ bộ nhớ - Memory Leak) trong Observer Pattern là gì? Làm thế nào để giải quyết triệt để?
* **Trả lời**: Đây là lỗi bảo mật và rò rỉ bộ nhớ kinh điển trong Java:
  * **Nguyên nhân**: Khi một đối tượng đăng ký làm Observer của Subject, Subject sẽ lưu giữ một **Tham chiếu mạnh (Strong Reference)** tới đối tượng đó trong danh sách `List<Observer> observers`. 
  * Ngay cả khi đối tượng Observer đó đã hoàn thành vòng đời và không còn được sử dụng ở bất kỳ nơi nào khác trong ứng dụng, bộ dọn rác **Garbage Collector (GC) vẫn không thể giải phóng nó** vì nó vẫn bị trỏ bởi danh sách của Subject.
  * **Giải pháp khắc phục**:
    1. **Luôn hủy đăng ký (Unregister)**: Bắt buộc phải viết code gọi `subject.unregister(this)` khi hủy bỏ đối tượng Observer (ví dụ: trong hàm dọn dẹp tài nguyên).
    2. **Sử dụng WeakReference**: Sử dụng lớp **`WeakReference<Observer>`** để lưu trữ danh sách Observers trong Subject. Tham chiếu yếu (Weak Reference) cho phép GC tự động dọn dẹp đối tượng Observer khi không còn luồng tham chiếu mạnh nào khác trỏ tới nó, ngăn ngừa hoàn toàn lỗi rò rỉ bộ nhớ.
