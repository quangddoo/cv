# Phân biệt Entity, Value Object và Aggregate trong DDD

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: Đây là 3 khối xây dựng cơ bản của **Thiết kế Chiến thuật (Tactical Design)** trong Domain-Driven Design (DDD), giúp lập trình viên tổ chức mô hình nghiệp vụ (Domain Model) có tổ chức cao và bảo vệ toàn vẹn dữ liệu.
* **Định nghĩa nhanh**:
  * **Entity (Thực thể)**: Đối tượng được định nghĩa bởi **Danh tính duy nhất (Identity/ID)**. Danh tính này bất biến suốt vòng đời của đối tượng, dù các thuộc tính khác có thay đổi. So sánh bằng ID.
  * **Value Object (Đối tượng Giá trị)**: Đối tượng không có danh tính, chỉ đại diện cho một tập hợp giá trị thuộc tính. Bắt buộc phải **bất biến (Immutable)**. So sánh bằng cách đối chiếu tất cả các trường dữ liệu bên trong.
  * **Aggregate (Cụm đối tượng)**: Một cụm liên kết gồm các Entities và Value Objects, được coi là **một đơn vị giao dịch duy nhất** để bảo vệ các ràng buộc nghiệp vụ (Invariants). Cụm này được kiểm soát bởi một thực thể gốc duy nhất gọi là **Aggregate Root**.

---

## 🔍 Phân tích chi tiết từng Khối xây dựng

### 1. Entity (Thực thể)
* **Đặc trưng**: Có tính liên tục (continuity) và định danh rõ ràng.
* *Ví dụ*: Khách hàng (`Customer`), Đơn hàng (`Order`), Bài viết (`Article`).
* *Đặc điểm phỏng vấn cần nhớ*: Một `Customer` có ID là `CUST-001`. Nếu ngày mai họ đổi tên, đổi địa chỉ, đổi số điện thoại thì họ **vẫn là khách hàng đó**. Trạng thái thay đổi nhưng danh tính giữ nguyên.

### 2. Value Object (Đối tượng Giá trị)
* **Đặc trưng**: Không quan tâm "nó là ai" mà chỉ quan tâm "nó có giá trị gì".
* *Ví dụ*: Số tiền (`Money` gồm amount và currency), Địa chỉ (`Address` gồm street, city, zip), Khoảng màu (`Color` gồm R, G, B).
* *Đặc điểm phỏng vấn cần nhớ*: Nếu bạn có ly nước giá `10 USD` và tôi có ly nước giá `10 USD`, hai giá trị tiền tệ này hoàn toàn tương đương và thay thế được cho nhau. Chúng ta so sánh bằng giá trị thô bên trong. Value Object **không có Setters**, muốn thay đổi phải tạo đối tượng mới hoàn toàn.

### 3. Aggregate & Aggregate Root (Cụm đối tượng & Thực thể gốc)
* **Đặc trưng**: Đóng vai trò là ranh giới giao dịch (transaction boundary).
* *Ví dụ*: Cụm `Order` gồm `Order` (Root), danh sách `OrderItem` (Entity con), và `ShippingAddress` (Value Object).
* *Quy tắc tối cao*: Thế giới bên ngoài (Client, Controller, Service khác) **chỉ được phép tương tác trực tiếp với Aggregate Root** (trong ví dụ này là `Order`). Không ai được tự ý gọi `OrderItem` để sửa đổi dữ liệu mà không đi qua `Order`. Aggregate Root chịu trách nhiệm bảo vệ tính đúng đắn của toàn cụm.

## 💻 Code Example: Triển khai Cụm Đơn hàng trong Java sạch

Dưới đây minh họa đầy đủ 3 khái niệm này phối hợp ăn khớp trong dự án:

### 1. Triển khai Value Object (Địa chỉ giao hàng - Bất biến)
```java
import java.util.Objects;

public final class Address { // 'final' đảm bảo không bị kế thừa phá vỡ
    private final String street;
    private final String city;
    private final String zipCode;

    // Chỉ có Constructor, không có Setters
    public Address(String street, String city, String zipCode) {
        this.street = street;
        this.city = city;
        this.zipCode = zipCode;
    }

    public String getStreet() { return street; }
    public String getCity() { return city; }
    public String getZipCode() { return zipCode; }

    // Bắt buộc override equals và hashCode để so sánh bằng giá trị
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Address address = (Address) o;
        return Objects.equals(street, address.street) &&
               Objects.equals(city, address.city) &&
               Objects.equals(zipCode, address.zipCode);
    }

    @Override
    public int hashCode() {
        return Objects.hash(street, city, zipCode);
    }
}
```

### 2. Triển khai Entity phụ thuộc (Sản phẩm trong Đơn hàng)
```java
public class OrderItem {
    private final String itemId; // ID nội bộ trong cụm
    private final String productId;
    private int quantity;
    private double price;

    public OrderItem(String itemId, String productId, int quantity, double price) {
        this.itemId = itemId;
        this.productId = productId;
        this.quantity = quantity;
        this.price = price;
    }
    // Getters & Setters có phạm vi truy cập package-private (chỉ Aggregate Root được gọi)
    String getItemId() { return itemId; }
    void changeQuantity(int newQty) { this.quantity = newQty; }
    double getSubtotal() { return price * quantity; }
}
```

### 3. Triển khai Aggregate Root (Quản lý và thực thi khế ước nghiệp vụ)
```java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Order {
    private final String orderId; // ID định danh toàn cục (Entity)
    private final List<OrderItem> items = new ArrayList<>(); // Thực thể phụ thuộc
    private Address shippingAddress; // Value Object
    private double totalAmount;

    public Order(String orderId, Address shippingAddress) {
        this.orderId = orderId;
        this.shippingAddress = shippingAddress;
        this.totalAmount = 0.0;
    }

    // Trả về Read-only List bảo vệ tính đóng gói
    public List<OrderItem> getItems() {
        return Collections.unmodifiableList(items);
    }

    // Thực thi khế ước (Invariant): Đơn hàng không được vượt quá 100 sản phẩm
    public void addItem(String productId, int qty, double price) {
        int currentTotalQty = items.stream().mapToInt(item -> item.getSubtotal() > 0 ? qty : 0).sum();
        if (currentTotalQty + qty > 100) {
            throw new IllegalStateException("Đơn hàng không được vượt quá 100 sản phẩm!");
        }

        OrderItem newItem = new OrderItem(UUID.randomUUID().toString(), productId, qty, price);
        this.items.add(newItem);
        recalculateTotal();
    }

    private void recalculateTotal() {
        this.totalAmount = items.stream().mapToDouble(OrderItem::getSubtotal).sum();
    }
}
```

## 🎨 Sơ đồ Ranh giới của một Aggregate

```
┌──────────────────────────────────────────────────────────────┐
│  RANH GIỚI TRANSACTION CỦA AGGREGATE                         │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │                     AGGREGATE ROOT                     │  │
│  │   Order (Entity - Identifiable by orderId)             │  │
│  └──────────────────────────┬─────────────────────────────┘  │
│                             │                                │
│                             ▼                                │
│        ┌────────────────────┴────────────────────┐           │
│        ▼                                         ▼           │
│  ┌─────────────────────────┐               ┌───────────────┐ │
│  │      Entities Con       │               │ Value Object  │ │
│  │  List<OrderItem>        │               │ Address       │ │

│  └─────────────────────────┘               └───────────────┘ │

```

## 📊 Phân tích Trade-offs: So sánh chi tiết Entity vs Value Object

| Tiêu chí | Entity (Thực thể) | Value Object (Đối tượng giá trị) |
| :--- | :--- | :--- |
| **Định danh (Identity)** | **Bắt buộc có**: Sử dụng ID duy nhất để phân biệt (như UUID, Auto-increment). | **Không có**: Định danh dựa trên tổng hợp các giá trị thuộc tính. |
| **Tính bất biến (Mutability)**| **Có thể thay đổi (Mutable)**: Các thuộc tính có thể cập nhật trong runtime. | **Bắt buộc bất biến (Immutable)**: Muốn sửa đổi phải thay thế bằng đối tượng mới. |
| **So sánh bằng** | So sánh hai đối tượng dựa trên ID: `a.getId() == b.getId()`. | So sánh bằng thuộc tính: `a.equals(b)` (mọi trường phải khớp). |
| **Vòng đời (Lifecycle)** | Có trạng thái vòng đời (khởi tạo, lưu trữ, cập nhật, xóa). | Không có vòng đời độc lập, luôn thuộc về một Entity. |
| **Lưu trữ database** | Có bảng riêng biệt (Table) trong cơ sở dữ liệu. | Thường được lưu nhúng trực tiếp trong bảng của Entity (`@Embedded` trong JPA). |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Tại sao Value Object BẮT BUỘC phải là Bất biến (Immutable)? Nếu cho phép thay đổi (Mutable) thì thảm họa gì sẽ xảy ra?
* **Trả lời**: Đây là câu hỏi kiểm tra tư duy sâu về bộ nhớ và chia sẻ dữ liệu:
  * **Thảm họa chia sẻ tham chiếu (Alias Bug)**: Hãy tưởng tượng trong bộ nhớ Heap, ta có một đối tượng `Address` đại diện cho địa chỉ "123 Đường Láng, Hà Nội". Cả hai đối tượng `UserA` và `UserB` đều đang sống chung một nhà nên cùng trỏ tới thực thể `Address` này.
  * Nếu `Address` là **Mutable** (có phương thức `setStreet()`): Khi `UserA` chuyển nhà sang "456 Cầu Giấy" và gọi `userA.getAddress().setStreet("456 Cầu Giấy")`, tham chiếu vùng nhớ bị thay đổi trực tiếp.
  * Hậu quả: Địa chỉ của `UserB` cũng tự động bị đổi sang "456 Cầu Giấy" một cách âm thầm mà hệ thống không hề hay biết, gây sai lệch dữ liệu nghiêm trọng.
  * **Giải pháp**: Giá trị bắt buộc phải bất biến. Khi `UserA` chuyển nhà, ta bắt buộc phải tạo một đối tượng Address hoàn toàn mới: `userA.setAddress(new Address("456 Cầu Giấy", ...))`, giữ an toàn tuyệt đối cho địa chỉ của `UserB`.

### 2. Quy tắc vàng khi giao tiếp giữa các Aggregates khác nhau trong DDD là gì? Có thể truyền trực tiếp một tham chiếu đối tượng (Object Reference) từ Aggregate A sang Aggregate B không?
* **Trả lời**: **TUYỆT ĐỐI KHÔNG.** Quy tắc vàng của DDD chỉ ra rằng:
  * Các Aggregates chỉ được phép liên kết và giao tiếp với nhau **thông qua ID (Identity Reference), không được truyền trực tiếp Object Reference**.
  * *Ví dụ*: Trong lớp `Order`, thuộc tính định danh khách hàng phải là `private String customerId;` chứ không được khai báo là `private Customer customer;`.
  * **Lý do**:
    1. **Ranh giới cô lập (Isolation)**: Nếu truyền trực tiếp Object, bạn đã phá vỡ ranh giới Aggregate Root. Một giao dịch lưu `Order` có thể vô tình kích hoạt lưu đè hoặc load toàn bộ dữ liệu của `Customer` lên bộ nhớ (gây thảm họa lazy loading / performance trong Hibernate).
    2. **Tương thích Microservices**: Việc tham chiếu qua ID giúp hệ thống dễ dàng chia tách thành các Microservices độc lập sau này (vì Order Service và Customer Service chạy ở 2 database vật lý khác nhau, không thể dùng con trỏ trỏ trực tiếp sang nhau).
