# Payment thành công nhưng order vẫn pending. Bạn xử lý ra sao?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Hiện tượng lệch trạng thái giữa cổng thanh toán (đã trừ tiền thành công) và hệ thống của bạn (đơn hàng vẫn ở trạng thái chờ) là bài toán **Bất đồng bộ & Tính nhất quán cuối cùng (Distributed Eventual Consistency)**. Nguyên nhân gốc rễ thường do lỗi mạng tạm thời (Timeout/Network Partition) khiến Webhook phản hồi từ cổng thanh toán bị thất bại hoặc hệ thống xử lý Webhook bị sập trong lúc xử lý logic.
* **Thảm họa thực chiến được giải quyết**:
  1. **Khách bị trừ tiền nhưng không nhận được hàng**: Khách hàng thanh toán 20 triệu mua điện thoại. Ngân hàng trừ tiền thành công. Tuy nhiên, do mạng lag, cổng thanh toán không thể gọi được webhook về Backend của bạn. Đơn hàng vẫn hiển thị "Chờ thanh toán" rồi tự động hủy sau 15 phút do hết hạn (Expired), trong khi tiền của khách đã mất. Khách hàng phẫn nộ, gọi hotline khiếu nại kịch liệt.
  2. **Giao vật phẩm số bị trễ (Digital Goods Delivery)**: Mua vật phẩm trong game. Stripe báo sòng phẳng thành công nhưng ứng dụng xử lý chậm làm luồng cập nhật vật phẩm bị nghẽn. Người chơi không nhận được vật phẩm lập tức, spam vote 1 sao trên App Store.
* **Quyết định Senior**:
  1. **Thiết kế Webhook có Idempotent & Retry**: Cho phép cổng thanh toán gọi lại webhook nhiều lần nếu gặp lỗi mạng. Backend dùng Idempotency Key (ví dụ: `payment_transaction_id`) để đảm bảo dù nhận trùng webhook cũng chỉ cập nhật trạng thái đơn hàng đúng 1 lần.
  2. **Bắt buộc có Hệ thống Đối soát Tự động (Active Reconciliation/Sync Job)**: Xây dựng một background worker quét toàn bộ các đơn hàng "PENDING" quá 10 phút, chủ động gọi sang API truy vấn trạng thái của Cổng thanh toán (Query Transaction API) để tự động cập nhật đồng bộ lại trạng thái.
  3. **Không xử lý nghiệp vụ nặng trong luồng Webhook**: Khi nhận được webhook, cập nhật DB lập tức và bắn một Event qua Message Broker (Kafka/RabbitMQ) để các downstream service (như kho hàng, giao hàng, gửi email) tự tiêu thụ bất đồng bộ, tránh làm nghẽn luồng callback nhạy cảm của cổng thanh toán.

## 🔍 Chi tiết bản chất thực chiến: Tại sao xảy ra & Luồng xử lý sự cố

### 3 Nguyên nhân cốt lõi gây lệch trạng thái dữ liệu:
1. **Lỗi đứt mạng (Network Timeout)**: Cổng thanh toán trừ tiền khách hàng thành công -> Cố gắng gọi API Webhook của bạn -> API của bạn phản hồi quá 10 giây (do DB bị chậm hoặc luồng xử lý bị nghẽn) -> Cổng thanh toán tự ngắt kết nối và đánh dấu cuộc gọi thất bại.
2. **Backend của bạn bị Crash đúng lúc**: Webhook gọi về thành công -> Backend đang xử lý cập nhật trạng thái đơn hàng thì bị Out-of-Memory hoặc pod Kubernetes bị khởi động lại -> Dữ liệu cập nhật nửa chừng bị Rollback, mất dấu giao dịch.
3. **Lỗi logic ghi đè (Race Condition)**: Khách hàng click "Tôi đã thanh toán" (luồng 1 - gọi API query chủ động) cùng lúc Webhook gọi về (luồng 2 - gọi thụ động). Hai luồng xung đột ghi đè dữ liệu trạng thái dẫn đến khóa hoặc deadlock.

## 🎨 Sơ đồ trực quan: Mô hình Xử lý Webhook & Hệ thống Đối soát tự động (Reconciliation Job)

Sự kết hợp giữa luồng Webhook (thụ động - thời gian thực) và Sync Job (chủ động - bù đắp sai sót):

```
Luồng 1: Webhook (Thời gian thực - Có thể fail do mạng)
 Cổng Thanh Toán ───[Gọi Webhook]───► Backend API ───► [Cập nhật Order = PAID] (Thành công ✔)
                                         │ (Lỗi mạng / Sập ❌)
                                         ▼ (Mất dấu!)

Luồng 2: Sync Job Đối Soát (Chủ động - Chạy định kỳ bù đắp lỗi)
 [Sync Job Worker] ─── (Mỗi 5 phút quét orders PENDING > 10p)
        │
        ▼ (Phát hiện Order 123 vẫn PENDING)
 [Sync Job Worker] ───[Gọi API tra cứu trạng thái]───► Cổng Thanh Toán API
        │                                                     │
        ▼ ◄──────────────────[Trả về: ĐÃ THANH TOÁN]──────────┘
 [Cập nhật Order 123 = PAID] ───► [Gửi Event hoàn tất đơn hàng]
```

## 💻 Code thực chiến: Webhook Controller An toàn & Scheduled Reconciliation Job

Dưới đây là thiết kế hoàn chỉnh gồm 2 lá chắn: API tiếp nhận Webhook (có kiểm tra Idempotency) và một Job chạy định kỳ để truy vấn chủ động.

### 1. Code Spring Boot tiếp nhận Webhook từ Cổng thanh toán một cách an toàn

```java
package com.example.payment;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import org.springframework.transaction.annotation.Transactional;

@RestController
@RequestMapping("/api/v1/payments")
@RequiredArgsConstructor
@Slf4j
public class PaymentWebhookController {

    private final OrderService orderService;
    private final PaymentRepository paymentRepository;

    @PostMapping("/webhook/vnpay")
    @Transactional
    public ResponseEntity<String> handleVNPayWebhook(@RequestBody VNPayWebhookPayload payload) {
        log.info("Received payment webhook for transaction: {}", payload.getTxnRef());

        // BƯỚC 1: Xác thực chữ ký số (Signature Verification) phòng chống giả mạo request
        if (!verifySignature(payload)) {
            log.error("Invalid signature detected for transaction: {}", payload.getTxnRef());
            return ResponseEntity.badRequest().body("Signature failed");
        }

        // BƯỚC 2: Kiểm tra Idempotency (Tránh xử lý trùng lặp webhook)
        PaymentTransaction existingPayment = paymentRepository.findByTransactionRef(payload.getTxnRef()).orElse(null);
        if (existingPayment != null) {
            log.info("Transaction {} already processed. Reponding with success to gate.", payload.getTxnRef());
            return ResponseEntity.ok("Success (Already Processed)"); // Trả về 200 để cổng thanh toán dừng retry
        }

        // BƯỚC 3: Cập nhật trạng thái giao dịch thanh toán
        PaymentTransaction payment = new PaymentTransaction();
        payment.setTransactionRef(payload.getTxnRef());
        payment.setAmount(payload.getAmount());
        payment.setOrderUuid(payload.getOrderUuid());
        payment.setStatus(payload.isSuccess() ? "SUCCESS" : "FAILED");
        paymentRepository.save(payment);

        // BƯỚC 4: Cập nhật trạng thái Đơn hàng (Delegation sang Service xử lý nghiệp vụ)
        if (payload.isSuccess()) {
            orderService.markAsPaid(payload.getOrderUuid(), payload.getTxnRef());
        } else {
            orderService.markAsFailed(payload.getOrderUuid(), "Payment failed at gateway");
        }

        return ResponseEntity.ok("Success");
    }

    private boolean verifySignature(VNPayWebhookPayload payload) {
        // Thực thi logic mã hóa MD5/SHA256 kiểm tra chữ ký số với Secret Key
        return true; 
    }
}
```

### 2. Active Reconciliation Job (Bù đắp lỗi khi Webhook bị đứt gãy)

```java
package com.example.payment;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

@Component
@RequiredArgsConstructor
@Slf4j
public class ReconciliationScheduler {

    private final OrderRepository orderRepository;
    private final PaymentGatewayClient paymentGatewayClient;
    private final OrderService orderService;

    // Chạy định kỳ mỗi 5 phút
    @Scheduled(cron = "0 */5 * * * *")
    public void reconcileStalePendingOrders() {
        log.info("Starting active payment reconciliation job...");

        // Tìm các đơn hàng PENDING được tạo từ 10 phút trước đến tối đa 2 giờ trước
        LocalDateTime toTime = LocalDateTime.now().minusMinutes(10);
        LocalDateTime fromTime = LocalDateTime.now().minusHours(2);
        
        List<Order> staleOrders = orderRepository.findStalePendingOrders(fromTime, toTime);
        log.info("Found {} stale pending orders for reconciliation", staleOrders.size());

        for (Order order : staleOrders) {
            try {
                // Gọi API sang Cổng thanh toán để kiểm tra trạng thái thực tế của giao dịch
                GatewayTransactionStatus gatewayStatus = paymentGatewayClient.queryTransactionStatus(order.getUuid());

                if (gatewayStatus.isPaidSuccessfully()) {
                    log.info("Reconciliation SUCCESS: Order {} was paid but state was pending. Syncing to PAID.", order.getUuid());
                    orderService.markAsPaid(order.getUuid(), gatewayStatus.getGatewayTransactionId());
                } else if (gatewayStatus.isTransactionFailed()) {
                    log.warn("Reconciliation FAILED: Order {} payment failed at gate. Syncing to FAILED.", order.getUuid());
                    orderService.markAsFailed(order.getUuid(), "Payment failed at gateway (detected by job)");
                } else {
                    log.info("Order {} is still pending payment at gateway. No sync needed.", order.getUuid());
                }
            } catch (Exception e) {
                log.error("Failed to reconcile order {}. Skipping for next run.", order.getUuid(), e);
            }
        }
        log.info("Payment reconciliation job finished.");
    }
}
```

## 📊 Bảng so sánh 3 Phương án thiết kế đồng bộ trạng thái thanh toán

| Tiêu chí | Phương án 1: Chỉ dựa vào Webhook | Phương án 2: Client tự Polling (Gọi liên tục từ Mobile) | Phương án 3: Webhook + Active Reconciliation Job (Khuyên dùng) |
| :--- | :--- | :--- | :--- |
| **Độ tin cậy** | **Thấp** (Chắc chắn sẽ lệch dữ liệu khi có sự cố mạng hoặc sập backend). | **Trung bình** (Khách hàng tắt app đột ngột sẽ ngắt luồng gọi kiểm tra). | **Tuyệt đối 100%** (Sync Job là lưới an toàn hốt trọn mọi trường hợp sót). |
| **Hiệu năng & Tài nguyên** | Tối ưu nhất (Chỉ xử lý khi có cuộc gọi thụ động từ cổng thanh toán). | Tệ nhất (Tạo ra hàng ngàn request đọc DB rác từ app khi người dùng chờ đợi). | Rất tốt (Sync job chỉ quét các đơn hàng stale, không gây tải diện rộng). |
| **Trải nghiệm người dùng (UX)** | Tốt khi mạng thông suốt, cực kỳ tệ khi bị lỗi lệch trạng thái đơn hàng. | Tốt trung bình (Cập nhật thời gian thực trên màn hình nếu khách không tắt app). | **Hoàn hảo** (Đơn hàng tự động hiển thị PAID sau vài phút dù khách tắt app). |
| **Chi phí bảo trì** | Thấp | Trung bình | Trung bình (Cần viết thêm code Scheduler và tích hợp API truy vấn). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Xung đột ghi đè giữa Job đối soát và Webhook về muộn"
* **Vấn đề nguy hiểm**: Tại giây thứ 0, Webhook của cổng thanh toán gọi về nhưng bị nghẽn mạng tạm thời ở Backend. Tại giây thứ 1, Sync Job quét thấy đơn hàng này và gọi API query trạng thái, DB trả về thành công và Job bắt đầu chạy hàm `markAsPaid()`. Đúng lúc đó, luồng Webhook giải phóng tắc nghẽn và cũng chạy hàm `markAsPaid()`. 
  * Hai luồng chạy song song chèn dữ liệu đè nhau, có thể gây ra hiện tượng gửi email xác nhận 2 lần hoặc tệ hơn là cộng tiền tài khoản 2 lần cho khách hàng.
* **Giải pháp khắc phục**:
  1. Sử dụng **Optimistic Locking** trên bảng `orders` (bằng trường `@Version`). Khi một luồng đã update trạng thái đơn hàng sang `PAID`, luồng còn lại cố gắng update sẽ bị ném lỗi `OptimisticLockingFailureException` và tự động rollback an toàn.
  2. Bắt buộc kiểm tra lại trạng thái đơn hàng ở bước đầu tiên của hàm `markAsPaid()` bằng câu truy vấn có điều kiện: `UPDATE orders SET status = 'PAID' WHERE id = 1 AND status = 'PENDING';` (kiểu Compare-and-Swap).

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Cổng thanh toán không hỗ trợ API truy vấn trạng thái (Query API), họ chỉ có Webhook thôi. Bây giờ Webhook bị mất dữ liệu do lỗi mạng kéo dài 2 tiếng. Bạn xử lý thế nào để cứu đơn hàng cho khách?"**
* **Trả lời**:
  * Trường hợp xấu nhất không có Query API, Senior sẽ thiết kế cơ chế **Đối soát file vật lý cuối ngày (End-of-day Batch Reconciliation)**:
    1. Cổng thanh toán luôn cung cấp một file giao dịch tổng hợp (thường là file CSV/XLSX) qua SFTP hoặc API xuất file lúc 0h00 sáng mỗi ngày.
    2. Viết một Job tự động tải file đối soát này về vào lúc 1h00 sáng.
    3. Thực hiện phân tích dữ liệu (Parse CSV), so sánh danh sách giao dịch thành công trong file với dữ liệu giao dịch trong DB của hệ thống.
    4. Tự động vá các đơn hàng bị lệch trạng thái và kích hoạt email xin lỗi/giao hàng tự động cho khách hàng.
