# Backfill dữ liệu production cần lưu ý gì?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Backfill dữ liệu (nạp bù/chuẩn hóa dữ liệu lịch sử) trên môi trường Production là một trong những tác vụ rủi ro cao nhất của kỹ sư dữ liệu. Nguyên tắc tối thượng của Senior Engineer khi backfill là **"Tuyệt đối không gây gián đoạn dịch vụ" (Do No Harm)**. Việc chạy một câu lệnh SQL khổng lồ để vá dữ liệu sẽ kích hoạt khóa bảng (Lock Escalation) hoặc tạo bão Event (Event Storm) làm tê liệt toàn bộ hệ thống đang hoạt động.
* **Thảm họa thực chiến được giải quyết**:
  1. **Nghẽn cổ chai sập hệ thống do Table Lock**: Dev chạy lệnh `UPDATE users SET status = 'ACTIVE'` trên bảng có 50 triệu dòng để đồng bộ cột mới. Database lập tức chuyển từ khóa dòng (Row-level Lock) sang **Khóa bảng (Exclusive Table Lock)** để tiết kiệm bộ nhớ RAM giữ lock. Toàn bộ các request đăng ký/đăng nhập của người dùng bị treo cứng chờ giải phóng lock, gây ra sự cố Downtime kéo dài 2 tiếng.
  2. **Bão Event tàn phá hệ thống downstream**: Sử dụng JPA/Hibernate chạy hàm `save()` để update hàng triệu bản ghi đơn hàng cũ. Việc này vô tình kích hoạt Entity Listener `@PostUpdate`, tự động đẩy hàng triệu message `OrderUpdated` lên Kafka. Cụm Kafka bị quá tải, kéo theo service gửi Email tự động gửi hàng loạt mail rác về đơn hàng cũ từ 3 năm trước cho khách hàng.
* **Quyết định Senior**:
  1. **Chia nhỏ và Chạy cuốn chiếu (Batching & Throttling)**: Tuyệt đối không chạy một transaction lớn. Bắt buộc chia nhỏ dữ liệu thành từng khối (Batch size từ 500 - 2000 bản ghi) dựa trên ID tăng dần (Cursor-based) và chèn khoảng nghỉ (Sleep/Delay) giữa các đợt để DB thở.
  2. **Vô hiệu hóa tác dụng phụ (Bypass Side-effects)**: Khi backfill, bắt buộc tắt các Database Trigger, ngắt kết nối với các Event Listener (hoặc dùng JDBC thuần để bỏ qua Hibernate Interceptor) để tránh kích hoạt bão Event bất ngờ.
  3. **Lưu vết tiến trình (Progress Tracking) & Khả năng Dry-run**: Thiết kế script có cơ chế chạy thử (Dry-run) trên Staging, có bảng lưu vết (Log/Checkpoint Table) ghi nhận ID cuối cùng đã xử lý để nếu script bị đứt gãy giữa chừng có thể tiếp tục chạy (Resume) thay vì chạy lại từ đầu.

## 🔍 Chi tiết bản chất thực chiến: Tại sao một Transaction lớn lại giết chết Database?

### 1. Hiện tượng Leo thang Khóa (Lock Escalation)
Mỗi dòng dữ liệu bị `UPDATE` sẽ bị khóa bởi một Row Lock trong bộ nhớ. Khi số lượng dòng bị cập nhật vượt quá một ngưỡng nhất định (ví dụ trong SQL Server hoặc PostgreSQL), hệ thống quản trị DB (RDBMS) sẽ tự động gộp hàng triệu khóa dòng này thành một khóa bảng duy nhất (`Table Lock`) để tiết kiệm RAM. 
* Khi bảng bị khóa Exclusive Lock, mọi câu lệnh `INSERT`, `UPDATE` của khách hàng gọi tới bảng đó đều phải xếp hàng chờ đợi, gây tràn Connection Pool và sập API Gateway.

### 2. Tràn bộ đệm Transaction Log (Log Buffer / WAL / Binlog)
Một transaction cập nhật hàng triệu bản ghi cùng lúc sẽ ghi đè dung lượng ghi của file Transaction Log (Write-Ahead Log - WAL trong Postgres hoặc Binlog trong MySQL) vượt quá giới hạn đĩa cứng, gây treo toàn bộ cụm Database chính và làm trễ quá trình nhân bản sang Database Replica (Replication Lag tăng vọt lên hàng giờ).

## 💻 Code thực chiến: Safe Backfill Script sử dụng Java JDBC & Python

### 1. Bản thiết kế DB lưu vết tiến trình Backfill (Checkpoint Table)
Bắt buộc phải có một bảng để ghi nhận trạng thái chạy phòng trường hợp mất điện, rớt mạng giữa chừng:
```sql
CREATE TABLE backfill_progress (
    job_name VARCHAR(100) PRIMARY KEY,
    last_processed_id BIGINT NOT NULL,
    total_processed BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL, -- RUNNING, COMPLETED, FAILED
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

### 2. Code Java Spring Boot sử dụng JDBC thuần (Bypass hoàn toàn Hibernate Listeners)

Đoạn code dưới đây sử dụng `JdbcTemplate` chạy SQL thuần để vá dữ liệu cuốn chiếu, kiểm soát tốc độ ghi bằng Sleep để DB không bị quá tải:

```java
package com.example.backfill;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
@Slf4j
public class SafeBackfillService {

    private final JdbcTemplate jdbcTemplate;
    private static final String JOB_NAME = "backfill_user_referral_code";
    private static final int BATCH_SIZE = 1000; // Khối lượng cập nhật an toàn
    private static final long THROTTLE_MS = 100; // Thời gian nghỉ giữa các Batch

    public void runSafeBackfill(boolean dryRun) {
        log.info("Starting safe backfill job. Dry-run mode: {}", dryRun);

        // 1. Đọc checkpoint gần nhất để chạy tiếp nếu bị ngắt quãng
        Long lastProcessedId = getOrCreateCheckpoint();
        log.info("Starting backfill from ID: {}", lastProcessedId);

        // Tìm Max ID hiện tại trong DB để làm điểm dừng
        Long maxId = jdbcTemplate.queryForObject("SELECT MAX(id) FROM users", Long.class);
        if (maxId == null || lastProcessedId >= maxId) {
            log.info("No records to backfill.");
            return;
        }

        long currentId = lastProcessedId;
        long totalProcessed = 0;

        while (currentId < maxId) {
            long nextId = currentId + BATCH_SIZE;

            if (dryRun) {
                log.info("[DRY RUN] Would update users in range ID {} to {}", currentId + 1, nextId);
                currentId = nextId;
                continue;
            }

            // 2. Thực thi update cuốn chiếu trực tiếp bằng SQL thuần (Không sinh Event JPA)
            // Chỉ cập nhật các bản ghi chưa có giá trị để đảm bảo Idempotent
            String updateSql = "UPDATE users SET referral_code = 'DEFAULT_VIP' " +
                               "WHERE id > ? AND id <= ? AND referral_code IS NULL";
            
            long startTime = System.currentTimeMillis();
            int rowsUpdated = jdbcTemplate.update(updateSql, currentId, nextId);
            long duration = System.currentTimeMillis() - startTime;

            totalProcessed += rowsUpdated;
            currentId = nextId;

            // 3. Cập nhật checkpoint vào DB
            updateCheckpoint(currentId, totalProcessed);

            log.info("Updated ID range {} to {}. Rows affected: {}. Duration: {}ms", 
                    currentId - BATCH_SIZE + 1, currentId, rowsUpdated, duration);

            // 4. Throttling - Cho DB nghỉ để xử lý các request thực tế của người dùng
            try {
                Thread.sleep(THROTTLE_MS);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                log.error("Backfill job was interrupted!", e);
                updateJobStatus("FAILED");
                return;
            }
        }

        updateJobStatus("COMPLETED");
        log.info("Backfill job finished successfully. Total rows updated: {}", totalProcessed);
    }

    private Long getOrCreateCheckpoint() {
        String selectSql = "SELECT last_processed_id FROM backfill_progress WHERE job_name = ?";
        try {
            return jdbcTemplate.queryForObject(selectSql, Long.class, JOB_NAME);
        } catch (Exception e) {
            jdbcTemplate.update("INSERT INTO backfill_progress (job_name, last_processed_id, total_processed, status) VALUES (?, 0, 0, 'RUNNING')", JOB_NAME);
            return 0L;
        }
    }

    private void updateCheckpoint(long lastId, long total) {
        String updateSql = "UPDATE backfill_progress SET last_processed_id = ?, total_processed = ? WHERE job_name = ?";
        jdbcTemplate.update(updateSql, lastId, total, JOB_NAME);
    }

    private void updateJobStatus(String status) {
        jdbcTemplate.update("UPDATE backfill_progress SET status = ? WHERE job_name = ?", status, JOB_NAME);
    }
}
```

## 📊 Bảng so sánh các Chiến lược Backfill Dữ liệu

| Tiêu chí | Phương án 1: Câu SQL đơn khối (Big Transaction) | Phương án 2: Script cuốn chiếu (Safe Batching - Khuyên dùng) | Phương án 3: Chạy Offline (Downtime/Maintenance Window) |
| :--- | :--- | :--- | :--- |
| **Ảnh hưởng hệ thống** | **Cực kỳ nguy hiểm** (Chắc chắn nghẽn DB và treo ứng dụng). | **Không đáng kể** (DB vẫn chạy mượt mà nhờ cơ chế nghỉ throttling). | An toàn (Không có người dùng thật sử dụng hệ thống). |
| **Thời gian chạy** | Nhanh nhất (Tận dụng tối đa tốc độ ghi luồng của DB). | Chậm (Tốn thời gian do các khoảng nghỉ chủ động giữa các batch). | Nhanh trung bình. |
| **Khả năng khôi phục (Resume)** | Kém (Nếu fail giữa chừng sẽ bị rollback toàn bộ, tốn tài nguyên và thời gian chạy lại). | **Hoàn hảo** (Chạy tiếp chính xác từ ID bị lỗi nhờ Checkpoint Table). | Kém. |
| **Chi phí triển khai** | Siêu rẻ | Trung bình (Cần viết script cẩn thận). | Rất đắt (Gây mất doanh thu do phải treo hệ thống bảo trì). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Lỗ hổng ID không liên tục khi dùng phân trang OFFSET" (The Offset Gotcha)
* **Vấn đề cực kỳ nguy hiểm**: Nhiều dev viết script chia lô bằng cách sử dụng phân trang `LIMIT 1000 OFFSET 2000`. 
  * Khi script đang chạy cập nhật trạng thái đơn hàng từ `PENDING` sang `COMPLETED`. 
  * Cứ mỗi lần cập nhật thành công, số lượng bản ghi `PENDING` sẽ bị giảm đi. 
  * Việc này làm dịch chuyển toàn bộ chỉ mục phân trang phía sau, khiến phân trang `OFFSET` **bỏ sót hàng ngàn bản ghi** hoặc xử lý trùng lặp một bản ghi nhiều lần.
* **Giải pháp khắc phục**:
  * Tuyệt đối không dùng `OFFSET` để backfill dữ liệu. Bắt buộc dùng phân trang bằng con trỏ định danh **(Cursor-based Pagination)** dựa trên ID tăng dần: `WHERE id > last_processed_id ORDER BY id ASC LIMIT 1000`. Con trỏ ID luôn cố định vật lý và không bị ảnh hưởng bởi sự thay đổi trạng thái của bản ghi.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Tôi muốn thêm một cột mới có ràng buộc `NOT NULL` và giá trị mặc định là chuỗi rỗng vào bảng chứa 100 triệu dòng đang chạy thực tế. Bạn thực thi câu lệnh SQL như thế nào để không làm sập DB?"**
* **Trả lời**:
  * Trong các DB cũ (như MySQL < 8.0 hay Postgres < 11), chạy lệnh `ALTER TABLE ADD COLUMN NOT NULL DEFAULT ''` sẽ khóa cứng bảng để quét toàn bộ 100 triệu dòng ghi đè giá trị rỗng lên đĩa cứng.
  * Senior sẽ thực hiện chiến lược **3 Bước Rollout an toàn**:
    1. **Bước 1**: Tạo cột mới cho phép `NULL` (Non-blocking): `ALTER TABLE users ADD COLUMN new_col VARCHAR(255) NULL;` (Lệnh này chạy tức thì vì DB chỉ cập nhật schema metadata).
    2. **Bước 2**: Viết script Backfill cuốn chiếu để cập nhật giá trị mặc định cho toàn bộ 100 triệu dòng cũ theo từng đợt ID.
    3. **Bước 3**: Sau khi toàn bộ dữ liệu cũ đã được điền đầy đủ giá trị mặc định, tiến hành sửa schema thêm ràng buộc cứng:
       `ALTER TABLE users ALTER COLUMN new_col SET NOT NULL;` (Chạy rất nhanh vì DB không cần quét đĩa để điền giá trị rỗng nữa).
