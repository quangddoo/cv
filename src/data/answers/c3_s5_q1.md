# Review Project Cũ — Checklist Toàn diện

## ⚡ Tóm tắt ngắn (30s)
* **Mục tiêu**: chuẩn bị 2-3 project gần nhất để walkthrough trong phỏng vấn.
* **Per project review checklist**:
  1. **Architecture**: vẽ diagram, biết mọi component.
  2. **Bottleneck**: identify slowest part, why.
  3. **Database schema**: key tables, indexes, why.
  4. **Transaction boundary**: where, why.
  5. **Cache layer**: what cached, why, TTL.
  6. **Async flow**: queue, retry, dead-letter.
  7. **Monitoring**: metrics, alerts, dashboards.
* **Goal**: 5-10 min walkthrough fluent, answer follow-ups.

---

## 🔍 Per-project checklist (Markdown template)

```markdown
# Project: [Name]

## Context
- Company, role, team size, duration.
- Business problem.

## Architecture
- High-level diagram (services, DB, cache, queue).
- Tech stack: language, framework, DB, infra.
- Scale: QPS, data volume, users.

## My Contribution
- Specific feature/module YOU built.
- Key decisions YOU made.

## Database
- Main tables (5-10 key).
- Indexing strategy.
- Partitioning if any.
- Replica setup.

## Transactions
- Service boundary.
- Tx isolation level.
- Why this choice.

## Cache
- What cached (key, value).
- TTL.
- Invalidation strategy.

## Async/Queue
- Kafka topics.
- Retry strategy.
- Dead-letter handling.

## Monitoring
- Key metrics tracked.
- Alerts set up.
- Dashboards used.

## Failures Handled
- Production incidents.
- Recovery process.

## Trade-offs
- Decisions you made + alternatives.

## Outcomes
- Metrics (perf, cost, revenue).

## Lessons
- What you'd do differently.
```

## 💻 Example skeleton (no real data, you fill in)

```markdown
# Project: Order Management System Refactor

## Context
At ABC E-commerce, 2023, Tech Lead, team 6, 8 months.
Legacy monolith → microservices for order flow.

## Architecture
[diagram: 
  API Gateway → Order Service → Inventory Service
                    ↓
                  Kafka (order.created, order.updated)
                    ↓
                  Payment Service, Shipping Service, Notification
]

## My Contribution
- Designed event-driven architecture.
- Migrated payment integration to Saga pattern.
- Set up observability stack.

## Database
- orders (PK, status, customer_id, created_at).
  - Index on (customer_id, created_at) for "my orders" query.
- order_items (FK order_id, product_id, quantity).

## Transactions
- Single tx per service.
- Cross-service: Saga (Temporal).
- Compensations: refund, restock.

## Cache (Redis)
- "popular products" - 5 min TTL.
- Cart - 24h TTL.
- Order status - 1 min TTL.
- Invalidate on order update event.

## Async
- Kafka topics: order.created, order.shipped, order.cancelled.
- Consumer group per service.
- Retry: 3 attempts exponential.
- DLQ for manual review.

## Monitoring
- Datadog: p99 latency per endpoint, error rate.
- Alerts: order.created lag > 5 min.

## Incident handled
- Black Friday Q4 2023: payment service overload.
- Root cause: no rate limit on retries.
- Fix: token bucket + circuit breaker.

## Trade-offs
- Saga vs 2PC: chose Saga for autonomy + compensability.
- Kafka vs RabbitMQ: Kafka for retention + replay.

## Outcomes
- p99 latency: 800ms → 200ms.
- 99.9% availability.
- Saved $40k/year ops.

## Lessons
- Should have invested in eventual consistency education team-wide earlier.
- Need better integration test for Saga.
```

## ⚠️ Common Mistakes & Pro Tips

1. **"We used Spring Boot"**: too generic. Specific decisions matter.
2. **No numbers**: "improved performance" weak. "p99 1s → 200ms" strong.
3. **Group success**: highlight YOUR contribution.
4. **Forgot details**: review notes/PRs/diagrams.
5. **Out-of-date**: skills from years ago — refresh latest version.
6. **Can't justify**: be ready for "Why X not Y?" follow-up.
