# Database Isolation Levels trong Spring Boot: Thực chiến & Bản chất

## ⚡ Tóm tắt ngắn (30s)
**Database Isolation Level (Mức độ cô lập giao dịch)** quy định cách các giao dịch chạy song song (concurrent transactions) nhìn thấy dữ liệu của nhau. Spring Boot cho phép thiết lập thông qua thuộc tính `isolation` trong `@Transactional`.
Có 4 mức cô lập tiêu chuẩn định nghĩa bởi chuẩn SQL (từ thấp đến cao):
1. **`READ_UNCOMMITTED`**: Nhìn thấy dữ liệu chưa commit của transaction khác. (Cực nhanh nhưng cực kỳ nguy hiểm).
2. **`READ_COMMITTED`**: Chỉ nhìn thấy dữ liệu đã được commit. Tránh được *Dirty Read*. Đây là mặc định của hầu hết DB (PostgreSQL, Oracle, SQL Server).
3. **`REPEATABLE_READ`**: Đảm bảo đọc một dòng dữ liệu nhiều lần trong cùng transaction luôn ra kết quả giống nhau. Tránh được *Non-repeatable Read*. Đây là mặc định của MySQL (InnoDB).
4. **`SERIALIZABLE`**: Các transaction chạy tuần tự. Tránh được tất cả hiện tượng bất thường kể cả *Phantom Read*. (Hiệu năng cực kỳ kém).

## 🔍 Chi tiết bản chất thực chiến

### 1. Bảng đối chiếu hiện tượng bất thường (Anomalies) và Isolation Levels

| Isolation Level | Dirty Read | Non-repeatable Read | Phantom Read | Hiệu năng hệ thống |
| :--- | :---: | :---: | :---: | :---: |
| **`READ_UNCOMMITTED`** | ❌ Bị ảnh hưởng | ❌ Bị ảnh hưởng | ❌ Bị ảnh hưởng | 🚀 Cao nhất |
| **`READ_COMMITTED`** | ✅ Khắc phục | ❌ Bị ảnh hưởng | ❌ Bị ảnh hưởng | 📊 Tốt/Mặc định |
| **`REPEATABLE_READ`** | ✅ Khắc phục | ✅ Khắc phục | ❌ Bị ảnh hưởng (tùy DB)* | 📉 Thấp |
| **`SERIALIZABLE`** | ✅ Khắc phục | ✅ Khắc phục | ✅ Khắc phục | 🐌 Thấp nhất |

> 📌 *Lưu ý thực chiến*: InnoDB của MySQL ở mức `REPEATABLE_READ` sử dụng cơ chế **MVCC** (Multi-Version Concurrency Control) và **Next-Key Lock** để giải quyết hầu hết các trường hợp *Phantom Read* mà không cần nâng lên `SERIALIZABLE`.

### 2. Giải nghĩa 3 hiện tượng bất thường kinh điển
*   **Dirty Read**: Transaction A sửa đổi một dòng dữ liệu nhưng chưa commit. Transaction B vào đọc dòng đó và lấy ra giá trị mới này. Sau đó Transaction A bị lỗi và `ROLLBACK`. Dữ liệu Transaction B vừa dùng là dữ liệu rác (chưa từng tồn tại chính thức).
*   **Non-repeatable Read**: Transaction A đọc một dòng dữ liệu. Transaction B vào cập nhật (`UPDATE`) hoặc xóa (`DELETE`) dòng đó và `COMMIT`. Transaction A đọc lại dòng đó lần nữa và thấy dữ liệu đã bị thay đổi hoặc biến mất.
*   **Phantom Read**: Transaction A thực hiện câu lệnh query lấy ra một tập hợp các dòng thỏa mãn điều kiện (ví dụ: `WHERE age > 18`). Transaction B thực hiện thêm mới (`INSERT`) một dòng thỏa mãn điều kiện đó và `COMMIT`. Transaction A query lại câu lệnh đó lần nữa và thấy xuất hiện thêm các dòng mới (bóng ma - phantom).

### 3. Cách hoạt động dưới mui xe của Spring `@Transactional(isolation = ...)`
Khi bạn khai báo mức cô lập trong Spring:
1. Spring AOP Proxy chặn lời gọi phương thức.
2. Nó lấy một Connection từ `DataSource`.
3. Spring sẽ gọi trực tiếp xuống JDBC Connection Driver: `connection.setTransactionIsolation(Connection.TRANSACTION_...)`.
4. Khi kết thúc transaction, Spring sẽ khôi phục lại mức cô lập mặc định của Connection pool để tránh ảnh hưởng đến các luồng khác sử dụng lại Connection này.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Dùng mặc định (READ_COMMITTED) cho tác vụ tổng hợp báo cáo tài chính tài khoản
Khi cần tính tổng số dư của toàn hệ thống để lập báo cáo, nếu dùng mức cô lập mặc định, các giao dịch chuyển tiền song song của người dùng có thể làm sai lệch hoàn toàn báo cáo cuối cùng (do hiện tượng Non-repeatable Read/Phantom Read).

```java
package com.example.service;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class ReportingServiceBad {

    private final AccountRepository accountRepository;

    public ReportingServiceBad(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    // ❌ Mặc định là READ_COMMITTED
    @Transactional(readOnly = true)
    public double generateFinancialReport() {
        // Bước 1: Lấy tổng số dư nhóm A
        double groupABalance = accountRepository.sumBalanceByGroup("A"); // Giả sử ra 100,000$

        // ⚠️ Giữa lúc này, một Transaction khác thực hiện chuyển tiền từ nhóm B sang nhóm A và COMMIT thành công.

        // Bước 2: Lấy tổng số dư nhóm B
        double groupBBalance = accountRepository.sumBalanceByGroup("B"); // Số dư nhóm B bị hụt đi nhưng bước 1 đã chạy xong

        // Hậu quả: Báo cáo tài chính bị mất cân đối dòng tiền do dữ liệu thay đổi giữa các câu query!
        return groupABalance + groupBBalance;
    }
}
```

### ✅ GOOD: Sử dụng REPEATABLE_READ và xử lý lỗi xung đột giao dịch chủ động
Để đảm bảo tính nhất quán của dữ liệu báo cáo, chúng ta nâng mức cô lập lên `REPEATABLE_READ`. Mọi dữ liệu đã đọc trong transaction sẽ được đóng băng trạng thái (snapshot-isolated) cho tới khi kết thúc.

```java
package com.example.service;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.dao.TransientDataAccessException;
import lombok.extern.slf4j.Slf4j;

@Slf4j
@Service
public class ReportingServiceGood {

    private final AccountRepository accountRepository;

    public ReportingServiceGood(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    // ✅ Nâng mức cô lập lên REPEATABLE_READ để đóng băng snapshot dữ liệu đọc được
    @Transactional(isolation = Isolation.REPEATABLE_READ, readOnly = true)
    public double generateFinancialReportWithRetry() {
        try {
            double groupABalance = accountRepository.sumBalanceByGroup("A");
            
            // ✅ Dù các transaction khác có cập nhật dữ liệu nhóm B hay nhóm A lúc này,
            // Database vẫn trả về snapshot nhất quán tại thời điểm transaction bắt đầu.
            double groupBBalance = accountRepository.sumBalanceByGroup("B");
            
            return groupABalance + groupBBalance;
        } catch (TransientDataAccessException e) {
            // ⚠️ Khi dùng mức cô lập cao, khả năng xảy ra lỗi lock tranh chấp (serialization error) cao hơn.
            // Phải catch các lỗi mang tính tạm thời (transient) và thực hiện cơ chế Retry.
            log.warn("Database lock/serialization conflict detected. Triggering retry flow...");
            throw e;
        }
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Spring Isolation.DEFAULT thực sự là gì?
Khi chọn `Isolation.DEFAULT` (mặc định), Spring sẽ tôn trọng và sử dụng mức cô lập được cấu hình sẵn của **Database vật lý bên dưới**:
*   Nếu dùng **MySQL (InnoDB)**: Mức mặc định sẽ là `REPEATABLE_READ`.
*   Nếu dùng **PostgreSQL, Oracle, SQL Server**: Mức mặc định sẽ là `READ_COMMITTED`.
*   *Lưu ý thực chiến*: Nếu dự án của bạn chuyển đổi cơ sở dữ liệu (ví dụ từ MySQL sang PostgreSQL) mà dựa hoàn toàn vào `DEFAULT`, hành vi của ứng dụng có thể bị thay đổi âm thầm mà bạn không hề hay biết!

### 2. Sự đánh đổi cực kỳ lớn về Hiệu năng (Performance Trade-off)
Tại sao không đặt mặc định hệ thống là `SERIALIZABLE` để đảm bảo an toàn tuyệt đối?
*   **Chi phí khóa (Lock Overhead)**: Để đạt được mức cô lập cao, Database phải sử dụng các khóa chia sẻ (Shared Locks), khóa độc quyền (Exclusive Locks), khóa dải (Range Locks) hoặc giữ nhiều phiên bản dữ liệu (MVCC overhead).
*   **Tranh chấp tài nguyên (Resource Contention)**: Các transaction sẽ phải xếp hàng đợi nhau giải phóng khóa. Điều này làm giảm dratic băng thông xử lý (throughput) của hệ thống và gây ra hàng loạt lỗi `Deadlock` hoặc `Connection Timeout` dưới tải cao.
*   *Lời khuyên thực chiến*: Luôn giữ mức mặc định là `READ_COMMITTED` hoặc `REPEATABLE_READ` cho 99% tác vụ nghiệp vụ. Đối với các tài nguyên nhạy cảm (như số dư ví, số lượng hàng tồn kho), hãy sử dụng **Optimistic Locking (`@Version`)** hoặc **Pessimistic Locking (`SELECT FOR UPDATE`)** thay vì nâng Isolation Level của toàn bộ Transaction lên cao.
