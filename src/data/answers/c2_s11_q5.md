# Có duplicate record trong bảng đáng lẽ unique. Vì sao?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Hiện tượng trùng lặp bản ghi trên trường đáng lẽ phải duy nhất (như trùng email user, trùng mã giao dịch order) là lỗi **Vỡ tính toàn vẹn dữ liệu (Data Integrity Violation)**. Nguyên nhân gốc rễ là do hệ thống áp dụng cơ chế phòng vệ lỏng lẻo ở tầng ứng dụng (kiểm tra bằng code) mà **bỏ quên ràng buộc vật lý ở tầng Database (Unique Constraint/Index)**, dẫn đến việc bị vượt qua bởi các điều kiện chạy đua song song (Race Conditions) hoặc cơ chế retry mạng (At-least-once delivery).
* **Thảm họa thực chiến được giải quyết**:
  1. **Lỗi đăng ký trùng email (Duplicate Registration)**: User click liên tục nút "Đăng ký" do mạng lag. Hai request gửi song song. Tầng ứng dụng chạy luồng đọc: `SELECT WHERE email = 'a@test.com'` thấy chưa tồn tại ở cả 2 luồng. Sau đó cả 2 luồng cùng thực hiện `INSERT`. Hệ thống tạo ra 2 user chung 1 email. Khi user đăng nhập lại, hàm `findByEmail()` của Spring Data JPA ném ra ngoại lệ `NonUniqueResultException` làm sập API.
  2. **Thảm họa thanh toán trùng (Double Charge)**: API thanh toán bị gọi trùng do client retry. Hệ thống chèn 2 bản ghi giao dịch có cùng một `transaction_code`, trực tiếp trừ tiền của khách hàng hai lần.
* **Quyết định Senior**:
  1. **Tuyệt đối tin tưởng Database Unique Constraint**: Tầng ứng dụng có thể scale ngang thành hàng trăm instances, nhưng Database chỉ có một nguồn ghi duy nhất. Bắt buộc tạo `UNIQUE INDEX` vật lý tại DB.
  2. **Cấu hình Unique Index thông minh với Soft-delete**: Kết hợp trường `is_deleted` hoặc `deleted_at` vào Unique Index để cho phép đăng ký lại email sau khi đã xóa tài khoản cũ.
  3. **Idempotency Key & Distributed Lock**: Áp dụng cơ chế khóa phân tán Redis (Redlock) hoặc Idempotency filter ở API Gateway để chặn đứng các request trùng lặp ngay từ cửa ngõ.

## 🔍 Chi tiết bản chất thực chiến: Tại sao xảy ra & Kịch bản thực tế

### 1. Tại sao kiểm tra bằng code (Read-then-Write) luôn thất bại?

Rất nhiều dev viết code theo dạng:
```java
if (!userService.existsByEmail(email)) {
    userRepository.save(new User(email));
}
```
Mã nguồn này chỉ hoạt động đúng trong môi trường đơn luồng (Single-thread). Trong môi trường sản xuất đa luồng, đa máy chủ (Distributed System), kịch bản sau sẽ phá hủy logic trên:

```
Request A (Luồng 1)                               Request B (Luồng 2)
┌─────────────────────────────────┐               ┌──────────────────────────────────┐
│ 1. Đọc DB: SELECT email = 'x'   │               │                                  │
│    -> Kết quả: Không tồn tại.   │               │                                  │
│                                 │               │ 2. Đọc DB: SELECT email = 'x'    │
│                                 │               │    -> Kết quả: Không tồn tại.    │
│ 3. INSERT user 'x' vào DB       │               │                                  │
│    (Thành công ✔)               │               │                                  │
│                                 │               │ 4. INSERT user 'x' vào DB        │
│                                 │               │    (Thành công ✔ - Do thiếu      │
│                                 │               │     Unique Constraint vật lý!)   │
└─────────────────────────────────┘               └──────────────────────────────────┘
=> HỆ QUẢ: Hai bản ghi trùng lặp email tồn tại song song trong Database.
```

### 2. Tác nhân do Retry Network (At-least-once Delivery)
* **Kịch bản**: Client gửi request tạo order. DB chèn thành công. Nhưng trên đường phản hồi về, mạng bị đứt (Timeout). Client nghĩ request thất bại, tự động gửi lại request thứ 2 kèm payload cũ.
* Do hệ thống không sử dụng **Idempotency Key** để nhận diện request cũ, DB chèn tiếp bản ghi thứ hai với dữ liệu tương đồng, gây ra lỗi trùng lặp.

## 🎨 Sơ đồ trực quan: Giải pháp Idempotency Key & Unique Index bảo vệ DB

Mô hình thiết kế 2 tầng bảo vệ chống trùng lặp dữ liệu tuyệt đối:

```
[Client Request]
       │
       ▼
┌───────────────────────────────────────────────┐
│ TẦNG 1: API GATEWAY / DISTRIBUTED LOCK        │
│ - Kiểm tra Idempotency Key trong Redis.       │
│ - Nếu Key đang xử lý -> Trả ngay HTTP 409 ❌   │
└───────────────────────────────────────────────┘
       │
       ▼ (Pass tầng 1)
┌───────────────────────────────────────────────┐
│ TẦNG 2: BACKEND APPLICATION                   │
│ - Thực hiện nghiệp vụ chèn dữ liệu.           │
└───────────────────────────────────────────────┘
       │
       ▼
┌───────────────────────────────────────────────┐
│ LA CHẮN CUỐI: DATABASE UNIQUE INDEX           │
│ - Thực thi kiểm tra mức vật lý ổ đĩa.          │
│ - Nếu trùng -> Trả lỗi DuplicateKeyException  │
│ - Cuộn ngược (Rollback) Transaction an toàn.  │
└───────────────────────────────────────────────┘
```

## 💻 Code thực chiến: SQL dọn dẹp dữ liệu trùng & Code Java bắt Exception an toàn

### 1. Script SQL Truy tìm và Dọn dẹp dữ liệu trùng lặp trên Production (Safe Deduplication)

Nếu DB đã lỡ bị trùng lặp dữ liệu và bạn muốn tạo `UNIQUE INDEX`, trước tiên bạn phải dọn sạch các bản ghi trùng lặp. Script dưới đây sử dụng Window Function `ROW_NUMBER()` để tìm và xóa các bản ghi trùng email, chỉ giữ lại bản ghi đầu tiên được tạo (`id` nhỏ nhất).

```sql
-- BƯỚC 1: Tìm kiếm các nhóm dữ liệu bị trùng lặp để kiểm tra mức độ ảnh hưởng
SELECT email, COUNT(*), MIN(id) as keep_id
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

-- BƯỚC 2: Viết câu lệnh xóa an toàn sử dụng CTE (Dành cho PostgreSQL / MySQL 8.0+)
WITH duplicate_records AS (
    SELECT 
        id,
        ROW_NUMBER() OVER (
            PARTITION BY email 
            ORDER BY created_at ASC, id ASC
        ) as row_num
    FROM users
)
-- Xóa toàn bộ các bản ghi trùng lặp, chỉ giữ lại bản ghi có row_num = 1
DELETE FROM users 
WHERE id IN (
    SELECT id 
    FROM duplicate_records 
    WHERE row_num > 1
);
```

### 2. Thiết lập Ràng buộc vật lý (Unique Constraint)
Sau khi dọn dẹp sạch dữ liệu trùng, ngay lập tức bổ sung Unique Index để khóa chặt lỗ hổng:
```sql
ALTER TABLE users ADD CONSTRAINT uq_user_email UNIQUE (email);
```

### 3. Code Java Spring Boot xử lý ngoại lệ trùng lặp dữ liệu một cách mượt mà

Khi DB có Unique Constraint, khi chèn trùng DB sẽ ném lỗi. Tầng Backend phải bắt lỗi này để trả về HTTP Status phù hợp cho Client thay vì ném lỗi `500 Internal Server Error` xấu xí.

```java
package com.example.exception;

import lombok.extern.slf4j.Slf4j;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ControllerAdvice;
import org.springframework.web.bind.annotation.ExceptionHandler;

import java.util.HashMap;
import java.util.Map;

@ControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    // Bắt lỗi vi phạm ràng buộc dữ liệu từ Spring Data JPA / Hibernate
    @ExceptionHandler(DataIntegrityViolationException.class)
    public ResponseEntity<Map<String, Object>> handleDataIntegrityViolation(DataIntegrityViolationException ex) {
        log.error("Data integrity violation occurred. Possible duplicate key error.", ex);
        
        Map<String, Object> response = new HashMap<>();
        response.clear();
        response.put("status", HttpStatus.CONFLICT.value());
        response.put("error", "Conflict");
        
        // Phân tích kỹ exception message để trả ra câu thông báo thân thiện
        String rootMsg = ex.getRootCause() != null ? ex.getRootCause().getMessage() : "";
        if (rootMsg.contains("uq_user_email") || rootMsg.toLowerCase().contains("duplicate entry")) {
            response.put("message", "Email address is already registered. Please use another one.");
        } else {
            response.put("message", "Database constraint violation. Duplicate resource detected.");
        }
        
        return new ResponseEntity<>(response, HttpStatus.CONFLICT);
    }
}
```

| Tiêu chí | Phương án 1: Check bằng Code (existsByEmail) | Phương án 2: Khóa phân tán (Redis Distributed Lock) | Phương án 3: DB Unique Constraint vật lý |
| :--- | :--- | :--- | :--- |
| **Độ tin cậy** | **Rất kém** (Vô dụng hoàn toàn khi có concurrency request). | **Rất cao** (Chặn đứng từ tầng bộ nhớ đệm trước khi xuống DB). | **Tuyệt đối 100%** (Lá chắn cuối cùng không thể bị vượt qua). |
| **Hiệu năng hệ thống** | Tốt (Chỉ chạy câu lệnh SELECT nhanh). | Ảnh hưởng nhẹ (Phải thực hiện thêm 1 chặng gọi sang Redis lấy lock). | Rất tốt (Unique Index giúp tăng tốc độ tìm kiếm `SELECT` đáng kể). |
| **Trải nghiệm người dùng (UX)** | Trả lỗi chậm khi chèn sâu xuống DB. | Phản hồi siêu nhanh ngay từ tầng API Gateway (HTTP 429/409). | Trả lỗi mượt mà thông qua cơ chế bắt Exception (HTTP 409). |
| **Chi phí triển khai** | Siêu rẻ. | Trung bình (Cần hạ tầng Redis). | Miễn phí (Tính năng cơ bản của mọi RDBMS). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Xung đột giữa Unique Index và cơ chế Soft-delete"
* **Vấn đề nguy hiểm**: Khi bạn sử dụng cờ xóa mềm `is_deleted` kiểu boolean.
  * Lần 1: User đăng ký email `a@test.com` -> Thành công (id = 1, `is_deleted = false`).
  * Lần 2: User xóa tài khoản -> Cập nhật `is_deleted = true`.
  * Lần 3: User muốn đăng ký lại bằng email `a@test.com` -> **Thất bại!** Vì Unique Index trên cột `email` báo lỗi trùng lặp với bản ghi đã xóa mềm trước đó.
* **Giải pháp khắc phục**:
  1. **PostgreSQL (Partial Index)**: Tạo index có điều kiện lọc chỉ áp dụng unique trên các bản ghi chưa xóa:
     ```sql
     CREATE UNIQUE INDEX uq_active_user_email ON users (email) WHERE is_deleted = false;
     ```
  2. **MySQL / Oracle (Composite Key)**: Chuyển cờ xóa mềm thành kiểu ngày giờ `deleted_at` (mặc định là `NULL` khi chưa xóa). Tạo Unique Index trên cả 2 trường: `UNIQUE(email, deleted_at)`. Do chuẩn SQL coi các giá trị `NULL` là độc lập và không trùng nhau, bạn có thể có vô số bản ghi có cùng email nhưng `deleted_at` là `NULL` (Gotchas: Chỉ đúng trên PostgreSQL/MySQL, còn Oracle coi các `NULL` trùng nhau nên ta cần gán giá trị mặc định cho `deleted_at` là `0` thay vì `NULL`).

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Tôi có một bảng khổng lồ chứa 500 triệu dòng đang chạy trên Production không có Unique Index và hiện tại đang phát hiện có hàng ngàn bản ghi bị trùng. Bây giờ tôi muốn thêm ràng buộc UNIQUE vật lý mà không gây khóa bảng (Locking) làm gián đoạn hệ thống. Bạn xử lý thế nào?"**
* **Trả lời**:
  * Chạy lệnh `ALTER TABLE ADD CONSTRAINT UNIQUE` trực tiếp trên bảng 500 triệu dòng sẽ kích hoạt **Exclusive Table Lock (Access Exclusive Lock)** quét toàn bộ bảng, gây treo hệ thống (Downtime) và ném lỗi timeout.
  * Chiến lược xử lý của Senior:
    1. **Tạo Index bất đồng bộ (Concurrent Index Creation)**:
       * Trong PostgreSQL: Sử dụng cú pháp `CREATE UNIQUE INDEX CONCURRENTLY idx_users_email ON users(email);`
       * Lệnh này sẽ quét bảng 2 lần mà không giữ lock ghi (Non-blocking). Quá trình ghi mới của người dùng vẫn diễn ra bình thường.
    2. **Xử lý bản ghi trùng phát sinh**: Trong quá trình build index concurrent, nếu phát hiện bản ghi trùng, lệnh build sẽ fail. Ta chạy script dọn dẹp trùng lặp cuốn chiếu (Deduplication Script) bằng cách chia nhỏ theo các khối ID (Batching) để tránh khóa bảng, sau đó chạy lại lệnh build.
    3. **Liên kết Index vào Constraint**: Sau khi Index Concurrent được tạo thành công, ta liên kết nó làm khóa chính thức:
       `ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE USING INDEX idx_users_email;`
