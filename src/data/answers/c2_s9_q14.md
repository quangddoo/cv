# Load balancer vẫn route traffic vào instance unhealthy. Vì sao?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Hiện tượng Load Balancer (Nginx, AWS ALB, Kubernetes Ingress) tiếp tục định tuyến traffic vào một instance đang lỗi là do sự lệch pha giữa **Tiêu chí đánh giá sức khỏe (Health Check Criteria)** và **Tình trạng thực tế của ứng dụng**. Lỗi này được gọi là **Lỗi bán phần (Gray Failure)** - instance vẫn "sống" ở tầng vật lý/TCP nhưng đã "chết" ở tầng nghiệp vụ/Database.
* **Thảm họa thực chiến được giải quyết**:
  1. **Lỗi 5xx chập chờn khó debug (Intermittent 500 Errors)**: Một instance bị nghẽn hoàn toàn kết nối Database (Database Connection Pool exhausted) hoặc bị khóa luồng (Thread Deadlock). Nó không thể xử lý bất kỳ request nào. Tuy nhiên, do cấu hình health check sơ sài (chỉ ping TCP port 8080), Load Balancer thấy port vẫn mở nên coi là `HEALTHY` và tiếp tục ném request của khách hàng vào đó, gây lỗi 500 chập chờn cho 25% người dùng.
  2. **Thảm họa vòng lặp khởi động lại (Restart Loop)**: Lọc lỗi quá đà khiến liveness probe bị fail khi database của bên thứ ba bị sập. Kubernetes lập tức restart pod liên tục, làm nghẽn luôn cả các tác vụ không cần DB.
* **Quyết định Senior**:
  1. **Phân tách rạch ròi Liveness và Readiness Probes**:
     - *Liveness Probe*: Kiểm tra ứng dụng có bị treo cứng (deadlock/OOM) không. Nếu fail -> Khởi động lại Pod.
     - *Readiness Probe*: Kiểm tra ứng dụng đã sẵn sàng nhận traffic chưa (kiểm tra kết nối DB, Redis, Kafka). Nếu fail -> **Tạm thời gạch tên khỏi Load Balancer** để không nhận traffic, nhưng **TUYỆT ĐỐI không restart Pod**.
  2. **Triển khai Deep Health Checking**: Không chỉ check port TCP. Phải trỏ health check vào endpoint `/actuator/health` của Spring Boot Actuator - nơi kiểm tra thực tế kết nối tới DB, Redis trước khi trả về HTTP 200.
  3. **Tuning thông số Probe khôn ngoan**: Cấu hình `periodSeconds = 5` (quét mỗi 5s) và `failureThreshold = 2` (sai 2 lần là gạch tên ngay) để phản ứng nhanh nhất khi sự cố xảy ra.

## 🔍 Chi tiết bản chất thực chiến: Gray Failure & Cơ chế hoạt động của Probe

Hiện tượng Gray Failure (Lỗi xám) xảy ra khi hệ thống đánh giá sức khỏe của Load Balancer quá đơn giản:

```
[Mất kết nối Database] ──> [Port 8080 vẫn mở] ──> [TCP Health Check: PASS! ✅]
                                                               │
                                                               ▼
[User nhận lỗi 500 liên tục] <── [Định tuyến request vào đây] <── [Load Balancer coi là HEALTHY]
```

### 1. Phân biệt Liveness Probe vs Readiness Probe trong Kubernetes
Để xử lý triệt để, Senior bắt buộc phải cấu hình hai loại probe này với hai hành vi hoàn toàn khác nhau:

* **Readiness Probe (Sẵn sàng tiếp nhận)**:
  * *Use case*: Khi ứng dụng của bạn vừa khởi động và đang cần load 1GB dữ liệu cache vào RAM, hoặc khi ứng dụng bị mất kết nối tới Database chính.
  * *Hành động khi fail*: Kubernetes gạch tên Pod này ra khỏi Service endpoint. Load Balancer **ngừng chuyển traffic** vào Pod này. Pod được chuyển sang trạng thái "Không sẵn sàng". Khi DB hoạt động trở lại, Pod tự động nhận traffic bình thường.
* **Liveness Probe (Còn sống vật lý)**:
  * *Use case*: Khi ứng dụng bị tràn bộ nhớ JVM (OOM) hoặc bị deadlock luồng xử lý chính, không phản hồi bất kỳ request nào.
  * *Hành động khi fail*: Kubernetes lập tức **kill Pod và khởi động lại Pod mới**.

## 💻 Code thực chiến: Cấu hình Deep Healthcheck chi tiết với Spring Boot Actuator

Dưới đây là cách cấu hình **Spring Boot Actuator** để phơi bày trạng thái sức khỏe chi tiết (bao gồm cả DB, Redis) phục vụ cho Kubernetes Readiness Probe.

### 1. Cấu hình Actuator trong `application.yml`
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health # ✅ Chỉ expose endpoint health ra ngoài
  endpoint:
    health:
      show-details: when_authorized # Chỉ show chi tiết khi có quyền hoặc tắt khi lên prod
      probes:
        enabled: true # ✅ Kích hoạt sẵn cấu hình liveness và readiness probes tiêu chuẩn của K8s
  health:
    db:
      enabled: true    # ✅ Tự động kiểm tra kết nối Database
    redis:
      enabled: true   # ✅ Tự động kiểm tra kết nối Redis
```
*Khi cấu hình như trên, Spring Boot tự động tạo ra 2 endpoint sạch cho Kubernetes gọi:*
* `/actuator/health/liveness` (Trả về nhanh trạng thái sống của JVM).
* `/actuator/health/readiness` (Trả về trạng thái sẵn sàng, bao gồm check DB + Redis).

### 2. Viết Custom Health Indicator kiểm tra tích hợp với Downstream API
Nếu ứng dụng của bạn bắt buộc phải có một Downstream Service hoạt động thì mới chạy được, hãy viết thêm Custom Health Indicator để tích hợp vào Readiness check:
```java
import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.HealthIndicator;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestTemplate;

@Component("downstreamServiceHealth")
public class DownstreamServiceHealthIndicator implements HealthIndicator {

    private final RestTemplate restTemplate = new RestTemplate();
    private static final String DOWNSTREAM_URL = "http://downstream-service/actuator/health/liveness";

    @Override
    public Health health() {
        try {
            // Gửi request nhanh check xem downstream có sống không
            restTemplate.getForObject(DOWNSTREAM_URL, String.class);
            return Health.up().withDetail("message", "Downstream service hoạt động tốt").build();
        } catch (Exception e) {
            // Trả về DOWN để thông báo service của ta không sẵn sàng nhận traffic
            return Health.down().withDetail("error", "Không thể kết nối tới Downstream service: " + e.getMessage()).build();
        }
    }
}
```

### 3. Cấu hình Deployment YAML trên Kubernetes bảo vệ Service
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: order-service-container
        image: order-service:v2
        ports:
        - containerPort: 8080
        
        # ✅ 1. LIVENESS PROBE: Chỉ kiểm tra jvm sống, cực nhẹ, tránh restart oan
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 30 # Đợi 30s sau khi start mới bắt đầu check
          periodSeconds: 10       # Check mỗi 10s
          
        # ✅ 2. READINESS PROBE: Kiểm tra sâu DB/Redis trước khi cho nhận traffic
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 35
          periodSeconds: 5        # Check khắt khe mỗi 5s
          failureThreshold: 2     # Sai 2 lần liên tiếp (10s) là gạch tên ngay khỏi LB
```

## 📊 Bảng so sánh Liveness Probe và Readiness Probe thực chiến

| Tiêu chí | Liveness Probe (Còn sống) | Readiness Probe (Sẵn sàng) |
| :--- | :--- | :--- |
| **Mục tiêu đánh giá** | Ứng dụng có bị treo cứng, vòng lặp vô hạn, deadlock hay sập JVM không. | Ứng dụng có đủ điều kiện kết nối để xử lý nghiệp vụ (DB, Cache) không. |
| **Hành động khi Thất Bại** | **Restart Pod ngay lập tức**. | **Gạch tên khỏi Load Balancer**, không route traffic vào nữa (Giữ nguyên Pod). |
| **Độ trễ kiểm tra (Period)** | Nên để dài (`10s - 20s`) để giảm tải CPU. | Nên để ngắn (`3s - 5s`) để phản ứng nhanh khi sập DB. |
| **Cạm bẫy cấu hình sai** | Check DB trong Liveness -> DB sập làm toàn bộ Pod bị restart liên tục vĩnh viễn (Thảm họa sập dây chuyền). | Đặt delay khởi động quá ngắn -> Pod chưa kịp start đã bị coi là lỗi. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Cơn bão Khởi động lại Dây chuyền (Cascading Restart Storm)"
* **Vấn đề**: Nhiều lập trình viên cấu hình kiểm tra kết nối Database bên trong **Liveness Probe**. Khi Database chính bị quá tải và chậm phản hồi trong 10 giây. Liveness Probe của cả 50 Pod đồng loạt bị fail. Kubernetes lập tức ra lệnh **khởi động lại (restart) toàn bộ 50 Pod cùng lúc**. Khi các Pod khởi động lại, chúng đồng loạt chạy code khởi tạo, gửi hàng loạt kết nối mới đè bẹp Database đang quá tải, làm hệ thống sập vĩnh viễn không thể hồi phục.
* **Giải pháp khắc phục**: **Tuyệt đối không đưa Database check vào Liveness Probe**. Database check chỉ được phép nằm trong **Readiness Probe**.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Nếu Database bị sập và Readiness Probe gạch tên toàn bộ các Pod của ta ra khỏi Load Balancer. Khi đó, Load Balancer không còn Pod nào để route traffic thì client sẽ nhận được phản hồi gì?**
  * *Trả lời*:
    * Khi 100% Pod bị gạch tên khỏi Service (trạng thái no endpoints), Load Balancer / API Gateway phía trước (như Nginx, Kong, K8s Ingress) sẽ không thể tìm thấy máy chủ đích.
    * Lúc này, Load Balancer sẽ lập tức trả về mã lỗi **HTTP 503 Service Unavailable** hoặc **HTTP 502 Bad Gateway**.
    * Đây là hành vi đúng chuẩn: Trả về lỗi 503 nhanh chóng để client biết hệ thống đang bảo trì/quá tải, còn hơn là tiếp tục ném request vào các Pod lỗi để rồi người dùng phải đợi treo màn hình 30 giây rồi nhận lỗi timeout 504.
