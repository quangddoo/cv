# Soft Delete: Ưu nhược điểm và giải pháp thực chiến nâng cao

## ⚡ Tóm tắt ngắn (30s)
* **Soft Delete (Xóa mềm)**: Là kỹ thuật không thực sự xóa vật lý dòng dữ liệu khỏi bảng bằng câu lệnh `DELETE`, mà chỉ cập nhật một cờ đánh dấu trạng thái (ví dụ: `is_deleted = true` hoặc `deleted_at = TIMESTAMP`).
* **Ưu điểm**: Dễ dàng khôi phục dữ liệu (Undelete), giữ lại dữ liệu lịch sử để thống kê/audit, tránh lỗi cascade delete làm vỡ tính toàn vẹn liên kết.
* **Nhược điểm**: Làm phình to dung lượng ổ đĩa theo thời gian, suy giảm hiệu năng index, làm phức tạp hóa các câu lệnh SQL (luôn phải đính kèm `WHERE is_deleted = false`), và gây xung đột nghiêm trọng với các ràng buộc **Unique Constraints** (ví dụ: không thể đăng ký lại cùng một email đã bị xóa mềm).

## 🔍 Chi tiết bản chất thực chiến

### 1. 4 Thử thách lớn nhất của Soft Delete & Giải pháp Senior

#### Thử thách 1: Phá vỡ Ràng buộc Duy nhất (Unique Constraints)
* **Vấn đề**: Bạn thiết kế bảng `users` có cột `email` là UNIQUE. Người dùng A xóa mềm tài khoản của mình (`is_deleted = true`). Ngày hôm sau, người dùng A (hoặc người dùng khác) muốn đăng ký tài khoản mới với email đó. DB sẽ ném ra lỗi `Duplicate key exception` vì email cũ vẫn tồn tại vật lý trong bảng!
* **Giải pháp thực chiến**:
  1. **Sử dụng `deleted_at` làm một phần của Khóa Unique**: Đổi khóa duy nhất thành khóa ghép `(email, deleted_at)`. Khi tài khoản hoạt động, `deleted_at` là `NULL`. Khi xóa, ta set `deleted_at = CURRENT_TIMESTAMP`. 
     * *Lưu ý*: Một số DB cũ coi các giá trị `NULL` là khác nhau, cho phép tạo trùng nhiều dòng có `deleted_at = NULL`.
  2. **Partial Unique Index (Chỉ số duy nhất từng phần - Khuyên dùng cho Postgres/SQL Server)**:
     ```sql
     -- Chỉ áp dụng ràng buộc UNIQUE cho những dòng chưa bị xóa!
     CREATE UNIQUE INDEX idx_users_unique_active_email 
     ON users (email) 
     WHERE deleted_at IS NULL;
     ```
  3. **Cột giá trị đặc biệt `delete_token`**: Thiết kế khóa duy nhất gồm `(email, delete_token)`. Khi active, `delete_token = 0`. Khi xóa mềm, `delete_token = user_id`.

#### Thử thách 2: Quên cờ `is_deleted = false` trong các câu lệnh SQL
* **Vấn đề**: Chỉ cần một lập trình viên trong team quên không thêm điều kiện `WHERE is_deleted = false` vào câu lệnh truy vấn thông tin nhạy cảm, dữ liệu đã bị xóa của khách hàng sẽ bị hiển thị ra ngoài, gây rò rỉ thông tin nghiêm trọng.
* **Giải pháp thực chiến**:
  * Sử dụng các tính năng tự động lọc của ORM. Ví dụ trong Hibernate (Spring Boot), ta sử dụng cặp Annotation `@SQLDelete` và `@Where`:
    ```java
    @Entity
    @Table(name = "users")
    @SQLDelete(sql = "UPDATE users SET is_deleted = true WHERE id = ?") // Tự động chuyển DELETE thành UPDATE
    @Where(clause = "is_deleted = false") // Tự động chèn WHERE is_deleted = false vào tất cả các câu SELECT
    public class User {
        @Id
        private Long id;
        private String email;
        private boolean isDeleted = false;
    }
    ```

#### Thử thách 3: Suy giảm hiệu năng Index
* **Vấn đề**: Các dòng dữ liệu đã bị xóa mềm vẫn nằm trong các file vật lý của Index. Khi thực hiện Index Scan, DB Engine vẫn phải duyệt qua các node của các bản ghi đã xóa, làm giảm tốc độ truy vấn.
* **Giải pháp thực chiến**: Sử dụng **Partial Index (Filtered Index)** để tối ưu hóa bộ nhớ và tốc độ quét index:
  ```sql
  -- Chỉ tạo index tìm kiếm cho những dữ liệu đang hoạt động
  CREATE INDEX idx_active_orders_user 
  ON orders (user_id) 
  WHERE is_deleted = false;
  ```

#### Thử thách 4: Dữ liệu lịch sử phình to vô hạn
* **Giải pháp thực chiến**: Thiết kế quy trình **Data Archiving & Purging (Lưu trữ và Xóa sạch định kỳ)**. Viết các scheduled job (Cron job) ngầm vào ban đêm để quét qua các bản ghi đã bị xóa mềm cách đây hơn 6 tháng, chuyển (archive) chúng sang các hệ thống lưu trữ giá rẻ (như AWS S3 Glacier hoặc Cold Storage) và thực thi lệnh `DELETE` vật lý dưới DB chính để giải phóng dung lượng.

## 💻 Code thực chiến: Implement Soft Delete chuẩn chỉ với Spring Boot

### 🛠️ Thiết kế Base Entity dùng chung cho toàn bộ dự án

```java
@MappedSuperclass
@Getter
@Setter
public abstract class BaseEntity {

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt = LocalDateTime.now();

    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    @Column(name = "is_deleted", nullable = false)
    private boolean isDeleted = false;

    @Column(name = "deleted_at")
    private LocalDateTime deletedAt;
    
    // Helper method thực hiện xóa mềm
    public void softDelete() {
        this.isDeleted = true;
        this.deletedAt = LocalDateTime.now();
    }
}
```

### 🛠️ Sử dụng trong Repository (Đọc cả dữ liệu đã xóa khi cần)
Đôi khi admin hệ thống cần xem lại các dữ liệu đã bị xóa để khôi phục hoặc đối soát tài chính. Việc sử dụng `@Where(clause = "is_deleted = false")` sẽ chặn đứng khả năng này. Ta có thể xử lý linh hoạt bằng cách sử dụng Hibernate Filter hoặc viết câu truy vấn Native Query:

```java
public interface UserRepository extends JpaRepository<User, Long> {
    
    // Native query cho phép bỏ qua bộ lọc mặc định của Hibernate @Where
    @Query(value = "SELECT * FROM users WHERE id = :id", nativeQuery = true)
    Optional<User> findByIdIncludingDeleted(@Param("id") Long id);
    
    @Modifying
    @Transactional
    @Query("UPDATE User u SET u.isDeleted = false, u.deletedAt = null WHERE u.id = :id")
    void restore(@Param("id") Long id);
}
```

## 📊 Bảng so sánh đa chiều: Soft Delete vs Hard Delete

| Tiêu chí | Soft Delete (Xóa mềm) | Hard Delete (Xóa cứng) |
| :--- | :--- | :--- |
| **Hành vi vật lý** | Thực thi lệnh `UPDATE` cờ trạng thái | Thực thi lệnh `DELETE` xóa sạch khỏi ổ đĩa |
| **Khả năng khôi phục**| Cực kỳ dễ dàng (`UPDATE active = true`) | Rất khó (phải khôi phục từ file Backup/Binlog) |
| **Toàn vẹn khóa ngoại**| Tự nhiên, không sợ lỗi Cascade | Dễ vỡ liên kết dữ liệu lịch sử (ví dụ: mất đơn hàng) |
| **Hiệu năng Đọc** | Chậm dần theo thời gian nếu không dọn dẹp | Tối ưu tuyệt đối (dung lượng bảng nhỏ gọn) |
| **Unique Constraint** | Phức tạp, dễ xung đột | Hoạt động tự nhiên không cần cấu hình thêm |
| **Tuân thủ GDPR (Quyền được xóa sạch)** | Không tuân thủ hoàn toàn (User yêu cầu xóa vĩnh viễn) | Tuân thủ hoàn hảo |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Luật bảo vệ dữ liệu (GDPR / Quyền được lãng quên)
Nếu hệ thống của bạn phục vụ người dùng tại Châu Âu (GDPR) hoặc các quốc gia có luật bảo vệ dữ liệu nghiêm ngặt, việc người dùng nhấn "Xóa tài khoản" nhưng bạn chỉ chạy **Soft Delete** để giữ lại thông tin cá nhân của họ ngầm dưới DB sẽ bị coi là **phạm luật** và có thể bị phạt cực kỳ nặng.
* **Giải pháp thực chiến**: 
  1. Khi người dùng yêu cầu xóa tài khoản, ta có thể áp dụng **Anonymization (Vô danh hóa dữ liệu)** thay vì xóa. Tiến hành `UPDATE` đè các cột nhạy cảm như `name`, `email`, `phone` thành các chuỗi ngẫu nhiên vô nghĩa (ví dụ: `deleted_user_99@system.local`), giữ lại lịch sử giao dịch không chứa thông tin định danh để phục vụ báo cáo tài chính.
  2. Thực hiện xóa cứng hoàn toàn nếu nghiệp vụ không yêu cầu lưu trữ lịch sử liên quan.
