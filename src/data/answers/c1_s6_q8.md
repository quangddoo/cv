# @Bean vs @Component: Khi nào nên dùng loại nào trong Spring?

## ⚡ Tóm tắt ngắn (30s)
Cả `@Component` và `@Bean` đều được dùng để đăng ký đối tượng vào **Spring IoC Container** dưới dạng các Spring Beans, nhưng chúng được sử dụng ở các ngữ cảnh hoàn toàn khác nhau:
*   **`@Component` (Class-level)**: Sử dụng để đánh dấu trên **Class do chúng ta tự viết code**. Spring Container sẽ tự động tìm kiếm (Component Scanning), dùng Java Reflection để gọi constructor khởi tạo đối tượng, tự động tiêm dependencies và quản lý vòng đời của đối tượng đó.
*   **`@Bean` (Method-level)**: Sử dụng trên **Method** nằm bên trong các Class cấu hình (`@Configuration`). Chúng ta sẽ **chủ động tự viết code khởi tạo đối tượng** (bằng từ khóa `new`, gọi hàm builder, config thuộc tính) và trả về đối tượng đó; Spring chỉ chịu trách nhiệm đưa đối tượng nhận được vào container để quản lý. Thích hợp cho việc cấu hình các **thư viện bên thứ ba** (khi ta không có quyền truy cập source code để gắn `@Component` lên class của họ).

## 🔍 Chi tiết bản chất thực chiến

### 1. Bản chất hoạt động của `@Component` (Cơ chế tự động - Implicit Configuration)
Với `@Component` (hoặc các kế thừa như `@Service`, `@Repository`), Spring hoạt động theo cơ chế phát hiện tự động. Bạn chỉ cần gắn annotation lên đầu class. Khi khởi chạy, Spring tự động tạo ra một instance duy nhất. Cơ chế này cực kỳ tối ưu cho các class nghiệp vụ phát triển hàng ngày vì lập trình viên không phải viết code cấu hình thủ công.

### 2. Bản chất hoạt động của `@Bean` (Cơ chế thủ công - Explicit Configuration)
Với `@Bean`, bạn có toàn quyền kiểm soát quá trình tạo lập đối tượng. Ví dụ, nếu bạn muốn sử dụng class `ObjectMapper` của Jackson nhưng muốn cấu hình định dạng ngày tháng riêng, bạn sẽ định nghĩa một method trả về `ObjectMapper` trong class `@Configuration` và đánh dấu method đó bằng `@Bean`.

### 3. Tầm quan trọng của `@Configuration` và cơ chế CGLIB Proxying
Khi một method `@Bean` được khai báo bên trong class đánh dấu **`@Configuration`**, Spring sẽ sử dụng kỹ thuật **CGLIB Dynamic Proxy** để bọc class cấu hình đó lại (được gọi là **Full Mode**).
*   **Cơ chế**: Khi bạn gọi chéo method `@Bean` này từ một method `@Bean` khác trong cùng class, Spring CGLIB Proxy sẽ can thiệp để kiểm tra xem Bean đó đã tồn tại trong Container chưa. Nếu đã tồn tại, nó trả về Singleton Bean hiện có thay vì gọi lại method cấu hình để tạo ra đối tượng mới. Điều này bảo vệ tính toàn vẹn Singleton của các Bean trong hệ thống.
*   **Lite Mode**: Nếu bạn khai báo `@Bean` bên trong một class thường không có `@Configuration` (chỉ dùng `@Component`), cơ chế proxy này sẽ bị tắt. Mỗi cuộc gọi chéo method sẽ thực thi code Java thuần túy và sinh ra đối tượng mới tinh, phá vỡ nguyên tắc Singleton và có thể gây rò rỉ tài nguyên db connection.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Định nghĩa `@Bean` sai lớp cấu hình dẫn đến mất tính chất Singleton (Lite Mode)
```java
package com.example.config;

import com.example.dto.UserMapper;
import org.springframework.context.annotation.Bean;
import org.springframework.stereotype.Component;

@Component // ❌ ANTI-PATTERN: Dùng Component thay vì Configuration để chứa @Bean
public class AppConfigBad {

    @Bean
    public UserMapper userMapper() {
        return new UserMapper(); // Khởi tạo một mapper
    }

    @Bean
    public UserService userService() {
        // ⚠️ NGUY HIỂM: Do không dùng @Configuration, Spring không bọc CGLIB Proxy.
        // Dòng gọi userMapper() dưới đây sẽ chạy như code Java thuần túy,
        // sinh ra instance UserMapper thứ hai hoàn toàn mới tinh, phá vỡ nguyên lý Singleton!
        return new UserService(userMapper()); 
    }
}
```

###  GOOD: Kết hợp đúng ngữ cảnh sử dụng
```java
package com.example.config;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.SerializationFeature;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration // ✅ CHUẨN: Bật Full Mode với CGLIB Proxying
public class AppConfigGood {

    // ✅ Dùng @Bean cho Class bên thứ 3 (Jackson ObjectMapper)
    @Bean
    public ObjectMapper customObjectMapper() {
        ObjectMapper mapper = new ObjectMapper();
        mapper.enable(SerializationFeature.INDENT_OUTPUT); // Cấu hình custom
        return mapper;
    }
}

package com.example.service;

import org.springframework.stereotype.Service;

@Service // ✅ Dùng @Component (Service) cho Class tự viết source code
public class UserReportService {
    // Business logic...
}
```

## 📊 Trade-off: So sánh `@Component` và `@Bean`

| Tiêu chí | `@Component` (Class-level) | `@Bean` (Method-level) |
| :--- | :--- | :--- |
| **Đối tượng áp dụng** | Áp dụng trên **Class** | Áp dụng trên **Method** |
| **Kiểm soát mã nguồn** | **Bắt buộc**: Phải có quyền sửa source code để gắn annotation lên class. | **Không cần**: Áp dụng được cho các class import từ thư viện ngoài (JAR). |
| **Quyền kiểm soát** | Do Spring IoC Container tự quyết định cách khởi tạo qua constructor. | Do **Lập trình viên hoàn toàn quyết định** (viết code new, config tùy biến). |
| **Configuration Style** | Declarative / Annotation-based (Quét tự động) | Explicit Configuration (Định nghĩa tường minh) |
| **Hỗ trợ nạp chồng (Overloading)**| ❌ Không thể tạo nhiều bean cùng loại với cấu hình khác nhau. | **Có thể**: Tạo nhiều method trả về cùng kiểu dữ liệu với cấu hình khác nhau. |

## ⚠️ Common Gotchas & Questions follow-up

* **Cạm bẫy lỗi "NoUniqueBeanDefinitionException"**:
  Nếu bạn khai báo 2 method `@Bean` cùng trả về kiểu dữ liệu `DataSource` (ví dụ: một cho DB chính, một cho DB phụ). Khi một class khác gọi `@Autowired private DataSource dataSource;`, Spring sẽ crash lập tức vì không biết chọn nguồn dữ liệu nào.
  * *Khắc phục:* Sử dụng annotation `@Qualifier("beanName")` tại vị trí tiêm để chỉ định rõ tên Bean, hoặc đánh dấu một trong hai Bean bằng `@Primary` làm mặc định.
* **Câu hỏi đào sâu từ interviewer**: *Làm thế nào để inject một dependency khác vào một method cấu hình `@Bean`?*
  * *(Trả lời: Spring giải quyết việc này vô cùng thanh lịch. Chúng ta chỉ cần khai báo dependency đó làm tham số của method `@Bean`. Khi gọi method, Spring Container sẽ tự động tìm kiếm Bean tương ứng trong hệ thống và truyền vào làm tham số truyền vào (argument) cho method của bạn).*
