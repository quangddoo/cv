# CORS vs. CSRF trong Spring Boot: Hiểu sâu bản chất & Cấu hình an toàn hệ thống

## ⚡ Tóm tắt ngắn (30s)
**CORS (Cross-Origin Resource Sharing)** và **CSRF (Cross-Site Request Forgery)** là hai khái niệm bảo mật web hoàn toàn khác nhau nhưng lập trình viên rất hay nhầm lẫn:
*   **CORS**: Là cơ chế của **Trình duyệt (Browser)** nhằm bảo vệ tài nguyên của máy chủ. Trình duyệt ngăn không cho mã JavaScript từ một Domain A đọc dữ liệu nhạy cảm từ API của Domain B, ngoại trừ khi Domain B cấp phép rõ ràng (qua Header `Access-Control-Allow-Origin`).
*   **CSRF**: Là phương thức **Tấn công giả mạo** lợi dụng cơ chế tự động đính kèm Cookie của Trình duyệt. Hacker lừa nạn nhân click vào link độc hại từ trang của hacker để gửi yêu cầu (như chuyển tiền) lên trang đáng tin cậy mà nạn nhân đang đăng nhập bằng Session/Cookie.
*   **Thực chiến Spring Boot**:
    *   **CORS**: Phải cấu hình ở tầng Spring Security Filter để cho phép Frontend (ví dụ: `domain-fe.com`) được gọi API của Backend (`domain-be.com`).
    *   **CSRF**: Bắt buộc kích hoạt cho các hệ thống dùng **Stateful Session (Cookie)**. Cần **vô hiệu hóa (disable)** khi xây dựng **Stateless API (JWT)** lưu token trong LocalStorage/Header vì trình duyệt không tự động gửi Header đi khi hacker kích hoạt link chéo trang.

## 🔍 Chi tiết bản chất thực chiến

### 1. Phân biệt sâu sắc bản chất

| Tiêu chí | CORS (Chia sẻ tài nguyên chéo nguồn) | CSRF (Giả mạo yêu cầu chéo trang) |
| :--- | :--- | :--- |
| **Bản chất** | **Cơ chế bảo vệ** của Browser chống lại truy cập dữ liệu trái phép. | **Kịch bản tấn công** lợi dụng cơ chế tự động gửi Cookie của Browser. |
| **Bên chịu rủi ro** | Client (Không đọc được dữ liệu nếu BE không cấu hình cho phép). | Server (Thực thi các lệnh phá hoại do tin tưởng Cookie gửi lên). |
| **Cách thức hoạt động** | Browser gửi request **`OPTIONS`** (Preflight) để hỏi BE xem Origin này có được phép gọi API này không. | Browser tự động đính kèm Session Cookie khi gửi request chéo trang từ thẻ `<img>`, `<form>`. |
| **Cách phòng vệ** | BE trả về Header: `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`... | Sử dụng **CSRF Token** (Synchronizer Token), cấu hình Cookie thuộc tính **`SameSite=Lax/Strict`**. |

### 2. Luồng hoạt động của CORS Preflight Request
Khi Client gọi một API chéo nguồn (ví dụ: JavaScript tại `app.com` gọi `api.com/users` với method `POST` và header `Content-Type: application/json`):
```text
[ Client (app.com) ]                                    [ Server (api.com) ]
        │                                                       │
        │ 1. OPTIONS /users (Preflight Request)                 │
        │    Headers: Origin: app.com                           │
        │             Access-Control-Request-Method: POST       │
        ├──────────────────────────────────────────────────────>│
        │                                                       │
        │ 2. Trả lời Preflight:                                 │
        │    Headers: Access-Control-Allow-Origin: app.com      │
        │             Access-Control-Allow-Methods: POST, GET   │
        │<──────────────────────────────────────────────────────┤
        │                                                       │
        │─── NẾU ĐƯỢC CHO PHÉP -> GỬI REQUEST THẬT ──────────────│
        │                                                       │
        │ 3. POST /users (Actual Request)                       │
        ├──────────────────────────────────────────────────────>│
        │ 4. HTTP 200 OK (Response Data)                        │
        │<──────────────────────────────────────────────────────┤
```

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Mở toang CORS bằng dấu wildcard (*) và tắt CSRF bừa bãi khi ứng dụng sử dụng Session
Cấu hình CORS cực kỳ nguy hiểm cho phép tất cả các nguồn truy cập kèm theo cookie nhạy cảm, đồng thời tắt bảo vệ CSRF trên một ứng dụng sử dụng Session, tạo sơ hở cho hacker chiếm đoạt tài khoản dễ dàng.

```java
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;

@Configuration
public class SecurityConfigBad {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // ❌ Lỗi 1: Tắt CSRF bừa bãi khi ứng dụng đang chạy Session-based Authentication!
            .csrf(csrf -> csrf.disable()) 
            
            .cors(cors -> cors.configurationSource(request -> {
                CorsConfiguration config = new CorsConfiguration();
                // ❌ Lỗi 2: Cho phép tất cả các Origin (*) và cho phép gửi kèm Credentials (Cookie)
                // Đây là lỗ hổng bảo mật nghiêm trọng. Trình duyệt hiện đại sẽ chặn cấu hình này,
                // nhưng nếu hoạt động, bất kỳ trang web nào cũng đọc được dữ liệu của bạn!
                config.addAllowedOriginPattern("*");
                config.setAllowCredentials(true); 
                config.addAllowedMethod("*");
                config.addAllowedHeader("*");
                return config;
            }));
            
        return http.build();
    }
}
```

### ✅ GOOD: Cấu hình CORS chặt chẽ và CSRF an toàn theo đúng kiến trúc
Phân định rõ ràng: Nếu ứng dụng là Stateful (dùng Session/Cookie), kích hoạt CSRF Token lưu trữ dưới dạng Cookie bảo mật. Nếu là Stateless (JWT), cấu hình CORS trỏ đích danh tên miền của Frontend và khóa chặt các method được phép.

```java
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.csrf.CookieCsrfTokenRepository;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsConfigurationSource;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;
import java.util.List;

@Configuration
public class SecurityConfigGood {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // ✅ KỊCH BẢN 1: Ứng dụng Stateful (Session-based) - BẮT BUỘC bật CSRF
            // Sử dụng CookieCsrfTokenRepository với HttpOnly=false để Single Page App (Angular/React) đọc được token và gửi ngược lại trong Header
            .csrf(csrf -> csrf
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            )
            
            // ✅ KỊCH BẢN 2: Nếu là ứng dụng Stateless JWT API (Không dùng Session Cookie)
            // Bạn có thể vô hiệu hóa an toàn bằng lệnh:
            // .csrf(AbstractHttpConfigurer::disable)

            // ✅ Cấu hình CORS chuẩn chỉ, an toàn
            .cors(cors -> cors.configurationSource(corsConfigurationSource()));

        return http.build();
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration configuration = new CorsConfiguration();
        // ✅ Chỉ cho phép Origin xác định rõ ràng của môi trường Staging/Production
        configuration.setAllowedOrigins(List.of("https://app.mycompany.com", "https://admin.mycompany.com"));
        // ✅ Hạn chế các Method được dùng chéo nguồn
        configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
        // ✅ Chỉ cho phép các Header tiêu chuẩn và an toàn
        configuration.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Requested-With", "X-XSRF-TOKEN"));
        // ✅ Cho phép gửi kèm Credentials (Cookie hoặc Authorization Header)
        configuration.setAllowCredentials(true);
        // ✅ Cache kết quả Preflight OPTIONS trong 1 giờ để giảm tải lượng request lên server
        configuration.setMaxAge(3600L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", configuration); // Áp dụng cho toàn bộ API
        return source;
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy lỗi CORS khi cấu hình sai vị trí (Spring Security CORS vs Spring MVC CORS)
Đây là tình huống cực kỳ phổ biến khiến nhiều lập trình viên bế tắc:
*   **Vấn đề**: Bạn cấu hình CORS rất đẹp bằng `@CrossOrigin` trên Controller hoặc kế thừa `WebMvcConfigurer` và override `addCorsMappings`. Tuy nhiên, khi gọi API từ Frontend, trình duyệt vẫn báo lỗi **CORS Blocked**. Khi mở tab Network, bạn thấy API trả về mã lỗi **401 Unauthorized** (hoặc 403) nhưng lại không có bất kỳ Header CORS nào!
*   **Nguyên nhân**: Bộ lọc CORS của Spring MVC (`WebMvcConfigurer`) được thực thi ở tầng **`DispatcherServlet`** (tầng sau). Trong khi đó, bộ lọc bảo mật Spring Security (`FilterSecurityInterceptor`, `UsernamePasswordAuthenticationFilter`) chạy trước ở tầng **Filter Chain**. Khi một request chưa được xác thực gửi tới, Spring Security sẽ chặn lại lập tức và trả về mã lỗi 401. Vì request bị chặn ngay ở tầng Filter, nó **chưa bao giờ chạm tới được DispatcherServlet**, dẫn đến các cấu hình CORS của Spring MVC hoàn toàn bị bỏ qua! Trình duyệt thấy mã 401 thiếu Header CORS nên quăng lỗi CORS, đánh lừa lập trình viên tưởng rằng lỗi là do CORS.
*   **Giải pháp thực chiến**: **Luôn luôn cấu hình CORS ở tầng Spring Security** thông qua việc khai báo `CorsConfigurationSource` như ví dụ GOOD ở trên. Điều này đảm bảo filter CORS luôn chạy đầu tiên trong chuỗi bảo mật và đính kèm đầy đủ Header CORS cho dù request có bị Security từ chối.

### 2. Tại sao Stateless API (sử dụng JWT lưu trong Header) lại miễn nhiễm với tấn công CSRF?
*   **Bản chất CSRF**: Dựa hoàn toàn vào việc trình duyệt tự động gửi kèm Cookie tương thích của trang web đích mỗi khi gửi request (cho dù request đó xuất phát từ trang web độc hại của hacker).
*   **JWT Header**: Khi chúng ta thiết lập stateless API và lưu JWT trong bộ nhớ JavaScript (`localStorage`/`sessionStorage`), để gửi token lên Server, Frontend bắt buộc phải viết mã JavaScript thủ công để đọc token ra và đính kèm vào Header `Authorization: Bearer <token>`.
*   **Tại sao an toàn**: Khi hacker lừa nạn nhân nhấn vào một liên kết chéo trang hoặc gửi một `<form>` từ trang web của hacker lên Backend của bạn, trình duyệt **không thể tự động truy cập và đọc bộ nhớ LocalStorage** của trang web bạn để trích xuất JWT và đính kèm vào Header được (do cơ chế Same-Origin Policy của trình duyệt bảo vệ bộ nhớ). Thiếu JWT trong Header, request của hacker lập tức bị từ chối 401. Do đó, bạn không cần cấu hình bảo vệ CSRF (disable CSRF) cho Stateless REST API.
*   *Lưu ý bảo mật bổ sung*: Nếu bạn quyết định lưu trữ JWT trong Cookie thay vì LocalStorage (để chống tấn công XSS), hãy chắc chắn bật thuộc tính **`SameSite=Strict`** hoặc **`SameSite=Lax`** trên Cookie đó để chống lại tấn công CSRF!
