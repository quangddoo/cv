# Constructor vs Setter vs Field Injection: Phân tích so sánh toàn diện

## ⚡ Tóm tắt ngắn (30s)
Ba kỹ thuật Dependency Injection (DI) này khác nhau cơ bản ở **thời điểm** và **cơ chế** nạp phụ thuộc vào đối tượng:
1.  **Constructor Injection**: Tiêm ngay tại thời điểm khởi tạo đối tượng qua phương thức khởi dựng. *Đặc điểm:* Đảm bảo tính bất biến (`final`), an toàn trước lỗi Null (không thể tạo đối tượng thiếu dependency), và dễ viết Unit Test nhất.
2.  **Setter Injection**: Khởi tạo đối tượng trước bằng constructor rỗng, sau đó nạp dependencies qua các phương thức `set()`. *Đặc điểm:* Thích hợp cho các phụ thuộc tùy chọn (optional) hoặc có thể thay đổi tại runtime.
3.  **Field Injection**: Sử dụng Java Reflection để tiêm trực tiếp vào thuộc tính ẩn (`private field`) bằng annotation `@Autowired`. *Đặc điểm:* Code trông rất ngắn gọn nhưng tạo ra sự phụ thuộc chặt chẽ vào Spring Container, khó test độc lập, và ẩn giấu các lỗi thiết kế hệ thống.

## 🔍 Chi tiết bản chất thực chiến

### 1. Cơ chế hoạt động nội bộ của Spring Container đối với từng loại

#### A. Constructor Injection: Khởi tạo nguyên khối (Atomic Instantiation)
Khi Spring nhận yêu cầu tạo `BeanA`, nó phân tích constructor của `BeanA`, tìm các dependency cần thiết trong ApplicationContext và gọi constructor đó. Đối tượng được tạo ra ở trạng thái hoàn hảo nhất (tất cả các dependencies bắt buộc đều đã có đầy đủ và không bao giờ bị đổi sang giá trị khác nhờ `final`).

#### B. Setter Injection: Khởi tạo từng bước (Two-phase Instantiation)
*   **Bước 1**: Spring gọi constructor mặc định (no-argument constructor) để tạo instance của Bean.
*   **Bước 2**: Spring quét các method setter có `@Autowired` và gọi chúng để nạp dependency vào.
*   *Nguy cơ:* Nếu luồng xử lý hoặc code gọi đến Bean trước khi Bước 2 hoàn tất, đối tượng sẽ ở trạng thái không đầy đủ và ném ra lỗi `NullPointerException` (NPE).

#### C. Field Injection: Phá vỡ tính đóng gói qua Reflection
Spring sử dụng Java Reflection API để can thiệp vào Class Definition, chuyển trạng thái của private field thành `setAccessible(true)` rồi nạp trực tiếp tham chiếu của dependency vào. 
*   *Nguy cơ:* Đối tượng hoàn toàn mất đi tính tự chủ. Bạn không thể tạo đối tượng này bằng tay bằng cách viết `new MyService()` trong class test thông thường vì không có constructor hay setter nào để đưa mock dependencies vào.

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Dùng Field Injection gây lỗi khi viết Unit Test độc lập
```java
package com.example.service;

import com.example.repository.ProductRepository;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service
public class ProductServiceBad {

    @Autowired // Field Injection
    private ProductRepository productRepository;

    public double getDiscountPrice(Long productId) {
        return productRepository.findById(productId)
                .map(product -> product.getPrice() * 0.9)
                .orElse(0.0);
    }
}

// ⚠️ Khi viết Unit Test độc lập (không khởi động cả Spring Context):
// class ProductServiceTest {
//     @Test
//     void testDiscount() {
//         ProductServiceBad service = new ProductServiceBad();
//         // service.productRepository đang là null! Không có cách nào truyền mock vào.
//         // Chạy test sẽ lập tức quăng NullPointerException!
//     }
// }
```

###  GOOD: Constructor Injection kết hợp Lombok để giữ code siêu sạch
```java
package com.example.service;

import com.example.repository.ProductRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor // Lombok tự động sinh ra Constructor cho tất cả các field final
public class ProductServiceGood {

    // Khai báo final bắt buộc phải truyền qua Constructor
    private final ProductRepository productRepository;

    public double getDiscountPrice(Long productId) {
        return productRepository.findById(productId)
                .map(product -> product.getPrice() * 0.9)
                .orElse(0.0);
    }
}

// ✅ Khi viết Unit Test độc lập cực kỳ đơn giản và nhanh chóng:
// class ProductServiceTest {
//     @Test
//     void testDiscount() {
//         ProductRepository mockRepo = Mockito.mock(ProductRepository.class);
//         // Dễ dàng truyền mock thông qua constructor do Lombok sinh ra
//         ProductServiceGood service = new ProductServiceGood(mockRepo); 
//         
//         // Tiến hành assert kết quả...
//     }
// }
```

## 📊 Trade-off: Bảng so sánh toàn diện 3 phương pháp DI

| Đặc tính kỹ thuật | Constructor Injection | Setter Injection | Field Injection |
| :--- | :--- | :--- | :--- |
| **Tính bất biến (Immutability)** | **Có** (Cho phép dùng `final` fields) | ❌ Không | ❌ Không |
| **Độ an toàn Null (NPE Safe)** | **Có** (JVM bắt buộc nạp đủ tham số) | ❌ Không | ❌ Không |
| **Dễ viết Unit Test (POJO-friendly)**| **Tuyệt đối** (Dùng từ khóa `new` truyền mock) | Trung bình (Dùng các hàm setter) | ❌ Cực khó (Phải dùng Reflection helper) |
| **Phát hiện Circular Dependency** | **Ngay khi startup ứng dụng (Compile-time/Boot)** | ❌ Trễ (Chỉ khi chạy runtime gọi method) | ❌ Trễ |
| **Spring Annotations xâm lấn** | **Không** (Không cần dùng `@Autowired` nếu có 1 constructor) | ❌ Có (Cần `@Autowired` trên setter) | ❌ Có (Cần `@Autowired` trên field) |
| **Độ gọn gàng của code** | Cần viết constructor (Có thể dùng Lombok `@RequiredArgsConstructor`) | Phải viết nhiều method setter | Cực kỳ ngắn gọn |

## ⚠️ Common Gotchas & Questions follow-up

* **Cạm bẫy Circular Dependency khi dùng Constructor Injection**:
  Nếu `ServiceA` cần `ServiceB` trong constructor, và ngược lại `ServiceB` cần `ServiceA`. Spring Boot sẽ lập tức báo lỗi đụng độ vòng và từ chối khởi động.
  * *Khắc phục:* Đây là dấu hiệu thiết kế sai kiến trúc. Tuy nhiên, nếu bắt buộc phải giữ cấu trúc này, có thể chuyển một trong hai sang **Setter Injection** hoặc sử dụng annotation `@Lazy` đặt trước tham số trong constructor để Spring tạo ra một proxy thay thế tạm thời.
* **Câu hỏi đào sâu từ interviewer**: *Tại sao từ Spring 4.3 trở đi, ta không cần viết annotation `@Autowired` trên constructor của class nữa?*
  * *(Trả lời: Spring nhận ra rằng nếu một class chỉ định nghĩa duy nhất một constructor, container sẽ tự hiểu đây là điểm tiêm dependency mặc định mà không cần nhà phát triển phải đánh dấu annotation của Spring. Điều này giúp code Java sạch hơn, không bị phụ thuộc vào các thư viện bên ngoài và tiệm cận tiêu chuẩn POJO thuần túy).*
