# Trade-off Model Portability vs Provider-specific Feature

## ⚡ Tóm tắt ngắn (30s)
* **Portability**: easy switch provider (cost saving, failover, vendor escape).
* **Provider-specific feature**: use latest (JSON mode, prompt caching, batch API) → quality/cost benefits.
* **Trade-off**:
  - Pure portable: lowest common denominator.
  - Provider-specific: lock-in, hard to migrate.
* **Pattern Senior**: abstraction layer (canonical) + per-provider extensions where benefits big.

---

## 💻 Layered abstraction

```java
public interface LlmProvider {
    Mono<LlmResponse> chat(LlmRequest req);  // portable
    
    default boolean supportsJsonMode() { return false; }  // capability check
}

// Provider-specific feature gated by capability
if (provider.supportsJsonMode()) {
    // Use it
} else {
    // Fallback: prompt with JSON instruction
}
```

## 📊 Examples

| Feature | OpenAI | Anthropic | Migration impact |
| :--- | :---: | :---: | :--- |
| JSON mode (strict) | ✓ | tool use | Medium |
| Prompt caching | recently | ✓ native | Cost diff |
| Function calling | ✓ | ✓ tool use | Adapter needed |
| Vision | ✓ | ✓ | API diff |
| Batch API | ✓ | ✗ | Big saving lost |

## ⚠️ Interviewer

**"Use Anthropic prompt caching for 90% cost saving. Migration to OpenAI?"**
1. If saves $$$, accept lock-in awareness.
2. Architecture: feature gated, fallback works without.
3. Migration plan: budget cost increase if switch.
4. Risk register: dependency on this feature.
5. Monitor provider parity (e.g. OpenAI may add similar feature).
