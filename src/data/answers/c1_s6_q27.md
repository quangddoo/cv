# Graceful Shutdown trong Spring Boot: Cơ chế hoạt động & Triển khai thực chiến

## ⚡ Tóm tắt ngắn (30s)
**Graceful Shutdown (Tắt ứng dụng êm ái)** là cơ chế cho phép một ứng dụng đang chạy dừng lại một cách an toàn mà không làm gián đoạn các yêu cầu (requests) hiện tại của người dùng.
*   **Cách thức hoạt động**: Khi nhận tín hiệu tắt (như `SIGTERM` từ Kubernetes hoặc lệnh shutdown):
    1.  Ứng dụng ngừng tiếp nhận các kết nối mới (New incoming connections).
    2.  Hệ thống tiếp tục xử lý nốt các request đang chạy dở dang (Active requests).
    3.  Sau khi tất cả active requests xử lý xong, hoặc khi hết thời gian chờ tối đa (Grace Period Timeout), ứng dụng sẽ chính thức đóng các kết nối vật lý và JVM tắt hoàn toàn.
*   **Cấu hình**: Kể từ Spring Boot 2.3, chỉ cần khai báo thuộc tính `server.shutdown = graceful` trong `application.yml`.

## 🔍 Chi tiết bản chất thực chiến

### 1. Quy trình xử lý của Graceful Shutdown dưới mui xe
```text
[ Tín hiệu SIGTERM gửi tới JVM ]
               │
┌──────────────▼──────────────────────────────────────────────┐
│ 1. Web Server (Tomcat/Undertow) ngắt kết nối mới             │
│  - Trình quản lý mạng từ chối các request TCP mới tới port.  │
│  - Không chấp nhận thêm HTTP request mới.                    │
└──────────────┬──────────────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────────────┐
│ 2. Xử lý nốt các Request đang chạy dở                        │
│  - Các Thread đang chạy request nghiệp vụ tiếp tục thực hiện. │
│  - Spring Boot bắt đầu đếm ngược thời gian Grace Period.     │
└──────────────┬──────────────────────────────────────────────┘
               │
 ⚖️ [ Có còn Request nào đang chạy không? ]
       ├── CÒN (Chưa hết Timeout) ──> Tiếp tục đợi...
       ├── HẾT                  ──> TẮT NGAY LẬP TỨC
       └── CÒN (Đã hết Timeout)  ──> Khai tử ép buộc (Kill remaining)
               │
┌──────────────▼──────────────────────────────────────────────┐
│ 3. Đóng các Bean Context và Shutdown JVM                      │
│  - Hủy các Spring Beans, đóng Connection Pool (HikariCP).    │
│  - JVM chấm dứt tiến trình an toàn.                          │
└─────────────────────────────────────────────────────────────┘
```

### 2. Sự phối hợp quan trọng giữa Spring Boot và Kubernetes (K8s)
Khi deploy ứng dụng trên K8s, nếu không đồng bộ thời gian tắt giữa hai hệ thống, bạn sẽ gặp lỗi mất mát request:
1.  **`spring.lifecycle.timeout-per-shutdown-phase`**: Thời gian Spring Boot đợi để hoàn thành các request đang chạy (Ví dụ: `30s`).
2.  **`terminationGracePeriodSeconds` của K8s**: Thời gian K8s đợi từ khi gửi tín hiệu `SIGTERM` trước khi quăng tiếp `SIGKILL` (khai tử thô bạo pod).
3.  **📌 Quy tắc thực chiến**: Thời gian chờ của K8s **phải lớn hơn** thời gian chờ của Spring Boot (Ví dụ: K8s đặt `45s`, Spring Boot đặt `30s`). Nếu K8s đặt nhỏ hơn, K8s sẽ nhảy vào "bóp chết" pod trước khi Spring Boot kịp xử lý xong các request dở dang!

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Tắt ứng dụng thô bạo (Abrupt Shutdown - Mặc định cũ)
Khi tắt ứng dụng, các request đang thực hiện dở dang (ví dụ: đang xử lý thanh toán mất 5 giây) lập tức bị ngắt kết nối đột ngột, gây ra lỗi HTTP 502 Bad Gateway phía Frontend và có khả năng làm sai lệch dữ liệu DB do transaction bị ngắt quãng thô bạo.

```yaml
# application.yml
# ❌ Mặc định Spring Boot (trước 2.3 hoặc khi không cấu hình) hoạt động ở chế độ IMMEDIATE
server:
  shutdown: immediate # Hủy lập tức mọi kết nối đang hoạt động
```

```java
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration
public class AsyncConfigBad {

    @Bean
    public ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(20);
        // ❌ Không cấu hình đợi task chạy ngầm hoàn thành khi tắt app.
        // Khi JVM shutdown, các task đang chạy trong hàng đợi bất đồng bộ này sẽ bị giết sạch lập tức!
        return executor;
    }
}
```

### ✅ GOOD: Cấu hình Graceful Shutdown toàn diện cho Web Server & Async Tasks
Bật chế độ tắt êm ái cho Web Server và cấu hình cho tất cả các Thread Pool xử lý bất đồng bộ hoặc lắng nghe message queue (Kafka/RabbitMQ) đợi hoàn thành công việc trước khi giải phóng.

```yaml
# application.yml
server:
  # ✅ Bật chế độ Graceful Shutdown cho Web Server (Tomcat/Jetty/Undertow)
  shutdown: graceful

spring:
  lifecycle:
    # ✅ Thiết lập thời gian tối đa để xử lý nốt các request dở dang trước khi ép buộc tắt (Mặc định là 30s)
    timeout-per-shutdown-phase: 30s
```

```java
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration
public class AsyncConfigGood {

    @Bean
    public ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(20);
        executor.setThreadNamePrefix("AsyncExecutor-");

        // ✅ 1. Ép buộc Thread Pool đợi toàn bộ task đang chạy hoàn thành khi shutdown
        executor.setWaitForTasksToCompleteOnShutdown(true);

        // ✅ 2. Thiết lập thời gian đợi tối đa cho Thread Pool này (Ví dụ: 25 giây)
        // Nên nhỏ hơn thời gian timeout-per-shutdown-phase của Spring Boot (30s)
        executor.setAwaitTerminationSeconds(25);

        executor.initialize();
        return executor;
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy lỗi 502 Bad Gateway trên Kubernetes do độ trễ truyền tin (Routing Propagation Latency)
Đây là lỗi cực kỳ kinh điển trong microservices thực tế:
*   **Vấn đề**: Bạn đã cấu hình `server.shutdown = graceful` hoàn hảo trên Spring Boot. Tuy nhiên, khi deploy phiên bản mới trên Kubernetes (K8s), hệ thống giám sát vẫn ghi nhận hàng loạt lỗi **502 Bad Gateway** hoặc **Connection Refused** xảy ra trong vài giây đầu tiên khi pod cũ bắt đầu tắt!
*   **Nguyên nhân dưới mui xe**: Khi một pod bị tắt, hai tiến trình sau xảy ra **song song bất đồng bộ**:
    1.  K8s gửi tín hiệu `SIGTERM` tới Pod -> Spring Boot nhận được và ngay lập tức dừng tiếp nhận kết nối mới (Tomcat đóng cổng kết nối).
    2.  K8s Service Controller bắt đầu gỡ bỏ IP của Pod đó ra khỏi danh sách Endpoint để Ingress/Load Balancer không chuyển traffic tới nữa. Do độ trễ phân tán mạng của K8s, tiến trình này mất từ **2 đến 5 giây** để lan truyền hoàn toàn.
    *   *Kết quả*: Trong vòng 2-5 giây đó, Load Balancer vẫn chuyển tiếp các request của người dùng tới Pod cũ. Nhưng Pod cũ đã dừng nhận kết nối do đã nhận `SIGTERM`, dẫn tới lỗi 502/Connection Refused lập tức!
*   **Giải pháp thực chiến**: Thêm cấu hình **`preStop` hook** trong file YAML của K8s để bắt Pod ngủ (`sleep`) một khoảng thời gian trước khi chuyển tiếp tín hiệu `SIGTERM` tới Spring Boot. Khoảng thời gian này giúp K8s cập nhật xong bảng định tuyến mạng:
    ```yaml
    # kubernetes-deployment.yaml
    spec:
      containers:
      - name: my-spring-boot-app
        lifecycle:
          preStop:
            exec:
              command: ["sh", "-c", "sleep 15"] # ✅ Đợi 15 giây để Load Balancer cập nhật, sau đó mới gửi SIGTERM tới App
    ```

### 2. Làm thế nào để đảm bảo dữ liệu Kafka Consumer không bị mất hoặc trùng lặp khi tắt ứng dụng?
*   Khi Spring Boot nhận lệnh tắt, Spring Kafka Container (`ConcurrentMessageListenerContainer`) sẽ tự động dừng lắng nghe (pause/stop consuming) các message mới từ Broker.
*   Tuy nhiên, các message đang được xử lý dở dang bởi các thread consumer cần được ưu tiên xử lý xong.
*   *Giải pháp*: Cần đảm bảo thuộc tính tự động commit offset được cấu hình an toàn hoặc sử dụng manual commit offset. Spring Kafka mặc định đã tích hợp sẵn cơ chế graceful shutdown cho các listener container, tự động đợi xử lý nốt bản ghi hiện tại trước khi thực hiện commit offset cuối cùng và ngắt kết nối với Kafka broker.
