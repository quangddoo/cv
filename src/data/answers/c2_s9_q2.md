# Circuit breaker mở liên tục. Bạn điều tra gì?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Khi Circuit Breaker chuyển sang trạng thái **OPEN** liên tục, tức là hệ thống đang kích hoạt chế độ tự vệ **Fail-Fast** vì tỷ lệ cuộc gọi bị lỗi (Failure Rate) hoặc xử lý chậm (Slow Call Rate) vượt quá ngưỡng cho phép (threshold) trong một cửa sổ trượt (sliding window). Đây là lúc "cầu chì đã đứt" để bảo hệ thống không bị sập dây chuyền.
* **Thảm họa thực chiến được giải quyết**:
  1. **Lỗi ngầm diện rộng (Silent Failures)**: Nếu Circuit Breaker mở liên tục mà không có cảnh báo rõ ràng, lập trình viên sẽ lầm tưởng hệ thống đang chạy mượt vì API vẫn phản hồi nhanh (do chạy vào code Fallback). Thực tế, tính năng cốt lõi đang bị lỗi hoàn toàn (Fail-Fast), trực tiếp gây mất doanh thu.
  2. **Kẹt trạng thái hở mạch (Circuit Breaker State Lock)**: Downstream service đã hồi phục hoàn toàn từ lâu, nhưng Circuit Breaker vẫn mở (OPEN) do cấu hình thời gian chờ chuyển trạng thái (`waitDurationInOpenState`) hoặc số lượng request thử nghiệm (`permittedNumberOfCallsInHalfOpenState`) quá khắt khe, chặn đứng cơ hội tự chữa lành của hệ thống.
* **Quyết định Senior**:
  1. **Săn lùng loại lỗi qua Metric**: Quét Grafana tìm các metric `resilience4j_circuitbreaker_state` và `resilience4j_circuitbreaker_calls` để xác định mạch mở do lỗi hệ thống (Exception/5xx) hay do lỗi phản hồi chậm (Slow Call).
  2. **Truy vết lỗi sâu (Distributed Tracing)**: Tìm Trace ID của các request bị lỗi ngay trước thời điểm mạch mở trên Jaeger/Zipkin để phát hiện nguyên nhân gốc rễ từ downstream (ví dụ: DB sập, nghẽn mạng, lỗi logic).
  3. **Điều chỉnh cấu hình nhạy cảm**: Tối ưu hóa kích thước cửa sổ trượt (`slidingWindowSize`), nâng thời gian chờ thử lại và đảm bảo có cơ chế cảnh báo tự động qua Slack/Telegram khi mạch chuyển trạng thái từ CLOSED sang OPEN.

## 🔍 Chi tiết bản chất thực chiến: Quy trình Điều tra sự cố Ngắt mạch

Khi nhận cảnh báo Circuit Breaker của một API quan trọng chuyển sang trạng thái OPEN liên tục, hãy tiến hành điều tra theo 3 bước sau:

```
[Nhận Cảnh Báo Circuit Breaker OPEN]
                 │
                 ▼
[Bước 1: Phân tích Metrics trên Grafana] ──> Xác định mạch mở do 'Failure Rate' hay 'Slow Call Rate'
                 │
                 ▼
[Bước 2: Quét Log & Distributed Tracing] ──> Tìm Trace ID có chứa Exception (Timeout, SocketException, 5xx)
                 │
                 ▼
[Bước 3: Rà soát & Tuning cấu hình]     ──> Đánh giá slidingWindowSize, waitDuration, và permittedCalls
```

### 1. Phân tích 3 Nguyên nhân chính làm Circuit Breaker mở liên tục

* **Nguyên nhân 1: Downstream Service sập vật lý / quá tải**
  * *Triệu chứng*: Log ngập tràn `ConnectException`, `SocketTimeoutException` hoặc lỗi HTTP `502 Bad Gateway`, `503 Service Unavailable`.
  * *Hành động*: Liên hệ đội ngũ vận hành downstream service để kiểm tra tình trạng tài nguyên (CPU, RAM, DB connection pool) của họ.
* **Nguyên nhân 2: Lỗi mạng hoặc cấu hình Timeout quá ngắn**
  * *Triệu chứng*: Tỷ lệ `Slow Call Rate` vượt ngưỡng. Mạch mở không phải vì downstream ném lỗi, mà vì thời gian phản hồi vượt quá `slowCallDurationThreshold`.
  * *Hành động*: Kiểm tra độ trễ mạng giữa 2 vùng (Network Latency), rà soát lại xem cấu hình timeout của HTTP client có quá nhạy cảm so với SLA thực tế của downstream không.
* **Nguyên nhân 3: Mạch bị kẹt ở trạng thái OPEN do cấu hình sai**
  * *Triệu chứng*: Downstream đã hết lỗi, nhưng mạch không chịu chuyển sang `HALF_OPEN`.
  * *Lý do*: Đặt `waitDurationInOpenState` quá lớn (ví dụ: 1 tiếng) hoặc do lưu lượng request thực tế quá thấp khiến cửa sổ trượt không thu thập đủ số lượng request tối thiểu (`minimumNumberOfCalls`) để đánh giá lại trạng thái ở vòng `HALF_OPEN`.

## 🎨 Sơ đồ trực quan (Vòng đời chuyển đổi trạng thái Circuit Breaker)

```mermaid
stateDiagram-v2
    [*] --> CLOSED : Khởi tạo hệ thống
    
    CLOSED --> OPEN : Tỷ lệ lỗi / chậm vượt ngưỡng \n (Failure Rate > Threshold)
    Note over OPEN: Chế độ Fail-Fast: \n Cắt kết nối hoàn toàn, \n Chạy trực tiếp vào Fallback.
    
    OPEN --> HALF_OPEN : Đợi hết thời gian \n waitDurationInOpenState
    Note over HALF_OPEN: Chế độ Thử Nghiệm: \n Cho phép số lượng nhỏ request đi qua \n (permittedNumberOfCalls)
    
    HALF_OPEN --> CLOSED : Các request thử nghiệm thành công \n (Tỷ lệ lỗi dưới ngưỡng)
    HALF_OPEN --> OPEN : Có request thử nghiệm bị lỗi \n (Tỷ lệ lỗi tiếp tục vượt ngưỡng)
```

## 💻 Code thực chiến: Lắng nghe trạng thái và cấu hình Alerting tự động

Để không bị rơi vào trạng thái "mù thông tin" khi Circuit Breaker hoạt động, chúng ta đăng ký Listener lắng nghe sự kiện chuyển trạng thái để tự động ghi log có cấu trúc (Structured Log) và kích hoạt cảnh báo khẩn cấp (Alerting).

```java
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.circuitbreaker.CircuitBreakerRegistry;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.context.annotation.Configuration;

import javax.annotation.PostConstruct;

@Slf4j
@Configuration
@RequiredArgsConstructor
public class CircuitBreakerMonitorConfig {

    private final CircuitBreakerRegistry circuitBreakerRegistry;
    private final AlertNotificationService alertNotificationService;

    @PostConstruct
    public void registerListeners() {
        // ✅ Duyệt qua toàn bộ các Circuit Breaker đã cấu hình trong hệ thống
        circuitBreakerRegistry.getAllCircuitBreakers().forEach(cb -> {
            log.info("ℹ️ Đang đăng ký Monitor Listener cho Circuit Breaker: {}", cb.getName());

            // 1. Lắng nghe sự kiện chuyển đổi trạng thái (CLOSED -> OPEN -> HALF_OPEN...)
            cb.getEventPublisher().onStateTransition(event -> {
                String cbName = event.getCircuitBreakerName();
                CircuitBreaker.StateTransition transition = event.getStateTransition();
                
                log.error("🚨 THAY ĐỔI TRẠNG THÁI MẠCH: Cầu chì [{}] chuyển từ {} sang {}", 
                        cbName, transition.getFromState(), transition.getToState());

                // Gửi cảnh báo khẩn cấp lên Slack/Telegram nếu mạch bị MỞ (OPEN)
                if (transition.getToState() == CircuitBreaker.State::OPEN) {
                    alertNotificationService.sendSlackAlert(cbName, 
                            "Cầu chì ngắt mạch đã mở! Hệ thống đang kích hoạt chế độ Fail-Fast bảo vệ luồng.");
                } else if (transition.getToState() == CircuitBreaker.State::CLOSED) {
                    alertNotificationService.sendSlackAlert(cbName, 
                            "Mạch đã đóng lại an toàn. Dịch vụ downstream đã hồi phục.");
                }
            });

            // 2. Lắng nghe sự kiện ném lỗi của Circuit Breaker
            cb.getEventPublisher().onError(event -> {
                log.warn("⚠️ Circuit Breaker [{}] ghi nhận lỗi thứ: {}. Chi tiết lỗi: {}", 
                        event.getCircuitBreakerName(), 
                        cb.getMetrics().getNumberOfFailedCalls(),
                        event.getThrowable().getMessage());
            });
        });
    }
}
```

## 📊 Bảng so sánh 3 trạng thái Circuit Breaker thực chiến

| Trạng thái | Lưu lượng đi qua | Thời gian xử lý request | Hành động khi có cuộc gọi mới | Trình kích hoạt chuyển trạng thái tiếp theo |
| :--- | :--- | :--- | :--- | :--- |
| **`CLOSED`** | **100% Traffic** | Bình thường | Gửi request trực tiếp sang downstream. | Chuyển sang `OPEN` khi tỷ lệ lỗi vượt ngưỡng trong cửa sổ trượt. |
| **`OPEN`** | **0% Traffic** | Cực nhanh (~5ms) | Ngăn chặn cuộc gọi ngay lập tức, trả lỗi Fail-Fast hoặc Fallback. | Tự động chuyển sang `HALF_OPEN` sau khoảng thời gian `waitDuration`. |
| **`HALF_OPEN`** | **Giới hạn nhỏ** (ví dụ: 5-10 request) | Bình thường | Cho phép một vài request đi qua để thử nghiệm sức khỏe downstream. | - Quay về `CLOSED` nếu thử nghiệm thành công.<br>- Trở lại `OPEN` lập tức nếu có lỗi xảy ra. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Mạch mở ảo (False Positive Circuit Breaking) do Cold Start"
* **Vấn đề**: Khi service của bạn vừa khởi động (hoặc khi mới deploy lúc sáng sớm traffic rất thấp), request đầu tiên gọi sang downstream bị timeout. Do `slidingWindowSize` nhỏ hoặc chưa nhận đủ số lượng request tối thiểu (`minimumNumberOfCalls` mặc định là 100 nhưng bạn đặt nhầm là 1), Circuit Breaker lập tức tính toán tỷ lệ lỗi là 100% và **mở mạch ngay lập tức**. Toàn bộ các request tiếp theo bị chặn đứng dù hệ thống hoàn toàn bình thường.
* **Giải pháp khắc phục**: Luôn thiết lập tham số `minimumNumberOfCalls` hợp lý (ví dụ: tối thiểu phải có 20 - 50 request đi qua mới bắt đầu tính tỷ lệ lỗi để mở mạch).

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Có nên cấu hình Circuit Breaker cho các API mang tính chất ghi dữ liệu (ví dụ: API Tạo Đơn Hàng) không? Nếu mạch mở và chạy vào Fallback thì xử lý đơn hàng thế nào?**
  * *Trả lời*:
    * **Tuyệt đối KHÔNG sử dụng Fallback trả dữ liệu ảo/dữ liệu mặc định** cho các API mang tính chất thay đổi trạng thái (State-changing transactions như thanh toán, tạo đơn hàng). Người dùng không thể chấp nhận việc bấm "Đặt mua" mà hệ thống trả về thông báo giả dạng thành công.
    * Thay vào đó, khi Circuit Breaker của API Ghi mở:
      1. Khối Fallback phải ném ra một Custom Exception được định nghĩa rõ ràng (ví dụ: `ServiceTemporarilyUnavailableException`).
      2. API Gateway dịch exception này thành mã lỗi **HTTP 429 Too Many Requests** hoặc **HTTP 503 Service Unavailable** kèm theo thông điệp rõ ràng: *"Hệ thống đang quá tải, vui lòng thử lại sau 30 giây"*.
      3. Hoặc chuyển đổi kiến trúc từ Đồng bộ (Synchronous) sang Bất đồng bộ (Asynchronous): Lưu yêu cầu tạo đơn hàng vào một Message Queue (Outbox/Kafka) và phản hồi cho client: *"Đơn hàng của bạn đang được xử lý ngầm"*.
