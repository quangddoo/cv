# Transaction thiếu isolation gây sai dữ liệu như thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Thiếu sự cô lập (Isolation) giữa các Transaction chạy song song là nguyên nhân gây ra các hiện tượng bất thường về dữ liệu (**Database Concurrency Anomalies**). Khi nhiều luồng cùng đọc và ghi vào một bảng dữ liệu mà không có cơ chế khóa (locking) hoặc phân chia phiên bản (versioning) phù hợp, hệ thống sẽ rơi vào trạng thái bất toàn vẹn, vi phạm trực tiếp chữ **I** trong nguyên lý **ACID**.
* **Thảm họa thực chiến được giải quyết**:
  1. **Thất thoát tài chính do Dirty Read (Đọc rác)**: Khách hàng A thực hiện giao dịch chuyển tiền. Giao dịch A cập nhật số dư tài khoản lên 10 triệu nhưng chưa commit. Đúng lúc đó, luồng đối soát B chạy qua đọc thấy số dư là 10 triệu và ghi nhận báo cáo thành công. Ngay sau đó, giao dịch A bị lỗi kết nối bên thứ ba và hệ thống thực hiện `ROLLBACK`. Kết quả: Báo cáo đối soát thừa tiền so với thực tế ở ngân quỹ.
  2. **Khuyến mãi quá hạn mức do Phantom Read (Đọc bóng ma)**: Chiến dịch phát 100 voucher VIP. Giao dịch 1 chạy câu lệnh `SELECT COUNT(*)` thấy mới có 99 voucher được phát. Cùng lúc, Giao dịch 2 cũng chạy và thấy 99 voucher. Cả hai giao dịch đều nghĩ mình an toàn nên cùng chèn (`INSERT`) thêm 2 voucher mới, đưa tổng số voucher phát ra lên 101, phá vỡ hạn ngạch kinh doanh.
* **Quyết định Senior**:
  1. **Tuyệt đối không dùng Read Uncommitted**: Mức cô lập này không cung cấp bất kỳ sự bảo vệ nào và hầu như không bao giờ được dùng trên Production.
  2. **Hiểu rõ cài đặt mặc định của DB**: PostgreSQL mặc định là `Read Committed`, MySQL mặc định là `Repeatable Read` (sử dụng MVCC và Next-Key Locks để chặn cả Phantom Read trong nhiều trường hợp).
  3. **Kết hợp Khóa nghiệp vụ thay vì nâng Isolation Level quá cao**: Thay vì chuyển toàn bộ DB sang mức `Serializable` (gây thắt nút cổ chai hiệu năng và tăng vọt Deadlock), Senior sử dụng `Read Committed` kết hợp với **Optimistic Locking (`@Version`)** hoặc **Pessimistic Locking (`SELECT FOR UPDATE`)** cho các tài nguyên nhạy cảm.

## 🔍 Chi tiết bản chất thực chiến: 3 Hiện tượng bất thường kinh điển

Để hiểu rõ cách thiếu isolation tàn phá hệ thống, ta cần mổ xẻ 3 hiện tượng xung đột dữ liệu:

### 1. Dirty Read (Đọc dữ liệu chưa commit)
Xảy ra khi Transaction A thay đổi một bản ghi nhưng chưa commit, Transaction B vào đọc bản ghi đó và sử dụng giá trị mới này. Nếu sau đó Transaction A rollback, dữ liệu Transaction B đã đọc và xử lý trở thành dữ liệu "ma", hoàn toàn không tồn tại trong DB.

### 2. Non-repeatable Read (Đọc không nhất quán giữa các lần)
Xảy ra khi Transaction A đọc một dòng dữ liệu. Transaction B nhảy vào sửa dòng dữ liệu đó và commit. Transaction A đọc lại dòng dữ liệu đó lần thứ 2 và thấy giá trị đã thay đổi. 
* *Hệ quả*: Logic nghiệp vụ của Transaction A dựa trên giá trị đọc lần 1 sẽ bị sai lệch hoàn toàn ở các bước tính toán phía sau.

### 3. Phantom Read (Đọc bóng ma - Xuất hiện dòng mới)
Xảy ra khi Transaction A truy vấn một dải dữ liệu thỏa mãn điều kiện lọc (ví dụ: các hóa đơn có giá trị > 1 triệu). Transaction B chèn thêm một dòng mới (`INSERT`) thỏa mãn điều kiện lọc này và commit. Transaction A chạy lại câu lệnh truy vấn cũ và đột nhiên thấy có thêm một bản ghi mới xuất hiện từ hư vô.

## 🎨 Sơ đồ trực quan: Luồng lỗi Non-repeatable Read tàn phá nghiệp vụ

Dưới đây là kịch bản Giao dịch kiểm tra hạn mức ví (Tx A) bị lỗi tính toán do Giao dịch rút tiền (Tx B) chen ngang:

```
Transaction A (Kiểm toán hạn mức)                   Transaction B (User Rút tiền)
┌─────────────────────────────────┐                 ┌─────────────────────────────────┐
│ 1. Đọc hạn mức ví:              │                 │                                 │
│    SELECT balance FROM wallet   │                 │                                 │
│    WHERE id = 1; -> Lấy 100$    │                 │                                 │
│                                 │                 │ 2. Khách rút 80$:               │
│                                 │                 │    UPDATE wallet SET balance=20 │
│                                 │                 │    WHERE id = 1;                │
│                                 │                 │    COMMIT; (Thành công ✔)       │
│ 3. Tính toán dựa trên 100$:     │                 │                                 │
│    Giả định ví vẫn còn 100$.    │                 │                                 │
│ 4. Chạy lại đối soát:           │                 │                                 │
│    SELECT balance FROM wallet   │                 │                                 │
│    WHERE id = 1; -> Thấy 20$!   │                 │                                 │
│    (Sai lệch logic nghiệp vụ!)  │                 │                                 │
└─────────────────────────────────┘                 └─────────────────────────────────┘
=> HỆ QUẢ: Báo cáo tài chính bị lệch hoặc hệ thống ném ngoại lệ do số liệu bất nhất.
```

## 💻 Code thực chiến: Bẫy Concurrency trong Java & Cách cứu nguy bằng Lock

### 1. Kịch bản lỗi khi dùng Isolation mặc định không kèm Lock
Đoạn code dưới đây chạy ở mức cô lập mặc định (thường là `Read Committed`). Khi hai luồng cùng đọc số dư và cộng tiền, hệ thống sẽ bị lỗi **Lost Update** (Cập nhật bị ghi đè chèn lấp).

```java
@Service
public class WalletService {

    @Autowired
    private WalletRepository walletRepository;

    // LỖI: Chạy song song sẽ bị đè dữ liệu (Lost Update)
    @Transactional
    public void addMoneyUnsafe(Long walletId, double amount) {
        Wallet wallet = walletRepository.findById(walletId)
            .orElseThrow(() -> new IllegalArgumentException("Wallet not found"));
        
        double newBalance = wallet.getBalance() + amount;
        wallet.setBalance(newBalance);
        walletRepository.save(wallet);
    }
}
```

### 2. Giải pháp 1: Sử dụng Optimistic Lock (Khóa lạc quan) với @Version (Khuyến nghị cho Write-low, Read-high)
Thêm trường `@Version` vào Entity. Hibernate sẽ tự động so khớp version khi update. Nếu có xung đột, hệ thống sẽ ném ra `ObjectOptimisticLockingFailureException` để ta chủ động retry hoặc trả lỗi cho client.

```java
// Entity định nghĩa trường Version
@Entity
@Getter
@Setter
public class Wallet {
    @Id
    private Long id;
    private double balance;
    
    @Version
    private Long version; // Trường thần thánh để kiểm soát concurrency
}

// Service xử lý bắt lỗi và Retry
@Service
@Slf4j
public class WalletService {
    @Autowired
    private WalletRepository walletRepository;

    @Transactional
    public void addMoneyOptimistic(Long walletId, double amount) {
        int maxRetries = 3;
        int attempt = 0;
        
        while (attempt < maxRetries) {
            try {
                Wallet wallet = walletRepository.findById(walletId)
                    .orElseThrow(() -> new IllegalArgumentException("Wallet not found"));
                
                wallet.setBalance(wallet.getBalance() + amount);
                walletRepository.saveAndFlush(wallet); // Kích hoạt ghi xuống DB ngay để check version
                return; // Thành công
            } catch (ObjectOptimisticLockingFailureException e) {
                attempt++;
                log.warn("Conflict detected for wallet {}. Retrying attempt {}/{}", walletId, attempt, maxRetries);
                if (attempt >= maxRetries) {
                    throw new RuntimeException("System is busy. Please try again later.", e);
                }
                // Có thể delay nhẹ trước khi thử lại (Exponential Backoff)
                try { Thread.sleep(50); } catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
            }
        }
    }
}
```

### 3. Giải pháp 2: Sử dụng Pessimistic Lock (Khóa bi quan - SELECT ... FOR UPDATE)
Phù hợp cho các ví dụ giao dịch tiền tệ khốc liệt, nơi tỷ lệ xung đột cực kỳ cao. Nó sẽ khóa cứng bản ghi ở tầng DB, buộc các transaction khác muốn đọc/ghi phải xếp hàng chờ đợi.

```java
public interface WalletRepository extends JpaRepository<Wallet, Long> {
    
    @Lock(LockModeType.PESSIMISTIC_WRITE) // Tạo câu lệnh SELECT ... FOR UPDATE
    @Query("SELECT w FROM Wallet w WHERE w.id = :id")
    Optional<Wallet> findByIdForUpdate(@Param("id") Long id);
}

@Service
public class WalletService {
    @Autowired
    private WalletRepository walletRepository;

    @Transactional
    public void addMoneyPessimistic(Long walletId, double amount) {
        // Luồng chạy sẽ block tại đây cho đến khi lấy được khóa độc quyền của DB
        Wallet wallet = walletRepository.findByIdForUpdate(walletId)
            .orElseThrow(() -> new IllegalArgumentException("Wallet not found"));
        
        wallet.setBalance(wallet.getBalance() + amount);
        walletRepository.save(wallet);
    }
}
```

## 📊 Bảng so sánh 4 Mức cô lập Transaction chuẩn SQL

| Isolation Level | Dirty Read | Non-repeatable Read | Phantom Read | Hiệu năng hệ thống | Đánh giá thực chiến |
| :--- | :---: | :---: | :---: | :--- | :--- |
| **Read Uncommitted** | ❌ Bị | ❌ Bị | ❌ Bị | **Siêu nhanh** | Tuyệt đối cấm dùng trên Production vì không an toàn. |
| **Read Committed** |  An toàn | ❌ Bị | ❌ Bị | **Rất tốt** | Mặc định của Oracle, PostgreSQL, SQL Server. Thường kết hợp thêm Lock ở ứng dụng. |
| **Repeatable Read** |  An toàn |  An toàn | ❌ Bị (MySQL xử lý được) | **Trung bình** | Mặc định của MySQL. Ngăn được Lost Update cơ bản nhờ snapshot đọc nhất quán. |
| **Serializable** |  An toàn |  An toàn |  An toàn | **Cực kỳ kém** | Gây nghẽn cổ chai trầm trọng, dễ tạo ra Deadlock hàng loạt. Hạn chế dùng. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Lock Timeout và treo ứng dụng khi dùng Pessimistic Lock"
* **Vấn đề**: Khi bạn dùng `PESSIMISTIC_WRITE` (khóa độc quyền), nếu Transaction A giữ khóa quá lâu (do gọi thêm API ngoài chậm chạp bên trong Transaction), toàn bộ các request khác gọi tới ví đó sẽ bị xếp hàng dài chờ đợi, dẫn đến cạn kiệt Connection Pool của ứng dụng (Thread Pool Exhaustion) và sập server.
* **Khắc phục**: 
  1. Cấu hình timeout cho khóa bi quan (ví dụ: `javax.persistence.lock.timeout` gán bằng `3000` - 3 giây). Nếu quá 3 giây không lấy được khóa, hệ thống ném lỗi ngay lập tức thay vì treo vô hạn.
  2. **Quy tắc vàng**: Tuyệt đối không gọi API bên thứ ba (như cổng thanh toán, service ngoài) bên trong một Transaction đang giữ khóa DB.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Trong Spring Boot, tôi có một hàm A có `@Transactional(isolation = Isolation.SERIALIZABLE)`. Hàm A gọi hàm B (không có annotation) nằm trong cùng một class. Hàm B thực hiện ghi dữ liệu. Mức isolation hoạt động thế nào?"**
* **Trả lời**: 
  * Đây là cạm bẫy tự gọi nội bộ (**Self-invocation**) do cơ chế Proxy-based AOP của Spring. Khi gọi trực tiếp phương thức trong cùng một class, cuộc gọi không đi qua Proxy của Spring, dẫn đến việc toàn bộ cấu hình `@Transactional` (bao gồm cả Isolation hay Propagation) trên phương thức được gọi sẽ **bị bỏ qua hoàn toàn**.
  * Giải pháp: Tách phương thức B sang một class Bean khác, hoặc tự inject chính proxy của mình (`@Autowired` vòng hoặc sử dụng `AopContext.currentProxy()`).
