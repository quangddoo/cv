# Những góc khuất và vấn đề của mẫu thiết kế Singleton (The Pitfalls of Singleton Pattern)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **Singleton Pattern** là mẫu thiết kế thuộc nhóm **Khởi tạo (Creational)**, nhằm đảm bảo một lớp chỉ có **duy nhất một thực thể (instance)** hoạt động trong toàn bộ vòng đời ứng dụng và cung cấp một điểm truy cập toàn cục tới nó.
* **Vì sao bị coi là Anti-Pattern?** Trong kỹ nghệ phần mềm hiện đại, Singleton thường bị hạn chế sử dụng vì:
  1. **Khó viết Unit Test**: Gây kết dính chặt chẽ (Tight Coupling) và lưu giữ trạng thái toàn cục (Global State) giữa các ca kiểm thử.
  2. **Vi phạm SRP (Đơn nhiệm)**: Lớp Singleton vừa gánh vác logic nghiệp vụ chính, vừa tự kiểm soát vòng đời khởi tạo của chính nó.
  3. **Vi phạm DIP (Đảo ngược phụ thuộc)**: Các lớp gọi phụ thuộc trực tiếp vào class vật lý Singleton thay vì Interface.
  4. **Vấn đề đa luồng (Concurrency)**: Dễ gây thắt nút cổ chai hiệu năng hoặc lỗi race-condition nếu không được đồng bộ đúng cách.

## 🔍 Phân tích chi tiết các vấn đề của Singleton

### 1. Cực kỳ khó viết Unit Test (The Testing Nightmare)
Đây là lý do lớn nhất khiến các kỹ sư từ chối Singleton. 
* Khi chạy Unit Test, mỗi test case cần được thực hiện độc lập trong một môi trường "sạch" (Isolated).
* Singleton giữ trạng thái toàn cục trong bộ nhớ. Nếu Test Case A thay đổi dữ liệu của Singleton, Test Case B chạy sau sẽ nhận dữ liệu bị biến đổi đó, dẫn đến kết quả kiểm thử không nhất quán (Flaky Tests).
* Rất khó Mock một Singleton truyền thống sử dụng phương thức static `getInstance()` mà không dùng các thư viện hack sâu vào ClassLoader (như PowerMock).

### 2. Tạo ra sự Kết dính chặt chẽ (Tight Coupling)
Khi sử dụng `MySingleton.getInstance().doSomething()`, bạn đang trực tiếp ghi cứng (hard-code) sự phụ thuộc vào mã nguồn. 
* Lớp gọi Singleton phụ thuộc hoàn toàn vào một cài đặt cụ thể cụ thể thay vì Interface trừu tượng.
* Điều này phá vỡ nguyên lý Dependency Inversion Principle (DIP), khiến việc thay đổi kiến trúc sau này trở thành thảm họa.

### 3. Vấn đề Đa luồng (Multi-threading Issues)
Nếu code Singleton viết không chuẩn, khi nhiều luồng cùng gọi `getInstance()` ở giây đầu tiên ứng dụng khởi chạy, hệ thống có thể tạo ra **nhiều hơn một thực thể** (phá vỡ hoàn toàn định nghĩa Singleton).
Nếu giải quyết bằng cách thêm `synchronized` vào toàn bộ phương thức `getInstance()`, hệ thống sẽ bị thắt nút cổ chai (bottleneck) hiệu năng cực kỳ nặng nề vì mọi luồng đọc đều phải xếp hàng đợi nhau.

## 💻 Code Example: Thiết kế Singleton đúng chuẩn và Giải pháp Thay thế

### ❌ Cài đặt sai/không an toàn (Classic Lazy Initialization Pitfall)
```java
public class UnsafeSingleton {
    private static UnsafeSingleton instance;
    private UnsafeSingleton() {}

    public static UnsafeSingleton getInstance() {
        if (instance == null) { // Luồng A và Luồng B cùng check thấy null ở cùng 1 thời điểm!
            instance = new UnsafeSingleton(); // Cả 2 luồng đều new => Tạo ra 2 instances!
        }
        return instance;
    }
}
```

### ✔️ Cài đặt đúng chuẩn (Bill Pugh Singleton Design - Khuyên dùng)
Tận dụng cơ chế ClassLoader của JVM để đạt được Lazy Loading và Thread-Safety tuyệt đối mà không cần dùng `synchronized`:

```java
public class SafeSingleton {
    private SafeSingleton() {
        // Chống phá vỡ Singleton bằng Reflection API
        if (SingletonHelper.INSTANCE != null) {
            throw new IllegalStateException("Thực thể đã tồn tại!");
        }
    }

    // Static nested class chỉ được load vào bộ nhớ khi phương thức getInstance() được gọi
    private static class SingletonHelper {
        private static final SafeSingleton INSTANCE = new SafeSingleton();
    }

    public static SafeSingleton getInstance() {
        return SingletonHelper.INSTANCE;
    }
}
```

### ✔️ Giải pháp Hiện đại: Hãy để Spring IoC Container quản lý Singleton
Thay vì tự code các cấu trúc Singleton thủ công lỗi thời, hãy để Spring quản lý vòng đời của đối tượng dưới dạng một **Spring Bean** có Scope mặc định là `Singleton`:

```java
@Service // Mặc định là Singleton Bean quản lý bởi Spring ApplicationContext
public class ModernDatabaseService {
    public void queryData() {
        // Thực thi logic database
    }
}

// Client nhận phụ thuộc qua Constructor (Dễ viết Unit Test, Dễ Mock!)
@RestController
public class OrderController {
    private final ModernDatabaseService dbService;

    public OrderController(ModernDatabaseService dbService) {
        this.dbService = dbService; // Dependency Injection!
    }
}
```

## 📊 So sánh: Singleton thủ công vs Spring Managed Singleton

| Tiêu chí | Singleton tự viết (Manual Code) | Spring Managed Singleton (IoC Bean) |
| :--- | :--- | :--- |
| **Cách truy cập** | Gọi qua static method: `Singleton.getInstance()`. | Được tiêm (Inject) tự động qua Constructor/Setter. |
| **Độ kết dính** | **Cực cao**: Liên kết cứng tên class vật lý vào code. | **Rất thấp**: Giao tiếp mượt mà qua Interface trừu tượng. |
| **Khả năng Unit Test** | **Cực kỳ khó**: Phải tìm cách reset state hoặc hack Reflection. | **Dễ dàng**: Chỉ cần Mock Interface và truyền vào Constructor. |
| **Khởi tạo trễ (Lazy)** | Phải viết code phức tạp (Double-Checked / Inner Class). | Chỉ cần thêm cấu hình `@Lazy` rất đơn giản. |
| **Đảm bảo Thread-safe**| Lập trình viên phải tự chịu trách nhiệm xử lý khóa luồng. | Container tự động đảm bảo an toàn đa luồng lúc khởi tạo. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Làm thế nào một lập trình viên có thể phá vỡ tính duy nhất (Singleton) của một Class trong Java? Làm sao để phòng chống?
* **Trả lời**: Có 3 cách kinh điển để phá vỡ Singleton và cách phòng chống tương ứng:
  1. **Dùng Reflection API**: Có thể thay đổi quyền truy cập của Constructor private thành `public` để `new` đối tượng mới.
     * *Phòng chống*: Throw Exception ngay bên trong Constructor nếu thực thể tĩnh đã khác null (như code ví dụ Bill Pugh ở trên).
  2. **Dùng Serialization/Deserialization**: Khi ghi một Singleton ra file rồi đọc ngược lại, JVM sẽ tạo ra một đối tượng hoàn toàn mới.
     * *Phòng chống*: Triển khai phương thức `readResolve()` để trả về thực thể hiện tại:
       ```java
       protected Object readResolve() { return getInstance(); }
       ```
  3. **Sử dụng Clone**: Nếu class kế thừa `Cloneable` và gọi hàm `clone()`.
     * *Phòng chống*: Override hàm `clone()` và ném ra ngoại lệ `CloneNotSupportedException`.
  * **Giải pháp tuyệt đối**: Sử dụng **Enum Singleton**. Java đảm bảo Enum không thể bị phá vỡ bởi Reflection hay Serialization:
    ```java
    public enum EnumSingleton {
        INSTANCE;
        public void doSomething() {}
    }
    ```

### 2. Kỹ thuật Double-Checked Locking (DCL) dưới đây có hoạt động đúng trong môi trường Java đa luồng không nếu thiếu từ khóa `volatile`? Tại sao?
```java
public class DclSingleton {
    private static DclSingleton instance; // Thiếu từ khóa volatile!
    private DclSingleton() {}

    public static DclSingleton getInstance() {
        if (instance == null) {
            synchronized (DclSingleton.class) {
                if (instance == null) {
                    instance = new DclSingleton();
                }
            }
        }
        return instance;
    }
}
```
* **Trả lời**: **KHÔNG HOẠT ĐỘNG ĐÚNG.** Đây là lỗi cực kỳ sâu sắc về bộ nhớ trong JVM (Java Memory Model):
  * Thao tác `instance = new DclSingleton();` không phải là một chỉ thị nguyên tử (atomic operation), mà nó được JVM biên dịch thành 3 bước:
    1. Cấp phát bộ nhớ cho đối tượng `DclSingleton`.
    2. Gọi Constructor để khởi tạo các thuộc tính của đối tượng.
    3. Trỏ biến `instance` tới vùng bộ nhớ đã cấp phát.
  * Vì JVM có cơ chế tối ưu **Tái sắp xếp chỉ thị (Instruction Reordering)**, thứ tự chạy có thể bị đổi thành 1 -> 3 -> 2.
  * Tại thời điểm bước 3 chạy xong nhưng bước 2 chưa chạy (đối tượng chưa khởi tạo xong hoàn toàn), một Luồng B khác gọi `getInstance()`. Nó thấy `instance != null` ở kiểm tra vòng ngoài, lập tức trả về `instance` này cho client sử dụng.
  * Hậu quả: Luồng B nhận được một đối tượng "rỗng/lỗi" (Partially Constructed Object) dẫn đến lỗi NullPointer hoặc dữ liệu sai lệch bất định.
  * *Khắc phục*: Bắt buộc phải khai báo biến `instance` là `private static volatile DclSingleton instance;` để chặn JVM tái sắp xếp chỉ thị.
