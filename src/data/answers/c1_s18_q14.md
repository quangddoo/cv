# Kiến trúc Sạch là gì? (Clean Architecture)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **Clean Architecture** (Kiến trúc Sạch) là một triết lý thiết kế kiến trúc phần mềm được đề xuất bởi Robert C. Martin (Uncle Bob). Nó tổ chức mã nguồn thành các **vòng tròn đồng tâm phân tầng** rõ rệt, bọc quanh nhân nghiệp vụ lõi ở trung tâm.
* **Quy tắc phụ thuộc (The Dependency Rule)**: Đây là luật tối cao của Clean Architecture: **Sự phụ thuộc mã nguồn chỉ được phép hướng từ ngoài vào trong**. Các vòng tròn bên trong hoàn toàn không biết gì về các vòng tròn bên ngoài (Không được import, không chứa class/kỹ thuật của vòng ngoài).
* **Các lớp phân tầng từ trong ra ngoài**:
  1. **Entities (Nghiệp vụ Doanh nghiệp)**: Chứa các quy tắc nghiệp vụ lõi bất biến.
  2. **Use Cases (Nghiệp vụ Ứng dụng)**: Điều phối luồng dữ liệu đi ra/vào các Entities để thực hiện các ca sử dụng cụ thể.
  3. **Interface Adapters (Bộ chuyển đổi)**: Chuyển đổi dữ liệu giữa dạng tối ưu của Use Case sang định dạng của tác nhân ngoài (Controller, Presenter, Gateway).
  4. **Frameworks & Drivers (Hạ tầng ngoài cùng)**: Nơi chứa Database, Web Server, UI, Frameworks (Spring Boot, Hibernate...).
* **Giá trị cốt lõi**: Giúp hệ thống độc lập hoàn toàn với Framework, độc lập với Database, độc lập với UI, dễ viết Unit Test và cực kỳ dễ bảo trì dài hạn.

## 🔍 Phân tích chuyên sâu Quy tắc Phụ thuộc (The Dependency Rule)

Trọng tâm của Clean Architecture nằm ở việc bảo vệ ranh giới kiến trúc. Sự phụ thuộc mã nguồn được định hướng như sau:

```
    ┌─────────────────────────────────────────────────────────────┐
    │  VÒNG 4: Frameworks & Drivers (Web, DB, Devices, UI)        │
    │    ┌─────────────────────────────────────────────────────┐  │
    │    │  VÒNG 3: Interface Adapters (Controllers, Gateways) │  │
    │    │    ┌─────────────────────────────────────────────┐  │  │
    │    │    │  VÒNG 2: Use Cases (Application Rules)      │  │  │  │
    │    │    │    ┌─────────────────────────────────────┐  │  │  │  │
    │    │    │    │  VÒNG 1: Entities (Enterprise Rules)│  │  │  │  │
    │    │    │    │                                     │  │  │  │  │
    │    │    │    └─────────────────────────────────────┘  │  │  │  │
    │    │    └─────────────────────────────────────────────┘  │  │  │  │
    │    └─────────────────────────────────────────────────────┘  │  │
    └─────────────────────────────────────────────────────────────┘
                ▲                     ▲                     ▲
                │      PHỤ THUỘC      │      PHỤ THUỘC      │
                └─────────────────────┴─────────────────────┘
                             (HƯỚNG VÀO TRONG)
```

### Chi tiết 4 phân tầng:
1. **Entities**: 
   * Là tầng sạch nhất. Chứa các đối tượng nghiệp vụ cốt lõi của doanh nghiệp (ví dụ: lớp `User` có phương thức `validatePassword()`).
   * Tầng này không thay đổi khi ứng dụng thay đổi giao diện hoặc đổi database.
2. **Use Cases**:
   * Chứa các luồng nghiệp vụ đặc thù của ứng dụng (ví dụ: `RegisterNewUser`, `CheckoutCart`).
   * Sử dụng các Entities để thực thi nghiệp vụ, nhận dữ liệu đầu vào và đẩy dữ liệu đầu ra mà không biết dữ liệu đó đến từ Web hay từ File.
3. **Interface Adapters**:
   * Chuyển đổi dữ liệu.
   * *Ví dụ*: Nhận request từ HTTP Controller (dạng JSON), chuyển đổi thành DTO truyền vào Use Case. Nhận kết quả từ Use Case, chuyển đổi thành JSON để Controller trả về cho Client.
4. **Frameworks & Drivers**:
   * Chứa các chi tiết vật lý cấp thấp nhất: Hệ quản trị CSDL cụ thể (PostgreSQL, MongoDB), Web Framework cụ thể (Spring Boot), các công cụ gửi mail.

## 💻 Code Example: Thiết kế hệ thống Đăng ký Thành viên

Dưới đây mô phỏng luồng đăng ký user qua các vòng tròn kiến trúc mà không vi phạm Dependency Rule.

### 1. Vòng 1: Entity (Domain Core)
```java
// domain.entity.User.java
public class User {
    private final String id;
    private final String email;
    private final String hashedPassword;

    public User(String id, String email, String hashedPassword) {
        this.id = id;
        this.email = email;
        this.hashedPassword = hashedPassword;
    }
    // Logic nghiệp vụ bất biến
    public boolean isValidEmail() {
        return email != null && email.contains("@");
    }
}
```

### 2. Vòng 2: Use Case (Application Business Rules)
```java
// domain.usecase.UserRegisterInputBoundary.java (Inbound Port)
public interface UserRegisterInputBoundary {
    void register(UserRegisterRequestModel request);
}

// domain.usecase.UserRegisterRequestModel.java (Pure DTO)
public class UserRegisterRequestModel {
    private String email;
    private String password;
    // Constructor, Getters
}

// domain.usecase.UserRegisterInteractor.java (Triển khai nghiệp vụ Use Case)
public class UserRegisterInteractor implements UserRegisterInputBoundary {
    private final UserRegisterOutputBoundary presenter; // Cổng ra
    private final UserRepositoryGateway repositoryGateway; // Cổng dữ liệu

    public UserRegisterInteractor(UserRegisterOutputBoundary presenter, UserRepositoryGateway repositoryGateway) {
        this.presenter = presenter;
        this.repositoryGateway = repositoryGateway;
    }

    @Override
    public void register(UserRegisterRequestModel request) {
        // Thực thi luồng nghiệp vụ sử dụng Entity
        String hashedPassword = PasswordHasher.hash(request.getPassword());
        User user = new User(UUID.randomUUID().toString(), request.getEmail(), hashedPassword);

        if (!user.isValidEmail()) {
            presenter.prepareFailView("Email không hợp lệ!");
            return;
        }

        repositoryGateway.saveUser(user);
        presenter.prepareSuccessView(new UserRegisterResponseModel(user.getEmail()));
    }
}
```

### 3. Vòng 3: Interface Adapter (Controller & Presenter)
```java
// adapter.controller.UserRegisterController.java
public class UserRegisterController {
    private final UserRegisterInputBoundary useCase;

    public UserRegisterController(UserRegisterInputBoundary useCase) {
        this.useCase = useCase;
    }

    // Nhận HTTP Request từ Vòng 4, chuyển đổi thành DTO gửi vào Vòng 2
    public void handlePostRequest(String email, String rawPassword) {
        UserRegisterRequestModel request = new UserRegisterRequestModel(email, rawPassword);
        useCase.register(request);
    }
}
```

## 📊 Phân tích Trade-offs: 3-Tier Layered vs Clean Architecture

| Tiêu chí | 3-Tier Layered Architecture (Truyền thống) | Clean Architecture (Sạch tuyệt đối) |
| :--- | :--- | :--- |
| **Hướng đi của code** | Thẳng tuột từ Controller -> Service -> DAO -> Database. | Hướng xuyên tâm từ Hạ tầng -> Bộ chuyển đổi -> Nghiệp vụ Use Cases. |
| **Độ độc lập Framework** | **Thấp**: Code nghiệp vụ ngập tràn các Annotation `@Entity`, `@Table` của Hibernate. | **Tuyệt đối**: Tầng lõi nghiệp vụ chỉ sử dụng Java thuần (Plain Java), không dính Framework. |
| **Tốc độ viết Unit Test** | Chậm hơn, thường phải khởi động Spring Context / DB Mock rườm rà. | **Siêu tốc**: Viết test cho toàn bộ logic Use Case chỉ tốn vài mili-giây vì là Object thuần. |
| **Dung lượng code và file** | Rất ít, code đi liền một mạch. | **Cực kỳ đồ sộ**: Phải viết rất nhiều Interface để phân ranh giới, sinh ra nhiều class DTO chuyển đổi. |
| **Tính ứng dụng phù hợp** | Phù hợp dự án vừa, nhỏ, MVP, ứng dụng CRUD đơn giản. | Phù hợp doanh nghiệp lớn (Enterprise), nghiệp vụ siêu phức tạp, vòng đời dự án trên 5 năm. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Tại sao quy tắc phụ thuộc (Dependency Rule) lại cấm việc truyền trực tiếp một JPA Entity (lớp có `@Entity` dùng cho Hibernate) đi thẳng từ Database lên Use Case hoặc REST Controller?
* **Trả lời**: Đây là lỗi thiết kế "phá vỡ Clean Architecture" phổ biến nhất:
  * **Nguyên nhân cấm**: Lớp JPA Entity bản chất là chi tiết kỹ thuật thuộc **Vòng 4 (Hạ tầng)**. Nó chứa các cấu trúc ràng buộc vật lý của Database (như `@Table`, `@Column`, khóa ngoại, quan hệ `@ManyToOne` lười tải).
  * Nếu đưa JPA Entity vào Use Case hay Controller, bạn đã vô tình cho phép tầng lõi nghiệp vụ phụ thuộc chặt chẽ vào cơ sở dữ liệu. Khi cơ sở dữ liệu thay đổi cấu trúc bảng, toàn bộ code nghiệp vụ trong Use Case cũng bị sập theo.
  * **Giải pháp chuẩn**: 
    1. Tầng Database (Vòng 4) sử dụng các class `JpaEntity`.
    2. Khi lấy dữ liệu lên, sử dụng Mapper để chuyển đổi sang lớp `Domain Entity` (Vòng 1 - thuần Java) trước khi đưa vào Use Case.
    3. Khi phản hồi Client, Use Case xuất ra một DTO đơn giản (`ResponseModel`) để Controller chuyển tiếp.

### 2. Khi nào Clean Architecture bị coi là "Over-engineering" (Quá đà vô ích) gây hại cho dự án? Làm sao để đưa ra quyết định áp dụng một cách thực tế?
* **Trả lời**: Clean Architecture sẽ phản tác dụng và gây hại trong 2 kịch bản:
  * **Dự án CRUD đơn giản**: Nếu ứng dụng chỉ thực hiện các thao tác thêm, đọc, xóa dữ liệu cơ bản không có logic phức tạp (ví dụ: trang quản lý danh mục), việc tạo ra 4-5 file class DTO, Interface, Mapper cho mỗi API là sự lãng phí tài nguyên khủng khiếp, làm chậm tiến độ dự án gấp 3 lần mà không mang lại giá trị nào.
  * **Quy tắc quyết định thực tế (Pragmatic Decision)**:
    * Chỉ áp dụng Clean Architecture khi **Logic nghiệp vụ (Business Rules) có độ phức tạp cao, thay đổi thường xuyên** và cần được bảo vệ độc lập khỏi sự thay đổi của công nghệ (như đổi DB, đổi Web Framework).
    * Nếu dự án ngắn hạn hoặc là bản thử nghiệm MVP, hãy chọn kiến trúc 3 lớp truyền thống để đi nhanh nhất có thể. Nếu hệ thống phình to sau này, ta có thể refactor dần sang Clean Architecture nhờ các Port/Adapter đã dựng sẵn.
