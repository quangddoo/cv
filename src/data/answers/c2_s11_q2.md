# Dữ liệu trong DB đúng nhưng API trả sai. Nguyên nhân có thể là gì?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Hiện tượng dữ liệu lưu trữ vật lý trong Database hoàn toàn chính xác (ví dụ: số dư là `100000000000000001` hoặc trạng thái đơn hàng là `COMPLETED`) nhưng khi gọi qua REST API hoặc GraphQL, kết quả trả về lại bị sai lệch (ví dụ: số dư biến thành `100000000000000000` hoặc trạng thái là `null`) là lỗi kinh điển về **Độ bất tương thích tầng biên (Edge-Boundary Incompatibility)**, thường xảy ra trong quá trình Serialization/Deserialization, Mapping logic hoặc Caching.
* **Thảm họa thực chiến được giải quyết**:
  1. **Lỗi mất độ chính xác JS (JavaScript Precision Loss)**: Sử dụng kiểu dữ liệu `Long` trong Java để lưu khóa chính hoặc số tiền cực lớn. Khi API trả về JSON dạng Number, JavaScript trên Frontend parse thành kiểu `Double-precision float` dẫn đến việc 4 chữ số cuối bị làm tròn. Kết quả là User click nút "Thanh toán" nhưng gọi API lên báo lỗi `Order Not Found` vì ID đơn hàng bị làm tròn sai lệch trên UI.
  2. **Cạm bẫy Vòng lặp tuần tuần hóa vô hạn (Infinite Serialization Loop)**: Biến mối quan hệ hai chiều `One-to-Many` (như `User` và `Orders`) thành JSON mà không cấu hình loại trừ, gây ra lỗi `StackOverflowError` làm crash luồng xử lý hoặc trả về JSON dài vô tận khiến API Gateway timeout.
* **Quyết định Senior**:
  1. **Phân rã kiểm tra từ lõi ra biên**: Thực hiện gọi API trực tiếp qua `cURL` hoặc `Postman` trực tiếp từ server để loại trừ khả năng lỗi do Frontend parse dữ liệu hoặc do CDN/Client-side cache.
  2. **Chuyển đổi số lớn thành String**: Luôn luôn serialize các ID kiểu `Long` hoặc số tài chính dạng `BigDecimal` thành định dạng chuỗi (`String`) trước khi đẩy ra JSON payload.
  3. **Tách biệt Entity khỏi DTO**: Tuyệt đối không bao giờ trả trực tiếp Hibernate Entity ra API. Luôn ánh xạ sang DTO (Data Transfer Object) với các validation và kiểu dữ liệu an toàn cho Serialization.

## 🔍 Chi tiết bản chất thực chiến: 4 Nhóm nguyên nhân đứt gãy

Khi database lưu dữ liệu chính xác nhưng API trả ra kết quả sai, nguyên nhân nằm ở một trong bốn tầng sau:

```
[Database: Dữ Liệu Đúng ✔]
          │
          ▼
┌───────────────────────────────────────────────┐
│ 1. Tầng ORM & Mapping Logic (Hibernate/Java)   │ 
│    - Lazy Loading trả về null hoặc proxy.      │
│    - Lombok @EqualsAndHashCode / Mapstruct lỗi.│
└───────────────────────────────────────────────┘
          │
          ▼
┌───────────────────────────────────────────────┐
│ 2. Tầng Serialization (Jackson/Gson)          │
│    - JSON Precision Loss (Long -> JS Number). │
│    - Mismatch Timezone / Format Date-Time.    │
└───────────────────────────────────────────────┘
          │
          ▼
┌───────────────────────────────────────────────┐
│ 3. Tầng Cache ứng dụng & Middleware (Redis/CDN)│
│    - Stale cache chưa được invalidate.        │
│    - Cấu hình Cache-Control nhầm trên Gateway.│
└───────────────────────────────────────────────┘
          │
          ▼
[API Response: Dữ Liệu Sai ❌]
```

### 1. Sai lệch do Serialization & Kiểu dữ liệu (Precision Loss & DateTime Mismatch)
* **Lỗi số lớn trong JavaScript (Safe Integer limit)**: Số nguyên an toàn tối đa trong JS là $2^{53} - 1$ (`9007199254740991`). Các ID được sinh tự động bằng cơ chế Snowflake ID hoặc số dư ví dạng xu (`nanoseconds` hoặc `micro-transactions`) thường vượt quá giới hạn này. Khi JSON truyền số nguyên này đi, JS tự động làm tròn các bit cuối.
* **Lỗi Timezone đứt gãy**: Database lưu trữ thời gian ở dạng `UTC` (`TIMESTAMP WITH TIME ZONE`). Nhưng tầng ứng dụng (như Jackson trong Spring Boot) mặc định serialize kiểu `Instant` hoặc `OffsetDateTime` về múi giờ local của server hoặc cấu hình mặc định là `GMT`. Kết quả là UI hiển thị ngày tạo đơn hàng bị lệch mất 7 tiếng (ở Việt Nam - GMT+7).

### 2. Sai lệch do Tầng ORM & Mapping (Lombok & Hibernate Lazy Loading)
* **Jackson nuốt Lazy Loading Proxy**: Khi serialize trực tiếp Hibernate Entity có chứa các quan hệ Lazy Loading (`@OneToMany(fetch = FetchType.LAZY)`), Jackson sẽ cố gắng đọc các trường này. Nếu Session của Hibernate đã đóng (`Detached Entity`), Jackson sẽ serialize trường đó thành `null` hoặc ném ra ngoại lệ `LazyInitializationException`. Nếu Session vẫn mở, nó sẽ tự động kích hoạt query phụ, gây ra thảm họa **N+1 Query** làm nghẽn băng thông DB và chậm API.
* **Lỗi mapper (MapStruct/ModelMapper)**: Sử dụng các thư viện tự động ánh xạ Entity sang DTO. Nếu tên các trường không khớp hoàn toàn (ví dụ: `isDeleted` trong Entity và `deleted` trong DTO), mapper có thể tự động gán giá trị mặc định (`false`) thay vì giá trị thực tế trong DB (`true`).

### 3. Sai lệch do Cache cũ (Stale Cache)
* Hệ thống cập nhật bản ghi trực tiếp bằng các câu lệnh SQL tự viết (`@Modifying` trong Spring Data JPA) bypass hoàn toàn lifecycle của JPA. Do đó, tầng ứng dụng không nhận biết được sự thay đổi để xóa cache Redis hay Hibernate Second-level cache, dẫn đến việc API vẫn liên tục đọc dữ liệu cũ từ cache.

## 💻 Code thực chiến: Cấu hình chuẩn hóa API Serialization với Spring Boot & Jackson

Dưới đây là cách giải quyết triệt để lỗi mất độ chính xác số lớn và cấu hình định dạng thời gian đồng bộ bằng cách sử dụng Custom Jackson Configuration.

### 1. DTO hoàn chỉnh giải quyết triệt để lỗi ép kiểu & Lazy Loading

```java
package com.example.dto;

import com.fasterxml.jackson.annotation.JsonFormat;
import com.fasterxml.jackson.databind.annotation.JsonSerialize;
import com.fasterxml.jackson.databind.ser.std.ToStringSerializer;
import lombok.Getter;
import lombok.Setter;

import java.math.BigDecimal;
import java.time.Instant;

@Getter
@Setter
public class OrderResponseDTO {

    // CHỐNG LỖI MẤT ĐỘ CHÍNH XÁC: Serialize Long thành String ở JSON payload
    @JsonSerialize(using = ToStringSerializer.class)
    private Long orderId;

    @JsonSerialize(using = ToStringSerializer.class)
    private Long userId;

    // Định dạng rõ ràng BigDecimal để tránh in ra dạng số khoa học (E-notation) như 1E+2
    @JsonFormat(shape = JsonFormat.Shape.STRING)
    private BigDecimal amount;

    private String status;

    // Chuẩn hóa định dạng thời gian theo chuẩn ISO-8601 UTC toàn cầu
    @JsonFormat(shape = JsonFormat.Shape.STRING, pattern = "yyyy-MM-dd'T'HH:mm:ss.SSS'Z'", timezone = "UTC")
    private Instant createdAt;
}
```

### 2. Cấu hình Jackson Global Configuration (Phương án quét diện rộng)

Nếu hệ thống có hàng trăm DTO, việc cấu hình thủ công `@JsonSerialize` trên từng trường rất dễ bị sót. Sử dụng cấu hình Global dưới đây để tự động convert tất cả các trường kiểu `Long`/`BigInteger` thành `String` khi serialize:

```java
package com.example.config;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.module.SimpleModule;
import com.fasterxml.jackson.databind.ser.std.ToStringSerializer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.converter.json.Jackson2ObjectMapperBuilder;

@Configuration
public class JacksonConfig {

    @Bean
    public ObjectMapper objectMapper(Jackson2ObjectMapperBuilder builder) {
        ObjectMapper objectMapper = builder.createXmlMapper(false).build();
        
        SimpleModule longToStringModule = new SimpleModule();
        // Áp dụng ToStringSerializer cho kiểu Long nguyên bản và kiểu Object Long
        longToStringModule.addSerializer(Long.class, ToStringSerializer.instance);
        longToStringModule.addSerializer(Long.TYPE, ToStringSerializer.instance);
        
        objectMapper.registerModule(longToStringModule);
        return objectMapper;
    }
}
```

### 3. Unit Test kiểm tra tính chính xác của JSON Payload

```java
package com.example.dto;

import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.json.JsonTest;
import org.springframework.boot.test.json.JacksonTester;
import org.springframework.boot.test.json.JsonContent;

import java.math.BigDecimal;
import java.time.Instant;

import static org.assertj.core.api.Assertions.assertThat;

@JsonTest
public class OrderSerializationTest {

    @Autowired
    private JacksonTester<OrderResponseDTO> jsonTester;

    @Test
    public void testSerialization_ShouldConvertLongToString_AndFormatInstantCorrectly() throws Exception {
        OrderResponseDTO dto = new OrderResponseDTO();
        dto.setOrderId(182736452910283745L);
        dto.setUserId(9007199254740999L); // Vượt giới hạn JS Safe Integer
        dto.setAmount(new BigDecimal("150000.50"));
        dto.setStatus("COMPLETED");
        dto.setCreatedAt(Instant.parse("2026-05-23T08:00:00Z"));

        JsonContent<OrderResponseDTO> result = jsonTester.write(dto);

        // Kiểm tra xem ID đã được bọc trong nháy kép (String) để bảo vệ độ chính xác hay chưa
        assertThat(result).extractingJsonPathStringValue("$.orderId").isEqualTo("182736452910283745");
        assertThat(result).extractingJsonPathStringValue("$.userId").isEqualTo("9007199254740999");
        
        // Kiểm tra BigDecimal định dạng phẳng
        assertThat(result).extractingJsonPathStringValue("$.amount").isEqualTo("150000.50");
        
        // Kiểm tra định dạng thời gian ISO chuẩn UTC
        assertThat(result).extractingJsonPathStringValue("$.createdAt").isEqualTo("2026-05-23T08:00:00.000Z");
    }
}
```

| :--- | :--- | :--- | :--- |
| **Biểu hiện lỗi** | Số cuối của ID lớn bị đổi thành các số 0 (ví dụ: `...83700` thay vì `...83745`). | Trực tiếp ném lỗi `500 Internal Server Error` hoặc trả về mảng quan hệ liên quan bị `null`. | User A thấy thông tin tài khoản hoặc số dư của User B sau khi đăng nhập. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy Lombok `@Data` trên Entity JPA làm hỏng luồng tuần hóa dữ liệu
* **Vấn đề nguy hiểm**: Khi bạn sử dụng `@Data` (tự động gen `@ToString` và `@EqualsAndHashCode`) của Lombok trên các JPA Entities có mối quan hệ hai chiều (`User` có `@OneToMany Orders`, và `Order` có `@ManyToOne User`). 
  Khi Jackson tiến hành serialize đối tượng `User`, nó gọi hàm `toString()` hoặc tuần hóa trường `orders`. Tầng con `Order` lại tuần hóa ngược về `User`. Quá trình này lặp lại vô tận cho đến khi máy chủ ném lỗi `java.lang.StackOverflowError` và sập luồng xử lý (Crash).
* **Giải pháp khắc phục**: Tuyệt đối không dùng `@Data` trên JPA Entity. Hãy thay thế bằng `@Getter` và `@Setter` riêng biệt. Đồng thời, cấu hình loại trừ trường quan hệ ở hàm toString/hashCode bằng cách sử dụng `@ToString.Exclude` của Lombok hoặc cấu hình `@JsonIgnore` / `@JsonBackReference` ở Jackson.

### 2. Câu hỏi đào sâu từ interviewer

* **Interviewer: "Tôi có một trường kiểu dữ liệu Instant lưu mốc thời gian trong DB đúng, nhưng khi trả ra JSON nó bị mất đi phần miligiây (.SSS), chỉ còn lại giây. Điều này làm hỏng logic so sánh phiên bản (Optimistic Locking/Concurrency) trên ứng dụng Client. Bạn xử lý thế nào?"**
* **Trả lời**:
  * Nguyên nhân là do cấu hình định dạng mặc định của Jackson khi serialize `java.time.Instant`. Theo mặc định, nếu phần miligiây bằng `.000`, Jackson sẽ tự động cắt bỏ phần đuôi và chỉ trả về dạng `yyyy-MM-dd'T'HH:mm:ssZ` để tối ưu hóa payload.
  * Để khắc phục triệt để và đảm bảo payload luôn có cấu trúc cố định, ta bắt buộc phải khai báo tường minh định dạng trên DTO hoặc cấu hình Object Mapper:
    1. **Khai báo tường minh trên trường**: Dùng `@JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ss.SSS'Z'", timezone = "UTC")`.
    2. **Tắt tính năng tự động cắt của Jackson**: Cấu hình trong file `application.properties`: 
       `spring.jackson.serialization.write-date-timestamps-as-nanoseconds=false` 
       để ép buộc Jackson luôn ghi đầy đủ độ chính xác của thời gian.
