# Thiết kế Dịch vụ Xác thực và Phân quyền (Authentication & Authorization Service)

## ⚡ Tóm tắt ngắn (30s)
* **Mục tiêu**: Thiết kế dịch vụ trung tâm chịu trách nhiệm xác thực danh tính người dùng (Authentication) và phân chia quyền hạn truy cập tài nguyên (Authorization). Hệ thống phải bảo mật tuyệt đối, hỗ trợ đăng nhập một lần (SSO), xác thực đa yếu tố (MFA), cấp phát thẻ bài truy cập (JWT/OAuth2) và phân quyền chi tiết (RBAC/ABAC) với hiệu năng kiểm tra cực nhanh ($< 2\text{ms}$ thông qua bộ nhớ đệm).
* **Core Logic**:
  * **JWT Lifecycle & Security**: Cấp phát cặp token: **Access Token** (thời gian sống ngắn, ví dụ 15 phút, tự chứa thông tin mã hóa bất đối xứng để Gateway tự giải mã mà không cần hỏi Auth Service) và **Refresh Token** (thời gian sống dài, lưu trong database để thu hồi phiên làm việc khi cần thiết).
  * **Phân quyền Phân tán (Decentralized AuthZ)**: Gateway hoặc các Microservice nghiệp vụ tự động xác thực quyền dựa trên các `claims` (vai trò/quyền hạn) nhúng trực tiếp bên trong Access Token (JWT), tránh nghẽn cổ chai truy vấn trực tiếp về Auth Service ở mỗi request.
  * **Mã hóa mật khẩu nâng cao**: Tuyệt đối không lưu mật khẩu dạng rõ. Sử dụng thuật toán băm chuyên dụng đi kèm muối (Salted) có độ trễ CPU điều chỉnh được như **Argon2id** hoặc **BCrypt** để chống lại các cuộc tấn công đoán mật khẩu (Brute-force) và bảng cầu vồng (Rainbow Table).

## 🔍 Phân tích yêu cầu (Requirements)

### 1. Functional Requirements (Yêu cầu chức năng)
* **Đăng ký / Đăng nhập**: Hỗ trợ đăng nhập bằng Email/Mật khẩu truyền thống, đăng nhập qua bên thứ ba (Google, Facebook via OAuth2/OIDC), và đăng nhập một lần (SSO).
* **Quản lý Quyền (Access Control)**: Phân quyền theo vai trò (**RBAC - Role-Based Access Control**) hoặc theo thuộc tính động (**ABAC - Attribute-Based Access Control**).
* **Xác thực đa yếu tố (MFA)**: Hỗ trợ mã xác thực một lần (TOTP qua Google Authenticator) hoặc gửi mã SMS/Email.
* **Thu hồi phiên (Logout/Revocation)**: Hỗ trợ đăng xuất toàn bộ thiết bị, thu hồi Token ngay lập tức khi phát hiện tài khoản bị hack.

### 2. Non-Functional Requirements (Yêu cầu phi chức năng)
* **Tính sẵn sàng cao (High Availability)**: Dịch vụ Auth sập đồng nghĩa với toàn bộ hệ thống bị đóng băng. Đòi hỏi thiết kế Active-Active đa vùng.
* **Hiệu năng kiểm tra Token cực nhanh**: Tận dụng cơ chế giải mã bất đối xứng (Public/Private Key) tại API Gateway để đạt thời gian kiểm tra quyền hạn $<1\text{ms}$.
* **Bảo mật tuyệt đối**: Đạt các chuẩn bảo mật khắt khe như OWASP Top 10, cấu hình mã hóa khóa ký JWT an toàn (rotate khóa định kỳ).

## 💾 Thiết kế Database & Quản lý Token Bất đối xứng (Asymmetric Signing)

### 1. Thuật toán ký JWT: Đối xứng (HS256) vs Bất đối xứng (RS256)
* **HS256 (HMAC with SHA-256)**: Dùng chung 1 khóa bí mật (Secret Key) để Ký và Xác minh Token. Có rủi ro lộ khóa cực kỳ nguy hiểm nếu chia sẻ khóa này cho toàn bộ các node Microservice để xác minh token.
* **RS256 (RSA Signature with SHA-256 - Khuyên dùng)**: Sử dụng cặp khóa công khai/bí mật:
  * **Auth Service** giữ kín **Khóa bí mật (Private Key)** để ký và tạo ra JWT.
  * **API Gateway & Microservices** chỉ cần giữ **Khóa công khai (Public Key)** để xác minh tính toàn vẹn của chữ ký JWT. Public Key có thể công khai rộng rãi (e.g., phơi qua JWKS endpoint `/.well-known/jwks.json`), đảm bảo độ an toàn tuyệt đối.

### 2. Thiết kế Schema Database cho Phân quyền (RBAC PostgreSQL)

```sql
-- Bảng người dùng chính
CREATE TABLE users (
    id VARCHAR(64) PRIMARY KEY,
    email VARCHAR(150) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL, -- Băm bằng BCrypt/Argon2
    is_mfa_enabled BOOLEAN DEFAULT FALSE,
    mfa_secret VARCHAR(64),
    status VARCHAR(30) DEFAULT 'ACTIVE', -- ACTIVE, LOCKED, PENDING
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Bảng Vai trò (Role)
CREATE TABLE roles (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) UNIQUE NOT NULL,    -- VIP_USER, ADMIN, SUPPORT
    description TEXT
);

-- Bảng Quyền hạn chi tiết (Permission)
CREATE TABLE permissions (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) UNIQUE NOT NULL,   -- order:create, order:refund, user:delete
    description TEXT
);

-- Bảng trung gian ánh xạ User - Role
CREATE TABLE user_roles (
    user_id VARCHAR(64) REFERENCES users(id) ON DELETE CASCADE,
    role_id INT REFERENCES roles(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, role_id)
);

-- Bảng trung gian ánh xạ Role - Permission
CREATE TABLE role_permissions (
    role_id INT REFERENCES roles(id) ON DELETE CASCADE,
    permission_id INT REFERENCES permissions(id) ON DELETE CASCADE,
    PRIMARY KEY (role_id, permission_id)
);
```

## 💻 Code Example: Sinh và Xác thực JWT bằng Java (RSA-256)

Dưới đây là mã nguồn Spring Boot thực thi việc ký tạo Access Token sử dụng **khóa bất đối xứng RSA** và giải mã xác thực chữ ký an toàn.

```java
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.PrivateKey;
import java.security.PublicKey;
import java.util.Date;
import java.util.List;

public class JwtTokenManager {

    private final PrivateKey privateKey;
    private final PublicKey publicKey;
    private static final long ACCESS_TOKEN_VALIDITY = 15 * 60 * 1000; // 15 phút

    public JwtTokenManager() throws Exception {
        // Sinh cặp khóa RSA 2048-bit (Trong thực tế nạp từ Vault hoặc Keystore)
        KeyPairGenerator keyPairGenerator = KeyPairGenerator.getInstance("RSA");
        keyPairGenerator.initialize(2048);
        KeyPair keyPair = keyPairGenerator.generateKeyPair();
        this.privateKey = keyPair.getPrivate();
        this.publicKey = keyPair.getPublic();
    }

    /**
     * Auth Service: Ký và tạo ra Access Token sử dụng Private Key
     */
    public String generateAccessToken(String userId, String email, List<String> permissions) {
        long now = System.currentTimeMillis();
        return Jwts.builder()
                .setSubject(userId)
                .claim("email", email)
                .claim("permissions", permissions) // Nhúng trực tiếp quyền hạn
                .setIssuedAt(new Date(now))
                .setExpiration(new Date(now + ACCESS_TOKEN_VALIDITY))
                .signWith(privateKey, SignatureAlgorithm.RS256) // Chữ ký bất đối xứng RS256
                .compact();
    }

    /**
     * API Gateway / Microservice: Xác thực token bằng Public Key công khai
     */
    public Claims parseAndVerifyToken(String token) {
        return Jwts.parserBuilder()
                .setSigningKey(publicKey) // Chỉ dùng Public Key để kiểm tra tính hợp lệ
                .build()
                .parseClaimsJws(token)
                .getBody();
    }

    public static void main(String[] args) throws Exception {
        JwtTokenManager manager = new JwtTokenManager();
        
        // 1. Giả lập đăng nhập thành công
        String token = manager.generateAccessToken(
                "usr_9988", 
                "alice@example.com", 
                List.of("order:create", "order:read")
        );
        System.out.println("🔑 JWT Token RS256: " + token);

        // 2. Giả lập API Gateway giải mã token
        Claims claims = manager.parseAndVerifyToken(token);
        System.out.println("✅ Xác thực thành công!");
        System.out.println("Subject UserID: " + claims.getSubject());
        System.out.println("User Email: " + claims.get("email"));
        System.out.println("User Permissions: " + claims.get("permissions"));
    }
}
```

## 📊 Trade-off Analysis: Session-based vs Token-based Authentication

| Đặc điểm | Session-based (Lưu trạng thái trên Server Cache) | Token-based (Stateless JWT - Khuyên dùng) |
| :--- | :--- | :--- |
| **Lưu trữ phía Server** | Tốn kém. Server phải duy trì bộ nhớ cache (Redis) để lưu trạng thái đăng nhập của toàn bộ user đang hoạt động. | **Không tốn kém**. Server hoàn toàn rảnh tay, không lưu trạng thái phiên, dữ liệu tự chứa trong Token ở Client. |
| **Khả năng co giãn (Scalability)** | Trung bình. Phải thiết kế cụm Redis tập trung cực lớn, gặp độ trễ mạng khi nhiều node truy vấn session đồng thời. | **Tốt nhất**. Phù hợp với kiến trúc phân tán toàn cầu, API Gateway tự giải mã bất đồng bộ cực nhanh mà không cần gọi API nội bộ nào. |
| **Thu hồi quyền lập tức (Revocation)** | **Tức thời**. Chỉ cần xóa session trong Redis, user lập tức bị đá ra ngoài ở request tiếp theo. | Gặp khó khăn. Một khi JWT được ký ra, nó sẽ có hiệu lực vĩnh viễn cho đến khi hết hạn (ví dụ sau 15 phút), trừ khi áp dụng kỹ thuật Blacklist. |
| **Bảo mật phía Client** | An toàn hơn nếu cấu hình Cookie `HttpOnly` và `Secure` (Chống tấn công XSS). | Dễ bị lộ nếu lưu trong LocalStorage của trình duyệt (dễ bị XSS đọc trộm). |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

1. **Làm thế nào để thu hồi ngay lập tức một JWT Token (e.g. khi người dùng đổi mật khẩu hoặc bấm Đăng xuất) trước khi nó tự hết hạn?**
   * *Trả lời*: Đây là điểm yếu kinh điển của Stateless JWT. Ta giải quyết bằng mô hình **Hybrid Token Validation**:
     * Access Token chỉ có thời hạn sống cực ngắn ($15$ phút).
     * Khi người dùng Đăng xuất hoặc Đổi mật khẩu, hệ thống sẽ lưu `jwt_id` (jti claim) của token đó vào một danh sách đen trong Redis (**Token Blacklist**) với thời gian sống bằng đúng thời gian còn lại của token.
     * API Gateway khi nhận request sẽ chạy một bộ lọc nhanh kiểm tra Redis Blacklist (mất $<0.5\text{ms}$). Nếu token nằm trong blacklist, lập tức từ chối truy cập.
     * Đối với Refresh Token, khi người dùng đổi mật khẩu, ta xóa toàn bộ Refresh Session trong PostgreSQL/Redis, buộc client khi hết hạn 15 phút Access Token sẽ không thể cấp mới được nữa và phải đăng nhập lại.

2. **Làm sao chống lại cuộc tấn công chiếm đoạt Refresh Token (Refresh Token Theft) để giả mạo phiên làm việc lâu dài của người dùng?**
   * *Trả lời*: Ta áp dụng cơ chế **Xoay vòng Refresh Token (Refresh Token Rotation)**:
     * Mỗi khi Client sử dụng một Refresh Token $R_1$ để đổi lấy Access Token mới, Auth Service sẽ đồng thời thu hồi $R_1$ và trả về một Refresh Token mới tinh $R_2$.
     * Trên server, ta lưu lại lịch sử liên kết chuỗi Token này. Nếu kẻ tấn công đánh cắp được $R_1$ và cố tình gửi lên để xin cấp phép sau khi Client thật đã dùng $R_1$ để đổi lấy $R_2$:
     * Auth Service sẽ lập tức phát hiện sự bất thường (một Refresh Token đã bị thu hồi nay lại được tái sử dụng). Hệ thống sẽ coi đây là hành vi xâm nhập, lập tức thu hồi toàn bộ các Refresh Token tiếp theo trong chuỗi liên kết ($R_2$, $R_3$) để đá cả kẻ tấn công lẫn nạn nhân ra ngoài, bắt buộc đăng nhập lại để đảm bảo an toàn.

3. **Làm thế nào để hệ thống Auth chịu tải được hàng trăm triệu request kiểm tra token mỗi ngày mà không bị quá tải CPU do mã hóa?**
   * *Trả lời*: 
     * Triển khai bộ lọc xác thực (JWT Signature Verification) trực tiếp tại biên của **API Gateway** hoặc chạy cục bộ ở từng Microservice (Decentralized Verification).
     * Cấu hình giải thuật mã hóa tối ưu như **EdDSA (ED25519)** thay vì RSA truyền thống. EdDSA cho phép sinh chữ ký ngắn hơn, bảo mật cao hơn và tốc độ xác thực nhanh gấp nhiều lần RSA, giúp giảm tải CPU tối đa cho API Gateway.
     * Phân phối Public Key qua **JWKS (JSON Web Key Set)** được cache mạnh mẽ tại Edge CDN của từng Region.
