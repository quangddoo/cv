# Quy trình manual data correction an toàn nên như thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Quy trình vá dữ liệu thủ công (Manual Data Correction / Data Patching) là quy trình vận hành nhạy cảm bậc nhất trên Production. Một quy trình chuẩn hóa của Senior/Staff Engineer phải tuân thủ nguyên tắc **"Không chạy lệnh ad-hoc trực tiếp, mọi thay đổi phải được coi như một đợt Deploy Code chính thức"**. Quy trình này bắt buộc đi qua 5 bước nghiêm ngặt: **Kiểm chứng -> Soạn thảo & Code Review -> Chạy thử Staging -> Dry-run trên Production -> Thực thi & Giám sát**.
* **Thảm họa thực chiến được giải quyết**:
  1. **Thảm họa "Sửa sai chồng sai"**: Kỹ sư vội vàng viết một script Python để tự động cộng bù tiền ví điện tử cho 200 khách hàng bị lỗi hệ thống. Do không có bước Code Review chéo, script bị lỗi logic vòng lặp làm cộng tiền lặp lại 10 lần cho mỗi khách, biến lỗi thất thoát nhỏ thành khủng hoảng thất thoát tiền tệ lớn.
  2. **Mất vết sửa lỗi khi Restore DB**: Đơn hàng bị lỗi được kỹ sư sửa trực tiếp bằng SQL. Một tuần sau, DB bị sự cố vật lý và phải Restore lại bản backup từ tuần trước. Do dữ liệu sửa tay trước đó không được lưu vết dưới dạng mã nguồn (Git Versioned) hay Audit Log, dữ liệu lỗi cũ xuất hiện trở lại mà không ai biết, làm nảy sinh khiếu nại cũ của khách hàng.
* **Quyết định Senior**:
  1. **Quản lý kịch bản vá dữ liệu bằng Git (GitOps for Data)**: Tuyệt đối không copy-paste SQL chạy thẳng. Mọi script vá dữ liệu (SQL, Python, Bash) phải được commit vào một repo Git chuyên biệt (`data-patches`), đi qua quy trình tạo Pull Request (PR) và được duyệt bởi ít nhất 1 Senior khác.
  2. **Bắt buộc có tham số `--dry-run`**: Mọi script chạy vá dữ liệu bắt buộc phải hỗ trợ chế độ chạy thử, in ra màn hình chính xác danh sách các ID sẽ bị ảnh hưởng và giá trị thay đổi trước/sau mà không thực sự ghi xuống DB.
  3. **Kiểm tra môi trường tự động (Environment Guard)**: Script phải tự động phát hiện chuỗi kết nối và bắt buộc người dùng nhập xác nhận bằng tay nếu phát hiện đang chạy trên môi trường `Production`.

## 🔍 Chi tiết bản chất thực chiến: Quy trình 5 Bước chuẩn hóa (Operational Runbook)

Khi có sự cố dữ liệu cần sửa tay diện rộng, Senior Engineer sẽ kích hoạt quy trình vận hành tiêu chuẩn:

```
[Sự cố dữ liệu cần vá] ──► [Bước 1: Điều tra & Trích xuất danh sách IDs ảnh hưởng]
                                      │
                                      ▼
                           [Bước 2: Soạn thảo script]
                             - Viết code có `--dry-run` & check env.
                             - Commit Git & Tạo Pull Request (PR).
                                      │
                                      ▼
                           [Bước 3: Code Review & Test]
                             - Senior khác review chéo và Approve PR.
                             - Chạy thử nghiệm trên môi trường Staging.
                                      │
                                      ▼
                        [Bước 4: Dry-run trên Production]
                             - Chạy script chế độ `--dry-run`.
                             - Xuất log, đối chiếu số lượng rows bị ảnh hưởng.
                                      │
                                      ▼
                         [Bước 5: Thực thi & Lưu vết]
                             - Chạy script `--execute` vào giờ thấp điểm.
                             - Bắn thông báo tự động lên Slack/Telegram.
```

### Bước 1: Xác định phạm vi ảnh hưởng (Targeting)
* Trích xuất danh sách các ID của bản ghi bị lỗi ra một file tĩnh (ví dụ: `target_ids.txt` hoặc `target_orders.csv`).
* Tuyệt đối không viết câu lệnh lọc động phức tạp trực tiếp trong script vá (ví dụ: `WHERE status = 'PENDING' AND updated_at < ...` vì trạng thái dữ liệu trên Prod biến động liên tục, có thể quét nhầm các đơn hàng mới tạo hợp lệ). File tĩnh chứa ID cứng là cách an toàn nhất để khoanh vùng blast radius.

### Bước 2: Soạn thảo Script có phòng vệ (Defensive Scripting)
* Script phải check chuỗi kết nối (Connection String), nếu phát hiện chữ `prod` hoặc cổng DB Production, bắt buộc hiển thị yêu cầu: `Type "CONFIRM_PROD_EXECUTION" to continue`.

### Bước 3: Chạy thử Staging & So sánh kết quả
* Tái tạo lại lỗi trên môi trường Staging, chạy script để đảm bảo dữ liệu biến đổi chính xác 100% như mong muốn, không sinh ra lỗi phụ.

## 🎨 Sơ đồ trực quan: Luồng hoạt động của Script vá dữ liệu phòng thủ

Sơ đồ mô tả cơ chế an toàn của script chặn đứng việc chạy nhầm môi trường hoặc chạy thiếu dry-run:

```
[Chạy Script] ──► [Kiểm tra Môi trường]
                         │
                         ├─► (Nếu là Production) ──► [Yêu cầu xác nhận thủ công bằng chữ]
                         │                                 │ (Nhập sai -> Abort ❌)
                         │                                 ▼ (Nhập đúng)
                         └─────────────────────────► [Kiểm tra Tham số]
                                                           │
                                 ┌─────────────────────────┴─────────────────────────┐
                                 ▼ (Nếu là --dry-run)                                ▼ (Nếu là --execute)
                      [Đọc DB, tính toán thay đổi]                        [Mở Transaction DB]
                      [In thông tin Before/After ra log]                  [Thực thi ghi dữ liệu]
                      [Rollback Transaction]                              [Commit Transaction]
                      [Thoát an toàn ✔]                                   [Bắn Alert thông báo hoàn tất 🚀]
```

## 💻 Code thực chiến: Mẫu Script Vá Dữ Liệu Python Phòng Thủ Chuẩn Mực

Dưới đây là một template script Python hoàn chỉnh, tích hợp đầy đủ cơ chế dry-run, kiểm tra môi trường, đọc ID từ file tĩnh và ghi log kiểm toán:

```python
#!/usr/bin/env python3
import sys
import argparse
import logging
import mysql.connector

# Cấu hình log ghi nhận chi tiết kiểm toán
logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s [%(levelname)s] [%(filename)s:%(lineno)d] - %(message)s',
    handlers=[
        logging.FileHandler("data_correction_audit.log"),
        logging.StreamHandler(sys.stdout)
    ]
)

def main():
    parser = argparse.ArgumentParser(description="Template vá dữ liệu an toàn cho Production")
    parser.add_argument("--db-host", required=True, help="Database Host URL")
    parser.add_argument("--file-ids", required=True, help="Đường dẫn file txt chứa danh sách ID cần vá")
    parser.add_argument("--dry-run", action="store_true", default=False, help="Chạy thử nghiệm không commit")
    parser.add_argument("--execute", action="store_true", default=False, help="Thực thi chạy thật vào DB")
    
    args = parser.parse_args()

    # 1. Bảo vệ môi trường: Chặn nếu chạy thiếu cả hai cờ hoặc bật cả hai
    if args.dry_run == args.execute:
        logging.error("LỖI: Bạn phải chọn duy nhất một cờ --dry-run HOẶC --execute")
        sys.exit(1)

    # 2. Phát hiện môi trường nhạy cảm
    is_production = "prod" in args.db_host.lower()
    if is_production and args.execute:
        logging.warning("🚨 CẢNH BÁO: BẠN ĐANG THỰC THI SỬA DỮ LIỆU TRÊN PRODUCTION! 🚨")
        confirm = input("Vui lòng nhập chính xác chữ 'CONFIRM_PRODUCTION_WRITE' để tiếp tục: ")
        if confirm != "CONFIRM_PRODUCTION_WRITE":
            logging.error("Hành động bị hủy do xác nhận sai.")
            sys.exit(1)

    # 3. Đọc danh sách ID tĩnh từ file
    try:
        with open(args.file_ids, "r") as f:
            target_ids = [int(line.strip()) for line in f if line.strip()]
        logging.info(f"Đọc thành công {len(target_ids)} IDs cần xử lý.")
    except Exception as e:
        logging.error(f"Không thể đọc file IDs: {e}")
        sys.exit(1)

    # 4. Kết nối Database và mở Transaction chủ động
    db_config = {
        'host': args.db_host,
        'user': 'data_patch_worker',
        'password': 'secure_password_123',
        'database': 'ecommerce'
    }
    
    conn = mysql.connector.connect(**db_config)
    conn.autocommit = False # Tắt autocommit để kiểm soát transaction thủ công
    cursor = conn.cursor(dictionary=True)

    total_updated = 0
    
    try:
        for idx, record_id in enumerate(target_ids):
            # Khóa dòng để tránh xung đột concurrent write
            cursor.execute("SELECT id, status, amount FROM orders WHERE id = %s FOR UPDATE", (record_id,))
            order = cursor.fetchone()
            
            if not order:
                logging.warning(f"ID {record_id} không tồn tại trong DB, bỏ qua.")
                continue
                
            old_status = order['status']
            
            # Chỉ vá các đơn hàng đang ở trạng thái lỗi PENDING
            if old_status == "PENDING":
                new_status = "PAID"
                
                # In thông tin kiểm toán trước/sau rõ ràng
                logging.info(f"[AUDIT] ID: {record_id} | Status: {old_status} -> {new_status} | Amount: {order['amount']}")
                
                if args.execute:
                    cursor.execute(
                        "UPDATE orders SET status = %s, updated_by = 'patch_job_q14' WHERE id = %s AND status = %s",
                        (new_status, record_id, old_status)
                    )
                    total_updated += 1
            
            # Cho DB nghỉ nhẹ nếu danh sách ID quá dài
            if idx % 100 == 0 and idx > 0:
                logging.info(f"Đã duyệt qua {idx}/{len(target_ids)} bản ghi...")

        # 5. Kết thúc Transaction
        if args.dry_run:
            logging.info(f"--- CHẾ ĐỘ DRY-RUN: ROLLBACK TOÀN BỘ THAY ĐỔI ---")
            conn.rollback()
            logging.info("Rollback thành công. Không có dữ liệu nào bị thay đổi.")
        elif args.execute:
            conn.commit()
            logging.info(f"--- THỰC THI THÀNH CÔNG: ĐÃ COMMIT ---")
            logging.info(f"Tổng số bản ghi thực tế được vá thành công: {total_updated}")

    except Exception as e:
        conn.rollback()
        logging.critical(f"LỖI HỆ THỐNG: Đã rollback toàn bộ giao dịch do gặp lỗi: {e}")
    finally:
        cursor.close()
        conn.close()

if __name__ == "__main__":
    main()
```

## 📊 Bảng so sánh các công cụ vận hành vá dữ liệu Production

| Tiêu chí | Dùng Script Python CLI chạy tay | Dùng Database Tool (DBeaver/PgAdmin) | Dùng Giao diện Quản trị (Admin Portal API) |
| :--- | :--- | :--- | :--- |
| **Tính an toàn** | **Rất cao** (Nhờ code kiểm tra môi trường, dry-run tự động). | Thấp (Dễ bấm nhầm execute nhầm file, quên rollback). | **Tuyệt đối 100%** (An toàn nhất vì không có quyền gõ query tự do). |
| **Lưu vết Git (Audit)** |  Có (File script lưu trên repo Git, có PR review lịch sử rõ ràng). | ❌ Không (Query gõ bay màu sau khi tắt ứng dụng). |  Có (Có log API của Admin). |
| **Tính linh hoạt** | **Siêu cao** (Vá được mọi ca lỗi nghiệp vụ phức tạp bằng code). | Cao | Thấp (Chỉ vá được các lỗi mà giao diện Admin hỗ trợ). |
| **Rủi ro Lock bảng** | Rất thấp (Do script tự chia nhỏ lô để cập nhật). | Cao (Kỹ sư hay chạy câu lệnh khổng lồ không chia lô). | Thấp. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Mất dấu dữ liệu lịch sử do ghi đè mù" (Blind Overwrite)
* **Vấn đề nguy hiểm**: Khi bạn thực hiện sửa trạng thái đơn hàng bị lỗi từ `PENDING` sang `PAID` bằng script. Tuy nhiên, trước thời điểm bạn chạy script 1 giây, khách hàng đã chủ động nhấn nút "Hủy đơn" trên ứng dụng và DB đã chuyển trạng thái thành `CANCELLED`. 
  * Nếu script của bạn không có điều kiện so khớp trạng thái cũ (`WHERE id = 456 AND status = 'PENDING'`), script sẽ ghi đè mù trạng thái `PAID` đè lên `CANCELLED`. Bạn vừa thực hiện một hành động vô lý: Giao hàng cho đơn hàng mà khách hàng đã hủy và hoàn tiền thành công.
* **Giải pháp khắc phục**:
  * Bắt buộc sử dụng kỹ thuật **Compare-and-Swap (CAS)** khi viết câu SQL Update trong script. Luôn đưa trạng thái cũ của bản ghi tại thời điểm trích xuất dữ liệu làm điều kiện lọc bắt buộc ở mệnh đề `WHERE` của câu lệnh `UPDATE`.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Sau khi bạn chạy script vá dữ liệu thành công cho 10,000 dòng trên Production, làm sao bạn chứng minh với tôi và bên Kiểm toán (Auditors) là dữ liệu đã được vá đúng 100% và không có bất kỳ dòng nào khác ngoài 10,000 dòng đó bị ảnh hưởng?"**
* **Trả lời**:
  * Để chứng minh một cách khoa học và thuyết phục trước kiểm toán, Senior áp dụng quy trình **Đối soát Hash chữ ký số (Checksum Verification)**:
    1. Trước khi chạy script, chạy câu lệnh xuất file chứa danh sách băm SHA256 trạng thái của 10,000 bản ghi lỗi làm mốc đối chứng (Baseline).
    2. Ghi nhận file log chạy của script (chứa thông tin Before/After chi tiết của từng dòng).
    3. Sau khi chạy, thực hiện chạy lại câu query xuất file băm của 10,000 bản ghi đó.
    4. So sánh số lượng dòng bị thay đổi trong bảng `audit_logs` của hệ thống trong khoảng thời gian chạy script. Số lượng bản ghi thay đổi trong bảng `audit_logs` phải khớp chính xác tuyệt đối bằng 10,000. Nếu có bất kỳ dòng nào khác bị thay đổi, bảng `audit_logs` sẽ lập tức tố cáo hành vi sai lệch này.
