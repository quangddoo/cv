# Tại sao không bao giờ nên sử dụng Lombok @Data trên JPA Entity?

## ⚡ Tóm tắt ngắn (30s)
*   **Bản chất**: Annotation `@Data` của Lombok là một công cụ tuyệt vời cho các lớp DTO/POJO phẳng vì nó tự động sinh ra `@Getter`, `@Setter`, `@ToString`, `@EqualsAndHashCode`, và `@RequiredArgsConstructor`. Tuy nhiên, áp dụng `@Data` lên **JPA Entity** là một lỗi thiết kế nghiêm trọng (Anti-pattern).
*   **Các thảm họa thực chiến**:
    1.  **Vòng lặp vô hạn gây sập luồng (`StackOverflowError`)**: Trong quan hệ hai chiều (ví dụ: `Parent` và `Child`), các hàm `toString()` và `hashCode()` do `@Data` tự sinh sẽ gọi đệ quy chéo nhau không điểm dừng khi bạn cố gắng ghi log hoặc đưa đối tượng vào Collection.
    2.  **Biến mất thực thể khỏi `Set` (Lost Entity in HashSet)**: `@EqualsAndHashCode` do `@Data` sinh ra sẽ so sánh **tất cả các trường** của thực thể. Khi thực thể mới được lưu xuống DB, trường ID thay đổi từ `null` sang một số cụ thể, làm giá trị `hashCode` thay đổi hoàn toàn. Kết quả: Bạn không thể tìm thấy hoặc xóa thực thể đó khỏi `HashSet` nữa, gây ra lỗi logic nghiệp vụ cực kỳ nghiêm trọng.
    3.  **Kích hoạt Lazy Loading ngoài ý muốn**: `toString()` tự động gọi getter của các quan hệ `@ManyToOne(fetch = FetchType.LAZY)`, ép Hibernate gửi câu lệnh SELECT tải dữ liệu không cần thiết dưới nền.
*   **Quyết định Senior**: Tuyệt đối không dùng `@Data`. Thay vào đó, hãy sử dụng riêng rẽ **`@Getter`**, **`@Setter`** và tự ghi đè `equals()`, `hashCode()` an toàn bằng tay.

## 🔍 Chi tiết bản chất thực chiến

### 1. Thảm họa đệ quy vô hạn trong quan hệ hai chiều
Khi sử dụng quan hệ hai chiều `@OneToMany` và `@ManyToOne` (ví dụ: `User` có danh sách `Order`, và `Order` có tham chiếu ngược lại `User`). 
Dưới đây là mô hình cuộc gọi đệ quy chết người khi bạn gọi `user.toString()` hoặc đưa đối tượng vào cấu trúc băm:

```mermaid
graph TD
    UserToString[User.toString] -->|In ra các thuộc tính bao gồm orders| OrdersList[orders Collection]
    OrdersList -->|In ra từng Order| OrderToString[Order.toString]
    OrderToString -->|In ra thuộc tính user| UserToString
    
    style UserToString fill:#f96,stroke:#333,stroke-width:2px
    style OrderToString fill:#f96,stroke:#333,stroke-width:2px
    Note over UserToString, OrderToString: Lặp vô tận trên RAM -> java.lang.StackOverflowError!
```

### 2. Sự cố phá vỡ cấu trúc HashSet (The Hash Contract Violation)
Cấu trúc dữ liệu `HashSet` hoặc `HashMap` hoạt động dựa trên hợp đồng bất biến của mã băm (`hashCode`). Khi bạn đưa một đối tượng vào `HashSet`, vị trí ngăn lưu trữ (bucket) của nó được quyết định bởi giá trị `hashCode` tại thời điểm đó.
*   **Bước 1**: Bạn tạo một thực thể mới: `User user = new User("John")` (ID là `null`).
*   **Bước 2**: Lombok `@Data` tính `hashCode` dựa trên mọi thuộc tính bao gồm cả ID null -> ví dụ trả về số `100500`. Bạn đưa user vào `Set`: `mySet.add(user)`. Đối tượng được xếp vào ngăn số `100500`.
*   **Bước 3**: Bạn lưu thực thể xuống DB: `userRepository.save(user)`. Database tự sinh ID cho user là `1`.
*   **Bước 4**: Vì ID thay đổi, Lombok tính lại `hashCode` -> lúc này trả về số `100999`.
*   **Bước 5**: Bạn kiểm tra xem đối tượng có trong Set không: `mySet.contains(user)`. `HashSet` sẽ đi tìm ở ngăn số `100999` và kết luận **không tìm thấy**!
Thực thể của bạn đã bị "mất tích" vĩnh viễn trong chính Collection của bạn trên RAM, gây ra những lỗi logic nghiệp vụ cực kỳ khó chịu.

## 💻 Code thực chiến: BAD vs GOOD trong sử dụng Lombok trên Entity

### ❌ BAD: Lạm dụng @Data bừa bãi gây lỗi sập hệ thống và hỏng HashSet
Lập trình viên đặt `@Data` trên cả hai thực thể `Department` và `Employee` có quan hệ hai chiều. Việc này lập tức gây ra lỗi `StackOverflowError` khi ghi log dữ liệu và làm hỏng cơ chế quản lý dữ liệu trong `Set`.

```java
@Entity
@Data // Anti-pattern 1: Sử dụng @Data sinh ra equals, hashCode, toString bừa bãi trên Entity!
public class DepartmentBad {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL)
    private List<EmployeeBad> employees = new ArrayList<>();
}

@Entity
@Data // Anti-pattern 2: Lặp lại sai lầm @Data trên thực thể con
public class EmployeeBad {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private DepartmentBad department;
}
```
*Kịch bản lỗi xảy ra lập tức khi gọi:*
```java
log.info("Bộ phận: {}", departmentBad); // Nổ StackOverflowError lập tức!
```

###  GOOD: Sử dụng các Annotation riêng biệt và ghi đè thủ công an toàn
Sử dụng các annotation đơn nhiệm của Lombok để tự động hóa Getter/Setter. Riêng các phương thức `equals()`, `hashCode()` và `toString()` nhạy cảm phải được định nghĩa thủ công, kiểm soát rõ ràng ranh giới thuộc tính để bảo vệ hệ thống 100%.

```java
@Entity
@Table(name = "departments")
@Getter // Đúng đắn 1: Chỉ tự động hóa Getter
@Setter // Đúng đắn 2: Chỉ tự động hóa Setter
public class DepartmentGood {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;

    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL)
    private List<EmployeeGood> employees = new ArrayList<>();

    // Đúng đắn 3: Tự viết toString() bỏ qua collection liên kết để tránh đệ quy vòng lặp
    @Override
    public String toString() {
        return "DepartmentGood{" +
               "id=" + id +
               ", name='" + name + '\'' +
               '}';
    }

    // Đúng đắn 4: equals và hashCode an toàn cho JPA Entity (chỉ so sánh ID vật lý)
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        DepartmentGood that = (DepartmentGood) o;
        return id != null && id.equals(that.id);
    }

    @Override
    public int hashCode() {
        // Luôn trả về 1 số hằng số cố định cho hashCode trên Entity!
        // Giúp bảo vệ tính nhất quán của đối tượng trong HashSet suốt vòng đời (Transient -> Managed)
        return getClass().hashCode(); 
    }
}
```

```java
@Entity
@Table(name = "employees")
@Getter
@Setter
public class EmployeeGood {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private DepartmentGood department;

    @Override
    public String toString() {
        return "EmployeeGood{" +
               "id=" + id +
               ", name='" + name + '\'' +
               '}'; // Tuyệt đối không in thuộc tính "department" để tránh kích hoạt Lazy loading và đệ quy!
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        EmployeeGood that = (EmployeeGood) o;
        return id != null && id.equals(that.id);
    }

    @Override
    public int hashCode() {
        return getClass().hashCode();
    }
}
```

## 📊 Bảng so sánh `@Data` mặc định và Lombok Best Practices trên Entity

| Tiêu chí phân tích | Sử dụng `@Data` mặc định | Áp dụng Lombok Best Practices |
| :--- | :--- | :--- |
| **Getter/Setter tự sinh** | Có. | **Có** (Thông qua `@Getter` và `@Setter`). |
| **Nguy cơ `StackOverflowError`**| **Cực kỳ cao** khi có quan hệ hai chiều. | **Bằng không** (Vì tự kiểm soát `toString` bỏ qua liên kết). |
| **Tính nhất quán trong `Set/Map`**| **Không** (Bị hỏng khi Entity chuyển từ Transient sang Managed). | **Hoàn hảo** (Do `hashCode` trả về giá trị hằng số cố định). |
| **Tự động kích hoạt Lazy Loading**| **Có** (Do `toString` quét qua toàn bộ trường liên quan). | **Không bao giờ** (Vì `toString` loại trừ các quan hệ Lazy). |
| **Nguyên lý SOLID** | Vi phạm (Gộp quá nhiều trách nhiệm vào một annotation). | Đảm bảo tốt (Tách biệt rõ ràng các hành vi đặc thù). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy sử dụng `@EqualsAndHashCode(exclude = "...")` của Lombok
*   **Vấn đề**: Để sửa nhanh lỗi đệ quy, lập trình viên thường đặt:
    ```java
    @Data
    @ToString(exclude = "employees")
    @EqualsAndHashCode(exclude = "employees")
    ```
    *   *Tại sao đây là cạm bẫy?* Cách làm này mang tính chắp vá thủ công và rất kém bền vững (Fragile design). Khi dự án phát triển lâu dài, một lập trình viên khác vào bảo trì và thêm một quan hệ mới (ví dụ: `@ManyToOne Manager manager`). Họ rất dễ quên không cập nhật danh sách loại trừ trong `exclude`. Lỗi `StackOverflowError` sẽ quay trở lại phá hoại hệ thống bất kỳ lúc nào.
*   **Giải pháp**: Tách biệt rõ ràng, tự viết tay phương thức `equals/hashCode` chỉ dựa trên khóa chính là giải pháp an toàn trọn đời.

### 2. Sự cố kết hợp `@Builder` thiếu `@NoArgsConstructor`
*   **Cạm bẫy**: Khi bạn đặt `@Builder` lên Entity để dễ tạo đối tượng. Mặc định, Lombok sẽ tự động tạo một constructor chứa đầy đủ tham số và **xóa bỏ constructor không tham số mặc định**.
    *   Hibernate bắt buộc phải có một Constructor không tham số (`public` hoặc `protected`) để tạo các thực thể Proxy qua cơ chế Reflection. Nếu thiếu, ứng dụng sẽ ném ra lỗi `InstantiationException` khi nạp dữ liệu từ DB lên.
*   **Giải pháp**: Khi dùng `@Builder` trên Entity, bắt buộc phải khai báo kèm cả hai annotation: `@NoArgsConstructor` và `@AllArgsConstructor`.

### 3. Câu hỏi đào sâu từ interviewer
*   **Q: Tại sao trong hàm `hashCode()` của Entity tốt nhất ta nên trả về giá trị hằng số cố định như `return getClass().hashCode()`? Điều này có làm suy giảm hiệu năng của các cấu trúc dữ liệu bảng băm (HashMap/HashSet) khi chúng ta quản lý hàng ngàn thực thể trên RAM không?**
    *   *Trả lời*: Đây là một câu hỏi cực kỳ sâu sắc chạm tới bản chất sâu xa của Java Collections và JPA Lifecycle.
    *   **Tại sao phải trả về hằng số cố định?**
        *   Một JPA Entity đi qua các trạng thái: *Transient* (ID null) -> *Managed* (ID có giá trị) -> *Detached*.
        *   Hợp đồng của `HashSet` yêu cầu: Nếu đối tượng đã nằm trong Set, giá trị `hashCode` của nó **bắt buộc phải không đổi** trong suốt thời gian tồn tại trong Set đó.
        *   Nếu ta dùng bất kỳ thuộc tính biến đổi nào (như ID tự sinh) để tính `hashCode`, hợp đồng trên sẽ bị phá vỡ ngay khi thực thể được lưu xuống DB. Việc trả về hằng số cố định (như `getClass().hashCode()`) là cách duy nhất đảm bảo giá trị băm luôn luôn bất biến trong mọi trạng thái vòng đời của Entity.
    *   **Có làm giảm hiệu năng của HashSet/HashMap không?**
        *   Có, về lý thuyết. Khi tất cả các đối tượng cùng một Class đều trả về cùng một giá trị `hashCode`, chúng sẽ bị xếp vào chung một ngăn lưu trữ (Hash Bucket) duy nhất dưới RAM (xảy ra tình trạng đụng độ băm tuyệt đối - Hash Collision). `HashSet` lúc này sẽ bị suy thoái hiệu năng tìm kiếm từ $O(1)$ xuống $O(N)$ (hoặc $O(\log N)$ trong Java 8+ nhờ cấu trúc Tree node) do phải lặp qua các phần tử và so sánh bằng hàm `equals()`.
        *   Tuy nhiên, trong thực tế phát triển phần mềm, số lượng thực thể Entity của cùng một lớp được quản lý đồng thời trên RAM trong một Session/HTTP Request thường rất nhỏ (vài chục đến vài trăm đối tượng). Với số lượng nhỏ như vậy, sự suy thoái hiệu năng tìm kiếm trên RAM là hoàn toàn không đáng kể và không thể nhận biết được.
        *   Sự đánh đổi này là hoàn toàn xứng đáng để đổi lấy **sự an toàn tuyệt đối** về mặt logic dữ liệu, tránh thảm họa mất tích thực thể trong cấu trúc băm.
        *   *Mẹo tối ưu*: Nếu thực thể có một khóa tự nhiên bất biến (Natural Key) như `email`, `SSN`, hoặc `UUID` được sinh chủ động trước khi lưu, ta hoàn toàn có thể dùng trường này để tính `hashCode` nhằm giữ nguyên hiệu năng $O(1)$ của bảng băm mà không lo bị thay đổi giá trị.
