# Mẫu thiết kế Người kiến tạo (Builder Design Pattern)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **Builder Pattern** là một mẫu thiết kế thuộc nhóm **Khởi tạo (Creational Patterns)**. Nó cho phép xây dựng một đối tượng phức tạp bằng cách tiếp cận từng bước (step-by-step), tách biệt quá trình xây dựng đối tượng ra khỏi biểu diễn thực tế của nó.
* **Giá trị cốt lõi**:
  * **Giải quyết "Mùi code" Telescoping Constructor**: Tránh việc quá tải hàm khởi tạo (overloaded constructors) với quá nhiều tham số tùy chọn dẫn đến các dòng code gọi constructor vô nghĩa dạng `new User("A", "B", null, null, 0, null)`.
  * **Đảm bảo tính Bất biến (Immutability)**: Cho phép tạo các đối tượng an toàn với các trường `final` mà vẫn linh hoạt cấu hình các trường tùy chọn khi khởi tạo.
  * **API mượt mà (Fluent API)**: Tạo trải nghiệm viết code rõ ràng, dễ đọc bằng cách chuỗi các phương thức (method chaining) như `.setName().setEmail().build()`.

---

## 🔍 Khi nào nên áp dụng Builder Pattern?

Hãy cân nhắc áp dụng Builder Pattern trong các trường hợp cụ thể sau:

1. **Khi đối tượng có số lượng tham số quá lớn (từ 4-5 tham số trở lên), đặc biệt là nhiều tham số tùy chọn (optional)**:
   * Nếu dùng Constructor truyền thống, lập trình viên rất dễ truyền nhầm thứ tự các đối tượng có cùng kiểu dữ liệu (ví dụ truyền nhầm `email` vào vị trí của `address` vì cả hai đều là `String`), gây lỗi logic âm thầm rất khó phát hiện.
2. **Khi bạn muốn đối tượng sau khi tạo ra phải là Bất biến (Immutable - Thread-safe)**:
   * Nếu dùng giải pháp JavaBeans (gọi hàm `set` sau khi `new` bằng constructor không tham số), đối tượng có thể bị thay đổi trạng thái bất cứ lúc nào trong runtime, và có thể rơi vào trạng thái "nửa vời" (chưa set xong đã bị luồng khác truy cập). Builder cho phép bạn gom toàn bộ thuộc tính, kiểm tra tính hợp lệ (validation) rồi mới chính thức đóng băng đối tượng bằng `build()`.
3. **Khi quá trình tạo đối tượng cần trải qua nhiều bước phức tạp hoặc thứ tự các bước quan trọng**:
   * *Ví dụ*: Xây dựng một câu lệnh SQL phức tạp (`select`, `where`, `join`, `groupBy`) hoặc cấu hình một HTTP Request Header.

## 💻 Code Example: Khởi tạo đối tượng `User` phức tạp

### ❌ Vi phạm thiết kế (Telescoping Constructor & JavaBean Pattern)

```java
// Cách 1: Quá tải Constructor (Telescoping) => Rất dễ nhầm lẫn thứ tự String
public class User {
    private String username; // Bắt buộc
    private String email;    // Bắt buộc
    private String phone;    // Tùy chọn
    private int age;         // Tùy chọn

    public User(String username, String email) {
        this(username, email, null, 0);
    }
    public User(String username, String email, String phone) {
        this(username, email, phone, 0);
    }
    public User(String username, String email, String phone, int age) {
        this.username = username;
        this.email = email;
        this.phone = phone;
        this.age = age;
    }
}
// Gọi khởi tạo:
User user = new User("hoang_long", "long@gmail.com", null, 25); // Nhìn rất rối!

// Cách 2: JavaBean (Không an toàn đa luồng)
User user = new User();
user.setUsername("hoang_long");
// Nếu giữa chừng một luồng khác đọc đối tượng này, trường email sẽ bị null (trạng thái không nhất quán)
user.setEmail("long@gmail.com"); 
```

### ✔️ Áp dụng Builder Pattern chuyên nghiệp
Đặt một lớp Static lồng trong lớp chính để quản lý quá trình xây dựng và kiểm tra tính toàn vẹn của dữ liệu:

```java
public class User {
    // Tất cả các trường đều là final để đảm bảo tính Immutable (Bất biến)
    private final String username; 
    private final String email;    
    private final String phone;    
    private final int age;         

    // Constructor private: Chỉ có thể được gọi từ lớp Builder của chính nó
    private User(UserBuilder builder) {
        this.username = builder.username;
        this.email = builder.email;
        this.phone = builder.phone;
        this.age = builder.age;
    }

    // Getters (Không có Setters!)
    public String getUsername() { return username; }
    public String getEmail() { return email; }
    public String getPhone() { return phone; }
    public int getAge() { return age; }

    // Static Inner Class đại diện cho Người kiến tạo
    public static class UserBuilder {
        private final String username; // Bắt buộc
        private final String email;    // Bắt buộc
        private String phone = "";     // Tùy chọn (Cung cấp giá trị mặc định)
        private int age = 0;           // Tùy chọn

        // Constructor của Builder nhận các trường bắt buộc
        public UserBuilder(String username, String email) {
            if (username == null || username.trim().isEmpty()) {
                throw new IllegalArgumentException("Username không được để trống!");
            }
            if (email == null || !email.contains("@")) {
                throw new IllegalArgumentException("Email không hợp lệ!");
            }
            this.username = username;
            this.email = email;
        }

        // Các phương thức fluent để gán giá trị tùy chọn (trả về chính UserBuilder)
        public UserBuilder phone(String phone) {
            this.phone = phone;
            return this;
        }

        public UserBuilder age(int age) {
            if (age < 0) {
                throw new IllegalArgumentException("Tuổi không được âm!");
            }
            this.age = age;
            return this;
        }

        // Phương thức cuối cùng để sinh ra đối tượng thật sau khi đã kiểm tra đầy đủ
        public User build() {
            // Có thể thực hiện kiểm tra chéo tính hợp lý dữ liệu tổng thể tại đây
            return new User(this);
        }
    }
}
```

* **Sử dụng Fluent API mượt mà**:
```java
User user = new User.UserBuilder("hoang_long", "long@gmail.com")
                .age(25)
                .phone("0987654321")
                .build(); // Tạo ra đối tượng User an toàn tuyệt đối
```

## 📊 Phân tích Trade-offs: So sánh các phương pháp khởi tạo

| Tiêu chí | Telescoping Constructor | JavaBeans Pattern (Get/Set) | Builder Pattern |
| :--- | :--- | :--- | :--- |
| **Tính bất biến (Immutability)** | **Có**: Các trường có thể khai báo `final`. | **Không**: Đối tượng có thể bị sửa đổi bất cứ lúc nào qua hàm set. | **Có**: Bảo vệ trạng thái đối tượng hoàn hảo sau khi build. |
| **Độ an toàn luồng (Thread-safety)**| **Có** | **Không**: Dễ bị tranh chấp tài nguyên (race condition). | **Có** |
| **Tính dễ đọc (Readability)** | **Rất kém**: Đặc biệt khi danh sách tham số dài và giống kiểu dữ liệu. | **Tốt**: Các phương thức `set` tự mô tả thuộc tính rõ ràng. | **Tuyệt vời**: Fluent API giúp code tự giải thích rõ ý định. |
| **Kiểm tra tính hợp lệ (Validation)**| Thực hiện tại Constructor, nhưng code kiểm tra sẽ rất cồng kềnh. | Khó kiểm tra chéo (ví dụ: trường A phụ thuộc điều kiện trường B) vì set rải rác. | **Lý tưởng**: Có thể kiểm tra chéo toàn bộ dữ liệu ngay trước khi gọi `new`. |
| **Dung lượng code Boilerplate** | Thấp. | Trung bình. | **Cao**: Phải viết thêm Class Builder lồng bên trong. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Thư viện Lombok cung cấp annotation `@Builder` cực kỳ tiện lợi để giảm thiểu code boilerplate. Tuy nhiên, việc sử dụng `@Builder` mặc định trên một Entity/DTO trong các dự án thực tế có những cạm bẫy gì cần lưu ý?
* **Trả lời**: `@Builder` của Lombok rất tốt nhưng có 3 gotchas chí mạng mà các Senior Developer cần kiểm soát:
  1. **Bỏ qua Constructor mặc định**: Khi dùng `@Builder`, Lombok tự động tạo một All-ArgsConstructor private và **loại bỏ** No-ArgsConstructor mặc định. Điều này làm sập các thư viện ORM như Hibernate/JPA hoặc các bộ ánh xạ JSON (Jackson) vì chúng bắt buộc cần constructor không tham số để hoạt động. 
     * *Khắc phục*: Luôn khai báo kèm `@NoArgsConstructor` và `@AllArgsConstructor` trên lớp đó.
  2. **Bỏ qua giá trị mặc định**: Nếu trường `private int status = 1;` được định nghĩa trong class, nhưng ta khởi tạo qua Builder mà không set `status`, giá trị được gán cho status sẽ là `0` chứ không phải `1` (do builder tạo ra một All-ArgsConstructor và truyền `0` vào vị trí của status).
     * *Khắc phục*: Sử dụng `@Builder.Default` của Lombok trên trường đó.
  3. **Không thực thi được Validation tùy biến**: `@Builder` tự động không cho phép ta can thiệp vào logic kiểm tra nghiệp vụ (ví dụ: tuổi không được âm) trước khi khởi tạo.
     * *Khắc phục*: Phải tự viết đè (override) lại Constructor của Builder hoặc viết thủ công phần logic Validation.

### 2. Sự khác biệt triết học giữa Builder Pattern và Abstract Factory là gì?
* **Trả lời**: Cả hai đều giải quyết vấn đề khởi tạo đối tượng phức tạp, nhưng triết lý thiết kế khác nhau:
  * **Abstract Factory**: Trả lời câu hỏi **"Cái gì" (What)**. Nó dùng để tạo lập ngay lập tức các dòng sản phẩm có liên quan (trả về Button, Checkbox cùng một tông màu). Quá trình tạo xảy ra trong 1 bước duy nhất (Single-step creation).
  * **Builder Pattern**: Trả lời câu hỏi **"Như thế nào" (How)**. Nó dùng để xây dựng một đối tượng duy nhất có cấu trúc cực kỳ phức tạp thông qua một quy trình nhiều bước tuần tự (Multi-step creation). Builder cho phép cấu hình linh hoạt chi tiết cấu tạo bên trong của sản phẩm trước khi xuất xưởng.
