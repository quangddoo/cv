# Một job batch update nhầm dữ liệu production. Bạn làm gì?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Đây là thảm họa hủy hoại dữ liệu diện rộng (Large-Scale Data Corruption Incident). Ưu tiên số một của Senior/Staff Engineer tuân thủ nguyên lý **"Kiểm soát thiệt hại & Cô lập trước khi khôi phục" (Containment First, Restoration Second)**, tuyệt đối không được hoảng loạn chạy thêm các lệnh UPDATE tay không đối soát (Blind Updates) để vá lỗi vì sẽ làm hỏng dữ liệu gốc, gây mất dấu kiểm toán.
* **Thảm họa thực chiến được giải quyết**:
  1. **Thảm họa "Mất điều kiện WHERE" (The Whereless Update)**: Kỹ sư chạy migration script để update trạng thái đơn hàng nhưng trỏ nhầm môi trường sang Production, hoặc câu lệnh SQL thiếu điều kiện lọc làm toàn bộ 10 triệu đơn hàng bị chuyển trạng thái thành `SUCCESS`.
  2. **Cơn ác mộng "Xóa đè dữ liệu mới sinh" (The Restoration Overwrite)**: Khi khôi phục DB bằng cách rollback toàn bộ DB về trạng thái backup lúc 0h00, ta vô tình xóa sạch toàn bộ các đơn hàng và giao dịch hợp lệ do người dùng mới tạo từ 0h00 đến thời điểm xảy ra sự cố.
* **Quyết định Senior**:
  1. **Đóng băng tức thì (Stop the Bleeding)**: Kill tiến trình của batch job, thu hồi quyền ghi (`WRITE`) của tài khoản chạy script hoặc chuyển service sang chế độ bảo trì (Read-only mode).
  2. **Trích xuất dữ liệu cũ bằng Point-in-Time Recovery (PITR)**: Khởi tạo một database phụ từ bản backup gần nhất, roll forward WAL/Binlog đến đúng mili-giây **trước khi** job lỗi chạy để lấy dữ liệu gốc làm nguồn đối chiếu chân lý.
  3. **Vá dữ liệu cuốn chiếu (Safe Rollback Script)**: Viết script so sánh dữ liệu ở DB phụ và DB chính, tạo ra các câu lệnh UPDATE có điều kiện cực kỳ chặt chẽ kèm cơ chế Dry-run kiểm thử trên Staging trước khi chạy thật.

## 🔍 Chi tiết bản chất thực chiến: Quy trình ứng phó 5 Bước (Incident Runbook)

Khi thảm họa xảy ra, Senior Engineer sẽ dẫn dắt đội ngũ kỹ thuật đi qua 5 bước của quy trình Runbook chuẩn hóa dưới đây:

```
                  [Thảm họa Batch Job ghi đè nhầm dữ liệu 🚨]
                                     │
                                     ▼
                [Bước 1: KIỂM SOÁT THIỆT HẠI (CONTAINMENT)]
                  ├── Kill ngay tiến trình batch job/service.
                  └── Chuyển app sang Read-Only hoặc Bảo trì.
                                     │
                                     ▼
               [Bước 2: CÔ LẬP & ĐÁNH GIÁ (ISOLATION & AUDIT)]
                  ├── Tìm thời điểm start/end chính xác của job.
                  └── Lọc ra danh sách IDs các bản ghi bị thay đổi.
                                     │
                                     ▼
                  [Bước 3: DỰNG CƠ SỞ DỮ LIỆU ĐỐI CHIẾU]
                  ├── Khôi phục bản backup gần nhất sang DB phụ độc lập.
                  └── Chạy WAL/Binlog tới thời điểm sát trước sự cố (PITR).
                                     │
                                     ▼
                   [Bước 4: SO SOẠN & VÁ DỮ LIỆU CUỐN CHIẾU]
                  ├── Viết script so sánh DB phụ (Đúng) & DB chính (Sai).
                  ├── Sinh file SQL Undo có điều kiện so khớp trạng thái.
                  └── Test thử (Dry-run) trên 100 bản ghi trước.
                                     │
                                     ▼
                    [Bước 5: PHÒNG NGỪA DÀI HẠN (PREVENTION)]
                  ├── Bật Temporal Tables / System-Versioned Tables.
                  └── Áp dụng nguyên tắc Đặc quyền tối thiểu (Least Privilege).
```

### Bước 1: Kiểm soát thiệt hại (Containment)
* **Hành động ngay lập tức**: Xác định Process ID (PID) của job trên server và dùng lệnh `kill -9` để hủy ngay lập tức nếu job vẫn đang chạy.
* Nếu job đã chạy xong và dữ liệu sai đang hiển thị cho người dùng, chuyển đổi ngay lập tức hệ thống sang chế độ bảo trì hoặc ngắt kết nối ghi để ngăn chặn việc người dùng thực hiện các hành động mới dựa trên dữ liệu sai lệch (ví dụ: rút tiền khi ví bị cộng nhầm).

### Bước 2: Cô lập & Đánh giá mức độ tàn phá (Impact Assessment)
* Tra cứu log của batch job để xác định thời điểm chính xác bắt đầu chạy (ví dụ: `2026-05-23T08:00:02.123Z`).
* Chạy truy vấn đếm số lượng bản ghi bị ảnh hưởng:
  `SELECT COUNT(*) FROM orders WHERE updated_by = 'batch_job_v2' AND updated_at >= '2026-05-23 08:00:00';`

### Bước 3: Dựng Database chân lý bằng PITR (Point-in-Time Recovery)
* Tuyệt đối không được đè bản backup cũ lên DB Production hiện tại vì sẽ làm mất các dữ liệu hợp lệ mới sinh.
* **Quy trình chuẩn**:
  1. Restore file backup (ví dụ bản backup tự động lúc 0h00 sáng) sang một cụm database phụ hoàn toàn độc lập (Temporary DB Instance).
  2. Áp dụng (Replay) các log thay đổi vật lý (MySQL Binlog / PostgreSQL WAL) từ 0h00 sáng và **dừng lại chính xác** tại thời điểm `2026-05-23 08:00:01` (1 giây trước khi job lỗi chạy).
  3. Lúc này, DB phụ chính là "chân lý" chứa toàn bộ dữ liệu đúng của hệ thống trước khi bị tàn phá.

### Bước 4: So sánh và Vá dữ liệu cuốn chiếu (Data Patching)
* Viết một script tự động (sử dụng Python hoặc Java) kết nối tới cả 2 DB (DB phụ và DB chính).
* Script sẽ quét qua toàn bộ các bản ghi bị lỗi, so sánh giá trị và sinh ra các câu lệnh SQL phục hồi có cấu trúc phòng vệ chặt chẽ:
  `UPDATE orders SET status = 'PENDING' WHERE id = 456 AND status = 'CANCELLED';`
  *(Chỉ cập nhật lại trạng thái cũ nếu trạng thái hiện tại trên Production vẫn là trạng thái bị lỗi, tránh đè lên các cập nhật mới hợp lệ).*

## 🎨 Sơ đồ trực quan: Point-in-Time Recovery (PITR) cứu dữ liệu

Sơ đồ dưới đây mô tả cách trích xuất dữ liệu gốc từ DB phụ mà không gây mất mát dữ liệu mới sinh trên DB Production:

```
[00:00 sáng]                 [08:00 sáng]            [08:15 sáng]
┌───────────┐                 ┌───────────┐           ┌───────────┐
│ Backup    │                 │ Batch Job │           │ Phát Hiện │
│ Tự Động   │                 │ Lỗi Chạy  │           │ Sự Cố 🚨  │
└─────┬─────┘                 └─────┬─────┘           └─────┬─────┘
      │                             │                       │
      │ 1. Restore Backup           │ 2. Replay Binlog      │
      └────────────────────────────►│ (Dừng tại 07:59:59)   │
                                    ▼                       │
                             ┌─────────────┐                │
                             │ Temporary   │                │
                             │ DB (Chân lý)│                │
                             └──────┬──────┘                │
                                    │                       │
                                    │ 3. So sánh đối chiếu  │
                                    └──────────────────────►│ 4. Chỉ vá những bản ghi
                                                            │    bị lỗi ở thời điểm 08:00
                                                            ▼
                                                     ┌─────────────┐
                                                     │ Production  │
                                                     │ DB (Sạch)   │
                                                     └─────────────┘
```

## 💻 Code thực chiến: Python Script tự động đối soát và sinh SQL vá dữ liệu an toàn

Script Python dưới đây kết nối song song vào Database Phụ (Chân lý trước lỗi) và Database Production (Đang bị sai dữ liệu) để tự động sinh câu lệnh vá dữ liệu có cơ chế Dry-run.

```python
import mysql.connector
import logging
import os

logging.basicConfig(level=logging.INFO, format='%(asctime)s - %(levelname)s - %(message)s')

# Cấu hình kết nối tới 2 Database
PROD_DB_CONFIG = {
    'host': 'prod-db-replica.internal',
    'user': 'data_patcher',
    'password': os.environ['PROD_DB_PASSWORD'],
    'database': 'ecommerce'
}

TEMP_DB_CONFIG = {
    'host': 'temp-pitr-db.internal',
    'user': 'data_patcher',
    'password': os.environ['TEMP_DB_PASSWORD'],
    'database': 'ecommerce'
}

def generate_revert_scripts(dry_run=True):
    prod_conn = mysql.connector.connect(**PROD_DB_CONFIG)
    temp_conn = mysql.connector.connect(**TEMP_DB_CONFIG)
    
    prod_cursor = prod_conn.cursor(dictionary=True)
    temp_cursor = temp_conn.cursor(dictionary=True)
    
    # 1. Lấy danh sách bản ghi bị ghi đè lỗi trên Prod (Ví dụ: trạng thái bị đổi thành CANCELLED bởi batch job)
    # Lọc theo mốc thời gian và tài khoản cập nhật của Job lỗi
    query_corrupted = """
        SELECT id, status, updated_at FROM orders 
        WHERE updated_by = 'corrupted_batch_job' 
          AND updated_at >= '2026-05-23 08:00:00'
    """
    prod_cursor.execute(query_corrupted)
    corrupted_records = prod_cursor.fetchall()
    
    logging.info(f"Found {len(corrupted_records)} potentially corrupted records on Production.")
    
    patch_queries = []
    
    # 2. Đối chiếu từng bản ghi với DB Chân lý (Temp DB)
    for record in corrupted_records:
        record_id = record['id']
        current_prod_status = record['status']
        
        # Lấy giá trị gốc trước khi xảy ra lỗi ở DB phụ
        temp_cursor.execute("SELECT status FROM orders WHERE id = %s", (record_id,))
        original_record = temp_cursor.fetchone()
        
        if original_record:
            original_status = original_record['status']
            
            # Nếu trạng thái bị khác biệt, tiến hành tạo query vá dữ liệu
            if current_prod_status != original_status:
                # Gotchas: Chỉ UPDATE nếu trạng thái trên Prod vẫn giữ nguyên trạng thái lỗi (CANCELLED)
                # để tránh ghi đè đè lên các cập nhật hợp lệ mới phát sinh của khách hàng sau đó
                patch_queries.append((
                    "UPDATE orders SET status = %s, updated_by = %s "
                    "WHERE id = %s AND status = %s",
                    (original_status, 'patch_job_recovery', record_id, current_prod_status),
                ))
                
    logging.info(f"Generated {len(patch_queries)} SQL patch queries.")
    
    # 3. Thực thi an toàn
    if dry_run:
        logging.info("--- DRY RUN MODE (No changes applied to Production) ---")
        for sql in patch_queries[:10]: # In thử 10 câu lệnh đầu tiên để kiểm tra
            print(sql)
        if len(patch_queries) > 10:
            print(f"... and {len(patch_queries) - 10} more queries.")
    else:
        logging.info("--- APPLYING PATCH TO PRODUCTION ---")
        # Thực hiện cập nhật cuốn chiếu theo từng Block 500 bản ghi để tránh khóa bảng lâu (Lock escalation)
        batch_size = 500
        for i in range(0, len(patch_queries), batch_size):
            batch = patch_queries[i:i+batch_size]
            write_cursor = prod_conn.cursor()
            for sql, params in batch:
                write_cursor.execute(sql, params)
            prod_conn.commit()
            logging.info(f"Successfully patched records {i} to {i + len(batch)}")
            
    prod_cursor.close()
    temp_cursor.close()
    prod_conn.close()
    temp_conn.close()

if __name__ == "__main__":
    # Bước 1: Chạy Dry-run để kiểm định logic đối soát trước
    generate_revert_scripts(dry_run=True)
    
    # Bước 2: Chỉ chuyển thành False sau khi Senior đã review kỹ output SQL
    # generate_revert_scripts(dry_run=False)

```
