# Loại bỏ các sự kiện trùng lặp với thời gian sống TTL (Deduplicate Events with TTL)

## ⚡ Tóm tắt ngắn (30s)
* **Bài toán**: Trong hệ thống xử lý dòng sự kiện (Event Streaming như Kafka, RabbitMQ), do chính sách đảm bảo phân phối **At-least-once (Ít nhất một lần)**, một sự kiện (Event) có thể bị gửi trùng lặp nhiều lần. Ta cần thiết kế một hệ thống loại bỏ sự kiện trùng lặp (Deduplication) trong một khoảng thời gian sống (TTL - Time To Live) xác định (ví dụ: bỏ qua nếu sự kiện trùng lặp xuất hiện lại trong vòng 10 phút).
* **Giải pháp cốt lõi**:
  1. **Môi trường đơn nút (In-Memory)**: Hiện thực hóa cấu trúc dữ liệu tự thiết kế sử dụng `ConcurrentHashMap` kết hợp với một luồng dọn dẹp định kỳ (Clean-up Scheduler) hoặc sử dụng thư viện Cache tối ưu như **Caffeine / Guava** với chính sách `expireAfterWrite`.
  2. **Môi trường phân tán (Distributed)**: Sử dụng **Redis** làm kho lưu trữ trung tâm nhờ lệnh nguyên tử `SET key value EX <seconds> NX`. Thao tác này chỉ thiết lập khóa nếu khóa chưa tồn tại và tự động thiết lập thời gian hết hạn (TTL).
* **Độ phức tạp**: Đọc và ghi $O(1)$, dọn dẹp chạy nền định kỳ $O(N)$ trong đó $N$ là số lượng phần tử đã hết hạn.

## 🔍 Phân tích yêu cầu (Requirements)

### 1. Functional Requirements (Yêu cầu chức năng)
* Kiểm tra một sự kiện dựa trên `eventId` duy nhất xem đã được xử lý chưa:
  * Nếu **chưa**: Ghi nhận `eventId` vào bộ nhớ với thời gian sống TTL và cho phép thực thi xử lý sự kiện.
  * Nếu **rồi** (trùng lặp): Từ chối sự kiện, không xử lý lại.
* Tự động xóa bỏ các `eventId` đã quá thời gian TTL ra khỏi hệ thống để giải phóng bộ nhớ.

### 2. Non-Functional Requirements (Yêu cầu phi chức năng)
* **Thread-Safety (An toàn đa luồng)**: Hệ thống phải đảm bảo hoạt động chính xác tuyệt đối khi có hàng ngàn luồng truy cập đồng thời kiểm tra trùng lặp sự kiện (Concurrent requests).
* **Memory Management (Quản trị bộ nhớ)**: Bộ nhớ không được phình to vô hạn. Cơ chế dọn dẹp (eviction/cleanup) phải diễn ra liên tục, mượt mà và không gây đứng hệ thống (tránh stop-the-world hoặc lock nghẽn).
* **High Performance (Hiệu suất cao)**: Thao tác kiểm tra trùng lặp (Deduplication Check) nằm trên luồng xử lý chính nên thời gian phản hồi bắt buộc phải cực nhanh (< 1ms).

 ┌───────────┐

## 💻 Code Example: Hiện thực hóa cấu trúc In-Memory Deduplicator bằng Java

Dưới đây là phiên bản hiện thực hóa cấu trúc In-Memory Event Deduplicator tự chế tinh gọn, hoàn toàn an toàn đa luồng bằng cách sử dụng `ConcurrentHashMap` phối hợp với `ScheduledExecutorService` để quét dọn rác nền:

```java
import java.util.Map;
import java.util.concurrent.*;

public class InMemoryEventDeduplicator {

    // Lớp bọc thông tin thời gian hết hạn của sự kiện
    private static class ExpirableEvent {
        final long expireAtTimestamp;

        IpOrEventInfo(long expireAtTimestamp) {
            this.expireAtTimestamp = expireAtTimestamp;
        }

        boolean isExpired() {
            return System.currentTimeMillis() > expireAtTimestamp;
        }
    }

    // Bản đồ lưu trữ thread-safe các sự kiện đang hoạt động
    private final ConcurrentHashMap<String, ExpirableEvent> cache = new ConcurrentHashMap<>();
    private final ScheduledExecutorService cleanupScheduler;
    private final long ttlMs;

    public InMemoryEventDeduplicator(long ttlDuration, TimeUnit timeUnit, int cleanupIntervalSeconds) {
        this.ttlMs = timeUnit.toMillis(ttlDuration);
        this.cleanupScheduler = Executors.newSingleThreadScheduledExecutor(runnable -> {
            Thread thread = new Thread(runnable, "event-dedup-cleanup");
            thread.setDaemon(true); // Đặt daemon thread để không block ứng dụng khi shutdown
            return thread;
        });

        // Thiết lập luồng dọn dẹp định kỳ chạy ngầm (Gotcha 1)
        this.cleanupScheduler.scheduleAtFixedRate(this::cleanExpiredEvents, 
                cleanupIntervalSeconds, cleanupIntervalSeconds, TimeUnit.SECONDS);
    }

    /**
     * Kiểm tra và đánh dấu sự kiện.
     * Trả về TRUE nếu sự kiện là DUY NHẤT (chưa từng xuất hiện) và cho phép xử lý.
     * Trả về FALSE nếu sự kiện trùng lặp (đã tồn tại trong khoảng thời gian TTL).
     */
    public boolean checkAndProcess(String eventId) {
        long now = System.currentTimeMillis();
        long expireTime = now + ttlMs;

        // compute(): Tính toán nguyên tử (atomic) trên khóa để tránh Race Condition kiểm tra và ghi nhận
        ExpirableEvent result = cache.compute(eventId, (key, existingValue) -> {
            // Nếu khóa chưa tồn tại hoặc đã hết hạn từ lâu nhưng luồng dọn dẹp chưa kịp quét tới
            if (existingValue == null || existingValue.isExpired()) {
                return new ExpirableEvent(expireTime);
            }
            // Khóa đã tồn tại và vẫn còn hạn sử dụng
            return existingValue;
        });

        // Nếu thời điểm hết hạn của phần tử vừa lưu khớp với thời điểm ta tính toán -> Đây là phần tử mới ghi nhận thành công!
        return result.expireAtTimestamp == expireTime;
    }

    /**
     * Luồng chạy ngầm định kỳ quét dọn các phần tử hết hạn để giải phóng bộ nhớ RAM
     */
    private void cleanExpiredEvents() {
        long now = System.currentTimeMillis();
        int beforeSize = cache.size();
        
        // Loại bỏ các entry đã hết hạn một cách an toàn thông qua Stream/Iterator của ConcurrentHashMap
        cache.entrySet().removeIf(entry -> entry.getValue().isExpired());
        
        int afterSize = cache.size();
        int removedCount = beforeSize - afterSize;
        if (removedCount > 0) {
            System.out.printf("[Cleanup Task] Đã dọn dẹp %d sự kiện hết hạn. Số lượng còn lại: %d\n", 
                              removedCount, afterSize);
        }
    }

    /**
     * Dọn dẹp tài nguyên khi hủy đối tượng
     */
    public void shutdown() {
        cleanupScheduler.shutdown();
        cache.clear();
    }

    // --- Hàm Demo hoạt động ---
    public static void main(String[] args) throws InterruptedException {
        // Thiết lập thời gian sống sự kiện 2 giây, dọn dẹp định kỳ mỗi 1 giây
        InMemoryEventDeduplicator deduplicator = new InMemoryEventDeduplicator(2, TimeUnit.SECONDS, 1);

        String eventId1 = "order_created_1001";
        String eventId2 = "order_created_1002";

        // Thử nghiệm lần 1
        System.out.println("Gửi Event 1: " + deduplicator.checkAndProcess(eventId1)); // true (Độc nhất)
        System.out.println("Gửi Event 2: " + deduplicator.checkAndProcess(eventId2)); // true (Độc nhất)
        
        // Thử nghiệm gửi trùng lập tức
        System.out.println("Gửi lại Event 1 trùng lặp: " + deduplicator.checkAndProcess(eventId1)); // false (Bị từ chối)

        // Ngủ chờ 3 giây để vượt quá TTL (2 giây)
        System.out.println("\nNgủ chờ 3 giây...");
        Thread.sleep(3000);

        // Thử lại sau khi hết TTL
        System.out.println("Gửi lại Event 1 sau khi hết TTL: " + deduplicator.checkAndProcess(eventId1)); // true (Được chấp nhận lại!)

        // Chờ luồng định kỳ in log dọn dẹp
        Thread.sleep(1500);
        
        deduplicator.shutdown();
    }
}
```

## 📊 Phân tích độ phức tạp & Trade-offs

### So sánh các mô hình Deduplication

| Tiêu chí | Sử dụng In-Memory Cache tự thiết kế | Sử dụng Thư viện chuyên nghiệp (Caffeine) | Sử dụng Distributed Cache (Redis) | Lưu trữ trực tiếp Database (Unique Constraint) |
| :--- | :--- | :--- | :--- | :--- |
| **Độ chính xác trên hệ thống phân tán** | **Kém**: Chỉ chống trùng lặp trên cùng 1 Pod/Instance của app. Nếu Request đi qua Pod khác sẽ bị lọt. | **Kém**: Giới hạn trong bộ nhớ cục bộ của từng nút mạng. | **Tuyệt vời**: Mọi instance của ứng dụng đều chia sẻ chung một kho trạng thái duy nhất. | **Tuyệt vời**: Đảm bảo toàn vẹn dữ liệu ở tầng cuối cùng. |
| **Tốc độ phản hồi (Latency)**| Siêu nhanh (<0.1ms) không tốn network call. | Siêu nhanh (<0.1ms). | Nhanh (~1-3ms) tốn chi phí gọi qua mạng sang Redis. | Chậm (~5-20ms) do phải ghi đĩa và xử lý transaction đắt đỏ. |
| **Quản trị bộ nhớ** | Phụ thuộc hoàn toàn vào cấu hình bộ dọn dẹp rác chạy ngầm. | Cực tốt nhờ giải thuật tối ưu TinyLFU tích hợp sẵn. | Tốt nhờ cấu hình MaxMemory và chính sách tự động hủy khóa của Redis. | Tốn tài nguyên đĩa cứng vô hạn nếu không có tiến trình purge định kỳ. |
| **Công sức triển khai** | Đơn giản, tự viết code gọn nhẹ. | Cần cài đặt thư viện bên ngoài. | Đòi hỏi vận hành cụm Redis và kết nối Client. | Dựa vào cấu trúc DB có sẵn. |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

### 1. Điều gì xảy ra đối với cơ chế In-Memory Deduplicator tự viết nếu ứng dụng bị Crash/Restart đột ngột?
* **Trả lời**: Đây là điểm yếu chí tử của giải pháp In-Memory:
  * **Hậu quả**: Toàn bộ danh sách `eventId` đang nằm trong RAM sẽ bị bốc hơi hoàn toàn. Khi ứng dụng khởi động lại, các sự kiện trùng lặp từ trước (vẫn trong khoảng TTL 10 phút) gửi lại sẽ được ứng dụng nhận diện như sự kiện mới và tiến hành xử lý lại từ đầu.
  * **Giải pháp khắc phục**:
    * Đối với hệ thống tài chính yêu cầu chính xác tuyệt đối (Exactly-once): Bắt buộc phải lưu trữ trạng thái idempotency khóa ghi nhận vào Database bền vững (Persistent DB như PostgreSQL, MySQL) với ràng buộc `UNIQUE` trên cột `event_id` hoặc sử dụng Redis lưu trữ bền vững (AOF bật).
    * Đối với hệ thống thông thường: Sử dụng hàng đợi Kafka với cơ chế **Transaction/Exactly-Once Semantics (EOS)** được bật để Kafka tự xử lý trùng lặp từ gốc.

### 2. Sự khác biệt giữa chính sách `expireAfterWrite` và `expireAfterAccess` trong việc thiết lập TTL sự kiện là gì? Ta nên chọn loại nào cho bài toán loại bỏ trùng lặp này?
* **Trả lời**:
  * **`expireAfterWrite` (Hết hạn sau khi ghi)**: Thời gian sống của khóa được tính từ thời điểm ghi nhận thành công đầu tiên. Cho dù ta có đọc hay truy cập kiểm tra khóa bao nhiêu lần đi nữa, khóa vẫn sẽ bị xóa đúng sau khoảng thời gian $T$ đã định.
  * **`expireAfterAccess` (Hết hạn sau khi truy cập)**: Mỗi khi có một thao tác đọc hoặc ghi nhận kiểm tra trùng lặp diễn ra trên khóa, thời gian sống TTL của khóa lại được **làm mới** (reset) từ đầu.
  * **Lựa chọn cho bài toán Deduplication**: Bắt buộc phải chọn **`expireAfterWrite`**. 
    * Vì nếu chọn `expireAfterAccess`, giả sử một Client bị lỗi vòng lặp gửi vô hạn sự kiện trùng lặp cứ mỗi 1 phút. Mỗi lần gửi trùng lặp sẽ làm mới thời gian sống của sự kiện thêm 10 phút nữa. Khóa này sẽ tồn tại vĩnh viễn không bao giờ được giải phóng, gây rò rỉ bộ nhớ RAM! Với `expireAfterWrite`, khóa sẽ tự hủy sau 10 phút bất kể có bao nhiêu cuộc tấn công trùng lặp.

### 3. Giải quyết bài toán Race Condition khi hai luồng cùng lúc kiểm tra trùng lặp cho một eventId?
* **Trả lời**:
  * Nếu dùng code không cẩn thận dạng: `if (!map.containsKey(id)) { map.put(id, val); }`, hai luồng chạy song song có thể cùng đi qua câu lệnh `if` kiểm tra và cùng coi mình là duy nhất, dẫn đến xử lý lặp sự kiện (Gotcha kinh điển).
  * **Khắc phục**: 
    * Trong Java In-Memory: Dùng `ConcurrentHashMap.compute()` hoặc `putIfAbsent()`. Những phương thức này được thiết kế đồng bộ hóa nội bộ ở mức phân mảnh khóa (bucket lock), đảm bảo tính nguyên tử tuyệt đối tại thời điểm kiểm tra và ghi đè.
    * Trong Redis: Dùng tính năng `NX` của lệnh `SET` (chỉ đặt nếu chưa có) hoặc thực thi một kịch bản **Lua Script** trực tiếp trên Redis Engine để khóa tài nguyên nguyên tử.
