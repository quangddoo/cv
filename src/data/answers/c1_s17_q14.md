# Hiện thực hóa bộ nhớ đệm trong RAM đơn giản với thời gian sống TTL (Implement Simple In-Memory Cache with TTL)

## ⚡ Tóm tắt ngắn (30s)
* **Bài toán**: Thiết kế và hiện thực hóa một bộ nhớ đệm lưu trữ trong RAM (In-Memory Cache) giống như Redis thu nhỏ từ đầu (from scratch) bằng ngôn ngữ Java, hỗ trợ tính năng tự động hủy dữ liệu sau một khoảng thời gian sống TTL (Time-To-Live).
* **Giải pháp cốt lõi**:
  1. **Thread-Safe Map**: Sử dụng `ConcurrentHashMap` để lưu trữ dữ liệu an toàn dưới dạng cặp Khóa - Giá trị giữa nhiều luồng.
  2. **Lớp bọc thời gian sống**: Đóng gói Giá trị thật (`Value`) kèm theo thời điểm hết hạn (`expiryTimestamp = currentTime + TTL`).
  3. **Chiến lược dọn dẹp kép (Dual Eviction Strategy)**:
     * **Lazy Eviction (Dọn dẹp thụ động)**: Khi thực hiện gọi hàm đọc `get(key)`, nếu phát hiện phần tử đã hết hạn, ta tiến hành xóa phần tử đó ngay lập tức và trả về `null`.
     * **Active Eviction (Dọn dẹp chủ động chạy ngầm)**: Dùng `ScheduledExecutorService` quét định kỳ toàn bộ Cache để xóa sổ những phần tử rác bị bỏ quên lâu ngày không ai sờ tới nhằm tránh rò rỉ RAM (Memory Leak).
* **Độ phức tạp**: Đọc và ghi dữ liệu $O(1)$, quét dọn định kỳ $O(N)$ chạy ngầm.

## 🔍 Phân tích yêu cầu (Requirements)

### 1. Functional Requirements (Yêu cầu chức năng)
* Thao tác cơ bản: Ghi nhận dữ liệu kèm TTL (`put(key, value, ttlMs)`), truy xuất dữ liệu (`get(key)`), xóa dữ liệu (`remove(key)`), và dọn sạch (`clear()`).
* Tự động trả về `null` nếu truy xuất một khóa đã quá thời gian TTL.
* Giới hạn kích thước tối đa của bộ nhớ đệm (Capacity Limit) để tránh đầy RAM. Nếu vượt quá giới hạn, áp dụng chính sách loại bỏ (ví dụ: LRU hoặc đơn giản là xóa phần tử hết hạn trước).

### 2. Non-Functional Requirements (Yêu cầu phi chức năng)
* **High Concurrency (Độ chịu tải đồng thời cực cao)**: Hỗ trợ hàng ngàn luồng đọc và ghi cùng lúc mà không xảy ra tranh chấp hoặc deadlock.
* **Không rò rỉ bộ nhớ (No Memory Leak)**: Đảm bảo bộ nhớ RAM được thu hồi triệt để đối với các khóa được ghi một lần duy nhất rồi bỏ quên (không bao giờ được gọi `get` lại).
* **Độ chính xác về thời gian**: Việc hết hạn của khóa phải diễn ra chuẩn xác đến đơn vị mili-giây.

## 🎨 Sơ đồ trực quan & Cơ chế hoạt động

### Sự kết hợp hoàn hảo của Cơ chế dọn dẹp kép (Dual Eviction)

```
        HÀNH ĐỘNG CỦA USER                      LUỒNG CHẠY NGẦM ĐỊNH KỲ
     (Ví dụ: Gọi hàm get("A"))                 (Active Eviction - Quét rác)
                │                                           │
                ▼                                           ▼
      ┌───────────────────┐                       ┌───────────────────┐
      │   Tìm khóa "A"?   │                       │ Duyệt danh sách   │
      └─────────┬─────────┘                       │ cache định kỳ     │
                │                                 └─────────┬─────────┘
        ┌───────┴───────┐                                   │
     NO │           YES │                                   │
        ▼               ▼                                   ▼
   [Trả null]  ┌─────────────────┐                 ┌─────────────────┐
               │ expireTimestamp │                 │ entry.isExpired?│
               │  < currentTime? │                 └────────┬────────┘
               └────────┬────────┘                          │
                ┌───────┴───────┐                   ┌───────┴───────┐
             NO │           YES │                NO │           YES │
                ▼               ▼                   ▼               ▼
          [Trả Value]      [XÓA KHÓA "A"]      [Bỏ qua]       [XÓA KHÓA]
                           [Trả null]                         (Giải phóng RAM)
```

## 💻 Code Example: Hiện thực hóa cấu trúc In-Memory Cache bằng Java

Dưới đây là phiên bản hiện thực hóa cấu trúc In-Memory Cache hoàn chỉnh theo tiêu chuẩn doanh nghiệp, an toàn đa luồng và tích hợp đầy đủ chiến lược dọn dẹp kép:

```java
import java.util.Map;
import java.util.concurrent.*;

public class SimpleInMemoryCache<K, V> {

    // Lớp chứa dữ liệu lưu trữ trong Cache bọc thời điểm hết hạn
    private static class CacheEntry<V> {
        final V value;
        final long expireAtTimestamp;

        CacheEntry(V value, long ttlMs) {
            this.value = value;
            // Nếu ttlMs <= 0 tức là tồn tại vô hạn (giống Redis)
            this.expireAtTimestamp = ttlMs > 0 ? System.currentTimeMillis() + ttlMs : Long.MAX_VALUE;
        }

        boolean isExpired() {
            return System.currentTimeMillis() > expireAtTimestamp;
        }
    }

    private final ConcurrentHashMap<K, CacheEntry<V>> cacheMap = new ConcurrentHashMap<>();
    private final ScheduledExecutorService cleanupScheduler;
    private final int maxCapacity;

    public SimpleInMemoryCache(int maxCapacity, int cleanupIntervalSeconds) {
        this.maxCapacity = maxCapacity;
        
        // Tạo luồng chạy ngầm quét rác định kỳ (Active Eviction)
        this.cleanupScheduler = Executors.newSingleThreadScheduledExecutor(runnable -> {
            Thread thread = new Thread(runnable, "in-memory-cache-cleaner");
            thread.setDaemon(true); // Tránh block JVM khi tắt ứng dụng
            return thread;
        });

        this.cleanupScheduler.scheduleAtFixedRate(
            this::cleanExpiredEntries, 
            cleanupIntervalSeconds, 
            cleanupIntervalSeconds, 
            TimeUnit.SECONDS
        );
    }

    /**
     * Đưa dữ liệu vào cache với thời gian sống TTL (mili-giây)
     */
    public void put(K key, V value, long ttlMs) {
        if (key == null || value == null) {
            throw new IllegalArgumentException("Khóa và Giá trị không được phép null!");
        }

        // Kiểm tra dung lượng tối đa trước khi đưa vào (Gotcha 2)
        if (cacheMap.size() >= maxCapacity && !cacheMap.containsKey(key)) {
            // Lọc dọn dẹp nhanh các khóa hết hạn để lấy chỗ trống
            cleanExpiredEntries();
            
            // Nếu sau khi dọn dẹp vẫn quá tải, ta tiến hành trục xuất ngẫu nhiên hoặc 1 phần tử
            if (cacheMap.size() >= maxCapacity) {
                K oldestKey = cacheMap.keySet().iterator().next(); // Lấy phần tử đầu tiên
                cacheMap.remove(oldestKey);
                System.out.printf("[Cache] Bộ nhớ đầy! Trục xuất khóa [%s] để lấy chỗ trống.\n", oldestKey);
            }
        }

        cacheMap.put(key, new CacheEntry<>(value, ttlMs));
    }

    /**
     * Lấy dữ liệu ra khỏi cache (Áp dụng Lazy Eviction)
     */
    public V get(K key) {
        CacheEntry<V> entry = cacheMap.get(key);
        if (entry == null) {
            return null;
        }

        // Lazy Eviction: Nếu phát hiện phần tử hết hạn khi được sờ tới, tiến hành xóa ngay lập tức
        if (entry.isExpired()) {
            cacheMap.remove(key);
            System.out.printf("[Lazy Eviction] Xóa bỏ khóa [%s] do đã hết hạn.\n", key);
            return null;
        }

        return entry.value;
    }

    /**
     * Chủ động xóa khóa
     */
    public V remove(K key) {
        CacheEntry<V> removed = cacheMap.remove(key);
        return removed != null && !removed.isExpired() ? removed.value : null;
    }

    /**
     * Xóa toàn bộ dữ liệu trong cache
     */
    public void clear() {
        cacheMap.clear();
    }

    /**
     * Lấy kích thước thực tế hiện tại
     */
    public int size() {
        return cacheMap.size();
    }

    /**
     * Quét và giải phóng toàn bộ phần tử hết hạn trong RAM (Active Eviction)
     */
    private void cleanExpiredEntries() {
        int before = cacheMap.size();
        
        // Xóa các entry đã hết hạn an toàn nhờ ConcurrentHashMap
        cacheMap.entrySet().removeIf(entry -> entry.getValue().isExpired());
        
        int removedCount = before - cacheMap.size();
        if (removedCount > 0) {
            System.out.printf("[Active Eviction] Đã giải phóng %d khóa hết hạn ra khỏi RAM.\n", removedCount);
        }
    }

    /**
     * Tắt bộ dọn dẹp khi hủy Cache
     */
    public void shutdown() {
        cleanupScheduler.shutdown();
        cacheMap.clear();
    }

    // --- Demo chạy thử ---
    public static void main(String[] args) throws InterruptedException {
        // Cache tối đa 5 phần tử, quét dọn rác định kỳ mỗi 1 giây
        SimpleInMemoryCache<String, String> sessionCache = new SimpleInMemoryCache<>(5, 1);

        System.out.println("--- ĐƯA DỮ LIỆU VÀO CACHE ---");
        sessionCache.put("user_1", "Data 1", 1000); // Hết hạn sau 1 giây
        sessionCache.put("user_2", "Data 2", 3000); // Hết hạn sau 3 giây
        sessionCache.put("user_3", "Data 3", 0);    // Vô hạn

        // Kiểm tra lập tức
        System.out.println("Đọc user_1 ngay lập tức: " + sessionCache.get("user_1")); // Data 1

        // Chờ 1.5 giây
        System.out.println("\nChờ 1.5 giây...");
        Thread.sleep(1500);

        // Đọc lại
        System.out.println("Đọc user_1 sau 1.5s: " + sessionCache.get("user_1")); // null (Lazy Eviction hoạt động)
        System.out.println("Đọc user_2 sau 1.5s: " + sessionCache.get("user_2")); // Data 2 (Vẫn còn hạn)

        // Chờ thêm 2 giây để kích hoạt luồng dọn dẹp quét rác chạy ngầm
        System.out.println("\nChờ thêm 2 giây để luồng chạy ngầm quét rác...");
        Thread.sleep(2000);
        
        System.out.println("Kích thước cache hiện tại: " + sessionCache.size()); // 1 (Chỉ còn user_3 vô hạn)
        
        sessionCache.shutdown();
    }
}
```

## 📊 Phân tích độ phức tạp & Trade-offs

### So sánh các chiến lược dọn dẹp dữ liệu (Eviction Policy)

| Chiến lược | Ưu điểm | Nhược điểm | Use Case phù hợp |
| :--- | :--- | :--- | :--- |
| **Chỉ dùng Lazy Eviction** | Siêu nhẹ, không tốn thêm CPU chạy nền định kỳ. | **Rò rỉ RAM (Memory Leak)** nặng nề nếu có hàng triệu khóa bị ghi vào rồi bị bỏ quên không bao giờ đọc lại. | Ứng dụng nhỏ, số lượng khóa biến đổi ít hoặc các khóa liên tục được đọc. |
| **Chỉ dùng Active Eviction (Quét toàn bộ)** | Thu hồi RAM triệt để nhất. | Tốn CPU để duyệt lặp qua toàn bộ Map. Nếu dung lượng Cache cực lớn (hàng triệu khóa) sẽ gây nghẽn CPU chính. | Hệ thống bắt buộc phải giải phóng RAM liên tục, số lượng khóa nhỏ. |
| **Sự kết hợp kép (Lazy + Active) - Khuyên dùng** | **Tối ưu tuyệt đối**: Vừa thu hồi RAM kịp thời lúc đọc, vừa giải quyết triệt để rác bỏ quên ngầm mà không gây tốn quá nhiều CPU. | Code phức tạp hơn đôi chút. | **Tiêu chuẩn công nghiệp** (Được áp dụng rộng rãi bởi Redis, Memcached). |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

### 1. Tại sao hàm quét rác ngầm định kỳ (Active Eviction) có thể trở thành ác mộng về hiệu năng nếu dung lượng Cache lớn? Làm thế nào để giải quyết giống Redis?
* **Trả lời**: Nếu trong Cache đang chứa 10 triệu phần tử, việc luồng chạy ngầm thực hiện duyệt vòng lặp qua toàn bộ 10 triệu bản ghi sẽ ngốn sạch tài nguyên CPU và khóa chặt cấu trúc Map.
  * **Giải pháp tối ưu theo kiểu Redis (Random Sampling)**:
    * Thay vì quét tuyến tính toàn bộ cấu trúc Map, luồng dọn dẹp ngầm chỉ lấy ngẫu nhiên ra $X$ phần tử (ví dụ $X=20$) để kiểm tra.
    * Tiến hành xóa các phần tử đã hết hạn trong nhóm 20 này.
    * Nếu tỷ lệ phần tử hết hạn vượt quá 25% (tức là lượng rác đang rất nhiều), luồng tiếp tục lặp lại quá trình lấy ngẫu nhiên 20 phần tử khác để xóa tiếp, cho đến khi tỷ lệ rác giảm xuống dưới 25% hoặc hết thời gian tối đa được phép quét (time limit, ví dụ tối đa 10ms).
    * Phương án này giúp giới hạn tuyệt đối CPU tiêu thụ ở mức hằng số nhỏ mà vẫn đảm bảo dọn dẹp rác hiệu quả!

### 2. Sự khác biệt giữa `ConcurrentHashMap` và `Collections.synchronizedMap` khi dùng làm cấu trúc nền cho Cache là gì?
* **Trả lời**:
  * **`Collections.synchronizedMap`**: Sử dụng cơ chế khóa toàn cục ở cấp độ đối tượng (Object-level lock). Nghĩa là mọi thao tác đọc/ghi vào Map tại một thời điểm đều khóa toàn bộ Map lại. Nếu có 100 luồng cùng lúc truy cập, 99 luồng sẽ phải xếp hàng chờ đợi, làm sụt giảm throughput hệ thống thê thảm.
  * **`ConcurrentHashMap`**: Sử dụng cơ chế khóa cực kỳ thông minh ở cấp độ phân mảnh (Bucket-level lock/Segment lock). Các luồng ghi vào các vị trí băm khác nhau của mảng sẽ không hề khóa lẫn nhau. Đặc biệt, các luồng đọc dữ liệu hoàn toàn không bị block bởi luồng ghi (Lock-free reads). Nhờ đó, hiệu năng xử lý đa luồng tăng lên hàng trăm lần!

### 3. Làm thế nào để bảo vệ Cache chống lại hiện tượng Cache Penentration (Truy cập khóa liên tục không tồn tại)?
* **Trả lời**: Nếu kẻ tấn công liên tục gọi `get(key)` với các khóa ngẫu nhiên không hề có trong cả Cache lẫn Database, Database sẽ nhanh chóng bị quá tải.
  * **Cách xử lý**:
    * **Lưu giá trị rỗng (Cache Null/Empty)**: Nếu truy vấn Database trả về null (không tồn tại), ta vẫn lưu khóa đó vào Cache với giá trị đặc biệt là "EMPTY" và đặt TTL cực ngắn (ví dụ 1 phút). Các yêu cầu tiếp theo sẽ gặp Cache "EMPTY" và trả về null ngay lập tức mà không cần gọi Database.
    * **Sử dụng Bloom Filter**: Đặt một bộ lọc Bloom Filter trước tầng Cache để kiểm tra nhanh xem khóa có khả năng tồn tại hay không. Nếu Bloom Filter báo không tồn tại (độ chính xác 100% khi báo không tồn tại), ta từ chối yêu cầu ngay lập tức.
