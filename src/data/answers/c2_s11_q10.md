# Làm sao reconcile dữ liệu giữa nhiều system?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Đối soát dữ liệu (Reconciliation) là quá trình so khớp độc lập thông tin giao dịch giữa các hệ thống lưu trữ khác nhau (ví dụ: DB Đơn hàng của bạn, DB của Cổng thanh toán, và File sao kê ngân hàng). Do định lý CAP, hệ thống phân tán không thể đạt được tính nhất quán tức thì (Immediate Consistency), vì vậy đối soát là cơ chế tối thượng để đạt được **Tính nhất quán cuối cùng (Eventual Consistency)** ở mức độ an toàn tài chính.
* **Thảm họa thực chiến được giải quyết**:
  1. **Khách nhận hàng miễn phí (Thất thoát doanh thu)**: Cổng thanh toán báo giao dịch bị `CANCELLED` (do thẻ lỗi), nhưng Backend của bạn bị lag và cập nhật đơn hàng thành `PAID` do nhận sai payload. Nếu không có hệ thống đối soát cuối ngày quét file sao kê ngân hàng, bạn sẽ giao chiếc laptop 30 triệu cho một khách hàng chưa trả một đồng nào.
  2. **Thất thoát phí dịch vụ (Vỡ ngân sách vận hành)**: Đối tác vận chuyển (như GHTK, GHN) tính phí ship của đơn hàng cao hơn so với bảng giá cam kết trong hợp đồng (do đo sai cân nặng). Hệ thống của bạn tự động thanh toán phí mà không đối soát chênh lệch, làm hao hụt hàng trăm triệu đồng tiền phí ship mỗi tháng.
* **Quyết định Senior**:
  1. **Tách biệt hoàn toàn luồng Đối soát (Out-of-band Reconciliation)**: Luồng đối soát phải chạy bất đồng bộ bằng một Service riêng (Reconciliation Engine), tuyệt đối không được gộp chung hoặc làm ảnh hưởng đến hiệu năng của luồng Core Transaction trực tiếp.
  2. **Đối soát 3 bên (Three-way Matching)**: Không chỉ so khớp DB của mình với Cổng thanh toán, mà bắt buộc phải đối chiếu chặng cuối với **Sao kê tài khoản ngân hàng thực tế (Bank Settlement Statement)**.
  3. **Tự động hóa xử lý chênh lệch (Auto-healing & Alerting)**: Phân loại các ca lệch dòng (Discrepancies). Với chênh lệch nhỏ hoặc lỗi trạng thái kỹ thuật -> Tự động kích hoạt API sửa đổi. Với chênh lệch số dư tài chính -> Đẩy vào Dashboard phê duyệt của con người và bắn cảnh báo lập tức.

## 🔍 Chi tiết bản chất thực chiến: Quy trình Đối soát 3 bên (Three-way Matching)

Đối soát tài chính chuyên nghiệp luôn phải thiết lập mô hình tam giác cân bằng dữ liệu:

```
                  ┌──────────────────────┐
                  │ 1. Hệ Thống Nội Bộ   │
                  │    (Internal DB)     │
                  └──────────┬───────────┘
                             │
                  (So khớp mã / số tiền)
                             │
                             ▼
 ┌──────────────────────┐    │    ┌──────────────────────┐
 │ 2. Cổng Thanh Toán   │◄───┴───►│ 3. Sao kê Ngân Hàng  │
 │ (Stripe/Paypal/Gate) │         │ (Bank Settlement)    │
 └──────────────────────┘         └──────────────────────┘
```

### 3 Chặng đối soát kinh điển:
1. **Chặng 1: Internal DB vs Gateway API (Real-time/Hourly)**: So khớp tức thì trạng thái đơn hàng trong DB của bạn với dữ liệu giao dịch trên Cổng thanh toán để nhanh chóng vá các ca rớt webhook.
2. **Chặng 2: Internal DB vs Gateway Settlement File (Daily)**: Cuối ngày, Cổng thanh toán xuất file báo cáo (Settlement Report) chứa danh sách các giao dịch thực tế đã được trừ tiền và chuẩn bị chuyển về tài khoản ngân hàng của bạn. So khớp file này với DB để tìm ra các đơn hàng bị lệch số tiền hoặc bị tính sai phí giao dịch (Gateway Fee).
3. **Chặng 3: Gateway Settlement vs Bank Statement (Weekly/Monthly)**: So khớp số tiền cổng thanh toán cam kết chuyển về với số tiền thực tế cộng vào tài khoản ngân hàng của công ty (Bank Account) để phát hiện thất thoát ở chặng cuối cùng.

```
 [File Báo Cáo Cổng (CSV)] ───► [Reconciliation Engine] ◄─── [Internal Replica DB]
                                          │
                                          ▼
                         [So khớp theo Transaction ID]

```

## 💻 Code thực chiến: SQL truy quét lệch dòng & Python Recon Job

### 1. SQL Query Đối soát nhanh phát hiện lệch dòng (Discrepancy Detection)
Câu lệnh dưới đây sử dụng `FULL OUTER JOIN` để tìm ra toàn bộ các giao dịch bị lệch trạng thái hoặc lệch số tiền giữa Database nội bộ và dữ liệu nhận về từ đối tác thanh toán.

```sql
SELECT 
    COALESCE(o.id, g.order_id) as txn_id,
    o.status as internal_status,
    g.status as gateway_status,
    o.total_amount as internal_amount,
    g.amount as gateway_amount,
    -- Tính toán chênh lệch số tiền
    (COALESCE(o.total_amount, 0) - COALESCE(g.amount, 0)) as amount_diff
FROM orders o
FULL OUTER JOIN gateway_transactions g ON o.id = g.order_id
WHERE 
    -- Lọc các ca lệch trạng thái
    (o.status <> g.status)
    -- Hoặc lệch số tiền thanh toán thực tế
    OR (o.total_amount <> g.amount)
    -- Hoặc giao dịch mồ côi (chỉ tồn tại ở 1 bên)
    OR (o.id IS NULL OR g.order_id IS NULL);
```

### 2. Python Batch Recon Engine tự động phân loại và xử lý chênh lệch

Mã nguồn Python dưới đây mô phỏng một dịch vụ đối soát tự động, đọc file báo cáo đối tác, so sánh DB và thực hiện tự động vá lỗi hoặc bắn cảnh báo:

```python
import csv
import logging
from typing import Dict, Any

logging.basicConfig(level=logging.INFO, format='%(asctime)s - %(levelname)s - %(message)s')

class ReconciliationEngine:
    def __init__(self, db_connection, alert_service):
        self.db = db_connection
        self.alert = alert_service

    def reconcile_daily_report(self, csv_filepath: str):
        logging.info(f"Starting reconciliation for file: {csv_filepath}")
        
        with open(csv_filepath, mode='r', encoding='utf-8') as file:
            reader = csv.DictReader(file)
            
            for row in reader:
                txn_id = row['transaction_id']
                gateway_amount = float(row['amount'])
                gateway_status = row['status'] # SUCCESS, FAILED
                
                # 1. Truy vấn thông tin đơn hàng trong Database nội bộ
                internal_order = self._get_internal_order(txn_id)
                
                if not internal_order:
                    # Trường hợp 1: Giao dịch mồ côi (Chỉ có ở cổng thanh toán, không có ở DB mình)
                    self._handle_orphan_transaction(txn_id, gateway_amount, gateway_status)
                    continue
                
                internal_amount = internal_order['total_amount']
                internal_status = internal_order['status'] # PENDING, PAID, CANCELLED
                
                # 2. So khớp số tiền
                if internal_amount != gateway_amount:
                    self._handle_amount_mismatch(txn_id, internal_amount, gateway_amount)
                    continue
                
                # 3. So khớp trạng thái
                if internal_status != gateway_status:
                    self._handle_status_mismatch(txn_id, internal_status, gateway_status)
                else:
                    logging.info(f"Transaction {txn_id} matched perfectly. OK.")

    def _get_internal_order(self, txn_id: str) -> Dict[str, Any]:
        cursor = self.db.cursor(dictionary=True)
        cursor.execute("SELECT status, total_amount FROM orders WHERE id = %s", (txn_id,))
        return cursor.fetchone()

    def _handle_orphan_transaction(self, txn_id: str, amount: float, status: str):
        # Đây là lỗi cực kỳ nguy hiểm: Khách đã bị trừ tiền nhưng DB không có bất kỳ hóa đơn nào
        msg = f"CRITICAL: Orphan transaction detected at gateway! ID: {txn_id}, Amount: {amount}, Status: {status}"
        logging.error(msg)
        self.alert.send_urgent_alert(msg)

    def _handle_amount_mismatch(self, txn_id: str, internal_amt: float, gate_amt: float):
        # Lỗi lệch tiền: Khách hàng tìm cách sửa request để trả ít tiền hơn hoặc cổng tính sai
        msg = f"WARNING: Amount mismatch for transaction {txn_id}! Internal: {internal_amt}, Gateway: {gate_amt}"
        logging.error(msg)
        self.alert.send_urgent_alert(msg)

    def _handle_status_mismatch(self, txn_id: str, internal_status: str, gate_status: str):
        if gate_status == "SUCCESS" and internal_status == "PENDING":
            # Ca lệch trạng thái lành tính: Đơn hàng đã trả tiền nhưng webhook bị rớt. Tự động vá DB.
            logging.info(f"Resolving status mismatch: Auto-updating order {txn_id} from PENDING to PAID.")
            self._auto_update_order_status(txn_id, "PAID")
        else:
            # Các trường hợp nguy hiểm khác (ví dụ: DB ghi PAID nhưng Gate báo FAILED)
            msg = f"ALERT: Status mismatch for transaction {txn_id}! Internal: {internal_status}, Gateway: {gate_status}"
            logging.error(msg)
            self.alert.send_standard_alert(msg)

    def _auto_update_order_status(self, txn_id: str, status: str):
        cursor = self.db.cursor()
        cursor.execute(
            "UPDATE orders SET status = %s, updated_by = 'recon_auto_healing' WHERE id = %s",
            (status, txn_id)
        )
        self.db.commit()
```

| Tiêu chí | Chiến lược 1: Đối soát thời gian thực (Real-time Sync) | Chiến lược 2: Đối soát theo lô định kỳ (Daily Batch Recon) | Chiến lược 3: Đối soát hỗn hợp (Hybrid - Khuyên dùng) |
| :--- | :--- | :--- | :--- |
| **Cơ chế hoạt động** | Cứ mỗi 10 phút, worker tự gọi sang API cổng thanh toán để check status. | Gom toàn bộ báo cáo cuối ngày thành file lớn rồi chạy đối chiếu 1 lần vào ban đêm. | Chạy real-time đối soát trạng thái mỗi giờ. Chạy đối soát số tiền và file sao kê ngân hàng vào ban đêm. |
| **Độ trễ phát hiện lỗi** | **Siêu thấp (Vài phút)** | Cao (Chỉ phát hiện sau 24 giờ). | Trung bình thấp. |
| **Tải lên hệ thống** | Rất cao (Gọi API và đọc DB liên tục). | **Rất thấp** (Chạy vào khung giờ thấp điểm ban đêm, không ảnh hưởng người dùng). | Trung bình tốt. |
| **Độ tin cậy tài chính** | Thấp (Chỉ so khớp trạng thái ảo của API cổng thanh toán, không so khớp sao kê dòng tiền thực). | **Tuyệt đối 100%** (Vì file đối soát cuối ngày là căn cứ pháp lý chuyển tiền). | **Tuyệt đối 100%**. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Múi giờ lệch tàn phá báo cáo đối soát" (The Timezone Gotchas)
* **Vấn đề cực kỳ đau đầu**: Hệ thống của bạn ghi nhận thời gian theo múi giờ Việt Nam (`UTC+7`), đơn hàng đặt lúc `00:30` ngày 24/05 sẽ được tính vào doanh thu ngày 24. Tuy nhiên, Cổng thanh toán quốc tế (như Stripe/Paypal) xuất file báo cáo theo múi giờ `UTC`. 
  * Giao dịch đó trên cổng thanh toán sẽ được ghi nhận vào lúc `17:30` ngày 23/05. 
  * Khi chạy Job đối soát theo ngày, hệ thống sẽ báo **lệch hàng loạt đơn hàng** do lệch khớp ngày, gây hoang mang cực lớn cho đội kế toán.
* **Giải pháp khắc phục**:
  1. Bắt buộc chuẩn hóa toàn bộ thời gian của các bên về chuẩn **UTC/Epoch Timestamp** trước khi thực hiện so khớp.
  2. Khi quét đối soát ngày X, hãy quét dải dữ liệu nới rộng ra thêm 7 tiếng ở cả hai đầu biên thời gian (từ `X-1 ngày` đến `X+1 ngày`) để không bỏ sót các giao dịch giao thoa múi giờ.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Hệ thống của tôi có quy mô cực khủng, file giao dịch đối soát cuối ngày chứa tới 100 triệu dòng. Việc đọc và dùng câu SQL JOIN như trên sẽ làm sập Database. Bạn thiết kế kiến trúc đối soát này thế nào để xử lý được?"**
* **Trả lời**:
  * Với quy mô 100 triệu dòng, tuyệt đối không được sử dụng RDBMS truyền thống và các câu lệnh `JOIN` trực tiếp trên Production DB.
  * Senior sẽ thiết kế kiến trúc **MapReduce / Big Data Reconciliation Engine**:
    1. Trích xuất (ETL) dữ liệu giao dịch từ Production DB Replica và tải file đối soát từ Cổng thanh toán lên **Object Storage (AWS S3)** dưới dạng định dạng cột tối ưu như **Apache Parquet**.
    2. Sử dụng công cụ xử lý dữ liệu lớn như **Apache Spark** hoặc **AWS Athena**.
    3. Spark sẽ thực hiện phân vùng dữ liệu (Partitioning) theo mã băm của Transaction ID, chia nhỏ 100 triệu dòng thành các cụm tính toán song song trên nhiều máy chủ mà không gây khóa bất kỳ cơ sở dữ liệu nào.
    4. Trích xuất file kết quả chênh lệch ra S3 và đẩy dữ liệu lỗi về một Service đối soát để xử lý cuốn chiếu.
