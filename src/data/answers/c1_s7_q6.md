# Query Parameter vs Path Parameter: Phân biệt và Thực chiến Lựa chọn

## ⚡ Tóm tắt ngắn (30s)
Cả **Path Parameter (Path Variable)** và **Query Parameter** đều dùng để truyền dữ liệu từ Client lên Server qua URI, nhưng chúng có mục đích kiến trúc hoàn toàn khác nhau trong REST:
*   **Path Parameter**: Dùng để **định danh tài nguyên** (Resource Identity) hoặc biểu diễn quan hệ phân cấp (Hierarchy). Nó là phần bắt buộc của URI.
    *   *Ví dụ:* `/api/v1/users/42` (Số `42` định danh chính xác user).
*   **Query Parameter**: Dùng để **lọc, sắp xếp, tìm kiếm hoặc phân trang** (Filter, Sort, Search, Paginate) danh sách tài nguyên. Nó nằm sau dấu `?` và là phần tùy chọn (Optional).
    *   *Ví dụ:* `/api/v1/users?status=ACTIVE&sort=createdAt,desc` (Chỉ lấy các user hoạt động và sắp xếp theo ngày tạo).

## 🔍 Chi tiết bản chất thực chiến

### 1. Nguyên tắc lựa chọn chuẩn RESTful

Để thiết kế API có tính nhất quán cao, ta áp dụng quy tắc vàng sau:

```mermaid
graph TD
    Data[Dữ liệu cần truyền] --> Identify{Dữ liệu có dùng để định danh duy nhất một tài nguyên không?}
    Identify -- Có --> Path[Dùng Path Parameter<br>/api/v1/users/{id}]
    Identify -- Không --> Hierarchy{Dữ liệu biểu diễn quan hệ cha-con bắt buộc?}
    Hierarchy -- Có --> Path[Dùng Path Parameter<br>/api/v1/users/{userId}/orders/{orderId}]
    Hierarchy -- Không --> Query[Dùng Query Parameter<br>/api/v1/users?role=ADMIN]
```

#### 📌 Quy tắc 1: Path Parameter đại diện cho Định danh & Phân cấp
Nếu không có tham số này, URI hoàn toàn vô nghĩa hoặc không thể xác định được đối tượng đích.
*   *Mối quan hệ cha-con*: Khi một tài nguyên con không thể tồn tại độc lập mà phải gắn liền với tài nguyên cha.
    *   *Đúng:* `GET /api/v1/users/{userId}/addresses/{addressId}`
    *   *Giải thích:* Để lấy địa chỉ cụ thể (`addressId`), ta buộc phải đi qua định danh của user (`userId`).

#### 📌 Quy tắc 2: Query Parameter đại diện cho Trạng thái / Thuộc tính tùy chọn
Nếu không truyền các tham số này, API vẫn hoạt động bình thường và trả về kết quả mặc định (ví dụ: trả về danh sách tất cả các thực thể).
*   *Lọc (Filtering)*: `/api/v1/products?category=electronics`
*   *Phân trang (Pagination)*: `/api/v1/products?page=0&size=20`
*   *Sắp xếp (Sorting)*: `/api/v1/products?sort=price,asc`

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Dùng lẫn lộn Path và Query Parameter
Thiết kế controller dưới đây vi phạm nghiêm trọng tính nhất quán của REST, dùng sai ngữ nghĩa của hai loại tham số.

```java
@RestController
@RequestMapping("/api/v1")
public class ProductBadController {

    // Anti-pattern 1: Dùng Query Param để truyền ID định danh tài nguyên bắt buộc
    // URI trở thành: /api/v1/products/detail?productId=123 (Rất xấu và mất tính REST)
    @GetMapping("/products/detail")
    public Product getProductBad(@RequestParam Long productId) {
        return productService.findById(productId);
    }

    // Anti-pattern 2: Dùng Path Param cho các bộ lọc tùy chọn
    // URI trở thành: /api/v1/products/by-category/electronics/min-price/100
    // Nếu client không muốn lọc theo min-price, họ không biết gọi thế nào vì Path này là bắt buộc!
    @GetMapping("/products/by-category/{category}/min-price/{minPrice}")
    public List<Product> filterProductsBad(
            @PathVariable String category,
            @PathVariable Double minPrice
    ) {
        return productService.filter(category, minPrice);
    }
}
```

###  GOOD: Phân chia chính xác theo chuẩn REST nghiệp vụ
Sử dụng Path Parameter để định danh đối tượng và quan hệ cha-con; sử dụng Query Parameter (thông qua đối tượng DTO tự động map) cho các bộ lọc và phân trang tùy chọn.

```java
@RestController
@RequestMapping("/api/v1/users")
public class UserGoodController {

    private final OrderService orderService;
    private final UserService userService;

    public UserGoodController(OrderService orderService, UserService userService) {
        this.orderService = orderService;
        this.userService = userService;
    }

    // 1. Dùng Path Parameter để xác định tài nguyên cụ thể (User 42 -> Order 99)
    // URI chuẩn: GET /api/v1/users/42/orders/99
    @GetMapping("/{userId}/orders/{orderId}")
    public ResponseEntity<OrderResponse> getUserOrder(
            @PathVariable Long userId,
            @PathVariable Long orderId
    ) {
        OrderResponse order = orderService.findByUserAndId(userId, orderId);
        return ResponseEntity.ok(order);
    }

    // 2. Dùng Query Parameter để lọc và phân trang danh sách (Optional)
    // URI chuẩn: GET /api/v1/users?role=ADMIN&status=ACTIVE&page=0&size=10
    // Spring Boot tự động map các query params trùng tên vào đối tượng UserSearchCriteria DTO
    @GetMapping
    public ResponseEntity<Page<UserResponse>> searchUsers(
            UserSearchCriteria criteria,
            @PageableDefault(size = 10, sort = "createdAt") Pageable pageable
    ) {
        Page<UserResponse> users = userService.search(criteria, pageable);
        return ResponseEntity.ok(users);
    }
}
```

## 📊 Trade-off: So sánh tính năng kỹ thuật

| Tiêu chí | Path Parameter | Query Parameter |
| :--- | :--- | :--- |
| **Tính bắt buộc** | **Bắt buộc**. Nếu thiếu, Spring Boot sẽ trả về `404 Not Found` (không khớp route). | **Tùy chọn (Optional)**. Nếu thiếu, Spring tự động gán giá trị mặc định hoặc null. |
| **Giới hạn độ dài** | Hạn chế hơn. URI path dài quá mức có thể bị gateway chặn. | Thoải mái hơn, nhưng vẫn bị giới hạn độ dài tổng URI của trình duyệt/proxy (thường là 2048 chars). |
| **Khả năng Caching** | Cực tốt. Từng Path cụ thể được cache riêng biệt ở CDN. | Tương đối tốt. Tuy nhiên, thứ tự các tham số khác nhau (ví dụ: `?a=1&b=2` vs `?b=2&a=1`) sẽ làm CDN hiểu là 2 request khác nhau và làm giảm cache hit ratio. |
| **Bảo mật** | Thường được ghi lại (logged) đầy đủ ở tất cả các lớp reverse proxy/APM. Không được truyền dữ liệu nhạy cảm ở đây. | Tương tự Path Param, dữ liệu hiện rõ trên thanh địa chỉ. **Tuyệt đối không truyền password/token qua query param!** |

## ⚠️ Common Gotchas & Questions follow-up

* **Cạm bẫy "Xung đột Routing" khi dùng Path Parameter quá đà**:
  Nếu bạn khai báo quá nhiều Path Parameter trùng cấu trúc trong cùng một Controller:
  * *Ví dụ:*
    ```java
    @GetMapping("/{id}") // Match GET /users/123
    public User getUser(@PathVariable Long id) { ... }
    
    @GetMapping("/{username}") // Match GET /users/alex -> GÂY LỖI AMBIGUOUS MAPPING!
    public User getUserByUsername(@PathVariable String username) { ... }
    ```
  * *Khắc phục:* Tránh sử dụng các Path Parameter có kiểu dữ liệu chồng lấp trên cùng một cấp độ URL. Hãy chuyển đổi cách định danh duy nhất qua một trường cụ thể hoặc chuyển giá trị tìm kiếm tùy chọn (`username`) sang Query Parameter: `/api/v1/users?username=alex`.

* **Câu hỏi đào sâu từ interviewer**: *Nếu tôi có một form tìm kiếm nâng cao với 50 bộ lọc khác nhau, tôi nên truyền chúng qua Query Parameter hay POST Body?*
  * *(Trả lời: Về mặt học thuật REST, hành động "Tìm kiếm" là đọc dữ liệu (Read-only), do đó phải dùng GET với Query Parameter. Tuy nhiên, nếu số lượng bộ lọc quá lớn (50 trường), việc gom hết vào Query Parameter sẽ khiến URI vượt quá giới hạn 2048 ký tự của trình duyệt/proxy cũ, dẫn đến lỗi `414 URI Too Long`.
    Trong thực tế dự án Enterprise, ta có thể đánh đổi tính chuẩn chỉ của REST để lấy tính ổn định bằng cách thiết kế API này sử dụng phương thức **POST** lên endpoint `/api/v1/users/search` (hoặc `/query`) và truyền 50 bộ lọc trong Request Body).*
