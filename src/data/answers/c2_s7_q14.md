# Làm sao đảm bảo idempotency cho Kafka consumer?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Hệ thống tin nhắn như Kafka hoạt động theo cơ chế **At-Least-Once Delivery (Đảm bảo giao hàng ít nhất một lần)**. Điều này đồng nghĩa với việc tin nhắn **chắc chắn sẽ bị trùng lặp (duplicate)** trên Production do lỗi mạng, rebalance, hoặc consumer bị crash trước khi kịp commit offset. **Idempotency (Tính bất biến)** yêu cầu dù consumer nhận và xử lý một tin nhắn $N$ lần thì kết quả lưu trữ cuối cùng ở Database vẫn y nguyên như chỉ xử lý 1 lần duy nhất và không sinh ra bất kỳ phản ứng phụ nào (side-effect).
* **Quyết định Senior**: Áp dụng cơ chế phòng thủ 3 lớp (Defense-in-Depth):
  1. **Lớp 1: Chốt chặn tốc độ nhanh (Redis Distributed Lock / Idempotency Key)**: Sử dụng Redis băm key `messageId` có TTL để lọc trùng nhanh tốc độ cao ở RAM.
  2. **Lớp 2: Chốt chặn cứng tối thượng (Database Unique Constraint)**: Tạo bảng lịch sử tin nhắn đã xử lý (`processed_messages`) với khóa chính `message_id`. Insert lỗi trùng khóa sẽ lập tức rollback transaction.
  3. **Lớp 3: Bất biến nghiệp vụ (State Machine Check)**: Chỉ thực hiện cập nhật nếu trạng thái hiện tại của thực thể là hợp lệ (ví dụ: chỉ chuyển từ `CREATED -> PAID`, nếu đã là `PAID` thì tự động bỏ qua).

## 🔍 Chi tiết bản chất thực chiến: Tại sao tin nhắn bị trùng lặp?

Để thiết kế đúng, ta phải hiểu 3 nguồn gốc sinh trùng lặp trong hệ thống phân tán:
1. **Producer Retry**: Producer gửi message thành công nhưng Broker phản hồi thất bại (do rớt mạng lúc ack). Producer gửi lại message đó, Broker ghi nhận thành 2 record khác nhau ở 2 offset khác nhau.
2. **Rebalance Offset Commit Failure**: Consumer tiêu thụ kéo về 10 tin nhắn, xử lý thành công 5 tin nhắn nhưng chưa kịp commit offset lên Broker thì bị trục xuất khỏi Group do Rebalance. Consumer mới nhảy vào nhận partition đó và sẽ **tiêu thụ lại từ đầu lô 10 tin nhắn đó**.
3. **Consumer Crash/Restart**: Consumer xử lý xong ghi DB nhưng sập nguồn máy chủ trước khi kịp gửi lệnh commit offset lên Broker.

## 💻 Code thực chiến: Triển khai Idempotent Consumer (Redis + RDBMS)

Dưới đây là mã nguồn Java hoàn chỉnh, kết hợp cả **Redis Distributed Lock (Redisson)** để lọc trùng hiệu năng cao ở RAM và **Database Unique Constraint** để đảm bảo an toàn tuyệt đối ở đĩa cứng.

```java
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.concurrent.TimeUnit;

@Slf4j
@Service
@RequiredArgsConstructor
public class IdempotentOrderConsumer {

    private final RedissonClient redissonClient;
    private final OrderService orderService;
    private final ProcessedMessageRepository processedMessageRepository;

    @KafkaListener(topics = "order-events", groupId = "order-idempotent-group")
    public void consumeOrder(String messagePayload, 
                             @org.springframework.messaging.handler.annotation.Header("messageId") String messageId,
                             Acknowledgment ack) {
                             
        log.info("📥 Nhận messageId: {}, Payload: {}", messageId, messagePayload);

        if (messageId == null) {
            log.error("❌ Message thiếu header bắt buộc 'messageId'! Từ chối xử lý.");
            ack.acknowledge();
            return;
        }

        // =======================================================
        // ✅ LỚP 1: LỌC TRÙNG BẰNG REDIS DISTRIBUTED LOCK (Tốc độ RAM)
        // =======================================================
        String lockKey = "lock:message:" + messageId;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // Thử giành lock trong 1 giây, nếu giành được thì giữ lock trong 10 giây
            boolean isLocked = lock.tryLock(1, 10, TimeUnit.SECONDS);
            if (!isLocked) {
                log.warn("⚠️ Message {} đang được xử lý bởi thread khác hoặc bị trùng lặp. Bỏ qua!", messageId);
                return;
            }

            // Gọi Transaction xử lý lõi nghiệp vụ tại DB
            orderService.processOrderWithDatabaseDefense(messageId, messagePayload);
            
            // Xử lý thành công hoàn toàn -> Commit offset lên Kafka
            ack.acknowledge();
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("❌ Thread bị ngắt quãng khi đang lấy lock cho message {}", messageId);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock(); // Giải phóng lock
            }
        }
    }
}

// ── LỚP NGHIỆP VỤ BỌC TRANSACTION ĐỂ BẢO VỆ TẠI DATABASE ───────────────────
@Slf4j
@Service
@RequiredArgsConstructor
class OrderService {

    private final OrderRepository orderRepository;
    private final ProcessedMessageRepository processedMessageRepository;

    @Transactional
    public void processOrderWithDatabaseDefense(String messageId, String payload) {
        
        // =======================================================
        // ✅ LỚP 2: CHỐT CHẶN CỨNG BẰNG DATABASE UNIQUE CONSTRAINT
        // =======================================================
        try {
            // Ghi nhận messageId vào bảng processed_messages (khóa chính message_id)
            ProcessedMessageEntity processedMessage = new ProcessedMessageEntity(messageId);
            processedMessageRepository.saveAndFlush(processedMessage);
        } catch (DataIntegrityViolationException e) {
            // Ném ngoại lệ trùng khóa chính, kích hoạt Rollback toàn bộ transaction tự động
            log.warn("⚠️ [DATABASE TRÙNG KHÓA] Message {} đã được xử lý thành công trước đó. Rollback!", messageId);
            return; // Trả về an toàn mà không ném lỗi sập luồng consumer
        }

        // Parse order info
        OrderDto orderDto = parseOrder(payload);

        // =======================================================
        // ✅ LỚP 3: BẤT BIẾN NGHIỆP VỤ BẰNG STATE MACHINE CHECK
        // =======================================================
        OrderEntity order = orderRepository.findById(orderDto.getOrderId()).orElse(null);
        if (order != null) {
            if ("PAID".equals(order.getStatus())) {
                log.info("⚠️ Đơn hàng {} đã được thanh toán rồi. Không xử lý lại logic nghiệp vụ.", order.getId());
                return; // Tránh chạy lại side-effect (ví dụ: trừ ví khách hàng, gửi email chúc mừng lần 2)
            }
            
            // Chỉ cho phép cập nhật nếu trạng thái hiện tại là PENDING
            if ("PENDING".equals(order.getStatus())) {
                order.setStatus("PAID");
                orderRepository.save(order);
                log.info("✅ Cập nhật trạng thái đơn hàng {} sang PAID thành công!", order.getId());
                
                // Gửi side-effect (Gửi OTP, Gọi API vận chuyển)
                callDeliveryPartnerAPI(order);
            }
        } else {
            // Xử lý tạo đơn hàng mới...
        }
    }

    private OrderDto parseOrder(String json) { return new OrderDto(100L, 50000.0); }
    private void callDeliveryPartnerAPI(OrderEntity order) { log.info("🚚 Đã gọi API đơn vị vận chuyển!"); }
}
```

## 📊 Bảng so sánh 3 Phương án lọc trùng tin nhắn

| Phương án phòng thủ | Tốc độ xử lý (Throughput) | Mức độ an toàn (Data Safety) | Ưu điểm cốt lõi | Nhược điểm |
| :--- | :--- | :--- | :--- | :--- |
| **Lớp 1: Redis Idempotency Key** | **Cực nhanh** (Xử lý trên RAM cỡ millisecond). | Khá (Có thể mất dữ liệu nếu Redis bị khởi động lại và mất AOF). | Lọc trùng siêu tốc từ xa, tránh làm phiền Database. | Phụ thuộc thêm hạ tầng Redis. Có rủi ro TTL quá hạn gây lọt lưới. |
| **Lớp 2: DB Unique Key Table** | Trung bình/Chậm (Tốn transaction ghi đĩa DB). | **Tuyệt đối an toàn** (Ràng buộc vật lý cứng của RDBMS). | Không bao giờ lọt lưới dù có lỗi mạng hay restart hệ thống. | Tăng tải I/O đĩa cho Database. |
| **Lớp 3: State Machine Logic** | **Rất tốt** (Chỉ tốn câu lệnh kiểm tra logic). | **Tuyệt đối an toàn** về mặt logic nghiệp vụ. | Ngăn chặn hoàn toàn lỗi side-effect nghiệp vụ chạy tuần hoàn. | Cần thiết kế cấu trúc State của Entity chặt chẽ ngay từ đầu. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Bão mạng làm sập API Downstream lần 2 (Unintended Side Effects)"
* **Vấn đề**: Consumer nhận message -> Thực hiện trừ tiền ngân hàng thành công ở DB -> Gọi API gửi tin nhắn SMS chúc mừng qua mạng -> Mạng sập -> Consumer crash trước khi kịp commit offset. 
* Khi consumer chạy lại, nó lọc trùng thành công ở DB (không trừ tiền lần 2) nhưng **vẫn chạy tiếp dòng code gọi API SMS lần thứ 2**, khiến khách hàng nhận được 2 SMS giống hệt nhau, gây phản cảm và tốn kém chi phí viễn thông.
* **Khắc phục (Quyết định Senior)**: 
  * Tách biệt logic **Cập nhật dữ liệu DB** và **Gửi Side-effect qua API**.
  * Không bao giờ gọi API bên ngoài trực tiếp bên trong DB Transaction nghiệp vụ của consumer.
  * Sử dụng **Transactional Outbox Pattern**: Chỉ ghi nhận một bản ghi tác vụ "Cần gửi SMS" vào Database. Một Worker ngẫu nhiên khác sẽ quét bảng Outbox này và gửi SMS, đảm bảo gửi thành công đúng một lần dựa trên ID của outbox record.

### 2. Câu hỏi đào sâu từ interviewer
* **Q2: Tại sao không nên thiết kế Key của bảng `processed_messages` là tự tăng (Auto-increment) mà phải là chính `messageId` của Kafka?**
  * *Trả lời*:
    * Nếu dùng khóa tự tăng, hệ thống sẽ không có cơ sở nào để phát hiện trùng lặp vì mỗi lần insert một bản ghi trùng lặp, Database sẽ đơn giản là cấp cho nó một ID mới tăng dần và cho phép ghi thành công.
    * Khóa chính của bảng `processed_messages` bắt buộc phải là chính chuỗi `messageId` (hoặc băm `eventUniqueKey`) nhận được từ Header của Kafka. Ràng buộc khóa chính (Primary Key Constraint) sẽ tự động ném ra lỗi `DuplicateKeyException` khi có bất kỳ dòng nào cố tình ghi đè trùng ID đó, đóng vai trò là chiếc khóa bảo vệ vật lý tuyệt đối cho dữ liệu.
