# Làm sao phân biệt latency do app, DB, network, cache hay downstream?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Để phân tách và xác định chính xác nguồn gốc gây trễ trong hệ thống phân tán phức tạp, kỹ sư phải sử dụng phương pháp **Giám sát quan trắc toàn diện (Full-stack Observability)**. Trọng tâm là công nghệ **Truy vết phân tán (Distributed Tracing)** giúp đo lường thời gian thực hiện (Spans) từ lúc request chạm vào Gateway cho đến khi hoàn thành dưới Database.
* **Các thảm họa thực chiến được giải quyết**:
    1. **Mất dấu vết khi gọi qua mạng (Black Box Communication)**: Hệ thống có 20 microservices gọi chéo nhau. Một request bị chậm 5 giây nhưng không thể biết service nào trong chuỗi là tác nhân gây chậm.
    2. **Đổ lỗi chéo giữa các phòng ban (Team Blaming)**: Đội hạ tầng mạng khẳng định mạng nhanh, đội DB khẳng định DB không nghẽn, đội ứng dụng khẳng định code tối ưu. Hệ thống vẫn chậm mà không có bằng chứng phân bổ thời gian rõ ràng.
* **Quyết định Senior**: Triển khai tích hợp chuẩn **OpenTelemetry** kết hợp cùng **Micrometer Tracing** (hoặc Spring Cloud Sleuth) để tự động đính kèm **Trace ID** và **Span ID** vào mọi cuộc giao tiếp HTTP/gRPC (W3C Trace Context). Sử dụng giao diện APM (Datadog, Jaeger, Zipkin) để hiển thị sơ đồ phân rã độ trễ trực quan theo trục thời gian (Timeline Waterfall chart).

## 🔍 Chi tiết bản chất thực chiến

Để phân biệt nguồn gốc gây ra độ trễ (latency), chúng ta dựa trên các chỉ số định lượng cụ thể:

### 1. Phân biệt trễ do Mạng (Network Latency)
* **Triệu chứng**: Thời gian phản hồi đo từ phía Client (ví dụ 1,200ms) lớn hơn nhiều so với tổng thời gian xử lý đo được ngay tại API Gateway (ví dụ 100ms).
* **Công cụ chẩn đoán**: Đo lường **TTFB (Time To First Byte)** trên trình duyệt, chạy lệnh `ping` hoặc `mtr` (My Traceroute) để đo đếm tỷ lệ mất gói tin (packet loss) và thời gian truyền tải vòng tròn (Round-Trip Time).

### 2. Phân biệt trễ do Cơ sở dữ liệu (Database Latency)
* **Triệu chứng**: Trên APM, thanh hiển thị thời gian truy vấn của Database (ví dụ: `SQL SELECT...`) chiếm hơn 80% tổng thời gian sống của cả request.
* **Công cụ chẩn đoán**: Xem chỉ số **Query Execution Time** từ database engine (như `slow_query_log` trong MySQL hoặc `pg_stat_statements` trong PostgreSQL), kiểm tra số lượng kết nối đang chờ trong hàng đợi pool.

### 3. Phân biệt trễ do Ứng dụng (Application Latency)
* **Triệu chứng**: DB phản hồi nhanh, mạng ổn định, nhưng thời gian xử lý nội bộ của API Controller vẫn rất dài. CPU của App server tăng cao.
* **Công cụ chẩn đoán**: Thực hiện **CPU Profiling** bằng Java Flight Recorder để tìm xem phương thức (method) Java nào đang chiếm dụng nhiều chu kỳ CPU vật lý (thường do vòng lặp vô hạn, JSON serialization, hoặc tranh chấp khóa).

### 4. Phân biệt trễ do Downstream Service / Third-party
* **Triệu chứng**: Sơ đồ Distributed Tracing hiển thị một Span gọi mạng HTTP/gRPC ra bên ngoài (ví dụ: gọi sang cổng thanh toán Stripe) kéo dài vô tận.
* **Công cụ chẩn đoán**: APM hiển thị thời gian phản hồi của outbound HTTP requests tăng cao, số lượng kết nối HTTP client pool bị cạn kiệt.

## 💻 Code thực chiến / Cấu hình thực tế: BAD vs GOOD

Để Distributed Tracing hoạt động, mọi microservice bắt buộc phải hợp tác để truyền tải **Trace Context** qua môi trường mạng (gọi là **Context Propagation**).

### ❌ BAD: Thực hiện cuộc gọi mạng thủ công làm đứt gãy chuỗi Trace Context
Sử dụng các thư viện HTTP client tự tạo mới hoàn toàn mà không đính kèm trace headers từ MDC (Mapped Diagnostic Context), khiến hệ thống APM tạo ra hai Trace ID riêng biệt cho hai service, làm mất khả năng liên kết bản đồ cuộc gọi.

```java
@Service
public class OrderServiceBad {
    public void callPayment(Order order) {
        // ❌ Tự tạo mới HttpClient thủ công làm mất hoàn toàn Trace ID đang có của request hiện tại
        HttpClient client = HttpClient.newHttpClient();
        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create("http://payment-service/api/charge"))
            .POST(HttpRequest.BodyPublishers.ofString("{...}"))
            .build(); // ❌ Không truyền trace headers (traceparent) qua HTTP Headers
            
        client.sendAsync(request, HttpResponse.BodyHandlers.ofString());
    }
}
```

---

### ✅ GOOD: Cấu hình Spring Boot Micrometer Tracing để tự động lan truyền Context qua mạng
Sử dụng thư viện Micrometer Tracing và bọc cấu hình `RestTemplate` để tự động chèn các tiêu chuẩn trace headers (như W3C `traceparent`: `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`) vào mọi request đi ra ngoài.

* **Cấu hình Spring Boot dependencies (build.gradle)**:
```groovy
dependencies {
    // Thư viện quan trắc và truy vết chuẩn hiện đại cho Spring Boot 3
    implementation 'io.micrometer:micrometer-observation'
    implementation 'io.micrometer:micrometer-tracing-bridge-otel' // Cầu nối OpenTelemetry
    implementation 'io.opentelemetry:opentelemetry-exporter-zipkin' // Xuất dữ liệu sang Zipkin/Jaeger
}
```

* **Mã nguồn Spring Boot tự động đồng bộ hóa Trace Context**:
```java
@Configuration
public class TracingConfig {
    // ✅ RestTemplate được build từ RestTemplateBuilder sẽ tự động được Spring 
    // tích hợp bộ lọc (Interceptor) để chèn Trace Context vào HTTP Headers đi ra ngoài.
    @Bean
    public RestTemplate restTemplate(RestTemplateBuilder builder) {
        return builder.build();
    }
}

@Service
public class OrderServiceGood {
    private static final Logger logger = LoggerFactory.getLogger(OrderServiceGood.class);

    @Autowired
    private RestTemplate restTemplate;

    public void callPayment(Order order) {
        // ✅ Log tự động in ra Trace ID hiện hành để dễ dàng tìm kiếm
        logger.info("Calling payment service for order ID: {}", order.getId());

        // RestTemplate tự động chèn HTTP Headers dạng:
        // traceparent: 00-traceId-spanId-sampled
        PaymentResponse response = restTemplate.postForObject(
            "http://payment-service/api/charge", 
            new PaymentRequest(order.getId()), 
            PaymentResponse.class
        );
        
        logger.info("Payment responded with status: {}", response.getStatus());
    }
}
```

## 📊 Bảng so sánh các công cụ khoanh vùng Latency

| Tiêu chí so sánh | Distributed Tracing (Jaeger / Zipkin) | Hệ thống APM (Datadog / Elastic) | Phân tích Log tập trung (ELK / Loki) |
| :--- | :--- | :--- | :--- |
| **Khả năng định vị** | Định vị chính xác microservice nào gây trễ trong chuỗi cuộc gọi. | Định vị sâu vào mã nguồn (method), JVM, và phần cứng. | Tìm kiếm lỗi dựa trên từ khóa hoặc mã lỗi cụ thể. |
| **Overhead hạ tầng** | Trung bình (Tốn băng thông mạng để gửi spans) | Cao (Cần agent chạy nền) | Rất cao (Tốn dung lượng ổ đĩa lưu trữ dòng text) |
| **Cách liên kết dữ liệu**| Sử dụng **Trace ID** truyền qua HTTP Headers. | Đồng bộ hóa từ JVM Agent đến OS. | Ghép nối thủ công qua timestamp và IP. |
| **Use case tốt nhất** | Đo đếm độ trễ truyền tải mạng giữa các microservices. | Chẩn đoán memory leak, CPU spike, slow query vật lý. | Điều tra chi tiết nghiệp vụ sau khi đã biết dòng code bị lỗi. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Mất dấu vết khi gọi bất đồng bộ" (Async Context Loss)
* **Vấn đề**: Khi request chạy qua các luồng xử lý bất đồng bộ (như `@Async`, CompletableFuture, ThreadPoolExecutor, hoặc Kafka producer), Trace ID đột ngột biến mất khỏi log hoặc bị ghi nhận sai thành một Trace ID của luồng khác.
* **Nguyên nhân**: Trace ID được lưu trữ trong bộ nhớ cục bộ của luồng (**ThreadLocal**). Khi bạn chuyển sang một thread mới từ thread pool, ThreadLocal không tự động sao chép sang thread mới, dẫn đến mất dấu vết (Context Loss).
* **Giải pháp**: Sử dụng các Wrapper của Micrometer/Spring để bọc ThreadPool executor (ví dụ: `LazyTraceExecutor` hoặc `ContextExecutorService`) giúp tự động sao chép ThreadLocal Trace Context từ Thread cha sang Thread con khi bắt đầu thực thi.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Làm thế nào bạn giải quyết bài toán "Chi phí băng thông quá lớn" (High Network Overhead) và "Chi phí lưu trữ đắt đỏ" (Storage Cost) khi hệ thống của bạn xử lý 100,000 RPS và ghi nhận 100% tất cả các spans Distributed Tracing?**
  * *Trả lời*: Đây là thách thức kinh điển về chi phí của Observability. Để tối ưu hóa, tôi sẽ triển khai cấu hình **Adaptive Sampling (Lấy mẫu thích ứng)** ở tầng OpenTelemetry Collector:
    1. **Head-based Sampling**: Chỉ lấy mẫu ngẫu nhiên 1% tổng số request thành công (200 OK) để làm thống kê chung.
    2. **Tail-based Sampling (Quan trọng nhất)**: Cấu hình bộ lọc thông minh tại Collector. Tất cả các request có độ trễ lớn hơn 1,000ms HOẶC trả về lỗi HTTP 5xx sẽ bắt buộc được giữ lại 100% để phục vụ debug.
    3. Việc này giúp giảm tới 90% dung lượng truyền tải mạng và chi phí lưu trữ trên mây, nhưng vẫn đảm bảo giữ lại đầy đủ mọi dữ liệu lỗi và độ trễ đuôi hữu ích cho đội ngũ kỹ sư.
