# Tái cấu trúc Hệ thống Quy mô lớn An toàn (Large-Scale Safe Code Refactoring)

## ⚡ Tóm tắt ngắn (30s)
* **Quy tắc vàng (Michael Feathers)**: **"Tuyệt đối không được thay đổi code nếu chưa có Test bao phủ"**. Nếu code cũ quá rối và kết dính (Tight Coupling) không thể viết Unit Test được, hãy viết **Characterization Tests (Golden Master Test)** ở mức tích hợp trước để làm lưới bảo hiểm hành vi.
* **Chiến thuật thực thi**: Tránh xa cạm bẫy *"Big Bang Rewrite" (đập đi viết lại từ đầu)* vì rủi ro sót logic ẩn là cực lớn. Hãy áp dụng kỹ thuật **Branch by Abstraction (Nhánh bằng Trừu tượng)** kết hợp với **Feature Flag** để thay thế từng phần nhỏ một cách liên tục trên nhánh chính (`main`).
* **Mục tiêu Senior**: Sau khi tái cấu trúc, mã nguồn phải tuân thủ chuẩn SOLID (đặc biệt là Single Responsibility và Open/Closed), độ bao phủ kiểm thử (Test Coverage) tăng cao, và **quá trình chuyển giao phải diễn ra êm đẹp không lỗi hồi quy (Zero Regression Bugs)**.

---

## 🔍 Kịch bản thực chiến (STAR Framework)

### 1. Situation (Bối cảnh)
Trong hệ thống Thương mại điện tử, module Tính điểm & Phân hạng Thành viên (`Loyalty-Engine`) là trái tim giữ chân người dùng. Tuy nhiên, qua 5 năm phát triển nóng, nó đã trở thành một "bãi rác kỹ thuật" khổng lồ. 
Toàn bộ logic tính điểm nằm trong một class duy nhất mang tên `LoyaltyProcessor` dài hơn **4.500 dòng code spaghetti** với các khối `if-else` lồng sâu tới 6-7 tầng. Lớp này kết nối trực tiếp với DB vật lý, gọi cứng các dịch vụ ngoài và **không có bất kỳ một bài Unit Test nào (0% coverage)**. Mỗi khi phòng Marketing muốn tung ra một chiến dịch khuyến mãi mới, đội Dev mất trung bình **7 ngày** để code, test thủ công, và luôn xảy ra lỗi hồi quy làm sai lệch điểm số của người dùng trên Production.

### 2. Task (Thử thách)
Với vai trò là Senior Backend Architect, tôi được giao nhiệm vụ:
1. Tái cấu trúc toàn bộ module `Loyalty-Engine` sang cấu trúc thiết kế sạch sẽ, dễ mở rộng (thêm rule mới không cần sửa code cũ).
2. Nâng độ bao phủ kiểm thử lên trên **90%**.
3. Đảm bảo luồng tính điểm hoạt động liên tục 24/7, quá trình chuyển giao code mới thay code cũ phải **an toàn tuyệt đối 100%**.

### 3. Action (Hành động)
Tôi đã lập kế hoạch và dẫn dắt team thực hiện tái cấu trúc an toàn theo 4 bước bài bản:

* **Bước 1: Thiết lập Lưới bảo hiểm bằng Characterization Tests (Golden Master)**
  Vì code cũ kết dính chặt chẽ, tôi không thể viết Unit Test riêng lẻ. Để tự vệ, tôi đã viết bộ **Characterization Tests (Kiểm thử đặc tả hành vi)**:
  - Tôi xuất **10.000 bộ dữ liệu giao dịch thực tế** của người dùng từ Database Production và đưa vào môi trường Staging.
  - Chạy code cũ với 10.000 bộ dữ liệu này và xuất kết quả đầu ra (Số điểm tích lũy, Hạng thành viên mới) ra các file JSON Snapshot (Golden Master).
  - Bất cứ khi nào tôi thay đổi cấu trúc code, tôi sẽ chạy lại bộ test này để so sánh tự động kết quả đầu ra với file Snapshot. Nếu lệch dù chỉ 1 ký tự, nghĩa là tôi đã làm sai hành vi hệ thống.

* **Bước 2: Áp dụng kỹ thuật Branch by Abstraction**
  Tôi không tạo nhánh Git dài hạn để sửa code nhằm tránh xung đột code kinh điển (Merge Hell). Thay vào đó, tôi tạo ra ranh giới trừu tượng ngay trên nhánh chính (`main`):
  1. Tạo interface trừu tượng mới bảo vệ Client:
     ```java
     public interface LoyaltyEvaluator {
         LoyaltyResult evaluate(User user, Order order);
     }
     ```
  2. Ép class cũ kế thừa Interface này và đổi tên thành `LegacyLoyaltyEvaluator`.
  3. Cấu hình để Client gọi thông qua Interface `LoyaltyEvaluator`, giữ nguyên logic hoạt động cũ an toàn.

* **Bước 3: Tách nhỏ cấu trúc bằng Strategy & Factory Pattern**
  Tôi viết lớp xử lý mới `ModernLoyaltyEvaluator` kế thừa `LoyaltyEvaluator`. Tại đây, tôi đập tan khối 4.500 dòng code if-else cũ bằng cách áp dụng **Strategy Pattern**:
  - Mỗi quy tắc tính điểm (như điểm sinh nhật, điểm Flash sale, điểm hạng VIP) được tách thành một lớp quy tắc độc lập implements interface `LoyaltyRule`:
    ```java
    public interface LoyaltyRule {
        boolean isApplicable(User user, Order order);
        BigDecimal calculatePoints(User user, Order order);
    }
    ```
  - Ví dụ quy tắc tính điểm sinh nhật siêu sạch sẽ, độc lập, có thể viết Unit Test bao phủ 100%:
    ```java
    @Component
    public class BirthdayLoyaltyRule implements LoyaltyRule {
        @Override
        public boolean isApplicable(User user, Order order) {
            return user.getBirthday().getMonth() == LocalDate.now().getMonth();
        }

        @Override
        public BigDecimal calculatePoints(User user, Order order) {
            return order.getAmount().multiply(new BigDecimal("0.10")); // Nhân đôi điểm sinh nhật
        }
    }
    ```
  - Lớp `ModernLoyaltyEvaluator` mới chỉ đóng vai trò là một điều phối viên (Engine) quét qua danh sách các Rule được Spring tự động inject vào:
    ```java
    @Primary
    @Service
    public class ModernLoyaltyEvaluator implements LoyaltyEvaluator {
        private final List<LoyaltyRule> rules;

        public ModernLoyaltyEvaluator(List<LoyaltyRule> rules) {
            this.rules = rules;
        }

        @Override
        public LoyaltyResult evaluate(User user, Order order) {
            BigDecimal totalPoints = rules.stream()
                .filter(rule -> rule.isApplicable(user, order))
                .map(rule -> rule.calculatePoints(user, order))
                .reduce(BigDecimal.ZERO, BigDecimal::add);
            return new LoyaltyResult(totalPoints);
        }
    }
    ```

* **Bước 4: Rollout an toàn bằng Shadow Execution & Feature Flag**
  Tôi cấu hình điều phối giao dịch sử dụng **Feature Flag** để thực hiện chuyển giao từng bước một cách an toàn tuyệt đối trên Production:
  1. *Giai đoạn 1 (Shadow Run - 1 tuần)*: Chạy cả hai luồng xử lý cũ và mới song song cho mọi giao dịch. Lấy kết quả của luồng cũ trả về cho khách hàng. Đồng thời, so sánh kết quả luồng mới với luồng cũ, nếu phát hiện sai lệch (Mismatch) thì bắn cảnh báo về Sentry để điều tra.
  2. *Giai đoạn 2 (Canary Rollout)*: Khi tỷ lệ sai lệch luồng mới về bằng **0%**, tiến hành gạt Feature Flag chuyển hướng **10% -> 50% -> 100%** người dùng sang sử dụng kết quả tính điểm của luồng mới.
  3. *Giai đoạn 3 (Cleanup)*: Sau 2 tuần chạy luồng mới ổn định hoàn hảo, tiến hành xóa bỏ hoàn toàn file code cũ `LegacyLoyaltyEvaluator` dài 4.500 dòng kia khỏi hệ thống.

### 4. Result (Kết quả)
* **Thời gian bàn giao**: Thời gian phát triển một chương trình khuyến mãi/tích điểm mới giảm ngoạn mục từ **7 ngày xuống chỉ còn đúng 2 giờ** (chỉ cần tạo một class Rule mới kế thừa `LoyaltyRule` mà hoàn toàn không ảnh hưởng tới code cũ).
* **Chất lượng kiểm thử**: Nâng Test Coverage của toàn bộ module từ **0% lên mức 94%**.
* **Độ tin cậy**: Quá trình chuyển dịch diễn ra mượt mà dưới lượng tải thực tế, **không xảy ra bất kỳ một sự cố hay sai lệch dữ liệu nào** trên Production.

## 💡 Nguyên tắc Senior & Bài học đắt giá

1. **Tuân thủ quy tắc Open/Closed (SOLID)**: Một hệ thống thiết kế tốt phải "Mở cho việc mở rộng, đóng cho việc sửa đổi". Kiến trúc Strategy Pattern giúp chúng ta thêm tính năng mới bằng cách "Viết thêm file code mới" thay vì "Chọc sửa vào file code cũ", loại bỏ 100% nguy cơ phá hỏng các tính năng cũ đang chạy tốt.
2. **Chiến lược "Xóa code cũ"**: Senior Engineer không bao giờ giữ lại code cũ không dùng đến dưới dạng comment hay class thừa. Khi code mới đã chạy ổn định 100%, việc xóa code cũ là bắt buộc để giữ cho dự án luôn sạch sẽ, tránh gây bối rối cho những kỹ sư vào sau.
3. **Kiên nhẫn và Kỷ luật**: Tái cấu trúc là một nghệ thuật đòi hỏi sự tỉ mỉ. Việc vội vã bỏ qua bước viết Characterization Tests hoặc không chạy Shadow Run trên Production chính là nguyên nhân hàng đầu biến các dự án refactor thành các thảm họa kỹ thuật.

## 📊 So sánh phương án quyết định (Trade-offs)

| Chiến lược thay thế | Điểm mạnh (Pros) | Điểm yếu (Cons) | Use Case Phù hợp |
| :--- | :--- | :--- | :--- |
| **Branch by Abstraction (Tái cấu trúc từng bước)** | **Rủi ro cực thấp**. Tích hợp code liên tục trên `main`, tránh xung đột merge code. Dễ dàng rollback qua Feature Flag trong 1 giây. | Đòi hỏi tính kiên trì, thời gian hoàn thành lâu hơn vì phải duy trì cả 2 luồng code chạy song song. | **Hệ thống lõi cốt yếu đang chạy**, dữ liệu nhạy cảm (thanh toán, tài khoản, điểm thưởng). |
| **Big Bang Rewrite (Viết lại hoàn toàn mới)** | Dev rất thích vì được tự do sáng tạo công nghệ mới từ đầu mà không cần đọc hiểu đống code cũ nát. | **Rủi ro cực kỳ cao**. Thường xuyên trễ deadline. Rất dễ thiếu sót các logic ẩn (Edge Cases) tích lũy nhiều năm của hệ thống cũ. | Hệ thống cũ quá nát không thể cứu vãn, nghiệp vụ đã thay đổi hoàn toàn, hoặc thay đổi toàn bộ ngôn ngữ lập trình. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Trong giai đoạn chạy song song (Shadow Run) của chiến dịch refactor trên, nếu phát hiện luồng mới tính toán lệch điểm số so với luồng cũ thì bạn làm thế nào để debug tìm lỗi sai lệch nhanh nhất dưới áp lực tải thực tế?
* **Trả lời**:
  * Để gỡ lỗi sai lệch nhanh nhất trong quá trình Shadow Run, tôi thiết kế cơ chế **Mismatch Logging & Tracing** chuyên nghiệp:
    1. **Log chi tiết cấu trúc so sánh (Structured Diff Logging)**: Khi phát hiện sai lệch, hệ thống sẽ ném ra một dòng log dạng JSON chứa đầy đủ: `CorrelationID, LegacyPoints, ModernPoints, DiffDetails`. Trong phần `DiffDetails`, tôi log rõ danh sách các quy tắc (Rules) đã áp dụng ở luồng mới và chuỗi logic lồng nhau tương ứng ở luồng cũ.
    2. **Tận dụng distributed tracing**: Tôi đính kèm trạng thái `mismatch=true` vào thẻ (tags) của **Jaeger/OpenTelemetry Trace**. Nhờ vậy, tôi có thể lên giao diện APM, gõ tìm kiếm đúng các trace có tag `mismatch=true` để xem toàn bộ sơ đồ timeline và các biến số đầu vào của riêng giao dịch lỗi đó.
    3. **Tái lập nhanh ngoại tuyến**: Tôi viết một script tự động xuất bộ dữ liệu đầu vào của giao dịch bị lệch đó về máy local để chạy kiểm thử đơn lẻ (Unit Test tái lập), từ đó tìm ra chính xác lỗi nằm ở lớp Strategy nào của luồng mới để chỉnh sửa nhanh chóng.

### 2. Nếu trong quá trình bạn đang refactor, các sếp kinh doanh liên tục yêu cầu phải thêm các tính năng tích điểm mới gấp vào hệ thống để chạy campaign, bạn xử lý thế nào để không bị xung đột code (code conflict) và trễ tiến độ?
* **Trả lời**:
  * Đây là bài toán quản lý tiến độ và phối hợp kỹ thuật kinh điển:
    1. **Khuyên nghị tận dụng Interface mới**: Tôi sẽ thuyết phục các sếp và team phát triển rằng: Để phục vụ campaign mới nhanh nhất, chúng ta nên triển khai tính năng đó dưới dạng một lớp Rule mới implement interface `LoyaltyRule` của luồng mới đang xây dựng.
    2. **Viết "bọc ngoài" (Adapter Pattern) cho code cũ**: Nếu tính năng mới bắt buộc phải chạy ngay lập tức trên luồng cũ khi luồng mới chưa hoàn thành, tôi sẽ viết một lớp Adapter nhỏ bọc tính năng mới đó lại, gọi nó từ code cũ, đồng thời đăng ký nó vào danh sách Rule của luồng mới. Điều này đảm bảo tính năng mới chỉ cần code đúng 1 lần và tự động tương thích với cả hai luồng xử lý cũ và mới, giảm thiểu tối đa rủi ro xung đột code và trễ tiến độ.
