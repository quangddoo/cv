# Làm sao thiết kế audit log để điều tra sai dữ liệu?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Nhật ký kiểm toán (Audit Log) là chiếc "hộp đen" tối thượng ghi nhận toàn bộ lịch sử biến động trạng thái của dữ liệu nhạy cảm (Ai thay đổi, Thay đổi lúc nào, Giá trị trước và sau là gì, Thay đổi từ thiết bị/IP nào). Hệ thống Audit Log chuẩn Senior phải đảm bảo tính **Bất biến (Immutable - Không thể bị sửa/xóa bởi bất kỳ ai)** và **Cấu trúc hóa (Structured - Lưu vết dạng JSON Diff trước/sau)** để dễ dàng truy vết tự động.
* **Thảm họa thực chiến được giải quyết**:
  1. **Gian lận nội bộ không dấu vết**: Một nhân viên quản trị (Admin) cấu kết với người ngoài, dùng Tool quản trị nội bộ chỉnh sửa số dư tài khoản của một ví điện tử lên 100 triệu đồng. Nếu không có Audit Log bất biến ghi nhận chính xác ID của Admin và dấu vết IP thiết bị, công ty sẽ mất trắng số tiền mà không thể chứng minh ai là thủ phạm trước pháp luật.
  2. **Lỗi ngầm trên Production (Silent Data Corruption)**: Đơn hàng bỗng dưng bị đổi trạng thái từ `PAID` sang `CANCELLED`. Kỹ sư lục lại log ứng dụng thông thường nhưng đã bị xoay vòng (Rotated) mất. Không có lịch sử biến động, đội kỹ thuật mất 3 ngày cãi nhau với bên thứ ba mà không tìm ra lỗi do luồng code nào kích hoạt.
* **Quyết định Senior**:
  1. **Tách biệt đặc quyền (Segregation of Duties)**: Service chạy ứng dụng chính chỉ có quyền chèn dữ liệu (`INSERT`), tuyệt đối không được cấp quyền cập nhật (`UPDATE`) hoặc xóa (`DELETE`) trên bảng Audit Log.
  2. **Lưu vết dạng Delta (JSON Diff)**: Không lưu toàn bộ Object cồng kềnh. Chỉ lưu trữ các trường thực sự thay đổi (Ví dụ: `status: PENDING -> PAID`) giúp tiết kiệm 80% dung lượng đĩa cứng và hỗ trợ đối soát tự động siêu tốc.
  3. **Tận dụng CDC (Change Data Capture) hoặc Database Triggers**: Để tránh việc dev vô tình viết code SQL bypass qua tầng Backend làm mất vết Audit, Senior sử dụng các công cụ CDC (như Debezium quét WAL/Binlog của DB) để tự động xuất log kiểm toán một cách độc lập và khách quan 100%.

## 🔍 Chi tiết bản chất thực chiến: Thiết kế Kiến trúc Audit Log Bất biến

Mọi bản ghi Audit Log chuẩn hóa phải trả lời trọn vẹn câu hỏi **5W1H**:
* **Who** (`actor_id`, `actor_type` - USER, ADMIN, SYSTEM): Ai thực hiện hành động?
* **When** (`timestamp`): Thực hiện chính xác vào mili-giây nào (Múi giờ UTC)?
* **Where** (`client_ip`, `user_agent`, `service_name`): Thực hiện từ thiết bị nào, máy chủ nào?
* **What** (`entity_name`, `entity_id`, `action` - CREATE, UPDATE, DELETE): Tác động vào thực thể nào?
* **Which** (`state_diff` - JSON format): Thay đổi giá trị cụ thể của những cột nào?
* **Why** (`correlation_id`, `reason`): Thay đổi trong phạm vi request nào (mã Trace ID để khớp với log hệ thống)?

## 🎨 Sơ đồ trực quan: Kiến trúc Audit Log bất biến sử dụng CDC (Change Data Capture)

Kiến trúc tối ưu, tách biệt hoàn toàn tải ghi và đảm bảo tính khách quan tuyệt đối của log:

```
 [Application API] ───► [Production DB]
                              │ (Ghi nhận thay đổi dữ liệu)
                              ▼
                         [WAL / Binlog]
                              │
                              ▼
                      [Debezium Connector] (CDC quét log vật lý)
                              │
                              ▼
                        [Kafka Topic] (event: order_changed)
                              │
                              ▼
                     [Audit Log Service]
                              │
                              ▼
             ┌────────────────┴────────────────┐
             ▼ (Lưu nhanh)                     ▼ (Lưu trữ vĩnh viễn)
 ┌──────────────────────┐          ┌──────────────────────┐
 │ Audit Database       │          │ Object Storage (S3)  │
 │ (Chỉ quyền INSERT)   │          │ (Bật WORM / Lock)    │
 └──────────────────────┘          └──────────────────────┘
```

## 💻 Code thực chiến: Java Hibernate Listener sinh JSON Diff tự động

Dưới đây là cách triển khai Audit Log tự động ở tầng Ứng dụng bằng cách sử dụng Hibernate `@EntityListeners` kết hợp với thư viện tính toán JSON Delta (Javers hoặc Jackson).

### 1. File DDL Database thiết kế bảng Audit Log an toàn
```sql
CREATE TABLE audit_logs (
    id BIGSERIAL PRIMARY KEY,
    entity_name VARCHAR(100) NOT NULL,
    entity_id VARCHAR(100) NOT NULL,
    action_type VARCHAR(20) NOT NULL, -- INSERT, UPDATE, DELETE
    state_diff JSONB NOT NULL, -- Định dạng JSONB của Postgres để truy vấn cực nhanh
    actor_id VARCHAR(50) NOT NULL,
    correlation_id VARCHAR(100) NOT NULL,
    client_ip VARCHAR(45) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- TẠO POLICY KHÓA QUYỀN: Cấm tuyệt đối UPDATE và DELETE trên bảng này
REVOKE UPDATE, DELETE ON audit_logs FROM web_application_user;
```

### 2. Code Java Spring Boot tạo Entity Listener bắt sự thay đổi và sinh Diff

```java
package com.example.audit;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.flipkart.zjsonpatch.JsonDiff;
import lombok.extern.slf4j.Slf4j;
import org.hibernate.event.spi.PostUpdateEvent;
import org.hibernate.event.spi.PostUpdateEventListener;
import org.hibernate.persister.entity.EntityPersister;
import org.springframework.stereotype.Component;

import java.util.HashMap;
import java.util.Map;

@Component
@Slf4j
public class EntityAuditEventListener implements PostUpdateEventListener {

    private final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public void onPostUpdate(PostUpdateEvent event) {
        try {
            Object entity = event.getEntity();
            
            // Chỉ áp dụng audit log cho các Entity nhạy cảm có annotation @Auditable
            if (!entity.getClass().isAnnotationPresent(Auditable.class)) {
                return;
            }

            String entityName = event.getPersister().getEntityName();
            String entityId = event.getId().toString();

            // Lấy danh sách các trường thay đổi
            Map<String, Object> oldStateMap = new HashMap<>();
            Map<String, Object> newStateMap = new HashMap<>();

            String[] propertyNames = event.getPersister().getPropertyNames();
            Object[] oldState = event.getOldState();
            Object[] newState = event.getState();
            int[] dirtyProperties = event.getDirtyProperties();

            for (int index : dirtyProperties) {
                String propertyName = propertyNames[index];
                oldStateMap.put(propertyName, oldState[index]);
                newStateMap.put(propertyName, newState[index]);
            }

            // Sinh JSON chứa thông tin cũ và mới của các trường bị thay đổi
            Map<String, Object> diffMap = new HashMap<>();
            diffMap.put("before", oldStateMap);
            diffMap.put("after", newStateMap);
            
            String jsonDiff = objectMapper.writeValueAsString(diffMap);

            // Ghi nhận thông tin ngữ cảnh người dùng thực hiện (ThreadLocal context)
            AuditContext context = AuditContextHolder.getContext();

            // Thực thi INSERT bản ghi Audit Log bất đồng bộ (tránh làm chậm transaction chính)
            saveAuditLogAsync(entityName, entityId, "UPDATE", jsonDiff, context);

        } catch (Exception e) {
            // Không được để lỗi ghi Audit Log làm crash luồng nghiệp vụ chính của người dùng
            log.error("Failed to generate audit log diff", e);
        }
    }

    private void saveAuditLogAsync(String entity, String id, String action, String diff, AuditContext ctx) {
        // Thực thi gửi sang Kafka hoặc dùng Threadpool chạy câu INSERT trực tiếp
        log.info("AUDIT LOG -> Entity: {}, ID: {}, Action: {}, Diff: {}, Actor: {}, IP: {}, TraceID: {}",
                entity, id, action, diff, ctx.getUserId(), ctx.getClientIp(), ctx.getCorrelationId());
    }

    @Override
    public boolean requiresPostCommitHanding(EntityPersister persister) {
        return true; 
    }
}
```

## 📊 Bảng so sánh 4 Kỹ thuật thu thập Audit Log

| Tiêu chí | Phương án 1: Tầng ứng dụng (Hibernate/AOP) | Phương án 2: Database Triggers | Phương án 3: CDC (Change Data Capture - Khuyên dùng) |
| :--- | :--- | :--- | :--- |
| **Độ tin cậy** | Trung bình (Dễ bị lọt vết nếu dev viết SQL native trực tiếp bỏ qua Hibernate). | **Tuyệt đối 100%** (Quét mọi thay đổi ở mức DB). | **Tuyệt đối 100%** (Quét log ghi vật lý của DB). |
| **Ảnh hưởng hiệu năng** | Ảnh hưởng nhẹ (Tốn tài nguyên tính toán JSON Diff ở CPU của App). | **Cực kỳ tệ** (Làm tăng đáng kể transaction time của DB do chạy trigger đồng bộ). | **Tối ưu nhất** (Hoàn toàn không ảnh hưởng DB do đọc file log bất đồng bộ). |
| **Khả năng lưu vết Metadata (User ID, IP)** | Dễ dàng (Đọc trực tiếp từ ThreadLocal Session). | Khó (DB không có thông tin về Web Request nếu không truyền qua session variable). | Trung bình (Phải kết hợp so khớp Trace ID giữa log app và log CDC). |
| **Chi phí hạ tầng** | Miễn phí | Thấp | Cao (Cần hạ tầng Kafka, Kafka Connect, Debezium). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Lưu vết PII trái luật bảo vệ dữ liệu (GDPR / ND CP 13)"
* **Vấn đề cực kỳ nghiêm trọng**: Audit Log ghi lại toàn bộ thay đổi dữ liệu của người dùng bao gồm cả Mật khẩu, Số thẻ tín dụng, Số điện thoại. Việc lưu trữ trực tiếp các dữ liệu này dưới dạng bản rõ (Plaintext JSON) trong bảng Audit Log sẽ vi phạm nghiêm trọng luật bảo vệ thông tin cá nhân và chứng chỉ bảo mật thanh toán **PCI-DSS**.
* **Giải pháp khắc phục**:
  1. Cấu hình Filter lọc bỏ hoàn toàn các trường nhạy cảm (`password`, `credit_card_cvv`) khỏi hàm sinh JSON Diff.
  2. Áp dụng kỹ thuật **Mã hóa một chiều (Masking / Hashing)** đối với các thông tin định danh nhạy cảm trước khi lưu xuống.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Làm sao bạn đảm bảo tính 'Bất biến tuyệt đối' (Immutability) của Audit Log? Nếu một hacker chiếm được quyền Root của Database hoặc AWS Account của công ty, họ hoàn toàn có thể chạy lệnh `DROP TABLE audit_logs` để xóa dấu vết tấn công."**
* **Trả lời**:
  * Để đạt được sự bảo vệ ở mức tối đa chống lại cả quyền Root/Admin, Senior sẽ áp dụng giải pháp **WORM (Write Once, Read Many) Storage**:
    1. Thiết lập Job tự động đẩy nén file Audit Log hàng giờ lên **AWS S3** hoặc **Google Cloud Storage**.
    2. Kích hoạt tính năng **S3 Object Lock** ở chế độ **Compliance Mode**. Chế độ này sử dụng phần cứng để khóa cứng file dữ liệu trên đĩa đệm. Một khi đã lock, **ngay cả tài khoản Root của AWS cũng không thể xóa hoặc chỉnh sửa file đó** cho đến khi hết thời hạn lưu trữ cam kết (ví dụ: 5 năm).
    3. Mọi hành vi cố gắng chỉnh sửa chính sách lock đều bị ghi nhận bởi CloudTrail và đẩy về hệ thống giám sát SIEM độc lập.
