# Retry storm là gì?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: **Retry Storm (Cơn bão thử lại)** là hiện tượng tự hủy hoại hệ thống (Self-inflicted DDoS) xảy ra khi một dịch vụ downstream bị quá tải hoặc phản hồi chậm, khiến hàng loạt service gọi nó đồng loạt gửi lại các request lỗi (retry) cùng lúc. Hành động này nhân cấp tải trọng lên gấp nhiều lần, biến một sự cố nghẽn mạng nhỏ thành thảm họa sập hoàn toàn hệ thống phân tán.
* **Thảm họa thực chiến được giải quyết**:
  1. **Dập tắt cơ hội tự chữa lành (Prevention of Recovery)**: Khi downstream service đang bị quá tải CPU 100%, thay vì được "thở" để dọn dẹp hàng chờ hoặc khởi động lại, nó phải chịu thêm đợt sóng request khổng lồ tăng gấp 3x - 5x từ các lần retry đồng loạt. Downstream service sẽ bị đè bẹp vĩnh viễn và không bao giờ tự phục hồi được.
  2. **Tràn bộ đệm API Gateway**: Cơn bão request thử lại dội ngược lên API Gateway, làm tràn hàng đợi kết nối (connection queue) và sập luôn cả các tính năng không liên quan.
* **Quyết định Senior**:
  1. **Áp dụng Exponential Backoff với Jitter**: Không bao giờ thử lại ngay lập tức hoặc thử lại sau khoảng thời gian cố định. Bắt buộc tăng thời gian chờ giữa các lần thử theo hàm mũ (Exponential) kết hợp cộng thêm độ trễ ngẫu nhiên (Jitter) để phân tán lưu lượng.
  2. **Cấu hình Retry Limit cực thấp**: Giới hạn số lần thử lại tối đa là 2 hoặc 3 lần. Chỉ thực hiện retry đối với các lỗi mạng tạm thời hoặc lỗi HTTP mang tính tạm thời (HTTP 429, 503, 504), tuyệt đối không retry lỗi logic (400, 401, 403, 404).
  3. **Tích hợp Circuit Breaker**: Bọc cơ chế Retry bên trong Circuit Breaker. Khi tỷ lệ lỗi vượt ngưỡng, Circuit Breaker ngắt mạch lập tức, chặn đứng toàn bộ các đợt retry vô ích.
  4. **Áp dụng Retry Budget (Ngân sách Retry)**: Chỉ cho phép tối đa ví dụ 10% tổng lưu lượng request của service được phép sử dụng quyền retry. Nếu vượt quá, lập tức báo lỗi Fail-Fast.

## 🔍 Chi tiết bản chất thực chiến: Cơ chế lan truyền của Cơn bão Retry

Quy trình hình thành một cơn bão Retry Storm diễn ra theo chuỗi phản ứng dây chuyền như sau:

```
[Downstream chậm 1s] ──> [1000 Clients cùng lúc gặp Timeout] ──> [Đồng loạt gửi 1000 Request thử lại]
                                                                                │
                                                                                ▼
[Downstream quá tải nặng hơn] <── [Tải trọng tăng 2x lập tức] <── [Hệ thống thử lại ngay lập tức]
```

### 1. Kỹ thuật toán học đằng sau Exponential Backoff và Jitter
Để dập tắt cơn bão Retry, Senior Engineer sử dụng thuật toán tính toán thời gian chờ dựa trên công thức của AWS Architecture:

* **Exponential Backoff**: Khoảng thời gian chờ tăng dần theo cấp số nhân để kéo giãn các đợt tấn công.
  $$\text{Interval} = \text{base\_delay} \times 2^{\text{attempt}}$$
  *Ví dụ với base = 100ms: Lần 1 chờ 100ms, lần 2 chờ 200ms, lần 3 chờ 400ms...*
* **Jitter (Độ trễ ngẫu nhiên)**: Nếu chỉ có Exponential Backoff, các client gặp lỗi cùng thời điểm vẫn sẽ đồng loạt retry tại cùng một mili-giây ở các bước tiếp theo (hiện tượng **Synchronization**). Jitter giải quyết triệt để điều này bằng cách phá vỡ tính đồng bộ:
  $$\text{Sleep Time} = \text{Random}(0, \text{Interval})$$
  *Kỹ thuật này gọi là **Full Jitter**, giúp dàn phẳng (flatten) hoàn toàn đỉnh tải trọng của các request gọi vào hệ thống.*

## 💻 Code thực chiến: Thuật toán Full Jitter Backoff tự triển khai bằng Java

Dưới đây là lớp Helper thiết kế chuẩn mẫu hình toán học **Full Jitter** được sử dụng phổ biến trong các hệ thống High Throughput để tính toán thời gian nghỉ ngơi trước khi gọi lại API.

```java
import lombok.extern.slf4j.Slf4j;
import java.util.Random;
import java.util.concurrent.TimeUnit;

@Slf4j
public class JitterRetryExecutor {

    private static final int MAX_RETRIES = 3;
    private static final long BASE_DELAY_MS = 100; // 100ms
    private static final long MAX_DELAY_MS = 3000; // Tối đa chờ 3 giây
    private static final Random random = new Random();

    public interface ApiCallable<T> {
        T call() throws Exception;
    }

    /**
     * ✅ Thực thi tác vụ gọi API an toàn với cơ chế Full Jitter Retry.
     */
    public static <T> T executeWithRetry(ApiCallable<T> callable, String apiName) throws Exception {
        int attempt = 0;
        
        while (true) {
            try {
                attempt++;
                return callable.call(); // Thực thi lệnh gọi thực tế
            } catch (Exception e) {
                // Chỉ retry nếu chưa vượt quá số lần cấu hình và lỗi là lỗi mạng tạm thời
                if (attempt >= MAX_RETRIES || !isTransientError(e)) {
                    log.error("🚨 Thất bại hoàn toàn sau {} lần thử gọi API [{}]. Ném lỗi!", attempt, apiName);
                    throw e;
                }

                // ✅ THUẬT TOÁN FULL JITTER: Tính toán thời gian ngủ ngẫu nhiên cực hạn
                long calculatedBackoff = BASE_DELAY_MS * (long) Math.pow(2, attempt);
                long cappedBackoff = Math.min(calculatedBackoff, MAX_DELAY_MS);
                long jitterSleepTime = random.nextLong(cappedBackoff); // Trả về giá trị ngẫu nhiên từ [0, cappedBackoff)

                log.warn("⚠️ API [{}] lỗi lần {}. Gặp lỗi: {}. Đang ngủ đông {} ms trước khi thử lại...", 
                        apiName, attempt, e.getMessage(), jitterSleepTime);

                try {
                    TimeUnit.MILLISECONDS.sleep(jitterSleepTime);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("Tiến trình retry bị ngắt quãng!", ie);
                }
            }
        }
    }

    /**
     * ✅ Chỉ retry đối với các lỗi tạm thời (Transient Errors)
     */
    private static boolean isTransientError(Exception e) {
        String msg = e.getMessage().toLowerCase();
        // Lỗi timeout kết nối, lỗi socket, lỗi 503, 504 là các lỗi tạm thời nên retry
        return msg.contains("timeout") || 
               msg.contains("connection reset") || 
               msg.contains("503") || 
               msg.contains("504") || 
               msg.contains("429");
    }
}
```

## 📊 Bảng so sánh 4 chiến lược Thử Lại (Retry Strategy)

| Chiến lược | Thuật toán tính delay | Nguy cơ gây Retry Storm | Khả năng tự chữa lành của hệ thống | Phù hợp với |
| :--- | :--- | :--- | :--- | :--- |
| **Immediate Retry** | `delay = 0ms` | **Cực kỳ nguy hiểm** | Không thể (Làm sập hệ thống ngay lập tức) | Tác vụ nội bộ cực nhẹ, không qua mạng. |
| **Fixed Interval** | `delay = 1000ms` (Cố định) | **Rất cao** | Kém (Tạo các đỉnh tải trọng theo chu kỳ) | Hệ thống quản trị nội bộ ít người dùng. |
| **Exponential Backoff** | `delay = base * 2^attempt` | **Trung bình** | Khá (Kéo giãn được tải nhưng vẫn bị đồng bộ hóa) | Phù hợp cơ bản nếu số lượng client nhỏ. |
| **Exponential + Jitter** | `delay = Random(0, base * 2^attempt)` | **Cực thấp** (An toàn nhất) | **Tuyệt vời** (Dàn phẳng đỉnh tải hoàn hảo) | Mọi cuộc gọi qua mạng trong hệ thống phân tán. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Nhân cấp số lần Retry ở kiến trúc đa tầng (Retry Amplification)"
* **Vấn đề**: Trong một chuỗi gọi microservices: **Client -> Service A -> Service B -> Service C**.
  * Khi Service C sập, Service B được cấu hình retry Service C `3 lần`.
  * Service A không gọi được Service B cũng tự động retry Service B `3 lần`.
  * Client không nhận được kết quả từ Service A cũng retry `3 lần`.
  * **Hậu quả**: Tổng số request thực tế đổ dồn xuống Service C bị nhân cấp thành: $3 \times 3 \times 3 = 27$ lần! Đây là sự khuếch đại lỗi kinh hoàng ở hệ thống phân tán.
* **Giải pháp khắc phục**: Tuyệt đối không cấu hình retry ở mọi tầng. Chỉ nên thực hiện **Retry ở tầng sát client nhất (Edge/API Gateway)** hoặc **chỉ Retry duy nhất 1 lần ở mỗi node trung gian**. Sử dụng cờ header `X-Is-Retried` để đánh dấu request này đã được retry trước đó, cấm các service phía sau tiếp tục retry thêm.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Làm sao để đảm bảo an toàn khi retry một request có thể KHÔNG idempotent (ví dụ: API thanh toán)?**
  * *Trả lời*:
    * **Tuyệt đối cấm retry các API không có cơ chế Idempotency!** Nếu không, bạn sẽ gặp thảm họa trừ tiền người dùng 2 lần.
    * Giải pháp bắt buộc:
      1. Phía Client/API Gateway trước khi gọi API thanh toán phải sinh ra một **Idempotency Key (UUID)** duy nhất cho giao dịch đó và truyền vào HTTP Header `X-Idempotency-Key`.
      2. Downstream Service trước khi xử lý phải lưu key này vào Redis/Database với trạng thái `PENDING/PROCESSING`.
      3. Khi có request retry gửi tới mang cùng `X-Idempotency-Key`, downstream service phát hiện ra key đã tồn tại và sẽ:
         - Đợi giao dịch đầu tiên xử lý xong và trả về kết quả giống hệt.
         - Hoặc từ chối xử lý, báo lỗi giao dịch đang được thực hiện.
