# Compensation action thất bại thì xử lý thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Giao dịch bù trừ (Compensating Transaction) là lá chắn cuối cùng để khôi phục tính nhất quán phân tán. Tuy nhiên, khi chính Giao dịch bù bị thất bại (do lỗi mạng, sập nguồn, DB sập hoặc đối tác bên thứ ba như ngân hàng bị sập), hệ thống sẽ rơi vào trạng thái nguy kịch nhất: **Bất nhất dữ liệu thực thể (Data Inconsistency)**. Một Senior không bao giờ được phép phó mặc cho may rủi mà phải thiết lập quy trình **Chịu lỗi 3 Lớp (3-Tier Failure Mitigation Framework)** để tự động hóa tối đa và can thiệp thủ công chính xác.
* **Thảm họa thực chiến được giải quyết**:
  1. **Khách hàng bị trừ tiền oan (Financial Loss)**: Hệ thống đặt vé sập ở bước cuối, Saga phát lệnh bù hoàn tiền. Cổng thanh toán bị sập nên API hoàn tiền trả về lỗi 500. Nếu ứng dụng bỏ qua âm thầm, tiền khách hàng mất vĩnh viễn nhưng không có vé, trực tiếp kéo tụt uy tín thương hiệu và đối mặt với rủi ro pháp lý.
  2. **Tràn dung lượng lưu trữ do Retry vô ích**: Lỗ hổng logic nghiệp vụ (ví dụ: truyền sai định dạng tài khoản ngân hàng khi hoàn tiền) dẫn đến lỗi HTTP 400. Nếu hệ thống retry vô hạn sẽ làm nghẽn toàn bộ hàng đợi xử lý.
* **Quyết định Senior**:
  1. **Tự động Retry có giới hạn với Exponential Backoff**: Cố gắng gọi lại giao dịch bù liên tục trong vài phút đầu với độ giãn thời gian để tự vượt qua lỗi mạng tạm thời.
  2. **Cô lập lỗi bền bỉ (DLQ & Failed Compensations Table)**: Lưu toàn bộ ngữ cảnh (context payload) của giao dịch bù bị lỗi vào một bảng DB chuyên biệt hoặc Dead Letter Queue (DLQ).
  3. **Hú còi khẩn cấp (Real-time Alerting)**: Bắn cảnh báo mức độ cao (Critical Alert) lên Slack/PagerDuty để đội ngũ trực vận hành (On-call) can thiệp thủ công ngay lập tức.
  4. **Triển khai Công cụ Đối soát tự động (Reconciliation Engine)**: Xây dựng background job đối soát dữ liệu chéo hàng đêm giữa các service và đối tác bên ngoài để tự động sửa chữa số dư/trạng thái lệch.

## 🔍 Chi tiết bản chất thực chiến: Quy trình Chịu lỗi 3 Lớp khi Giao dịch Bù thất bại

Kiến trúc chuẩn Enterprise xử lý thảm họa gãy giao dịch bù thông qua **Quy trình Chịu lỗi 3 Lớp** nghiêm ngặt dưới đây:

```
[Giao dịch Bù Thất Bại 💥]
           │
           ▼
[LỚP 1: Tự động phục hồi] ───> Sử dụng Retry với Exponential Backoff để vượt qua lỗi mạng tạm thời
           │ (Vẫn lỗi sau 5 lần)
           ▼
[LỚP 2: Cô lập & Cảnh báo] ──> Lưu vào bảng 'failed_compensations' & Hú còi báo động Slack/PagerDuty
           │
           ▼
[LỚP 3: Đối soát & Hòa giải] ─> Đối soát chéo tự động (Reconciliation) hàng đêm để tự vá dữ liệu
```

### 1. Phân loại lỗi của Giao dịch bù để xử lý thông minh

Một Senior cần hiểu rõ bản chất lỗi để cấu hình hành động phản ứng phù hợp:

* **Lỗi tạm thời (Transient Error)**: Lỗi nghẽn mạng, cổng thanh toán timeout, database bị khóa bảng tạm thời.
  * *Cách xử lý*: **Cho phép tự động Retry** nhiều lần vì hệ thống có khả năng tự chữa lành khi mạng ổn định trở lại.
* **Lỗi vĩnh viễn (Permanent/Logical Error)**: Truyền sai số tài khoản hoàn tiền, tài khoản đối tác bị khóa, lỗi logic code nghiệp vụ ném ra ngoại lệ 400 Bad Request.
  * *Cách xử lý*: **Tuyệt đối CẤM retry tự động**. Việc gọi lại vô hạn một request sai logic chỉ làm tốn tài nguyên vô ích. Phải đẩy thẳng bản ghi lỗi này ra bảng cách ly và bắn Alert để kỹ sư vào sửa tay hoặc sửa code.

## 💻 Code thực chiến: Triển khai Lớp 2 & Lớp 3 - Quét lỗi và Cảnh báo Tự động

Dưới đây là cách triển khai background job quét bảng `failed_compensations`, tự động retry thông minh bằng **Exponential Backoff** và gửi cảnh báo khẩn cấp nếu thất bại hoàn toàn.

```java
import lombok.Getter;
import lombok.Setter;
import java.time.LocalDateTime;

@Getter
@Setter
public class FailedCompensation {
    private Long id;
    private String sagaId;
    private String serviceName;
    private String actionName;
    private String payload;
    private String errorReason;
    private int retryCount;
    private LocalDateTime nextRetryTime;
    private String status; // "PENDING_RETRY", "FAILED_CRITICAL", "RESOLVED"
}
```

```java
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;
import org.springframework.web.client.RestTemplate;

import java.time.LocalDateTime;
import java.util.List;

@Slf4j
@Component
@RequiredArgsConstructor
public class AutomatedReconciliationJob {

    private final FailedCompensationRepository repository;
    private final RestTemplate restTemplate;
    private final AlertService alertService;

    private static final int MAX_RETRY_LIMIT = 5;

    /**
     * ✅ Background Job tự động quét và hòa giải các giao dịch bù bị lỗi.
     * Chạy định kỳ mỗi 5 phút.
     */
    @Scheduled(fixedDelay = 300000) 
    public void retryFailedCompensations() {
        // Quét các bản ghi đang chờ xử lý và đã đến thời điểm retry tiếp theo
        List<FailedCompensation> failures = repository.findPendingCompensations(
                "PENDING_RETRY", LocalDateTime.now());

        if (failures.isEmpty()) return;

        log.info("🔎 Phát phát hiện {} giao dịch bù bị kẹt lỗi. Đang xử lý hòa giải...", failures.size());

        for (FailedCompensation failure : failures) {
            try {
                log.info("🔄 Thử lại hoàn tác cho Saga: {} (Lần {})", failure.getSagaId(), failure.getRetryCount() + 1);

                // 1. Thực hiện gọi lại API bù thực tế bằng REST client
                restTemplate.postForObject(failure.getActionName(), failure.getPayload(), String.class);

                // 2. Nếu thành công, cập nhật trạng thái đã giải quyết
                failure.setStatus("RESOLVED");
                repository.save(failure);
                log.info("✅ Giải quyết thành công giao dịch bù bị kẹt của Saga: {}", failure.getSagaId());

            } catch (Exception e) {
                // 3. Nếu tiếp tục thất bại, tăng bộ đếm và tính toán thời gian retry tiếp theo theo hàm mũ
                int nextAttempt = failure.getRetryCount() + 1;
                failure.setRetryCount(nextAttempt);
                failure.setErrorReason(e.getMessage());

                if (nextAttempt >= MAX_RETRY_LIMIT) {
                    // 🚨 THẢM HỌA: Vượt quá giới hạn retry tối đa
                    failure.setStatus("FAILED_CRITICAL");
                    repository.save(failure);

                    // Gửi thông báo khẩn cấp lên Slack/PagerDuty cho kỹ sư trực vận hành
                    alertService.triggerCriticalAlert(
                            failure.getSagaId(),
                            failure.getServiceName(),
                            "Giao dịch bù bị sập hoàn toàn sau 5 lần thử lại! Yêu cầu can thiệp thủ công gấp. Lỗi: " + e.getMessage()
                    );
                } else {
                    // Tính toán giãn cách: 2^attempt * 5 phút (ví dụ: 10 phút, 20 phút, 40 phút...)
                    long nextDelayMinutes = (long) Math.pow(2, nextAttempt) * 5;
                    failure.setNextRetryTime(LocalDateTime.now().plusMinutes(nextDelayMinutes));
                    repository.save(failure);
                    log.warn("⚠️ Tiếp tục lỗi khi bù Saga: {}. Sẽ thử lại sau {} phút.", failure.getSagaId(), nextDelayMinutes);
                }
            }
        }
    }
}
```

## 📊 Bảng so sánh các giải pháp xử lý khi Hoàn tác bị lỗi

| Tiêu chí | Bỏ qua âm thầm (Chống chỉ định) | Gọi điện nhờ Kỹ sư sửa tay lập tức | Triển khai Chịu lỗi 3 Lớp (Chuẩn Senior) |
| :--- | :--- | :--- | :--- |
| **Độ an toàn dữ liệu** | **Không có** (Mất tiền khách hàng, lệch sổ sách vĩnh viễn). | Cao (Được con người rà soát kỹ). | **Tuyệt đối** (Dữ liệu được lưu vết bền bỉ trong DB cách ly). |
| **Tác động lên nhân sự** | Rảnh rỗi tạm thời, sau đó đi giải trình sự cố. | Cực tệ (Kỹ sư bị dựng dậy lúc 3h sáng để sửa tay các lỗi mạng vớ vẩn). | **Tuyệt vời** (Hệ thống tự động hóa xử lý 99% lỗi mạng ngầm). |
| **MTTR (Thời gian sửa lỗi)** | Vô hạn. | Từ 30 phút - vài tiếng tùy tốc độ phản ứng của con người. | **Cực nhanh** (Tự động tự vá lỗi trong vài giây đến vài phút). |
| **Chi phí xây dựng** | Bằng 0. | Thấp. | Trung bình - Cao (Đòi hỏi thiết kế bảng DB phụ và viết background job đối soát). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Bão Retry đè bẹp hệ thống đối tác (Third-Party Throttling)"
* **Vấn đề**: Khi API hoàn tiền của đối tác thanh toán bị lỗi 500. Bạn cấu hình retry hoàn tiền liên tục. Đối tác phát hiện bạn đang spam request và kích hoạt cơ chế **Rate Limiting / IP Blocking**. Hệ thống của bạn bị khóa IP hoàn toàn, làm đóng băng toàn bộ các giao dịch thanh toán thông thường khác.
* **Giải pháp khắc phục**: Thiết lập trần thời gian chờ tối đa (`MAX_DELAY_MS`) cho cơ chế backoff và tôn trọng HTTP Header `Retry-After` trả về từ đối tác để tự động hoãn binh.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Làm sao để thiết kế File Đối Soát (Reconciliation File) để phát hiện chênh lệch tài chính giữa database nội bộ của ta và cổng thanh toán bên thứ ba (như Momo, VNPay) hàng ngày?**
  * *Trả lời*:
    * Đây là quy trình nghiệp vụ bắt buộc của mọi Fintech / E-commerce lớn:
      1. Hàng đêm (thường là 1h sáng), Cổng thanh toán sẽ kết xuất (export) một file đối soát chứa toàn bộ giao dịch thành công của họ trong ngày dưới dạng CSV/Excel và đẩy lên máy chủ SFTP bảo mật.
      2. Hệ thống của ta thiết lập một Scheduled Job tải file này về.
      3. Đọc tuần tự từng dòng của file đối soát và thực hiện so sánh chéo với Database giao dịch nội bộ:
         - **Trường hợp 1**: Giao dịch có ở DB nội bộ (`SUCCESS`) và có ở file đối soát -> Hợp lệ.
         - **Trường hợp 2**: Giao dịch có ở DB nội bộ nhưng **không có** ở file đối soát ->DB nội bộ bị ảo (chưa trừ tiền thực tế). Cần chạy script rollback trạng thái.
         - **Trường hợp 3**: Giao dịch không có ở DB nội bộ nhưng **có** ở file đối soát ->Khách đã bị trừ tiền nhưng app lỗi nên không ghi nhận. Hệ thống tự động tạo giao dịch hoàn tiền hoặc cộng tiền thủ công cho khách.
