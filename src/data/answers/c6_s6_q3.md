# Reliability trong feature plan — Reliability là acceptance criterion
## ⚡ Tóm tắt ngắn (30s)
* Định nghĩa SLI, failure mode, dependency budget, degraded behavior và on-call owner từ planning.
* Observability, rollout, rollback, runbook và load/failure test nằm trong definition of done.
* Theo dõi customer-visible và technical metric sau launch.

---

## 🔍 Cách trả lời từng bước
### 1. Map failure mode
Tôi hỏi feature fail ở đâu: timeout, duplicate, stale data, queue backlog, partial dependency, bad deploy, overload hoặc data migration. Với mỗi mode, cần mitigation, detection và recovery.

### 2. Đặt budget
Latency budget được chia cho downstream; error budget cho feature không thể vượt SLO của service. Tôi tính peak capacity, connection/thread pool, retry amplification và storage growth. Reliability plan phải phù hợp với on-call và cost.

### 3. Build operational readiness
Definition of done gồm structured log/correlation, metrics/traces, dashboard, actionable alert, runbook, ownership, canary, rollback và test degraded mode. Nếu feature có async, monitor lag, retry, DLQ và stuck state.

### 4. Observe và learn
Sau launch, tôi theo dõi window đủ dài, review near miss và xóa workaround/flag. Nếu feature làm error budget cạn, tốc độ mở rộng phải dừng.

---

## 💻 Ví dụ trả lời / worked example
Với export report lớn, tôi không cho request giữ connection tới khi file xong. Tôi dùng job state machine, queue, object storage signed URL và giới hạn concurrent export theo tenant.

SLI gồm job acceptance, completion within target, failed/cancelled rate, queue lag, storage error và API p99. Runbook có pause worker, retry idempotently, cleanup orphan file và communicate delayed report. Canary một tenant trước, test provider storage down và kiểm tra permission signed URL.

Feature được coi là done khi operational path chạy được, không chỉ khi happy-path demo thành công.

## 📊 Follow-up interviewer có thể hỏi
| Follow-up | Hướng trả lời mạnh |
| :--- | :--- |
| Alert nào actionable? | Alert gắn customer/SLO, có owner và playbook; không alert mọi log. |
| Nếu không đủ thời gian? | Giảm scope, không bỏ safety-critical observability/rollback. |
| Error budget dùng thế nào? | Giới hạn rollout và cân bằng feature velocity với reliability. |
| Degraded mode là gì? | Behavior hữu ích/an toàn khi dependency chậm hoặc unavailable. |

---

## ⚠️ Common Mistakes & Pro Tips
1. **Không để on-call discover architecture sau launch.**
2. **Không chỉ test 200 response.**
3. **Không gọi autoscaling là reliability plan đầy đủ.**
4. **Không quên cleanup async state và data.**

**Mục tiêu của câu trả lời:** cho thấy cách suy nghĩ có cấu trúc, ownership cá nhân, khả năng định lượng impact và sự trung thực về trade-off cũng như giới hạn của solution.
