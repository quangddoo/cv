# REST API Versioning trong Spring Boot: Thiết kế Kiến trúc & So sánh 4 Phương pháp

## ⚡ Tóm tắt ngắn (30s)
Quản lý phiên bản (**API Versioning**) là yêu cầu bắt buộc để đảm bảo tính tương thích ngược (Backward Compatibility) khi nâng cấp hệ thống mà không làm ảnh hưởng đến các Client cũ đang hoạt động.
Spring Boot hỗ trợ hoàn hảo cả **4 phương pháp định nghĩa Version**:
1.  **URI Versioning**: Nhúng trực tiếp phiên bản vào đường dẫn (ví dụ: `/api/v1/users`). *Thổ dân, phổ biến nhất, dễ cache nhất.*
2.  **Query Parameter**: Sử dụng tham số truy vấn (ví dụ: `/api/users?version=1`). *Rõ ràng nhưng làm bẩn URL.*
3.  **Custom Header**: Sử dụng HTTP Header tự định nghĩa (ví dụ: `X-API-VERSION: 1`). *URL sạch sẽ nhưng khó test trên trình duyệt.*
4.  **Media Type (Accept Header/Content Negotiation)**: Sử dụng Header `Accept` chuẩn (ví dụ: `Accept: application/vnd.mycompany.v1+json`). *Chuẩn RESTful tinh tế nhất (HATEOAS), nhưng cực kỳ phức tạp.*

## 💻 Code thực chiến: BAD vs GOOD

### ❌ BAD: Trộn lẫn logic xử lý V1 và V2 bằng mã nhánh `if-else` trong cùng một Service/Controller
Việc gộp chung các phiên bản vào một Controller và dùng code rẽ nhánh nghiệp vụ khiến class phình to, vi phạm nguyên tắc Đơn nhiệm (Single Responsibility Principle) và cực kỳ dễ gây ra lỗi hồi quy (Regression Bugs) trên phiên bản cũ khi sửa đổi phiên bản mới.

```java
package com.example.controller;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.example.service.UserServiceBad;
import com.example.dto.UserDto;

@RestController
@RequestMapping("/api/users")
public class UserControllerBad {

    private final UserServiceBad userService;

    public UserControllerBad(UserServiceBad userService) {
        this.userService = userService;
    }

    // ❌ BAD: Dùng chung 1 endpoint và phân nhánh logic thô sơ
    @GetMapping("/{id}")
    public ResponseEntity<?> getUser(@PathVariable Long id, @RequestParam(defaultValue = "1") int version) {
        if (version == 1) {
            // Trả về DTO kiểu cũ (thiếu trường sinh nhật)
            return ResponseEntity.ok(userService.getUserV1(id));
        } else if (version == 2) {
            // Trả về DTO kiểu mới có định dạng khác hoàn toàn
            return ResponseEntity.ok(userService.getUserV2(id));
        }
        
        return ResponseEntity.badRequest().body("Unsupported version");
    }
}
```

### ✅ GOOD: Phân tách rõ ràng luồng Controller và áp dụng Strategy Pattern cho nghiệp vụ
Sử dụng các cơ chế định tuyến mạnh mẽ của Spring Boot để phân tách rõ rệt các Controller theo phiên bản, đồng thời tách biệt lớp DTO và Service tương ứng.

#### Cách 1: Triển khai URI Versioning (Phương pháp khuyên dùng cho phần lớn dự án)
```java
package com.example.controller.v1;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.example.dto.v1.UserResponseV1;
import com.example.service.UserService;

@RestController
@RequestMapping("/api/v1/users") // ✅ Rõ ràng, tách biệt thư mục v1
public class UserControllerV1 {

    private final UserService userService;

    public UserControllerV1(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<UserResponseV1> getUser(@PathVariable Long id) {
        return ResponseEntity.ok(userService.findByIdV1(id));
    }
}
```

```java
package com.example.controller.v2;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import com.example.dto.v2.UserResponseV2;
import com.example.service.UserService;

@RestController
@RequestMapping("/api/v2/users") // ✅ Endpoint v2 hoàn toàn độc lập
public class UserControllerV2 {

    private final UserService userService;

    public UserControllerV2(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<UserResponseV2> getUser(@PathVariable Long id) {
        return ResponseEntity.ok(userService.findByIdV2(id));
    }
}
```

#### Cách 2: Triển khai bằng Header / Media Type Versioning (Nếu muốn giữ sạch URL)
Spring Boot hỗ trợ các tham số cấu hình định tuyến rất mạnh mẽ ngay trong `@GetMapping`:

```java
package com.example.controller;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/products")
public class ProductController {

    // ✅ PHƯƠNG PHÁP 2: Định tuyến bằng Query Parameter (/api/products?version=1)
    @GetMapping(params = "version=1")
    public ResponseEntity<String> getProductsParamV1() {
        return ResponseEntity.ok("Products V1 (Query Param)");
    }

    @GetMapping(params = "version=2")
    public ResponseEntity<String> getProductsParamV2() {
        return ResponseEntity.ok("Products V2 (Query Param)");
    }

    // ✅ PHƯƠNG PHÁP 3: Định tuyến bằng Custom Header (Header: X-API-VERSION = 1)
    @GetMapping(headers = "X-API-VERSION=1")
    public ResponseEntity<String> getProductsHeaderV1() {
        return ResponseEntity.ok("Products V1 (Custom Header)");
    }

    @GetMapping(headers = "X-API-VERSION=2")
    public ResponseEntity<String> getProductsHeaderV2() {
        return ResponseEntity.ok("Products V2 (Custom Header)");
    }

    // ✅ PHƯƠNG PHÁP 4: Định tuyến bằng Media Type (Accept Header: application/vnd.company.v1+json)
    @GetMapping(produces = "application/vnd.company.v1+json")
    public ResponseEntity<String> getProductsMediaV1() {
        return ResponseEntity.ok("Products V1 (Media Type)");
    }

    @GetMapping(produces = "application/vnd.company.v2+json")
    public ResponseEntity<String> getProductsMediaV2() {
        return ResponseEntity.ok("Products V2 (Media Type)");
    }
}
```

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy phá vỡ bộ nhớ Cache (Proxy Cache Invalidation) khi dùng Header/Accept Versioning
*   **Vấn đề**: Bạn quyết định sử dụng phương pháp **Custom Header** hoặc **Media Type** để giữ cho URL luôn sạch đẹp (`/api/products`). Hệ thống chạy mượt mà ở Local. Tuy nhiên khi lên production và đặt sau các hệ thống Proxy Cache (như CDN Cloudflare, Varnish Cache, hoặc Nginx Cache), Client V1 liên tục nhận được dữ liệu định dạng của V2 (hoặc ngược lại)!
*   **Nguyên nhân dưới mui xe**: Theo mặc định, các Proxy Cache trung gian chỉ sử dụng **đường dẫn URL làm khóa duy nhất (Cache Key)** để lưu trữ phản hồi. Khi Client V1 gửi request `/api/products` kèm header `X-API-VERSION: 1`, Proxy lưu kết quả ứng với key `/api/products`. Khi Client V2 gửi request `/api/products` kèm header `X-API-VERSION: 2`, Proxy phát hiện trùng khớp key `/api/products` nên lập tức trả ngay kết quả đã cache của V1 cho V2!
*   **Giải pháp thực chiến**:
    1.  *Khuyên dùng*: Sử dụng **URI Versioning** vì mỗi phiên bản là một URL khác nhau hoàn toàn, tự động tương thích 100% với mọi hệ thống Cache mà không cần cấu hình thêm.
    2.  *Nếu bắt buộc dùng Header*: Bạn phải cấu hình máy chủ Backend bổ sung thêm Header phản hồi **`Vary`** (ví dụ: `Vary: X-API-VERSION` hoặc `Vary: Accept`). Header này ra lệnh cho Proxy Cache phải nhân bản bộ khóa cache kết hợp cả URL và giá trị của Header chỉ định.

### 2. Sự đánh đổi hạ tầng: Định tuyến tại API Gateway
*   Trong mô hình kiến trúc Microservices, việc chuyển tiếp và cân bằng tải request thường được đảm nhận bởi API Gateway (như Kong, Apisix, AWS API Gateway) hoặc Reverse Proxy (Nginx).
*   **URI Versioning**: Cho phép viết các rule định tuyến cực kỳ nhanh chóng và đơn giản ngay tại tầng cấu hình mạng (ví dụ: `rewrite /api/v1/(.*) to service-v1`).
*   **Header / Media Type Versioning**: Buộc API Gateway phải thực hiện phân tích sâu gói tin (Deep Packet Inspection), đọc và parse toàn bộ HTTP Header của request để đưa ra quyết định chuyển tiếp. Điều này làm tăng độ trễ mạng (Network Latency), hao phí năng lực xử lý CPU của Gateway dưới tải hàng triệu request/giây.
