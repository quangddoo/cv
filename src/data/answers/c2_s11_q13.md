# Có nên sửa dữ liệu trực tiếp bằng SQL production không?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Câu trả lời dứt khoát của một Senior/Staff Engineer là **"Không, ngoại trừ trường hợp bất khả kháng cực kỳ khẩn cấp và phải tuân thủ nghiêm ngặt quy trình Kiểm soát 4 mắt (Four-Eyes Principle)"**. Chạy lệnh `UPDATE/DELETE` trực tiếp bằng SQL bypass qua toàn bộ tầng ứng dụng (Application Layer), để lại hậu quả khôn lường về tính toàn vẹn dữ liệu, gây stale cache và phá hủy tính bất biến của Audit Log.
* **Thảm họa thực chiến được giải quyết**:
  1. **Thảm họa "Quên mệnh đề WHERE" (The Whereless Nightmare)**: Kỹ sư được yêu cầu đổi số điện thoại của một user VIP. Trong trạng thái căng thẳng lúc nửa đêm, anh ta viết: `UPDATE users SET phone = '0901234567'` và nhấn Execute trước khi gõ xong dòng `WHERE id = 456`. Kết quả: Toàn bộ 5 triệu user trong hệ thống bị đổi chung về một số điện thoại, làm tê liệt tính năng OTP đăng nhập toàn hệ thống.
  2. **Lệch bộ nhớ đệm (Stale Cache)**: DB được sửa trực tiếp trạng thái đơn hàng thành `PAID` bằng SQL. Tuy nhiên, tầng ứng dụng vẫn giữ cache thông tin đơn hàng này trong Redis dưới trạng thái `PENDING`. Khách hàng liên tục thấy đơn hàng chưa thanh toán, hệ thống kho không nhận được tín hiệu để chuẩn bị hàng, gây tắc nghẽn luồng vận hành.
* **Quyết định Senior**:
  1. **Tước quyền ghi (`WRITE`) mặc định trên Production**: Mọi kỹ sư (kể cả Tech Lead) mặc định chỉ được cấp quyền đọc (`READ-ONLY`) trên DB Production. Quyền ghi chỉ được mở cấp thời qua hệ thống IAM có thời hạn (ví dụ: cấp quyền ghi 30 phút và tự động thu hồi).
  2. **Tuyệt đối cấm viết SQL chạy tay "sống" (Raw SQL Execution)**: Bắt buộc phải viết câu lệnh phục hồi dữ liệu dưới dạng **Script đối soát có cơ chế Rollback an toàn (Dry-run)** và phải được test kỹ lưỡng trên môi trường Staging trước khi chạy thật.
  3. **Ưu tiên Sửa dữ liệu thông qua Application API**: Thay vì chọc trực tiếp vào DB, thiết kế các API admin bảo mật (Admin Portal) để sửa dữ liệu, đảm bảo cuộc gọi đi qua đầy đủ logic kiểm tra quyền, ghi log kiểm toán và xóa cache tự động.

## 🔍 Chi tiết bản chất thực chiến: Tại sao SQL chạy tay lại phá hủy hệ thống?

### 1. Bỏ qua cơ chế Xóa Cache (Cache Invalidation)
Hệ thống hiện đại luôn dùng Redis làm bộ đệm để giảm tải cho DB. Khi bạn dùng SQL cập nhật trực tiếp DB:
```sql
UPDATE orders SET status = 'SUCCESS' WHERE id = 123;
```
Database thay đổi, nhưng **Redis hoàn toàn không biết sự kiện này**. Tầng ứng dụng vẫn tiếp tục đọc thông tin cũ từ Redis. Sự lệch dữ liệu giữa DB và Cache tạo ra các lỗi logic ngầm cực kỳ khó debug.

### 2. Bypass cơ chế sinh Event và Lịch sử (Side-effects Bypassing)
Khi sửa trực tiếp DB, toàn bộ các cơ chế tự động của tầng Ứng dụng như:
* Đẩy tin nhắn báo trạng thái qua Kafka.
* Sinh nhật ký kiểm toán (Audit Log) lưu vết người dùng.
* Gửi Email/SMS thông báo trạng thái mới cho khách hàng.
* Tự động hoàn kho (Inventory release) khi hủy đơn.
...đều **bị vô hiệu hóa hoàn toàn**, dẫn đến hệ thống bị mất đồng bộ trên diện rộng.

## 💻 Code thực chiến: Quy trình chạy SQL cứu hộ khẩn cấp an toàn (Emergency Runbook)

Nếu rơi vào tình huống bắt buộc phải chạy lệnh SQL bằng tay để sửa dữ liệu Production (ví dụ: DB bị nghẽn và API Admin bị sập), Senior sẽ tuân thủ nghiêm ngặt **Quy trình chạy Transaction an toàn 5 bước** dưới đây:

### Runbook chạy SQL khẩn cấp:

```sql
-- BƯỚC 1: KHỞI TẠO TRANSACTION CHỦ ĐỘNG
-- Tuyệt đối không dùng chế độ Auto-commit. Bắt buộc mở Transaction thủ công.
START TRANSACTION;

-- BƯỚC 2: SELECT ĐỐI SOÁT TRƯỚC KHI UPDATE
-- Khóa dòng cần cập nhật để tránh luồng khác nhảy vào sửa song song
SELECT id, status, total_amount 
FROM orders 
WHERE id = 456 AND status = 'PENDING'
FOR UPDATE;

-- BƯỚC 3: THỰC THI UPDATE KÈM THEO ĐIỀU KIỆN CHẶT CHẼ
-- Không bao giờ chỉ WHERE theo ID, bắt buộc WHERE kèm theo trạng thái cũ (Optimistic Lock)
UPDATE orders 
SET status = 'PAID', updated_by = 'emergency_sql_patch_tuan_nguyen'
WHERE id = 456 AND status = 'PENDING';

-- BƯỚC 4: KIỂM TRA SỐ DÒNG BỊ ẢNH HƯỞNG (ROW AFFECTED)
-- Trong DB Client (như DBeaver/PgAdmin), kiểm tra log output:
-- "1 row affected" -> AN TOÀN ✔
-- "5,000,000 rows affected" -> THẢM HỌA 🚨 (Chạy ngay lệnh ROLLBACK ở Bước 5.2!)

-- BƯỚC 5.1: NẾU AN TOÀN -> COMMIT GIAO DỊCH
COMMIT;

-- BƯỚC 5.2: NẾU THẤY BẤT THƯỜNG -> ROLLBACK LẬP TỨC ĐỂ CỨU HỆ THỐNG
ROLLBACK;
```

| Tiêu chí | Phương án 1: Viết Raw SQL chạy trực tiếp | Phương án 2: Viết Python Script chạy CLI | Phương án 3: Tool Admin Nội bộ (Admin Portal) |
| :--- | :--- | :--- | :--- |
| **Độ an toàn** | **Cực kỳ thấp** (Rủi ro lỗi cú pháp, quên WHERE làm hỏng toàn bộ DB). | Trung bình | **Tuyệt đối 100%** (Được kiểm thử kỹ, đi qua đủ bộ lọc nghiệp vụ). |
| **Tự động xóa Cache & Bắn Event** | ❌ Không (Bypass hoàn toàn App). | ❌ Không (Ngoại trừ script tự viết logic xóa cache thủ công). |  Có (Tự động thực thi như luồng người dùng). |

| **Tốc độ triển khai** | **Siêu nhanh** (Viết lệnh mất 10 giây). | Trung bình (Tốn vài chục phút viết script). | Chậm (Phải tốn công code giao diện và API). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Xung đột Khóa và treo DB khi chạy lệnh SQL kiểm tra không COMMIT"
* **Vấn đề nguy hiểm**: Khi kỹ sư chạy lệnh `START TRANSACTION` và chạy câu lệnh `UPDATE` hoặc `SELECT FOR UPDATE` để kiểm tra dữ liệu. Tuy nhiên, sau đó anh ta bận đi họp hoặc chuyển tab ứng dụng và **quên gõ lệnh `COMMIT` hoặc `ROLLBACK`**.
  * Hậu quả: DB tiếp tục giữ các khóa độc quyền trên các dòng dữ liệu đó vĩnh viễn. Toàn bộ các request sau này của khách hàng đụng tới các dòng đó sẽ bị khóa treo cứng, gây lỗi sập API âm thầm cực kỳ khó phát hiện.
* **Giải pháp khắc phục**:
  1. Luôn cài đặt **Transaction Timeout** ở mức thấp trên công cụ Client của nhà phát triển (ví dụ: DBeaver cấu hình tự động ngắt transaction sau 60 giây).
  2. Bật monitoring cảnh báo các Transaction chạy lâu (Long-running Transactions) ở tầng DB.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Bây giờ hệ thống đang bị lỗi ngầm, 50,000 đơn hàng bị lỗi hiển thị số tiền thanh toán là 0đ. Tôi muốn sửa nhanh trong 5 phút để kịp giờ chiến dịch lớn, API Admin thì chưa viết tính năng này. Bạn xử lý thế nào để vừa nhanh vừa tuyệt đối an toàn?"**
* **Trả lời**:
  * Senior sẽ **từ chối việc chạy Raw SQL UPDATE bằng tay** trên 50,000 dòng vì rủi ro khóa bảng diện rộng và lỗi lệch cache.
  * Thay vào đó, Senior áp dụng chiến lược **CLI Script gọi qua API nội bộ (API-Driven CLI script)**:
    1. Viết một script Python nhanh dạng cuốn chiếu.
    2. Script này đọc danh sách 50,000 ID đơn hàng lỗi từ một file text.
    3. Duyệt qua từng ID và thực hiện gửi HTTP Request gọi trực tiếp tới API sửa đổi nội bộ của Backend (`PUT /internal/orders/{id}/correct-amount` kèm theo API Key bảo mật).
    4. Giao dịch đi qua API sẽ tự động thực thi việc kiểm tra logic, xóa cache Redis, bắn event sang Kafka, ghi Audit Log sòng phẳng.
    5. Đặt độ trễ (Sleep 50ms) giữa các request để không gây quá tải CPU của máy chủ Backend.
