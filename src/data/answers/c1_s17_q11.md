# Phân tích file log lớn và tìm các IP truy cập nhiều nhất (Parse Large Log File and Find Top IPs)

## ⚡ Tóm tắt ngắn (30s)
* **Bài toán**: Phân tích một file log dung lượng khổng lồ (ví dụ 100GB, vượt quá RAM hệ thống) để tìm ra Top $K$ địa chỉ IP xuất hiện nhiều nhất (truy cập nhiều nhất).
* **Giải pháp cốt lõi**:
  1. **Tránh tải toàn bộ file vào RAM**: Sử dụng cơ chế đọc luồng (Streaming/BufferedReader) để đọc từng dòng.
  2. **Xử lý giới hạn bộ nhớ (Nếu unique IPs cực lớn)**: Áp dụng phương pháp **Chia để trị bằng Hash Partitioning** - Băm địa chỉ IP thành $N$ file nhỏ tạm thời dựa trên công thức `hash(IP) % N`. Việc này đảm bảo toàn bộ dòng log của cùng một IP sẽ rơi vào cùng một file nhỏ.
  3. **Tính toán tần suất & Lọc Top K**: Dùng một bảng băm (`HashMap`) để đếm tần suất của mỗi IP trong từng file nhỏ, sau đó dùng một cấu trúc **Min-Heap** (`PriorityQueue` kích thước cố định $K$) để duy trì Top $K$ IP có tần suất cao nhất.
* **Độ phức tạp**: Thời gian $O(L + U \log K)$ với $L$ là tổng số dòng log, $U$ là số IP duy nhất ($U \le L$), $K$ là số lượng IP cần tìm. Không gian bộ nhớ cực nhỏ $O(U/N + K)$ nhờ cơ chế phân mảnh file.

---

## 🔍 Phân tích yêu cầu (Requirements)

### 1. Functional Requirements (Yêu cầu chức năng)
* Đọc dữ liệu từ file log nguồn cấu trúc lớn, trích xuất địa chỉ IP từ mỗi dòng.
* Tìm chính xác danh sách Top $K$ IP (ví dụ: top 100) truy cập nhiều nhất kèm tần suất.
* Ghi kết quả đầu ra ra file báo cáo hoặc hiển thị trực quan lên màn hình.

### 2. Non-Functional Requirements (Yêu cầu phi chức năng)
* **Khả năng chịu tải & Tránh sập nguồn (Memory Efficiency)**: Hệ thống **không được** ném ra lỗi `OutOfMemoryError` cho dù file log có lớn đến hàng trăm GB hay thậm chí hàng TB. RAM sử dụng phải được kiểm soát ở mức hằng số hoặc giới hạn nhỏ tối đa (ví dụ < 256MB).
* **Độ chính xác (Accuracy)**: Phép đếm tần suất phải chính xác tuyệt đối, không được sử dụng các thuật toán ước lượng xác suất (như Count-Min Sketch) trừ khi khách hàng yêu cầu cụ thể.
* **Hiệu suất xử lý (Throughput)**: Khai thác tối đa tốc độ đọc I/O của ổ đĩa và xử lý song song đa luồng (Multi-threading) nếu có thể để giảm thời gian xử lý tổng thể.

## 🎨 Sơ đồ trực quan & Giải thuật

Khi xử lý file lớn vượt RAM, giải pháp tối ưu nhất theo mô hình Map-Reduce thu nhỏ trên máy đơn là **Hash Partitioning (Phân mảnh băm)**:

### 1. Quy trình xử lý gồm 3 pha (Phase) chính:

```
[ FILE LOG LỚN 100GB ] (Đọc từng dòng - Stream)
          │
          ▼  (Pha 1: Chia file bằng Hash)
 ┌───────────────────────────────────┐
 │ hash(IP) % N (Ví dụ N = 100)      │
 └───────────────────────────────────┘
     │           │               │
     ▼           ▼               ▼
[File Tạm 0] [File Tạm 1] ... [File Tạm 99]  (Mỗi file nhỏ khoảng 1GB)
     │           │               │
     ▼           ▼               ▼  (Pha 2: Đếm tần suất từng file nhỏ)
 ┌───────────────────────────────────┐
 │ Dùng HashMap<String, Long>        │
 └───────────────────────────────────┘
     │           │               │
     ▼           ▼               ▼
 [Map Tạm 0] [Map Tạm 1]  ... [Map Tạm 99]
     │           │               │
     └───────────┼───────────────┘
                 │
                 ▼  (Pha 3: Hợp nhất vào Min-Heap kích thước K)
       ┌───────────────────┐
       │     Min-Heap      │ ◄─── (Duy trì K phần tử lớn nhất)
       └───────────────────┘
                 │
                 ▼
       [ KẾT QUẢ TOP K IP ]
```

## 💻 Code Example: Hiện thực hóa quy trình bằng Java

Dưới đây là mã nguồn Java hoàn chỉnh, tối ưu hóa bộ nhớ thông qua cơ chế đọc từng dòng và phân tách file tạm (Hash Partitioning). Code xử lý cực kỳ chặt chẽ bao gồm cả việc dọn dẹp file tạm sau khi chạy xong.

```java
import java.io.*;
import java.nio.file.*;
import java.util.*;
import java.util.regex.*;

public class LargeLogParser {

    private static final int NUM_PARTITIONS = 10; // Số lượng file nhỏ để phân mảnh
    private static final Pattern IP_PATTERN = Pattern.compile("^(((25[0-5]|(2[0-4]|1\\d|[1-9]|)\\d)\\.?\\b){4})");

    public static class IpFreq implements Comparable<IpFreq> {
        String ip;
        long count;

        public IpFreq(String ip, long count) {
            this.ip = ip;
            this.count = count;
        }

        @Override
        public int compareTo(IpFreq o) {
            // Sắp xếp tăng dần theo tần suất để dùng cho Min-Heap
            return Long.compare(this.count, o.count);
        }
    }

    /**
     * Quy trình chính xử lý file log lớn
     */
    public List<IpFreq> findTopK(String logFilePath, int k) throws IOException {
        String tempDirName = "temp_partitions";
        Path tempDirPath = Paths.get(tempDirName);
        Files.createDirectories(tempDirPath);

        // --- PHA 1: CHIA FILE NGUỒN THÀNH CÁC FILE PHÂN MẢNH ---
        BufferedWriter[] writers = new BufferedWriter[NUM_PARTITIONS];
        try {
            for (int i = 0; i < NUM_PARTITIONS; i++) {
                writers[i] = new BufferedWriter(new FileWriter(tempDirName + "/part_" + i + ".txt"));
            }

            try (BufferedReader reader = new BufferedReader(new FileReader(logFilePath))) {
                String line;
                while ((line = reader.readLine()) != null) {
                    String ip = extractIp(line);
                    if (ip != null) {
                        int partitionIndex = Math.abs(ip.hashCode()) % NUM_PARTITIONS;
                        writers[partitionIndex].write(ip);
                        writers[partitionIndex].newLine();
                    }
                }
            }
        } finally {
            // Đóng toàn bộ luồng ghi để đảm bảo dữ liệu ghi hết xuống đĩa
            for (BufferedWriter writer : writers) {
                if (writer != null) writer.close();
            }
        }

        // --- PHA 2 & 3: ĐẾM TẦN SUẤT TỪNG PHÂN MẢNH VÀ ĐƯA VÀO MIN-HEAP ---
        PriorityQueue<IpFreq> minHeap = new PriorityQueue<>(k);

        for (int i = 0; i < NUM_PARTITIONS; i++) {
            File partFile = new File(tempDirName + "/part_" + i + ".txt");
            if (!partFile.exists()) continue;

            // HashMap cục bộ cho từng phân mảnh (bộ nhớ RAM được giải phóng sau mỗi vòng lặp)
            Map<String, Long> localFreqMap = new HashMap<>();

            try (BufferedReader partReader = new BufferedReader(new FileReader(partFile))) {
                String ip;
                while ((ip = partReader.readLine()) != null) {
                    localFreqMap.put(ip, localFreqMap.getOrDefault(ip, 0L) + 1);
                }
            }

            // Hợp nhất dữ liệu của phân mảnh hiện tại vào Min-Heap tổng thể
            for (Map.Entry<String, Long> entry : localFreqMap.entrySet()) {
                IpFreq candidate = new IpFreq(entry.getKey(), entry.getValue());
                if (minHeap.size() < k) {
                    minHeap.offer(candidate);
                } else if (candidate.count > minHeap.peek().count) {
                    minHeap.poll(); // Loại bỏ IP có tần suất thấp nhất hiện tại
                    minHeap.offer(candidate); // Đưa ứng viên sáng giá hơn vào
                }
            }

            // Dọn dẹp file tạm ngay lập tức sau khi dùng xong để tiết kiệm đĩa (Gotcha 2)
            partFile.delete();
        }

        // Dọn dẹp thư mục tạm
        Files.deleteIfExists(tempDirPath);

        // Chuyển kết quả từ Heap ra danh sách đã sắp xếp giảm dần
        List<IpFreq> result = new ArrayList<>(minHeap);
        result.sort(Collections.reverseOrder());
        return result;
    }

    /**
     * Trích xuất IP bằng Regex đơn giản từ dòng log (giả sử IP nằm đầu dòng)
     */
    private String extractIp(String logLine) {
        Matcher matcher = IP_PATTERN.matcher(logLine);
        if (matcher.find()) {
            return matcher.group(1);
        }
        return null;
    }

    // --- Demo chạy thử ---
    public static void main(String[] args) {
        // Giả lập tạo file log mẫu 
        String demoLog = "demo_large_access.log";
        try (PrintWriter writer = new PrintWriter(new FileWriter(demoLog))) {
            for (int i = 0; i < 1000; i++) {
                writer.println("192.168.1.10 - - [23/May/2026] \"GET /index.html\"");
            }
            for (int i = 0; i < 500; i++) {
                writer.println("10.0.0.5 - - [23/May/2026] \"POST /login\"");
            }
            for (int i = 0; i < 2000; i++) {
                writer.println("172.16.254.1 - - [23/May/2026] \"GET /api/v1/users\"");
            }
        } catch (IOException e) {
            e.printStackTrace();
        }

        LargeLogParser parser = new LargeLogParser();
        try {
            System.out.println("Đang bắt đầu phân tích file log...");
            List<IpFreq> topIPs = parser.findTopK(demoLog, 2);

            System.out.println("\n--- TOP IP TRUY CẬP NHIỀU NHẤT ---");
            for (IpFreq ip : topIPs) {
                System.out.printf("IP: %-15s | Tần suất: %d lần\n", ip.ip, ip.count);
            }

            // Xóa file demo sau khi kết thúc
            new File(demoLog).delete();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
```

## 📊 Phân tích độ phức tạp & Trade-offs

### So sánh các phương pháp xử lý file log lớn

| Tiêu chí | Đọc nén toàn bộ vào RAM | Streaming + HashMap đơn thuần | Hash Partitioning + Min-Heap (Tối ưu) | Sử dụng Bloom Filter / Count-Min Sketch |
| :--- | :--- | :--- | :--- | :--- |
| **Độ chính xác** | 100% chính xác. | 100% chính xác. | **100% chính xác.** | Chỉ mang tính ước lượng xấp xỉ (Có sai số). |
| **Tiêu tốn bộ nhớ (RAM)** | **Cực cao**: $O(L)$ RAM tỉ lệ thuận với tổng dung lượng file log. Dễ gây OOM. | **Cao**: $O(U)$ RAM phụ thuộc vào số lượng địa chỉ IP duy nhất. Vẫn có rủi ro OOM lớn. | **Rất thấp**: $O(U/N + K)$ RAM được chia nhỏ tối đa thông qua $N$ phân mảnh. | **Siêu thấp**: $O(M)$ bộ nhớ cố định (dựa trên mảng bit tuần hoàn). |
| **Độ phức tạp I/O đĩa** | Đọc đĩa 1 lần. | Đọc đĩa 1 lần. | Đọc đĩa 1 lần để băm + Ghi file tạm + Đọc lại file tạm. (I/O overhead nhẹ). | Đọc đĩa 1 lần. |
| **Khả năng Scale-out** | Không thể. | Rất khó. | **Dễ dàng**: Thiết kế này chính là nền tảng của MapReduce xử lý phân tán đa nút. | Rất dễ. |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

### 1. Nếu số lượng địa chỉ IP duy nhất (Unique IPs) vẫn vượt quá giới hạn RAM của một file phân mảnh tạm thì sao?
* **Trả lời**: Đây là trường hợp cực đoan nhưng hoàn toàn có thể xảy ra (ví dụ trong mạng IPv6 với hàng tỷ thiết bị IoT). 
  * Nếu một file phân mảnh tạm vẫn quá lớn làm HashMap đếm tần suất bị tràn RAM, ta tiếp tục thực hiện **phân mảnh đệ quy (Recursive Partitioning)**. Nghĩa là, ta áp dụng một hàm băm thứ hai (ví dụ `hash2(IP) % M`) trên file tạm hiện tại để chẻ nó thành các file con nhỏ hơn nữa, cho đến khi mỗi file con hoàn toàn vừa vặn trong RAM.
  * Ngoài ra, ta có thể chuyển sang sử dụng công cụ lưu trữ ngoài đĩa bền vững dạng nhúng như **RocksDB** hoặc **BerkeleyDB** để lưu HashMap tạm thời thay vì giữ trên RAM.

### 2. Các file phân mảnh tạm (Temporary partition files) ghi xuống đĩa có thể gây nghẽn I/O (I/O Bottleneck) và hết dung lượng bộ nhớ đĩa không? Cách phòng ngừa?
* **Trả lời**: Có, việc mở quá nhiều luồng ghi file đồng thời cùng lúc sẽ làm đầu đọc của HDD bị phân mảnh di chuyển liên tục gây sụt giảm hiệu năng nặng nề (mặc dù SSD đỡ hơn).
  * **Giải pháp phòng ngừa nghẽn I/O**: Dùng một vùng đệm bộ nhớ đệm (Buffered Write Buffer) cho mỗi Writer trước khi đẩy dữ liệu xuống đĩa. Hoặc cấu hình số lượng phân mảnh $N$ vừa phải (ví dụ 10-100) để không vượt quá giới hạn file descriptor của hệ điều hành.
  * **Giải pháp phòng ngừa tràn đĩa**: Đảm bảo dọn dẹp (delete) ngay lập tức file tạm của phân mảnh thứ $i$ ngay sau khi đã đếm xong tần suất và hợp nhất vào Min-Heap, trước khi chuyển sang đọc file tạm thứ $i+1$ (như đã triển khai trong code mẫu). Không đợi đến khi toàn bộ tiến trình kết thúc mới xóa tập loạt.

### 3. Tại sao chọn Min-Heap để tìm Top K thay vì thu thập toàn bộ rồi sắp xếp QuickSort/MergeSort?
* **Trả lời**: 
  * Nếu dùng thuật toán sắp xếp thông thường trên danh sách $U$ phần tử duy nhất, độ phức tạp thời gian sẽ là $O(U \log U)$ và đòi hỏi cấu trúc lưu trữ lớn.
  * Dùng **Min-Heap** kích thước cố định là $K$, ta chỉ cần duyệt qua danh sách phần tử. Với mỗi phần tử, ta so sánh với đỉnh Heap (phần tử nhỏ nhất trong nhóm Top K hiện tại). Nếu lớn hơn, ta loại bỏ đỉnh và thêm phần tử mới vào với chi phí chỉ là $O(\log K)$.
  * Vì thông thường $K \ll U$ (ví dụ tìm top 100 IP trong số 10 triệu IP), độ phức tạp thời gian giảm xuống còn $O(U \log K)$, đồng thời lượng RAM tiêu thụ để tìm top là tối thiểu $O(K)$. Tiết kiệm tài nguyên vượt trội!
