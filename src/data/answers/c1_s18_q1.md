# Nguyên lý SOLID trong thiết kế hướng đối tượng (SOLID Principles in OOP)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **SOLID** là viết tắt của 5 nguyên lý thiết kế hướng đối tượng cốt lõi giúp hệ thống phần mềm dễ bảo trì, dễ mở rộng và hạn chế tối đa lỗi (bugs) khi nâng cấp:
  1. **S - Single Responsibility Principle (Đơn nhiệm)**: Một lớp chỉ nên giữ một trách nhiệm duy nhất (chỉ có duy nhất một lý do để thay đổi).
  2. **O - Open/Closed Principle (Đóng/Mở)**: Mở rộng cho phát triển, đóng cho sửa đổi (thêm tính năng mới bằng cách viết code mới, không chỉnh sửa code cũ đã chạy ổn định).
  3. **L - Liskov Substitution Principle (Thay thế Liskov)**: Các lớp con phải có khả năng thay thế hoàn toàn lớp cha mà không làm thay đổi tính đúng đắn của chương trình.
  4. **I - Interface Segregation Principle (Phân tách Interface)**: Thà sử dụng nhiều interface nhỏ, chuyên biệt còn hơn sử dụng một interface lớn, đa năng nhưng dư thừa.
  5. **D - Dependency Inversion Principle (Đảo ngược phụ thuộc)**: Các mô-đun cấp cao không nên phụ thuộc trực tiếp vào mô-đun cấp thấp; cả hai nên phụ thuộc vào abstractions (giao diện/lớp trừu tượng).
* **Giá trị cốt lõi**: Tránh biến mã nguồn thành "Spaghetti Code" rối rắm, giảm độ kết dính chặt chẽ (Tight Coupling) và tăng tính tái sử dụng.

## 🔍 Phân tích từng nguyên lý & Ví dụ thực tế bằng Java

### 1. S — Single Responsibility Principle (SRP)
* **Ý nghĩa**: Một lớp chỉ nên chịu trách nhiệm cho một phần chức năng nghiệp vụ cụ thể. Nếu một lớp gánh quá nhiều vai trò, khi một vai trò thay đổi, ta có thể vô tình làm sập các vai trò khác.

#### ❌ Vi phạm (SRP Violation)
Lớp `Invoice` vừa xử lý tính tiền, vừa định dạng in hóa đơn PDF, vừa kết nối database để lưu trữ:
```java
public class Invoice {
    public double calculateTotal() { /* Logic tính tiền */ return 100.0; }
    public void generatePdfReport() { /* Logic định dạng và tạo PDF */ }
    public void saveToDatabase() { /* Logic SQL lưu hóa đơn */ }
}
```

####  Tối ưu (SRP Applied)
Tách thành 3 lớp riêng biệt, mỗi lớp chịu trách nhiệm một chuyên môn:
```java
public class Invoice {
    public double calculateTotal() { return 100.0; }
}

public class InvoiceRepository {
    public void save(Invoice invoice) { /* Chỉ kết nối DB và lưu */ }
}

public class InvoicePdfPrinter {
    public void print(Invoice invoice) { /* Chỉ làm nhiệm vụ xuất PDF */ }
}
```

### 2. O — Open/Closed Principle (OCP)
* **Ý nghĩa**: Khi muốn thêm hành vi/tính năng mới, ta nên viết lớp mới kế thừa hoặc hiện thực hóa từ thiết kế cũ, thay vì trực tiếp nhảy vào sửa đổi các file mã nguồn cũ vốn đang chạy trơn tru trên Production.

#### ❌ Vi phạm (OCP Violation)
Khi cần thêm một loại hình thanh toán mới (ví dụ: Momo), ta phải sửa trực tiếp cấu trúc rẽ nhánh `switch-case` của lớp thanh toán cũ:
```java
public class PaymentService {
    public void processPayment(String type) {
        if (type.equals("CREDIT_CARD")) {
            // Thanh toán thẻ
        } else if (type.equals("PAYPAL")) {
            // Thanh toán Paypal
        }
        // Thêm Momo => Bắt buộc phải thêm block else-if ở đây (Sửa code cũ!)
    }
}
```

####  Tối ưu (OCP Applied)
Ứng dụng tính đa hình (Polymorphism) thông qua Interface hoặc Pattern Strategy:
```java
public interface PaymentMethod {
    void pay();
}

public class CreditCardPayment implements PaymentMethod {
    public void pay() { /* Thanh toán thẻ */ }
}

public class PaypalPayment implements PaymentMethod {
    public void pay() { /* Thanh toán Paypal */ }
}

// Khi có Momo, chỉ cần viết class mới:
public class MomoPayment implements PaymentMethod {
    public void pay() { /* Thanh toán Momo */ }
}

// Lớp điều phối đóng hoàn toàn trước sự thay đổi, chỉ cần nhận Interface đầu vào:
public class PaymentService {
    public void processPayment(PaymentMethod method) {
        method.pay();
    }
}
```

### 3. L — Liskov Substitution Principle (LSP)
* **Ý nghĩa**: Lớp con kế thừa lớp cha không được phép phá vỡ hoặc phủ quyết hành vi logic sẵn có của lớp cha.

#### ❌ Vi phạm (LSP Violation)
Lớp `Ostrich` (Đà điểu) kế thừa `Bird` (Chim) nhưng lại không biết bay, dẫn đến việc ném ngoại lệ khi gọi hàm bay:
```java
public class Bird {
    public void fly() { System.out.println("Đang bay..."); }
}

public class Ostrich extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Đà điểu không biết bay!");
    }
}

// Ứng dụng client bị lỗi sập khi chạy danh sách chim:
public void makeAllBirdsFly(List<Bird> birds) {
    for (Bird bird : birds) {
        bird.fly(); // Sẽ sập hoàn toàn chương trình khi gặp Ostrich!
    }
}
```

####  Tối ưu (LSP Applied)
Thiết kế lại cây kế thừa chính xác hơn dựa trên năng lực hành vi thực tế thay vì tên gọi sinh học chung chung:
```java
public class Bird {
    // Các thuộc tính chung của chim: đẻ trứng, ăn...
}

public class FlyingBird extends Bird {
    public void fly() { System.out.println("Đang bay..."); }
}

public class Ostrich extends Bird {
    // Chỉ đẻ trứng, chạy nhảy, không kế thừa FlyingBird
}
```

### 4. I — Interface Segregation Principle (ISP)
* **Ý nghĩa**: Tránh thiết kế interface "béo phì" chứa quá nhiều phương thức. Hãy chẻ nhỏ interface để các lớp triển khai không bị ép buộc phải viết mã trống (dummy code) cho các hàm mà chúng không hề sử dụng.

#### ❌ Vi phạm (ISP Violation)
Interface `Worker` bắt buộc cả con người và Robot đều phải triển khai cả hàm Ăn (`eat`):
```java
public interface Worker {
    void work();
    void eat(); // Robot bị ép buộc triển khai hàm này vô nghĩa!
}
```

####  Tối ưu (ISP Applied)
Tách thành các interface nhỏ chuyên biệt:
```java
public interface Workable {
    void work();
}

public interface Feedable {
    void eat();
}

// Người làm việc và cần ăn uống:
public class Human implements Workable, Feedable {
    public void work() {}
    public void eat() {}
}

// Robot chỉ làm việc, không cần ăn uống:
public class Robot implements Workable {
    public void work() {}
}
```

### 5. D — Dependency Inversion Principle (DIP)
* **Ý nghĩa**:
  * Các mô-đun cấp cao (chứa logic nghiệp vụ lõi) không được phụ thuộc trực tiếp vào các mô-đun cấp thấp (cụ thể hóa chi tiết kỹ thuật như Database, Network, API). Cả hai phải giao tiếp thông qua một lớp trừu tượng (Interface).
  * **Đảo ngược phụ thuộc**: Chi tiết kỹ thuật phụ thuộc vào thiết kế trừu tượng của nghiệp vụ, chứ không phải nghiệp vụ đi theo chi tiết kỹ thuật.

#### ❌ Vi phạm (DIP Violation)
Lớp dịch vụ cấp cao `OrderService` trực tiếp khởi tạo và phụ thuộc vào lớp kết nối dữ liệu cấp thấp `MySqlDatabase`:
```java
public class MySqlDatabase {
    public void insertOrder() { /* SQL insert MySQL */ }
}

public class OrderService {
    // Khởi tạo trực tiếp đối tượng cụ thể (Tight Coupling)
    private MySqlDatabase database = new MySqlDatabase();

    public void createOrder() {
        database.insertOrder(); // Nếu đổi sang PostgresSql, ta phải viết lại toàn bộ lớp OrderService!
    }
}
```

####  Tối ưu (DIP Applied)
Đặt một Interface trừu tượng ở giữa làm cầu nối:
```java
// Thiết kế trừu tượng
public interface Database {
    void insertOrder();
}

// Các lớp cụ thể hóa phụ thuộc vào Interface
public class MySqlDatabase implements Database {
    public void insertOrder() { /* MySQL insert */ }
}

public class PostgresSqlDatabase implements Database {
    public void insertOrder() { /* Postgres insert */ }
}

// Mô-đun cấp cao hoàn toàn độc lập, nhận phụ thuộc thông qua Interface (Dependency Injection)
public class OrderService {
    private final Database database;

    // Tiêm phụ thuộc (Dependency Injection)
    public OrderService(Database database) {
        this.database = database;
    }

    public void createOrder() {
        database.insertOrder(); // Thoải mái thay đổi Database mà không cần sửa 1 dòng code nghiệp vụ!
    }
}
```

## 🎨 Sơ đồ kiến trúc Đảo ngược phụ thuộc (DIP)

```
❌ THIẾT KẾ SAI (Phụ thuộc chặt chẽ - Tight Coupling)
┌──────────────────────┐
│  OrderService (Cao)  │ ───────────────► ┌─────────────────────────┐
└──────────────────────┘                  │ MySqlDatabase (Thấp)   │
                                          └─────────────────────────┘

 THIẾT KẾ ĐÚNG (Đảo ngược phụ thuộc - DIP)
┌──────────────────────┐
│  OrderService (Cao)  │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  <<Interface>>       │ ◄──────────────── ┌─────────────────────────┐
│    Database          │                   │ MySqlDatabase (Thấp)   │
└──────────────────────┘                   └─────────────────────────┘
                                                       ▲
                                                       │
                                           ┌─────────────────────────┐
                                           │ PostgresSqlDatabase     │
                                           └─────────────────────────┘
```

## 📊 Phân tích & So sánh Trade-offs của SOLID

### Lợi ích vs Chi phí khi áp dụng SOLID

| Tiêu chí | Viết code nhanh, bỏ qua SOLID (Ad-hoc Coding) | Áp dụng triệt để SOLID (SOLID Architecture) |
| :--- | :--- | :--- |
| **Tốc độ phát triển ban đầu** | **Siêu nhanh**: Chỉ cần viết vài dòng lệnh trực tiếp là xong tính năng. | **Chậm hơn**: Phải dành thời gian thiết kế Interface, phân tách file, thiết lập Dependency Injection. |
| **Công sức mở rộng hệ thống** | **Cực khó**: Càng phình to, việc sửa một chỗ có thể làm sập dây chuyền mười chỗ khác (Fragile Code). | **Dễ dàng**: Chỉ cần viết thêm Class mới hiện thực hóa Interface cũ, lắp ráp thông qua IoC Container. |
| **Khả năng viết Unit Test** | **Rất kém**: Do các lớp dính chặt vào nhau, không thể Mock/Stub các thành phần Database hay Network để cô lập Test. | **Tuyệt vời**: Mọi thành phần đều giao tiếp qua Interface nên dễ dàng Mock hoàn toàn dữ liệu để Test độc lập. |
| **Độ phức tạp tổng thể** | Thấp, ít số lượng file class. | Cao, số lượng file mã nguồn và cấu trúc phân tầng tăng lên đáng kể (Over-engineering risk). |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

### 1. Việc áp dụng SOLID quá mức (Over-engineering) có thể gây hại cho hệ thống như thế nào? Làm sao biết khi nào nên dừng lại?
* **Trả lời**: Đây là câu hỏi rất sâu sắc chứng minh kinh nghiệm thực chiến của Senior:
  * **Tác hại của việc quá đà**: 
    * Khiến hệ thống bị phân mảnh quá mức thành hàng ngàn Interface và Class siêu nhỏ vô nghĩa (ví dụ: viết một Interface chỉ có đúng 1 Class triển khai suốt đời). Điều này làm tăng độ trễ đọc code (Cognitive Load), khiến nhà phát triển mới cực kỳ khó nắm bắt mạch chạy luồng của chương trình.
    * Gây lãng phí tài nguyên CPU để JVM phân giải đa hình động (Dynamic dispatch) liên tục.
  * **Quy tắc dừng lại (KISS - Keep It Simple, Stupid)**:
    * Chỉ thiết lập trừu tượng hóa (Interface/Abstract) khi có thực tế từ **hai cấu trúc nghiệp vụ khác nhau trở lên** cùng sử dụng chung hành vi, hoặc khi có nhu cầu bắt buộc cần viết Unit Test chuyên sâu cho lớp đó.
    * Áp dụng **YAGNI (You Aren't Gonna Need It)**: Không viết các cấu trúc phòng hờ cho tương lai xa vời nếu hiện tại chưa có nhu cầu sử dụng thực tế.

### 2. Sự khác biệt giữa Dependency Inversion Principle (DIP) và Dependency Injection (DI) là gì?
* **Trả lời**: Đây là hai khái niệm thường bị hiểu nhầm là một:
  * **Dependency Inversion Principle (DIP)**: Là một **Nguyên lý thiết kế kiến trúc lý thuyết** (thuộc SOLID). Nó định hướng cách tổ chức mối quan hệ phụ thuộc giữa các mô-đun (Cao phụ thuộc trừu tượng, không phụ thuộc chi tiết).
  * **Dependency Injection (DI)**: Là một **Kỹ thuật hiện thực hóa thực tế (Pattern)**. DI là công cụ để thực thi nguyên lý DIP bằng cách "tiêm" (inject) các đối tượng phụ thuộc cụ thể vào trong lớp sử dụng thông qua Constructor, Setter hoặc Field thay vì để lớp đó tự khởi tạo `new`.

### 3. Nguyên lý Liskov Substitution Principle (LSP) liên quan như thế nào đến tính toàn vẹn của một API?
* **Trả lời**: 
  * LSP đảm bảo **Khế ước hành vi (Behavioral Contract)** của API được giữ vững. Khi Client gọi API của một lớp Cha, họ kỳ vọng một kết quả và một số hành vi nhất quán cụ thể (ví dụ: gọi hàm lưu file thì dữ liệu phải được ghi xuống).
  * Nếu lớp con vi phạm LSP bằng cách ném ra `UnsupportedOperationException` (như ví dụ đà điểu không biết bay) hoặc âm thầm không làm gì cả, lớp con đã phá vỡ hoàn toàn khế ước hoạt động mà lớp cha đã hứa với client. Điều này làm cho API của toàn hệ thống trở nên không đáng tin cậy và cực kỳ dễ đổ vỡ khi thay đổi đa hình.
