# synchronized quá rộng gây giảm throughput như thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Từ khóa `synchronized` bọc quá rộng (Lock Over-Granularity) gây giảm băng thông xử lý (Throughput) bằng cách **tuần tự hóa cưỡng bức (Forced Serialization)**. Khi một luồng chiếm giữ khóa Monitor trong thời gian dài (do bọc cả các tác vụ chậm như gọi DB, I/O, nén file), toàn bộ các luồng song song khác cố gắng lấy khóa đều bị đẩy vào trạng thái `BLOCKED`. Lúc này, hệ thống đa luồng đắt đỏ bị bóp nghẹt thành hệ thống đơn luồng chạy tuần tự, lãng phí hoàn toàn tài nguyên CPU đa nhân của máy chủ.
* **Các thảm họa thực chiến được giải quyết**:
    1. **Thảm họa treo cổ chai (Bottleneck Freeze)**: Đánh dấu từ khóa `synchronized` ở cấp độ toàn bộ phương thức xử lý đơn hàng (`public synchronized void processOrder()`). Khi lượng truy cập tăng cao (ví dụ: ngày hội Sale), luồng đầu tiên giữ khóa gọi DB chậm mất 200ms. Hàng nghìn luồng tiếp theo bị chặn cứng xếp hàng đợi, khiến throughput toàn hệ thống tụt thảm hại từ 5000 requests/giây xuống còn đúng 5 requests/giây.
* **Quyết định Senior**: Tối ưu hóa cực mịn khóa tranh chấp:
    1. **Thu hẹp phạm vi khóa (Lock Narrowing)**: Chỉ đồng bộ hóa đúng dòng code ghi dữ liệu vào biến chia sẻ (mất vài nano-giây), tuyệt đối đưa toàn bộ logic đọc, tính toán, và gọi I/O ra ngoài khối `synchronized`.
    2. **Chuyển sang cơ chế Lock-free / Read-Write Lock**: Sử dụng `ReentrantReadWriteLock` hoặc **`StampedLock`** để cho phép hàng nghìn luồng đọc đồng thời chạy song song không block nhau, chỉ block khi có luồng ghi dữ liệu.

## 🔍 Chi tiết bản chất thực chiến: Cơ chế hủy diệt Throughput của synchronized quá rộng

Senior Engineer phân tích tác hại của khóa thô dựa trên các thông số chuyển ngữ cảnh luồng và hiệu năng sử dụng CPU đa nhân.

### 1. Hiện tượng Tuần tự hóa cưỡng bức (Forced Serialization)
Khi bọc `synchronized` quá rộng hoặc đánh dấu ở method signature:
* JVM áp dụng cơ chế khóa độc quyền (Exclusive Lock). Chỉ có 1 luồng duy nhất được quyền đi vào thực thi tại một thời điểm.
* Các luồng khác lập tức bị đưa vào hàng đợi `Entry Set` của Monitor Object và chuyển sang trạng thái ngủ `BLOCKED`.
* **Hậu quả**: Thay vì tận dụng 16 hay 32 cores CPU chạy song song, hệ thống chỉ có đúng 1 core hoạt động xử lý tác vụ tuần tự từng luồng một, trong khi các core khác nhàn rỗi.

### 2. Chi phí chuyển ngữ cảnh luồng cực cao (Context Switching Overhead)
* Khi một luồng bị chuyển sang trạng thái `BLOCKED`, hệ điều hành (OS) phải thực hiện lưu lại trạng thái thanh ghi của luồng đó (Context Save) để nạp luồng khác vào CPU core.
* Khi luồng nắm giữ khóa kết thúc, OS lại phải đánh thức luồng đang ngủ dậy và nạp lại trạng thái (Context Restore).
* Thao tác Context Switch cực kỳ đắt đỏ, tiêu tốn hàng nghìn chu kỳ xử lý của CPU. Khi tranh chấp khóa thô xảy ra liên tục, CPU máy chủ sẽ bị vắt kiệt công suất chỉ để làm nhiệm vụ chuyển đổi luồng chạy, throughput thực tế xử lý nghiệp vụ giảm về gần như bằng 0.

### 3. Cấm kỵ: Đưa tác vụ I/O vào trong synchronized block
* Khi một luồng nắm giữ khóa và thực hiện gọi HTTP API ngoài mất 2 giây, luồng này sẽ ngủ chờ I/O mạng nhưng **vẫn tiếp tục nắm chặt khóa không nhả**.
* Toàn bộ hệ thống sẽ bị đóng băng vĩnh viễn trong 2 giây đó. Đây là cấm kỵ hàng đầu của lập trình đa luồng.

## 💻 Code thực chiến / Cấu hình thực tế: BAD vs GOOD

### ❌ BAD: Dùng synchronized cấp độ Method chứa tác vụ I/O chậm chạp
Đánh dấu `synchronized` ở toàn bộ phương thức, bên trong chứa câu lệnh truy vấn Database hoặc gọi API ngoài làm nghẽn toàn bộ luồng xếp hàng.

```java
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;

@Service
@Slf4j
public class BadSynchronizedService {

    private int activeUserCount = 0;

    // ❌ TỒI: synchronized thô bọc toàn bộ method chứa tác vụ chậm
    // Chỉ có 1 luồng được chạy. Luồng 2, 3 bị BLOCKED đứng đợi vĩnh viễn ở ngoài.
    public synchronized void registerUser(String username) {
        log.info("Bắt đầu đăng ký user: {}", username);
        
        try {
            // Tác vụ I/O gọi mạng / DB rất chậm
            Thread.sleep(100); 
        } catch (InterruptedException e) {}

        // Chỉ có dòng code này thực sự cần đồng bộ hoá để tránh data race!
        this.activeUserCount++; 
        
        log.info("Đăng ký thành công! Tổng số active user: {}", this.activeUserCount);
    }
}
```

### ✅ GOOD: Thu hẹp tối đa vùng khóa và áp dụng StampedLock hiệu năng cao
Senior đưa toàn bộ tác vụ chậm ra ngoài khóa, chỉ khóa đúng dòng code thay đổi trạng thái chia sẻ (Lock Narrowing). Hoặc tối ưu hóa đọc/ghi song song bằng `StampedLock` của Java 8.

* **Cách 1: Thu hẹp tối đa khối synchronized (Lock Narrowing)**:
```java
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;

@Service
@Slf4j
public class OptimizedLockNarrowingService {

    private int activeUserCount = 0;
    private final Object lock = new Object();

    public void registerUserSafe(String username) {
        // ✅ TỐT: Phần log và I/O DB chạy song song tự do không cần Lock
        log.info("Bắt đầu đăng ký user: {}", username);
        try {
            Thread.sleep(100); // DB call chạy song song
        } catch (InterruptedException e) {}

        // ✅ TỐT: Chỉ khóa đúng dòng code ghi dữ liệu nhạy cảm. 
        // Thời gian giữ khóa giảm từ 100ms xuống còn 5 nano-giây!
        synchronized (lock) {
            this.activeUserCount++;
        }
        
        log.info("Đăng ký thành công! Tổng số active user: {}", this.activeUserCount);
    }
}
```

---

* **Cách 2: Sử dụng StampedLock với cơ chế Đọc lạc quan (Optimistic Reading) cực nhanh**:
```java
import java.util.concurrent.locks.StampedLock;
import lombok.extern.slf4j.Slf4j;

@Slf4j
public class StampedLockMetricsTracker {
    private double balance = 100.0;
    
    // ✅ TỐT: StampedLock cung cấp khả năng Đọc lạc quan không dùng Lock vật lý
    private final StampedLock lock = new StampedLock();

    public void updateBalance(double amount) {
        long stamp = lock.writeLock(); // Khóa ghi độc quyền
        try {
            this.balance += amount;
        } finally {
            lock.unlockWrite(stamp); // Giải phóng khóa ghi
        }
    }

    public double getBalanceOptimistic() {
        // 1. Thử đọc lạc quan (Không hề dùng Lock, tốc độ cực nhanh)
        long stamp = lock.tryOptimisticRead();
        double currentBalance = this.balance;

        // 2. Kiểm tra xem trong lúc ta đang đọc, có luồng nào nhảy vào GHI hay không
        if (!lock.validate(stamp)) {
            log.warn("Phát hiện có luồng ghi đè trong lúc đọc! Chuyển sang Khóa đọc truyền thống (Pessimistic Read)");
            // 3. Nếu bị ghi đè, lùi lại sử dụng Khóa đọc thông thường để đảm bảo nhất quán
            stamp = lock.readLock();
            try {
                currentBalance = this.balance;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return currentBalance; // Trả về kết quả an toàn
    }
}
```

## 📊 Bảng so sánh các giải pháp nâng cao hiệu năng Khóa

| Đặc trưng | Synchronized truyền thống | ReentrantReadWriteLock | StampedLock (Java 8) |
| :--- | :--- | :--- | :--- |
| **Loại khóa** | Khóa độc quyền (Mutual Exclusion). | Khóa phân biệt Đọc/Ghi. | Khóa phân biệt Đọc/Ghi + Đọc lạc quan (Optimistic). |
| **Hiệu năng khi nhiều luồng Đọc** | Thấp (Luồng đọc cũng block luồng đọc khác). | Cao (Hàng nghìn luồng đọc song song thoải mái). | **Cực kỳ cao** (Luồng đọc hoàn toàn không dùng lock vật lý nếu không có ghi). |
| **Tính năng bổ sung** | Tự động giải phóng khi ném exception. | Hỗ trợ Reentrancy (Khóa lặp lại), hỗ trợ Fair lock. | Hỗ trợ chuyển đổi khóa động (Upgrade to write lock). |
| **Khả năng bị Starvation** | Thấp. | Cao (Luồng ghi có thể bị bỏ đói nếu luồng đọc truy cập liên tục). | Thấp (Đọc lạc quan không chặn luồng ghi). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Nâng cấp khóa ngầm định gây Deadlock trong ReentrantReadWriteLock"
* **Vấn đề nguy hiểm**: Nhiều lập trình viên cố gắng nâng cấp khóa đọc lên khóa ghi bên trong cùng một luồng khi dùng `ReentrantReadWriteLock`:
  ```java
  readLock.lock();
  try {
      if (needToWrite) {
          writeLock.lock(); // ❌ TỒI: Gây DEADLOCK lập tức!
      }
  } finally {
      readLock.unlock();
  }
  ```
* **Bản chất**: Luồng đang giữ khóa đọc và yêu cầu thêm khóa ghi. Nhưng khóa ghi yêu cầu không có luồng nào đang giữ khóa đọc. Vòng lặp chờ đợi lẫn nhau xảy ra trên chính một luồng, khóa cứng ứng dụng.
* **Khắc phục**: Phải giải phóng khóa đọc trước khi yêu cầu khóa ghi, hoặc chuyển sang dùng **`StampedLock`** hỗ trợ API chuyển đổi khóa an toàn: `lock.tryConvertToWriteLock(stamp)`.

### 2. Câu hỏi đào sâu từ interviewer

* **Q1: Khái niệm "Lock Splitting" (Chia nhỏ khóa) và "Lock Striping" (Phân đoạn khóa) giúp tối ưu hóa throughput của synchronized như thế nào? Cho ví dụ thực tế.**
  * *Trả lời*: Đây là hai kỹ thuật nâng cao để giảm bớt tranh chấp trên một khóa duy nhất:
    1. **Lock Splitting (Chia nhỏ khóa)**: Nếu một class có 2 biến instance độc lập (ví dụ: `activeUsers` và `totalOrders`), thay vì dùng chung 1 khóa `synchronized(this)`, ta tạo ra 2 đối tượng lock riêng biệt: `Object userLock = new Object()` và `Object orderLock = new Object()`. Nhờ đó, luồng cập nhật order không làm block luồng cập nhật user.
    2. **Lock Striping (Phân đoạn khóa)**: Chia nhỏ một cấu trúc dữ liệu lớn thành nhiều phân đoạn nhỏ độc lập, mỗi phân đoạn có một lock riêng. Ví dụ điển hình là `ConcurrentHashMap` phiên bản cũ chia bảng băm thành 16 phân đoạn. Luồng ghi vào bucket 1 chỉ lock phân đoạn 1, luồng ghi vào bucket 5 ghi song song hoàn toàn vì thuộc phân đoạn khác, tăng throughput hệ thống gấp 16 lần.

* **Q2: Tại sao JVM tự động tối ưu hóa từ khóa `synchronized` bằng kỹ thuật Biased Locking (Khóa thiên vị) và Lock Coarsening (Gộp khóa)?**
  * *Trả lời*: JVM rất thông minh khi tối ưu hóa synchronized lúc runtime để giảm thiểu cost:
    1. **Biased Locking (Khóa thiên vị)**: JVM nhận thấy trong thực tế $80\%$ trường hợp chỉ có duy nhất 1 luồng truy cập vào khối synchronized đó suốt thời gian dài. JVM sẽ "thiên vị" gán trực tiếp khóa cho luồng đó. Ở các lần vào tiếp theo, luồng này đi thẳng vào thực thi mà không tốn bất kỳ chi phí thao tác CPU atomic lock nào.
    2. **Lock Coarsening (Gộp khóa)**: Nếu JVM phát hiện ra một chuỗi các khối synchronized liên tiếp nhau trên cùng một đối tượng (ví dụ: gọi `synchronized(lock)` liên tục trong vòng lặp), JVM sẽ tự động "gộp" chúng lại thành một khối synchronized duy nhất bọc ngoài toàn bộ vòng lặp, nhằm triệt tiêu overhead giải phóng và xin lại khóa liên tục.
