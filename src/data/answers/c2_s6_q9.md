# Race condition chỉ xảy ra vài lần mỗi ngày. Bạn xử lý thế nào?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Lỗi tương tranh bất định (Flaky Race Condition) xảy ra vài lần mỗi ngày là do **khoảng thời gian xen kẽ luồng cực hẹp (Microsecond Interleaving Window)**. Lỗi chỉ xuất hiện khi hai hoặc nhiều luồng cùng đập vào một vị trí nhạy cảm trong code tại đúng một phần triệu giây (Microsecond). Đây là dạng **Heisenbug** điển hình: Một lỗi sẽ lập tức biến mất hoặc thay đổi hành vi khi ta cố tình can thiệp bằng cách thêm log debug thô sơ (vì ghi log ra đĩa rất chậm, vô tình tạo ra khoảng nghỉ làm lệch nhịp tương tranh).
* **Các thảm họa thực chiến được giải quyết**:
    1. **Thảm họa "Mua trùng voucher" (Double Claiming)**: Hệ thống tặng 1 mã giảm giá duy nhất cho khách hàng. Hàng triệu user bấm nhận cùng lúc. Do dính race condition ngẫu nhiên ở 0.001% request, một khách hàng có thể bấm liên tục cực nhanh và nhận được 2 voucher trùng nhau, gây thất thoát trực tiếp ngân sách khuyến mãi.
* **Quyết định Senior**: Triển khai chiến lược 4 bước:
    1. **Bẫy lỗi thụ động**: Tuyệt đối không thêm log debug. Giữ nguyên code, bổ sung các metric cảnh báo sớm hoặc dùng cơ chế ghi nhận tập trung (Correlation ID + Unique Request Hash).
    2. **Tái hiện cưỡng bức**: Viết kịch bản kiểm thử tải (Stress Test bằng k6 hoặc JMeter) kết hợp tạo độ trễ nhân tạo (Chaos Injection) để bắt luồng xung đột tại local/staging.
    3. **Khóa chốt cấp Database**: Sử dụng **Optimistic Locking (`@Version`)** cho hệ thống tải cao, hoặc **Pessimistic Locking (`SELECT FOR UPDATE`)** / **Distributed Lock (Redis)** cho các nghiệp vụ thanh toán, chuyển tiền tài chính.

## 🔍 Chi tiết bản chất thực chiến: Quy trình xử lý Heisenbug - Lỗi đa luồng ẩn nấp

Lỗi chỉ xảy ra vài lần một ngày là nỗi ám ảnh của các kỹ sư trung cấp vì họ luôn cố gắng tái hiện nó bằng tay. Senior chẩn đoán bằng tư duy phân tích toán học và cấu trúc dữ liệu.

### 1. Tại sao Heisenbug lại biến mất khi thêm Log?
* **Cơ chế**: Thao tác in log `log.info(...)` thực chất là hoạt động ghi dữ liệu bất đồng bộ hoặc đồng bộ ra file trên đĩa cứng (Disk I/O) hoặc console. Hoạt động này tiêu tốn từ vài micro-giây đến vài mili-giây.
* **Tác hại**: Việc chèn thêm dòng log ngay trước dòng code xảy ra race condition đóng vai trò như một **rào cản thời gian nhân tạo (Barrier)**. Nó làm chậm luồng này lại, khiến khoảng thời gian tương tranh của hai luồng bị lệch pha hoàn toàn, làm lỗi biến mất một cách kỳ bí trong khi test debug, nhưng lại bùng phát trở lại trên Production khi chịu tải thực.

### 2. Các phương án bẫy và tái hiện lỗi đa luồng (Bohrbug vs Heisenbug)
* **Bẫy bằng Kiểm thử tải cưỡng bức**:
  * Senior sử dụng kịch bản stress test đa luồng cao (ví dụ: dùng k6 với 1000 Virtual Users đồng thời gọi cùng một endpoint thanh toán cho cùng một User ID).
  * Kết hợp với việc tiêm mã trễ ngầm (`Thread.yield()` hoặc sleep ngẫu nhiên từ 1 - 5 nano-giây) ở môi trường Staging để mở rộng khoảng thời gian tương tranh, ép buộc lỗi xuất hiện 100%.
* **Sử dụng Công cụ Phân tích tĩnh**:
  * Sử dụng các bộ quét code chuyên sâu như **SpotBugs** kết hợp plugin **JCIP (Java Concurrency in Practice)** để quét toàn bộ mã nguồn tìm các mẫu phản cấu trúc (Anti-pattern) của biến chia sẻ hoặc các trường hợp gọi khóa không an toàn.

## 💻 Code thực chiến / Cấu hình thực tế: BAD vs GOOD

### ❌ BAD: Phương thức rút tiền nghiệp vụ bị dính lỗi tương tranh Check-then-Act
Hàm thực hiện đọc dữ liệu ra kiểm tra (Check), sau đó mới cập nhật (Act). Dưới môi trường đa luồng, hai luồng cùng đọc tại một thời điểm sẽ xác thực thành công và cùng thực hiện rút tiền, làm số dư ví bị âm hoặc mất mát tiền.

```java
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Slf4j
public class BadWalletService {

    // Giả lập Repository giả định
    private double balance = 100.0;

    @Transactional
    public void withdraw(double amount) {
        // ❌ TỒI: Cơ chế Check-then-Act không được đồng bộ hoá.
        // Luồng 1 đọc balance = 100. Luồng 2 đọc balance = 100.
        // Cả hai cùng xác thực lượng tiền OK và cùng trừ tiền.
        if (this.balance >= amount) {
            try {
                // Giả lập I/O database mất 20ms
                Thread.sleep(20); 
            } catch (InterruptedException e) {}
            
            this.balance -= amount;
            log.info("Rút tiền thành công! Số dư còn lại: {}", this.balance);
        } else {
            log.error("Giao dịch thất bại: Không đủ số dư!");
        }
    }
}
```

### ✅ GOOD: Áp dụng Optimistic Locking (Khóa lạc quan `@Version`) giải quyết triệt để
Senior sử dụng cơ chế Khóa lạc quan `@Version` thông qua Hibernate JPA. Khi cập nhật dữ liệu, JPA sẽ tự động chèn phiên bản vào câu lệnh SQL: `WHERE id = ? AND version = ?`. Nếu luồng khác đã cập nhật trước đó, phiên bản sẽ bị tăng lên, câu lệnh cập nhật của luồng sau sẽ trả về số dòng cập nhật là 0, JPA ném lỗi `OptimisticLockException` giúp ta bắt lỗi và retry an toàn.

* **1. Entity định nghĩa phiên bản**:
```java
import jakarta.persistence.*;
import lombok.Getter;
import lombok.Setter;

@Entity
@Table(name = "wallets")
@Getter
@Setter
public class Wallet {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private double balance;

    // ✅ TỐT: Version giúp ngăn chặn 100% race condition ghi đè mất dữ liệu ở Database
    @Version
    private Long version;
}
```

---

* **2. Service xử lý giao dịch an toàn với cơ chế Retry**:
```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import lombok.extern.slf4j.Slf4j;

@Service
@Slf4j
public class SafeWalletService {

    @Autowired
    private WalletRepository walletRepository;

    @Transactional
    public void withdrawSafe(Long walletId, double amount) {
        int maxRetries = 3;
        int attempt = 0;

        while (attempt < maxRetries) {
            try {
                // 1. Đọc dữ liệu lên kèm theo version hiện tại (ví dụ: version = 1)
                Wallet wallet = walletRepository.findById(walletId)
                        .orElseThrow(() -> new IllegalArgumentException("Không tìm thấy ví!"));

                if (wallet.getBalance() >= amount) {
                    wallet.setBalance(wallet.getBalance() - amount);
                    
                    // 2. Lưu lại. Hibernate tự động gọi: 
                    // UPDATE wallets SET balance = balance - ?, version = version + 1 WHERE id = ? AND version = 1;
                    walletRepository.save(wallet); 
                    log.info("Giao dịch thành công!");
                    return; // Thoát hàm khi giao dịch thành công
                } else {
                    throw new IllegalStateException("Không đủ số dư ví!");
                }
            } catch (ObjectOptimisticLockingFailureException e) {
                // ✅ Bắt lỗi ghi đè đồng thời do luồng khác cập nhật trước
                attempt++;
                log.warn("Phát hiện lỗi tương tranh! Tiến hành thử lại (Retry) lần: {}", attempt);
                if (attempt >= maxRetries) {
                    log.error("Giao dịch thất bại sau {} lần thử lại do tải quá cao!", maxRetries);
                    throw new RuntimeException("Hệ thống bận, vui lòng thử lại sau.");
                }
                
                // Ngủ ngẫu nhiên một chút trước khi thử lại để lệch pha nhịp (Backoff)
                try {
                    Thread.sleep((long) (Math.random() * 30 + 10));
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        }
    }
}
```

## 📊 Bảng so sánh 3 vũ khí xử lý Race Condition cấp độ Database/Hệ thống

| Tiêu chí | Khóa lạc quan (Optimistic Lock) | Khóa bi quan (Pessimistic Lock) | Distributed Lock (Redis/Redlock) |
| :--- | :--- | :--- | :--- |
| **Cơ chế cốt lõi** | Kiểm tra thuộc tính phiên bản `@Version` trước khi ghi đè. | Dùng cơ chế khóa dòng của DB: `SELECT FOR UPDATE` để chặn luồng khác đọc/ghi. | Dành cho hệ thống phân tán, mượn khóa chung từ Redis (`SETNX`) trước khi xử lý. |
| **Hiệu năng hệ thống**| **Cực cao** (Không tốn chi phí khóa dòng dưới DB, không block các câu lệnh read). | **Thấp** (Block toàn bộ các luồng đọc/ghi khác trên cùng dòng dữ liệu, dễ gây nghẽn DB). | **Trung bình - Cao** (Tốn thêm I/O mạng gọi sang Redis để check/release lock). |
| **Khả năng dính Deadlock**| **Không bao giờ**. | **Rất cao** nếu các luồng cập nhật nhiều bảng lồng nhau ngược thứ tự. | Rất thấp (Nhờ cơ chế tự động giải phóng khóa bằng TTL - Time to Live). |
| **Use case phù hợp** | Hệ thống có lượng đọc nhiều, ghi đồng thời trung bình (ví dụ: cập nhật hồ sơ, ví thông thường). | Hệ thống thanh toán lõi, tài chính, giao dịch nhạy cảm bắt buộc tính chính xác cao. | Xử lý đa máy chủ (Distributed), tranh chấp tài nguyên chung cấp Cluster (ví dụ: mua vé xem phim). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Lỗi tương tranh câm lặng khi sử dụng biến Static không an toàn"
* **Vấn đề**: Nhiều kỹ sư sử dụng biến static (như `private static int counter = 0;`) để làm bộ đếm ID cục bộ hoặc lưu trữ thông tin cấu hình thay đổi được.
* **Hậu quả**: Thao tác `counter++` thực chất là 3 lệnh mã máy: Đọc giá trị $\to$ Tăng giá trị $\to$ Ghi lại giá trị. Dưới môi trường đa luồng, lỗi ghi đè xảy ra ngẫu nhiên làm bộ đếm bị nhảy sai lệch hoặc trùng lặp ID, tạo ra những lỗi dữ liệu cực kỳ khó hiểu trên Production.
* **Khắc phục**: Thay thế biến static nguyên thủy bằng các lớp nguyên tử được bảo vệ bằng CAS ở cấp độ phần cứng: `private static final AtomicInteger counter = new AtomicInteger(0);` và gọi hàm `counter.incrementAndGet()`.

### 2. Câu hỏi đào sâu từ interviewer

* **Q1: Phân biệt sự khác nhau bản chất giữa lỗi Race Condition (Điều kiện tương tranh) và lỗi Data Race (Tranh chấp dữ liệu)?**
  * *Trả lời*: Đây là hai khái niệm thường bị nhầm lẫn trong lập trình đa luồng:
    1. **Data Race**: Xảy ra khi hai luồng đồng thời truy cập vào cùng một ô nhớ mà không có rào cản đồng bộ, và có ít nhất một luồng thực hiện thao tác ghi. Data Race dẫn đến hiện tượng dữ liệu không nhất quán (JMM reordering/visibility issues).
    2. **Race Condition**: Là lỗi logic nghiệp vụ cấp độ cao hơn. Nó xảy ra khi tính chính xác của chương trình phụ thuộc vào **thứ tự thực thi ngẫu nhiên** của các luồng. Ngay cả khi ta dùng các biến thread-safe (không bị data race), lỗi race condition vẫn có thể xảy ra ở logic Check-then-Act nếu ta không gom các thao tác kiểm tra và thực thi vào một khối nguyên tử duy nhất (Atomic Block).

* **Q2: Tại sao việc sử dụng cơ chế Distributed Lock bằng Redis (Redisson/SETNX) lại bắt buộc phải đi kèm với thông số TTL (Time-To-Live) cho khóa? Điều gì xảy ra nếu tiến trình Java bị crash ngay sau khi lấy được khóa nhưng chưa kịp nhả khóa?**
  * *Trả lời*: 
    * Khi mượn khóa từ Redis, ta thực hiện ghi một key duy nhất lên Redis đại diện cho khóa đó.
    * **Bắt buộc phải có TTL**: Để chống treo cứng hệ thống. Nếu luồng lấy khóa thành công nhưng ngay lập tức máy chủ bị sập nguồn đột ngột (hoặc tiến trình JVM bị crash OOM), code giải phóng khóa (`finally { redis.delete(lockKey) }`) sẽ không bao giờ được thực hiện. Nếu không có TTL (thời gian tự hủy), khóa đó sẽ tồn tại vĩnh viễn trên Redis, và toàn bộ hệ thống phân tán sẽ bị khóa cứng vĩnh viễn tính năng nghiệp vụ đó.
    * **Giải pháp tự động**: Bằng cách gán TTL (ví dụ: 10 giây), nếu sau 10 giây máy chủ không hồi đáp hoặc không tự động gia hạn khóa, Redis sẽ tự hủy key đó để giải thoát cho các instance khác tiếp tục tranh chấp khóa an toàn.
