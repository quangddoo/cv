# Kiến trúc Lục giác là gì? (Hexagonal Architecture / Ports & Adapters)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: **Kiến trúc Lục giác** (còn gọi là **Ports & Adapters**) là một mẫu kiến trúc phần mềm hướng tới việc **tách biệt hoàn toàn Business Logic cốt lõi (Domain Core)** khỏi các chi tiết kỹ thuật hạ tầng (Database, Web, API bên thứ ba, Message Broker).
* **Cấu trúc cốt lõi**:
  * **Domain Core**: Nằm ở trung tâm lục giác, chỉ chứa thuần nghiệp vụ (Entities, Use Cases) và không phụ thuộc vào bất kỳ thư viện hay framework bên ngoài nào (kể cả Spring).
  * **Ports (Cổng)**: Các Interface trừu tượng khai báo ở ranh giới Domain Core, định nghĩa cách Core giao tiếp với thế giới bên ngoài.
  * **Adapters (Bộ chuyển đổi)**: Lớp triển khai vật lý bên ngoài (Web Controller, JPA Repository, RabbitMQ Sender) kết nối vào Core thông qua các Ports tương ứng.
* **Giá trị cốt lõi**: Giảm thiểu tối đa sự phụ thuộc kỹ thuật, dễ viết Unit Test cho Core không cần database, và cực kỳ linh hoạt khi thay đổi công nghệ hạ tầng.

## 🔍 Phân tích cấu trúc: Khái niệm Lục giác & Cơ chế hoạt động

Kiến trúc Lục giác biểu diễn hệ thống dưới dạng một hình lục giác với các phân tầng từ trong ra ngoài:

```
                  ┌───────────────────────────────┐
                  │       TẦNG HẠ TẦNG (INFRA)    │
                  │  ┌─────────────────────────┐  │
                  │  │     Primary Adapters    │  │ (REST, CLI, GraphQL)
                  │  └────────────┬────────────┘  │
                  │               │ Gọi qua
                  │  ┌────────────▼────────────┐  │
                  │  │    Inbound/Primary Port │  │ (Interface Use Cases)
                  │  └────────────┬────────────┘  │
                  │               │ Triển khai
                  │  ┌────────────▼────────────┐  │
                  │  │       DOMAIN CORE       │  │ (Pure Business Logic)
                  │  └────────────┬────────────┘  │
                  │               │ Gọi qua
                  │  ┌────────────▼────────────┐  │
                  │  │   Outbound/SecondaryPort│  │ (Interface Repository)
                  │  └────────────┬────────────┘  │
                  │               │ Triển khai
                  │  ┌────────────▼────────────┐  │
                  │  │    Secondary Adapters   │  │ (JPA, Redis, Kafka)
                  │  └─────────────────────────┘  │
                  └───────────────────────────────┘
```

### 1. Phân biệt Inbound Port vs Outbound Port
* **Inbound Ports (Primary - Cổng vào)**:
  * **Vai trò**: Định nghĩa các hành động/nghiệp vụ mà thế giới bên ngoài có thể yêu cầu Domain Core thực hiện.
  * **Cơ chế**: Thường là các Interface nghiệp vụ (ví dụ: `CreateOrderUseCase`).
  * **Lớp tương tác**: **Primary Adapters** (như Spring REST Controller) sẽ gọi vào Inbound Port này.
* **Outbound Ports (Secondary - Cổng ra)**:
  * **Vai trò**: Định nghĩa các hành động mà Domain Core cần thế giới bên ngoài cung cấp để hoàn thành nghiệp vụ.
  * **Cơ chế**: Thường là các Interface cổng kết nối dữ liệu (ví dụ: `OrderRepository`, `SmsSender`).
  * **Lớp tương tác**: **Secondary Adapters** (như JpaOrderRepository) sẽ triển khai (implement) Outbound Port này.

## 💻 Code Example: Cấu trúc thư mục & Triển khai Java sạch

Dưới đây là sơ đồ tổ chức thư mục của một Service tuân thủ nghiêm ngặt Kiến trúc Lục giác:

```
com.company.order
├── domain (Không import bất kỳ thư viện Spring hay JPA nào)
│   ├── model
│   │   └── Order.java (Domain Entity)
│   └── port
│       ├── inbound
│       │   └── CreateOrderUseCase.java (Inbound Port)
│       └── outbound
│           └── OrderRepositoryPort.java (Outbound Port)
│   └── service
│       └── OrderService.java (Core Service triển khai Inbound Port)
└── infrastructure (Tầng chứa mọi cấu hình Framework & Database)
    └── adapter
        ├── inbound
        │   └── OrderRestController.java (Primary Adapter)
        └── outbound
            └── JpaOrderRepositoryAdapter.java (Secondary Adapter)
```

### Triển khai mã nguồn:

#### 1. Lớp DOMAIN CORE (Không dính Spring/JPA)
```java
// domain.port.outbound.OrderRepositoryPort.java (Outbound Port)
public interface OrderRepositoryPort {
    void save(Order order);
}

// domain.port.inbound.CreateOrderUseCase.java (Inbound Port)
public interface CreateOrderUseCase {
    void create(String productId, int quantity);
}

// domain.service.OrderService.java (Domain Service Core)
public class OrderService implements CreateOrderUseCase {
    private final OrderRepositoryPort repositoryPort; // Chỉ giao tiếp qua Port

    public OrderService(OrderRepositoryPort repositoryPort) {
        this.repositoryPort = repositoryPort;
    }

    @Override
    public void create(String productId, int quantity) {
        // Thực thi business logic thuần nghiệp vụ
        Order order = new Order(productId, quantity);
        order.calculateDiscount();
        
        repositoryPort.save(order); // Ủy quyền cho Outbound Port
    }
}
```

#### 2. Lớp INFRASTRUCTURE ADAPTER (Chứa chi tiết kỹ thuật)
```java
// infrastructure.adapter.inbound.OrderRestController.java (Primary Adapter)
@RestController
@RequestMapping("/orders")
public class OrderRestController {
    private final CreateOrderUseCase createOrderUseCase; // Gọi qua Inbound Port

    public OrderRestController(CreateOrderUseCase createOrderUseCase) {
        this.createOrderUseCase = createOrderUseCase;
    }

    @PostMapping
    public ResponseEntity<Void> createOrder(@RequestParam String productId, @RequestParam int qty) {
        createOrderUseCase.create(productId, qty);
        return ResponseEntity.ok().build();
    }
}

// infrastructure.adapter.outbound.JpaOrderRepositoryAdapter.java (Secondary Adapter)
@Component
public class JpaOrderRepositoryAdapter implements OrderRepositoryPort {
    private final SpringDataJpaOrderRepository jpaRepo; // Chi tiết JPA thực tế

    public JpaOrderRepositoryAdapter(SpringDataJpaOrderRepository jpaRepo) {
        this.jpaRepo = jpaRepo;
    }

    @Override
    public void save(Order order) {
        // Chuyển đổi từ Domain Model sang JPA Entity trước khi ghi xuống
        OrderEntity entity = OrderEntity.fromDomain(order);
        jpaRepo.save(entity);
    }
}
```

## 📊 Phân tích Trade-offs: Kiến trúc 3 lớp truyền thống vs Kiến trúc Lục giác

| Tiêu chí | Kiến trúc 3 lớp truyền thống (3-Tier Layered) | Kiến trúc Lục giác (Ports & Adapters) |
| :--- | :--- | :--- |
| **Hướng phụ thuộc** | Tầng Service phụ thuộc trực tiếp vào tầng Data Access và thư viện JPA Entity. | **Đảo ngược hoàn toàn**: Mọi tầng ngoài phụ thuộc hướng vào lõi Domain Core ở trung tâm. |
| **Viết Unit Test** | Khó khăn. Dù có Mock, các JPA Entity vẫn bị dính vào framework gây rườm rà. | **Hoàn hảo**: Có thể test toàn bộ logic cốt lõi bằng Plain Unit Test (JUnit thuần) không cần Mockito. |
| **Tốc độ thay thế công nghệ**| **Khó khăn**: Chuyển từ SQL sang NoSQL đòi hỏi viết lại rất nhiều code nghiệp vụ. | **Dễ dàng**: Chỉ cần viết 1 Adapter mới, lắp vào Port cũ, code Domain Service giữ nguyên 100%. |
| **Dung lượng boilerplate code**| **Thấp**: Rất ít class chuyển đổi (Mappers). | **Cao**: Đòi hỏi nhiều class chuyển đổi model (Domain Model <-> JPA Entity <-> DTO). |
| **Learning Curve (Học hỏi)** | Dễ hiểu, cực kỳ quen thuộc với hầu hết lập trình viên. | Khó làm quen ban đầu do cấu trúc phân tầng và phân chia package khắt khe. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Nếu Domain Service hoàn toàn độc lập với Spring Framework (để giữ lõi Domain sạch sẽ), làm sao ta có thể sử dụng tính năng Dependency Injection (`@Autowired` / Spring Context) để tiêm các Outbound Ports vào Domain Service được?
* **Trả lời**: Đây là câu hỏi thực chiến Spring xuất sắc:
  * Nếu ta không đánh dấu `@Service` hay `@Component` của Spring lên lớp `OrderService` (vì tầng Domain Core cấm import thư viện Spring), Spring Container sẽ không tự động nhận diện và quản lý `OrderService` dưới dạng Bean.
  * **Giải pháp**: Sử dụng một **Configuration Class** nằm ở tầng Infrastructure để khai báo thủ công các Bean của Domain Service:
    ```java
    @Configuration
    public class BeanConfiguration {
        // Spring tự động tiêm JpaOrderRepositoryAdapter vì nó triển khai OrderRepositoryPort
        @Bean
        public CreateOrderUseCase createOrderUseCase(OrderRepositoryPort repositoryPort) {
            return new OrderService(repositoryPort); // Khởi tạo thuần túy bằng code Java!
        }
    }
    ```
    *Cách này hoàn hảo vì tầng Domain hoàn toàn sạch bóng thư viện Spring, trong khi tầng Infrastructure vẫn tận dụng trọn vẹn sức mạnh DI của Spring.*

### 2. Sự khác biệt giữa Ports & Adapters (Hexagonal) và Clean Architecture của Uncle Bob là gì? Chúng trông có vẻ giống nhau!
* **Trả lời**: 
  * **Ports & Adapters** là tiền thân của **Clean Architecture**. Ports & Adapters chỉ tập trung giải quyết bài toán: **Tách biệt Core nghiệp vụ ra khỏi thế giới bên ngoài (Hạ tầng)** thông qua cơ chế phân tách ranh giới cổng.
  * **Clean Architecture** (của Robert C. Martin) kế thừa trọn vẹn Ports & Adapters nhưng cụ thể hóa sâu hơn nữa cấu trúc phân cấp bên trong của phần Core: chia Core thành tầng **Entities** (Enterprise business rules) độc lập với tầng **Use Cases / Interactors** (Application business rules). Clean Architecture áp dụng mô hình lục giác lồng nhau dạng các vòng tròn đồng tâm.
