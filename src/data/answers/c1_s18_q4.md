# Phân biệt Factory Method và Abstract Factory (Factory Method vs Abstract Factory Pattern)

## ⚡ Tóm tắt ngắn (30s)
* **Sự khác biệt cốt lõi**:
  * **Factory Method**: Tập trung vào việc tạo ra **một sản phẩm duy nhất (Single Product)**. Nó đạt được sự trừu tượng hóa bằng cách sử dụng **tính kế thừa (Inheritance)** – định nghĩa một phương thức tạo lập trong lớp cha và để các lớp con ghi đè (override) quyết định đối tượng cụ thể nào được sinh ra.
  * **Abstract Factory**: Tập trung vào việc tạo ra **một họ các sản phẩm liên quan/phụ thuộc lẫn nhau (Family of Related/Dependent Products)**. Nó đạt được sự trừu tượng hóa bằng cách sử dụng **tính đóng gói đối tượng (Object Composition)** – định nghĩa một Interface chứa nhiều phương thức nhà máy (Factory Methods) khác nhau, mỗi phương thức chịu trách nhiệm tạo ra một sản phẩm trong hệ sinh thái đó.
* **Cú pháp ghi nhớ ngắn**: 
  * *Factory Method = "Một phương thức"* (để tạo một đối tượng).
  * *Abstract Factory = "Một đối tượng chứa nhiều phương thức"* (để tạo một họ đối tượng).

## 🔍 Phân tích chuyên sâu & Mô hình hóa ý tưởng

Để tránh nhầm lẫn, trước hết cần làm rõ **Simple Factory** (không phải là một Design Pattern chính thức của GoF mà chỉ là thói quen lập trình dùng `switch-case` trong một hàm static) khác hoàn toàn với **Factory Method** và **Abstract Factory**.

### 1. Factory Method (Trừu tượng hóa một phương thức)
* **Cơ chế**: Khai báo phương thức `createProduct()` trong một lớp `Creator` trừu tượng. Lớp con của `Creator` sẽ kế thừa và hiện thực hóa phương thức này để trả về lớp con tương ứng của `Product`.
* **Ví dụ**: 
  * Lớp cha `DocumentCreator` định nghĩa hàm `createDocument()`.
  * Lớp con `PdfDocumentCreator` trả về `PdfDocument`.
  * Lớp con `WordDocumentCreator` trả về `WordDocument`.

### 2. Abstract Factory (Trừu tượng hóa cả một nhà máy lớn)
* **Cơ chế**: Định nghĩa một interface `UIFactory` lớn. Interface này chứa các phương thức như `createButton()`, `createCheckbox()`, `createTextBox()`. Một họ sản phẩm phải luôn đồng nhất về mặt chủ đề thiết kế (Theme).
* **Ví dụ**:
  * `MacUIFactory` bắt buộc phải trả về một bộ gồm: `MacButton`, `MacCheckbox`, `MacTextBox`.
  * `WindowsUIFactory` bắt buộc phải trả về một bộ gồm: `WinButton`, `WinCheckbox`, `WinTextBox`.
  * Người dùng (Client) chỉ gọi `factory.createButton()`, đảm bảo không có tình trạng nút bấm kiểu macOS hiển thị trên khung cửa sổ của Windows (mất tính nhất quán).

## 💻 Code Example: Thiết kế hệ thống UI Components (Button & Checkbox)

Dưới đây là cách mô hình hóa hệ thống nút bấm và hộp kiểm trên đa nền tảng bằng Java:

### 1. Khai báo các Interface của Sản phẩm (Products)
```java
public interface Button { void paint(); }
public interface Checkbox { void render(); }

// Dòng sản phẩm Windows
public class WindowsButton implements Button {
    public void paint() { System.out.println("Vẽ nút bấm Windows màu xanh lam."); }
}
public class WindowsCheckbox implements Checkbox {
    public void render() { System.out.println("Vẽ hộp kiểm Windows dạng vuông."); }
}

// Dòng sản phẩm MacOS
public class MacButton implements Button {
    public void paint() { System.out.println("Vẽ nút bấm MacOS bo tròn bóng bẩy."); }
}
public class MacCheckbox implements Checkbox {
    public void render() { System.out.println("Vẽ hộp kiểm MacOS màu xám tro."); }
}
```

### 2. Triển khai bằng Factory Method (Tạo 1 sản phẩm đơn lẻ)
Sử dụng tính kế thừa để tạo ra loại Button phù hợp:
```java
// Creator trừu tượng
public abstract class ButtonStore {
    // Factory Method
    protected abstract Button createButton();

    public void renderScreen() {
        Button btn = createButton();
        btn.paint(); // Thực hiện nghiệp vụ vẽ màn hình
    }
}

// Lớp con quyết định sản phẩm cụ thể
public class WindowsButtonStore extends ButtonStore {
    @Override
    protected Button createButton() { return new WindowsButton(); }
}

public class MacButtonStore extends ButtonStore {
    @Override
    protected Button createButton() { return new MacButton(); }
}
```

### 3. Triển khai bằng Abstract Factory (Tạo một họ sản phẩm nhất quán)
Sử dụng Composition để tạo ra cả bộ Button & Checkbox ăn khớp với nhau:
```java
// Abstract Factory Interface
public interface UIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

// Windows Factory cụ thể
public class WindowsUIFactory implements UIFactory {
    @Override
    public Button createButton() { return new WindowsButton(); }
    @Override
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}

// MacOS Factory cụ thể
public class MacUIFactory implements UIFactory {
    @Override
    public Button createButton() { return new MacButton(); }
    @Override
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

// Lớp Client sử dụng bộ sản phẩm đồng bộ thông qua composition
public class Application {
    private final Button button;
    private final Checkbox checkbox;

    public Application(UIFactory factory) {
        // Trừu tượng hóa hoàn toàn chi tiết khởi tạo đối tượng cụ thể
        this.button = factory.createButton();
        this.checkbox = factory.createCheckbox();
    }

    public void paintUI() {
        button.paint();
        checkbox.render();
    }
}
```

## 📊 Phân tích Trade-offs: So sánh chi tiết

| Tiêu chí | Factory Method | Abstract Factory |
| :--- | :--- | :--- |
| **Mục tiêu chế tạo** | Tạo ra **một sản phẩm duy nhất** (Ví dụ: Chỉ tạo Button). | Tạo ra **cả một bộ sưu tập / họ sản phẩm** liên quan (Ví dụ: Button + Checkbox + Input). |
| **Mức độ trừu tượng** | Thấp hơn. Tập trung vào lớp con của chính nó để quyết định. | Cao hơn. Tạo ra một thực thể Factory làm nhiệm vụ phân phối cả hệ sinh thái sản phẩm. |
| **Cơ chế hoạt động** | **Kế thừa (Inheritance)**: Định nghĩa lại phương thức của lớp cha. | **Đóng gói (Composition)**: Ủy quyền cho đối tượng Factory được truyền vào. |
| **Khi muốn thêm Sản phẩm mới** | Rất dễ dàng: Chỉ cần tạo Class Product mới và class Creator mới (Tuân thủ OCP tuyệt đối). | Cực kỳ phức tạp: Nếu muốn thêm `createTextBox()` vào UIFactory, ta phải sửa đổi tất cả các Concrete Factory hiện có (Phá vỡ OCP). |
| **Độ phức tạp hệ thống** | Thấp hơn, dễ triển khai ban đầu. | Rất cao, đòi hỏi cấu trúc phân cấp interface nghiêm ngặt ngay từ đầu. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Trong Spring Framework, ta có thể tích hợp Factory Pattern mà không cần viết các câu lệnh `new` thủ công hay không? Làm sao để Spring quản lý các sản phẩm này dưới dạng Spring Beans?
* **Trả lời**: Đây là một câu hỏi thực chiến Spring xuất sắc. Có hai cách tiếp cận chính:
  * **Sử dụng Map Injection (Spring Service Locator)**: Spring cho phép tự động inject tất cả các implementations của một Interface vào một `Map<String, Service>` dựa trên Bean Name. Ta có thể viết một Factory cực kỳ sạch sẽ:
    ```java
    @Service
    public class PaymentFactory {
        // Spring tự động tiêm tất cả Beans hiện thực PaymentProcessor
        // key là tên bean (ví dụ: "paypalProcessor"), value là đối tượng bean cụ thể.
        @Autowired
        private Map<String, PaymentProcessor> processors;

        public PaymentProcessor getProcessor(String type) {
            PaymentProcessor processor = processors.get(type.toLowerCase() + "Processor");
            if (processor == null) {
                throw new IllegalArgumentException("Không tìm thấy cổng thanh toán!");
            }
            return processor;
        }
    }
    ```
    *Cách này hoàn hảo vì ta không tự gọi `new`, vòng đời của các sản phẩm vẫn được Spring quản lý chặt chẽ.*

### 2. Sự vi phạm OCP của Abstract Factory khi thêm một sản phẩm mới (ví dụ thêm Checkbox vào Factory trước đây chỉ có Button) là cực kỳ nghiêm trọng. Làm cách nào để giảm bớt rủi ro này?
* **Trả lời**: Có hai giải pháp kiến trúc để xử lý nhược điểm này:
  * **Dùng Generic & Dynamic Factory**: Thay vì định nghĩa cứng các phương thức như `createButton()`, ta định nghĩa một phương thức generic duy nhất: `public <T extends UIComponent> T createComponent(Class<T> clazz)`. Mỗi Concrete Factory sẽ duy trì một Registry để ánh xạ class cần tạo sang đối tượng tương ứng. Điều này cho phép mở rộng các kiểu component mới mà không cần chỉnh sửa chữ ký (signature) của Interface gốc.
  * **Chỉ áp dụng khi họ sản phẩm cực kỳ ổn định**: Chỉ chọn Abstract Factory khi thiết kế nghiệp vụ của họ sản phẩm đã chín muồi và rất ít khi phát sinh thêm loại sản phẩm mới. Nếu nghiệp vụ liên tục thay đổi, hãy lùi lại sử dụng nhiều Factory Method độc lập.
