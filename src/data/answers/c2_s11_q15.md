# Làm sao đảm bảo idempotency khi tạo transaction/order/payment?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Tính lũy đẳng (Idempotency) là khả năng đảm bảo một API khi bị gọi trùng lặp nhiều lần với cùng một payload **chỉ thực thi nghiệp vụ đúng 1 lần duy nhất** và luôn trả về cùng một kết quả như nhau. Trong hệ thống tài chính/thương mại điện tử, Idempotency là lá chắn sinh tử để chống lại việc trừ tiền trùng lặp (Double Charge) hoặc tạo đơn hàng ảo do mạng lag và cơ chế tự động gửi lại (Retry) của Client.
* **Thảm họa thực chiến được giải quyết**:
  1. **Khách bị trừ tiền 2 lần (Double Charge)**: Khách hàng thanh toán hóa đơn. Mạng bị chập chờn đúng lúc API phản hồi thành công. App điện thoại không nhận được kết quả, tự động thực thi cơ chế Retry gửi lại request thanh toán lần 2. Do API thiếu Idempotency, Backend tiếp tục gọi sang ngân hàng trừ tiền lần thứ hai, làm khách hàng nổi giận đòi tẩy chay ứng dụng.
  2. **Tạo 2 đơn hàng trùng (Duplicate Orders)**: User click liên tục nút "Đặt hàng" do mạng lag. Hai request giống hệt nhau gửi song song lên máy chủ. Hệ thống tạo ra 2 đơn hàng khác nhau, giữ 2 lần số lượng tồn kho ảo, gây thiệt hại nghiêm trọng cho chỉ số tồn kho của doanh nghiệp.
* **Quyết định Senior**:
  1. **Bắt buộc truyền Header `Idempotency-Key` (UUID)**: Ép buộc toàn bộ các API thay đổi trạng thái (POST/PUT/PATCH) liên quan đến tiền tệ, đơn hàng phải nhận diện một khóa duy nhất do Client tự sinh trước khi gửi request.
  2. **Xây dựng Tầng lọc Lũy đẳng bằng Redis (Idempotency Filter)**: Lưu trạng thái xử lý của `Idempotency-Key` trong Redis dưới 3 trạng thái: `PROCESSING` (Đang xử lý) -> Trả về HTTP 409 Conflict; `SUCCESS` -> Trả về ngay lập tức dữ liệu phản hồi đã cache từ lần trước mà không chạy lại DB; `FAILED` -> Cho phép chạy lại nếu lỗi là lỗi mạng nhất thời.
  3. **Unique Constraint làm lá chắn vật lý cuối**: Lưu `idempotency_key` trực tiếp vào bảng `payments` hoặc `orders` dưới dạng khóa duy nhất để DB chặn đứng mọi nỗ lực chèn trùng.

## 🔍 Chi tiết bản chất thực chiến: Thuật toán trạng thái Lũy đẳng bằng Redis

Để triển khai Idempotency chuẩn doanh nghiệp, ta phải áp dụng mô hình máy trạng thái của Key trên bộ nhớ đệm tốc độ cao Redis:

```
[Request với Idempotency-Key "key_123"]
                  │
                  ▼
   [Kiểm tra Key "key_123" trong Redis]
                  │
                  ├─► (Không tồn tại) ──► [Lưu Key = PROCESSING (TTL = 10 phút)] ──► [Xử lý nghiệp vụ chính] ──► [Lưu kết quả thành công + cache response]
                  │                                                                                                        │
                  ├─► (Tồn tại, trạng thái = PROCESSING) ──► [Trả lỗi ngay: HTTP 409 Conflict ❌]                                 ▼
                  │                                                                                             [Đổi trạng thái = SUCCESS (TTL = 24 giờ)]
                  └─► (Tồn tại, trạng thái = SUCCESS)    ──► [Đọc dữ liệu phản hồi từ cache và trả về ngay ✔]
```

### Tại sao không dùng DB để check Idempotency?
Việc check trùng bằng DB đòi hỏi câu lệnh `SELECT` trước khi `INSERT`. Trong môi trường high-concurrency, hai request trùng lặp gửi lên cùng 1 mili-giây sẽ cùng vượt qua bước `SELECT` (vì cả hai đều thấy chưa tồn tại bản ghi trong DB) và cùng thực hiện `INSERT`, gây sập logic. Việc dùng lệnh nguyên tử `SETNX` (Set if Not Exists) của Redis là cách duy nhất để khóa luồng ở tốc độ nano-giây.

## 🎨 Sơ đồ trực quan: Luồng hoạt động của API Gateway / Filter Idempotency

Mô hình thiết kế lá chắn lũy đẳng tách biệt khỏi nghiệp vụ chính, bảo vệ hoàn toàn Backend Service phía sau:

```
 [Client Request] ───(Idempotency-Key: uuid-999)───► [API Gateway / Filter]
                                                            │
                                             ┌──────────────┴──────────────┐
                                             ▼ (Chưa tồn tại)              ▼ (Đang xử lý / Đã xử lý)
                                      [Ghi lock PROCESSING]          [Trả lỗi 409 / Trả kết quả cũ]
                                             │
                                             ▼
                                     [Backend Service]
                                             │ (Thanh toán, tạo đơn...)
                                             ▼
                                      [Database Ghi] ───► (Lưu idempotency_key vật lý khóa chặt 100%)
```

## 💻 Code thực chiến: Spring Boot Interceptor sử dụng Redis Atomic Command

Dưới đây là mã nguồn Java hoàn chỉnh thiết lập một `HandlerInterceptor` để tự động chặn các request trùng lặp, xử lý khóa nguyên tử bằng Redis một cách chuyên nghiệp.

### 1. Code Java Spring Boot tạo Annotation `@Idempotent` để đánh dấu API cần bảo vệ

```java
package com.example.idempotency;

import java.lang.annotation.*;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    long expireTimeInSeconds() default 86400; // Mặc định giữ cache kết quả 24 giờ
}
```

### 2. Triển khai Interceptor đánh dấu và khóa Request trùng lặp

```java
package com.example.idempotency;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.util.concurrent.TimeUnit;

@Component
@RequiredArgsConstructor
@Slf4j
public class IdempotencyInterceptor implements HandlerInterceptor {

    private final StringRedisTemplate redisTemplate;
    private static final String HEADER_IDEMPOTENCY_KEY = "Idempotency-Key";
    private static final String REDIS_KEY_PREFIX = "idempotency:";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        if (!(handler instanceof HandlerMethod)) {
            return true;
        }

        HandlerMethod handlerMethod = (HandlerMethod) handler;
        // Chỉ xử lý nếu API được đánh dấu Annotation @Idempotent
        if (!handlerMethod.getMethod().isAnnotationPresent(Idempotent.class)) {
            return true;
        }

        // BƯỚC 1: Lấy Idempotency-Key từ Header
        String key = request.getHeader(HEADER_IDEMPOTENCY_KEY);
        if (key == null || key.trim().isEmpty()) {
            log.error("Missing mandatory Idempotency-Key header");
            response.sendError(HttpStatus.BAD_REQUEST.value(), "Missing mandatory Idempotency-Key header");
            return false;
        }

        String redisKey = REDIS_KEY_PREFIX + key;
        Idempotent annotation = handlerMethod.getMethodAnnotation(Idempotent.class);

        // BƯỚC 2: Thử thiết lập trạng thái PROCESSING nguyên tử sử dụng SETNX (Set if Not Exists)
        // Set giá trị là "PROCESSING", nếu key chưa tồn tại -> trả về true, nếu đã tồn tại -> trả về false
        Boolean isAbsent = redisTemplate.opsForValue().setIfAbsent(redisKey, "PROCESSING", 5, TimeUnit.MINUTES);

        if (Boolean.TRUE.equals(isAbsent)) {
            // Lấy lock thành công -> Cho phép đi tiếp vào Controller xử lý nghiệp vụ chính
            log.info("Acquired idempotency lock for key: {}. Processing request.", redisKey);
            request.setAttribute("current_idempotency_key", redisKey);
            request.setAttribute("idempotency_expire_seconds", annotation.expireTimeInSeconds());
            return true;
        } else {
            // Lấy lock thất bại -> Khóa đã tồn tại. Đọc giá trị hiện tại của khóa
            String currentValue = redisTemplate.opsForValue().get(redisKey);
            
            if ("PROCESSING".equals(currentValue)) {
                // Trường hợp trùng lặp khi request đầu tiên vẫn đang chạy ngầm
                log.warn("Duplicate request detected for key: {}. Transaction is still processing.", redisKey);
                response.setStatus(HttpStatus.CONFLICT.value()); // Trả về HTTP 409 Conflict
                response.getWriter().write("Request is already being processed. Please wait.");
            } else {
                // Trường hợp request trước đó đã xử lý xong thành công -> Trả về cached response
                log.info("Returning cached response for key: {}", redisKey);
                response.setStatus(HttpStatus.OK.value());
                response.setContentType("application/json");
                response.getWriter().write(currentValue); // Trả lại payload thành công cũ
            }
            return false; // Ngắt luồng gọi, không cho vào Controller
        }
    }
}
```

### 3. Cập nhật kết quả vào Redis sau khi Controller hoàn tất xử lý (Response Caching)

Sử dụng `ResponseBodyAdvice` hoặc Filter ghi đè sau khi Response được sinh ra để cập nhật giá trị từ `PROCESSING` thành Payload phản hồi thực tế:

```java
package com.example.idempotency;

import lombok.RequiredArgsConstructor;
import org.springframework.core.MethodParameter;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.http.MediaType;
import org.springframework.http.converter.HttpMessageConverter;
import org.springframework.http.server.ServerHttpRequest;
import org.springframework.http.server.ServerHttpResponse;
import org.springframework.http.server.ServletServerHttpRequest;
import org.springframework.web.bind.annotation.ControllerAdvice;
import org.springframework.web.servlet.mvc.method.annotation.ResponseBodyAdvice;

import jakarta.servlet.http.HttpServletRequest;
import java.util.concurrent.TimeUnit;

@ControllerAdvice
@RequiredArgsConstructor
public class IdempotencyResponseAdvice implements ResponseBodyAdvice<Object> {

    private final StringRedisTemplate redisTemplate;

    @Override
    public boolean supports(MethodParameter returnType, Class<? extends HttpMessageConverter<?>> converterType) {
        return returnType.hasMethodAnnotation(Idempotent.class);
    }

    @Override
    public Object beforeBodyWrite(Object body, MethodParameter returnType, MediaType selectedContentType,
                                  Class<? extends HttpMessageConverter<?>> selectedConverterType,
                                  ServerHttpRequest request, ServerHttpResponse response) {
        
        HttpServletRequest servletRequest = ((ServletServerHttpRequest) request).getServletRequest();
        String redisKey = (String) servletRequest.getAttribute("current_idempotency_key");
        Long expireSeconds = (Long) servletRequest.getAttribute("idempotency_expire_seconds");

        if (redisKey != null && body != null) {
            try {
                // Chuyển đối tượng phản hồi thành JSON String để lưu vào Redis
                String jsonResponse = new com.fasterxml.jackson.databind.ObjectMapper().writeValueAsString(body);
                
                // Cập nhật đè giá trị từ "PROCESSING" thành nội dung phản hồi, set thời hạn lưu trữ lâu dài
                redisTemplate.opsForValue().set(redisKey, jsonResponse, expireSeconds, TimeUnit.SECONDS);
            } catch (Exception e) {
                // Bắt lỗi serialize, chủ động xóa key để cho phép retry
                redisTemplate.delete(redisKey);
            }
        }
        return body;
    }
}
```

## 📊 Bảng so sánh 3 Kỹ thuật thiết kế Idempotency

| Tiêu chí | Phương án 1: Khóa phân tán & Lưu vết Redis (Khuyên dùng) | Phương án 2: Database Unique Key duy nhất | Phương án 3: Băm dữ liệu payload (Request Hash) |
| :--- | :--- | :--- | :--- |
| **Độ tin cậy** | **Rất cao** (Chặn đứng từ cửa ngõ API Gateway trước khi vào luồng xử lý DB nặng). | **Tuyệt đối 100%** (Lá chắn vật lý không thể bị phá vỡ). | Trung bình (Nếu khách hàng click mua 2 đơn hàng khác nhau có cùng số tiền và vật phẩm, request hash sẽ chặn nhầm đơn hàng hợp lệ). |
| **Hiệu năng hệ thống** | **Siêu tốt** (Redis xử lý khóa tốc độ nano-giây ở bộ nhớ đệm, bảo vệ DB hoàn hảo). | Kém (Phải chịu tải ghi lỗi `DuplicateKeyException` xuống DB). | Tốt. |
| **Trải nghiệm khách hàng** | **Hoàn hảo** (Khách hàng nhận được chính xác mã hóa đơn và kết quả cũ tức thì mà không bị báo lỗi). | Tệ (Hệ thống ném lỗi Database Error thô kệch nếu cố chèn trùng). | Tốt. |
| **Độ phức tạp code** | Cao (Cần viết Interceptor và xử lý ghi đè Cache Response). | Rất thấp (Chỉ cần tạo unique index). | Thấp. |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Xử lý sập ứng dụng nửa chừng và khóa chết key"
* **Vấn đề nguy hiểm**: Khi request đầu tiên gửi lên, hệ thống ghi nhận trạng thái `PROCESSING`. Đúng lúc đó, Backend Server bị sập (Crash / OOM) trước khi kịp cập nhật kết quả thành `SUCCESS` hoặc xóa key.
  * Hậu quả: Khóa bị treo ở trạng thái `PROCESSING` vĩnh viễn (hoặc cho đến khi hết hạn TTL). Khách hàng bấm gửi lại request sẽ liên tục nhận lỗi `409 Conflict` và **vĩnh viễn không thể thực hiện giao dịch này được nữa**.
* **Giải pháp khắc phục**:
  1. Chỉ đặt thời hạn khóa (TTL) cho trạng thái `PROCESSING` ở mức cực kỳ ngắn (ví dụ: tối đa 15 đến 30 giây).
  2. Bọc toàn bộ code xử lý nghiệp vụ chính trong khối `try-catch`. Nếu có bất kỳ lỗi runtime nào xảy ra khiến giao dịch thất bại hoàn toàn (không trừ tiền ngân hàng), chủ động gọi lệnh `redisTemplate.delete(redisKey)` để giải phóng lock lập tức, cho phép người dùng bấm thử lại.

### 2. Câu hỏi đào sâu từ interviewer
* **Interviewer: "Ai là người chịu trách nhiệm sinh Idempotency-Key? Nếu Client viết code cẩu thả và sinh ra Key trùng lặp cho hai đơn hàng khác nhau của hai khách hàng khác nhau thì sao?"**
* **Trả lời**:
  * **Client (Mobile App / Web Frontend)** là người bắt buộc phải sinh `Idempotency-Key` vì chỉ Client mới biết khi nào họ đang thực hiện hành động gửi lại (Retry) cho cùng một ý định giao dịch.
  * Để phòng chống việc Client sinh Key trùng lặp bừa bãi phá hủy dữ liệu của người khác, Senior sẽ áp dụng cơ chế **"Khóa Lũy Đẳng Tổ Hợp" (Composite Idempotency Key)**:
    1. Khi lưu trữ khóa trong Redis, Backend không dùng trực tiếp key của Client.
    2. Backend tự động sinh Key tổ hợp bằng cách ghép thêm thông tin của User hiện tại: `redisKey = "idempotency:" + current_user_id + ":" + client_idempotency_key`.
    3. Việc này đảm bảo dù Client của User A sinh key trùng với Client của User B, hai giao dịch vẫn hoàn toàn cô lập và an toàn 100%.
