# Hiện thực hóa bộ lập lịch tác vụ chạy tại thời điểm xác định (Implement Task Scheduler at Specific Time)

## ⚡ Tóm tắt ngắn (30s)
* **Bài toán**: Thiết kế và hiện thực hóa một công cụ lập lịch tác vụ (Task Scheduler) từ đầu bằng Java. Hệ thống cho phép đăng ký các tác vụ (`Runnable`) chạy tại một thời điểm cụ thể trong tương lai (Specific execution time).
* **Giải pháp cốt lõi**:
  1. **Đóng gói Tác vụ**: Tạo lớp `ScheduledTask` đóng gói tác vụ `Runnable` và thời điểm chạy `scheduledTime` (tính bằng mili-giây).
  2. **PriorityQueue**: Sử dụng một hàng đợi ưu tiên Min-Heap làm bộ lưu trữ, sắp xếp các tác vụ theo thời gian chạy tăng dần (phần tử chạy sớm nhất nằm ở đỉnh heap).
  3. **Thuật toán Worker Thread (Loại bỏ Busy-Waiting)**: Luồng chạy nền (Worker Thread) liên tục kiểm tra phần tử ở đỉnh heap:
     * Nếu trống: ngủ chờ vô hạn (`Condition.await()`) cho tới khi có tác vụ mới.
     * Nếu có tác vụ: tính toán khoảng thời gian chờ `delay = scheduledTime - currentTime`.
     * Nếu `delay <= 0`: lấy tác vụ ra và thực thi (chạy trên một luồng riêng để tránh làm nghẽn bộ lập lịch).
     * Nếu `delay > 0`: ngủ chờ chính xác trong khoảng thời gian `delay` bằng lệnh `Condition.awaitNanos(delay)`.
     * **Tính chất Đánh thức sớm**: Nếu có một tác vụ mới được nạp vào có lịch chạy sớm hơn tác vụ đang chờ ở đỉnh, ta thực hiện phát tín hiệu `signal()` để đánh thức Worker Thread tính toán lại thời gian ngủ.
* **Độ phức tạp**: Thêm tác vụ $O(\log N)$, định vị tác vụ chạy tiếp theo $O(1)$, không gian $O(N)$ lưu trữ.

## 🔍 Phân tích yêu cầu (Requirements)

### 1. Functional Requirements (Yêu cầu chức năng)
* Đăng ký tác vụ kèm mốc thời gian chạy tuyệt đối: `schedule(Runnable task, long executionTime)`.
* Quản lý thực thi tác vụ chuẩn xác đến mili-giây.
* Hỗ trợ tắt bộ lập lịch an toàn (`shutdown`) giải phóng tài nguyên.

### 2. Non-Functional Requirements (Yêu cầu phi chức năng)
* **Tuyệt đối chống nghẽn CPU (No Busy-Waiting)**: Tránh tuyệt đối việc sử dụng vòng lặp vô hạn `while(true)` kiểm tra liên tục gây tăng vọt CPU lên 100%. Luồng Worker phải ngủ chờ thực thụ.
* **Thực thi bất tuần tự (Non-blocking Task Execution)**: Việc thực thi nghiệp vụ của một tác vụ này không được phép làm ảnh hưởng hoặc chậm trễ lịch chạy của tác vụ khác (phải chạy đa luồng).
* **Thread-Safety**: An toàn đa luồng tuyệt đối khi có nhiều Client cùng lúc đẩy tác vụ vào lập lịch.

## 🎨 Sơ đồ trực quan & Cơ chế hoạt động của Worker Thread

### Quy trình Ngủ-Thức thông minh với Khóa nâng cao (Condition Variable)

```
       Worker Thread thức giấc
                 │
                 ▼
     ┌──────────────────────┐
     │  Hàng đợi trống?     ├─────► YES ─────► Ngủ chờ vô hạn (await)
     └───────────┬──────────┘
                 │ NO
                 ▼
     ┌──────────────────────┐
     │ Tính toán delay      │ (delay = scheduledTime - currentTime)
     └───────────┬──────────┘
                 │
         ┌───────┴───────┐
         │  delay <= 0?  │
         └───────┬───────┘
              NO │           │ YES
                 │           ▼
                 │     [ Lấy tác vụ ra khỏi Heap ]
                 │     [ Đẩy vào ThreadPool để thực thi ]
                 │           │
                 ▼           ▼
         [ Ngủ chờ có kỳ hạn ]  ◄── (Được đánh thức sớm nếu có tác vụ mới)
         [ awaitNanos(delay) ]
```

## 💻 Code Example: Hiện thực hóa bộ lập lịch bằng Java

Dưới đây là phiên bản hiện thực hóa cấu trúc Task Scheduler tự thiết kế từ đầu (tương tự như `DelayQueue` phối hợp với `ThreadPool` nội bộ), đảm bảo tối ưu hóa CPU và an toàn đa luồng tuyệt đối:

```java
import java.util.Comparator;
import java.util.PriorityQueue;
import java.util.concurrent.*;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class CustomTaskScheduler {

    // Lớp đóng gói thông tin tác vụ lập lịch
    private static class ScheduledTask implements Comparable<ScheduledTask> {
        final Runnable runnable;
        final long scheduledTimeMs; // Thời điểm chạy (Absolute timestamp in ms)

        ScheduledTask(Runnable runnable, long scheduledTimeMs) {
            this.runnable = runnable;
            this.scheduledTimeMs = scheduledTimeMs;
        }

        @Override
        public int compareTo(ScheduledTask o) {
            // Phần tử chạy sớm hơn sẽ đứng đầu (Min-Heap)
            return Long.compare(this.scheduledTimeMs, o.scheduledTimeMs);
        }
    }

    private final PriorityQueue<ScheduledTask> queue = new PriorityQueue<>();
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition available = lock.newCondition();
    
    // Thread pool chịu trách nhiệm thực thi các tác vụ khi đến giờ, 
    // tránh làm tắc nghẽn luồng lập lịch chính (Gotcha 2)
    private final ExecutorService taskExecutor = Executors.newCachedThreadPool();
    private final Thread schedulerThread;
    private volatile boolean isShutdown = false;

    public CustomTaskScheduler() {
        this.schedulerThread = new Thread(this::runSchedulerLoop, "custom-scheduler-loop");
        this.schedulerThread.start();
    }

    /**
     * Lập lịch chạy một tác vụ tại thời điểm tuyệt đối (executionTimeMs)
     */
    public void schedule(Runnable task, long executionTimeMs) {
        if (task == null) throw new NullPointerException();

        lock.lock();
        try {
            if (isShutdown) {
                throw new IllegalStateException("Bộ lập lịch đã tắt, không nhận thêm tác vụ!");
            }

            ScheduledTask scheduledTask = new ScheduledTask(task, executionTimeMs);
            queue.offer(scheduledTask);

            // Nếu tác vụ mới thêm vào nằm ở đỉnh Heap (đây là tác vụ có lịch chạy sớm nhất hiện tại)
            // Chúng ta bắt buộc phải đánh thức Worker Thread đang ngủ để tính toán lại thời gian chờ (Gotcha 1)
            if (queue.peek() == scheduledTask) {
                available.signal();
            }
        } finally {
            lock.unlock();
        }
    }

    /**
     * Vòng lặp quản lý lập lịch cốt lõi chạy ngầm
     */
    private void runSchedulerLoop() {
        try {
            while (!isShutdown) {
                lock.lock();
                try {
                    // Nếu hàng đợi rỗng, ngủ chờ vô hạn cho tới khi có tác vụ mới
                    while (queue.isEmpty() && !isShutdown) {
                        available.await();
                    }

                    if (isShutdown) break;

                    ScheduledTask firstTask = queue.peek();
                    long currentTime = System.currentTimeMillis();
                    long delay = firstTask.scheduledTimeMs - currentTime;

                    if (delay <= 0) {
                        // Đã đến hoặc quá giờ chạy! Lấy ra khỏi hàng đợi
                        queue.poll();
                        
                        // Đẩy tác vụ vào Thread Pool chạy độc lập, không block luồng lập lịch
                        taskExecutor.submit(firstTask.runnable);
                    } else {
                        // Chưa đến giờ chạy, ngủ chờ chính xác lượng thời gian delay (nano-giây)
                        // Trong lúc ngủ, nếu có luồng khác gọi signal() (do có tác vụ khẩn cấp hơn nạp vào)
                        // Luồng này sẽ tỉnh dậy sớm để cập nhật lại.
                        available.awaitNanos(TimeUnit.MILLISECONDS.toNanos(delay));
                    }
                } finally {
                    lock.unlock();
                }
            }
        } catch (InterruptedException e) {
            System.err.println("[Scheduler] Luồng lập lịch bị ngắt!");
        }
    }

    /**
     * Tắt bộ lập lịch an toàn
     */
    public void shutdown() {
        lock.lock();
        try {
            isShutdown = true;
            available.signalAll(); // Đánh thức toàn bộ luồng đang chờ
        } finally {
            lock.unlock();
        }
        
        schedulerThread.interrupt();
        taskExecutor.shutdown(); // Ngắt pool thực thi tác vụ
        System.out.println("[Scheduler] Đã dừng hoạt động an toàn.");
    }

    // --- Hàm Demo chạy thử ---
    public static void main(String[] args) throws InterruptedException {
        CustomTaskScheduler scheduler = new CustomTaskScheduler();
        long now = System.currentTimeMillis();

        System.out.println("Đang nạp các tác vụ lập lịch...");

        // Lập lịch Tác vụ A: Chạy sau 3 giây
        scheduler.schedule(() -> System.out.println("-> Tác vụ A thực thi! (Lên lịch chạy sau 3s)"), now + 3000);

        // Lập lịch Tác vụ B: Chạy sau 1 giây
        scheduler.schedule(() -> System.out.println("-> Tác vụ B thực thi! (Lên lịch chạy sau 1s)"), now + 1000);

        // Lập lịch Tác vụ C: Chạy sau 5 giây
        scheduler.schedule(() -> System.out.println("-> Tác vụ C thực thi! (Lên lịch chạy sau 5s)"), now + 5000);

        // Chờ 6 giây để xem tất cả tác vụ in kết quả
        Thread.sleep(6000);

        scheduler.shutdown();
    }
}
```

## 📊 Phân tích độ phức tạp & Trade-offs

### So sánh các mô hình lập lịch tác vụ

| Tiêu chí | Busy-Waiting Loop | Sử dụng Timer (`java.util.Timer`) | Bộ lập lịch tự thiết kế (Custom Scheduler - Tối ưu) |
| :--- | :--- | :--- | :--- |
| **Tiêu tốn CPU** | **Hủy diệt**: CPU luôn ở ngưỡng 100% do luồng kiểm tra thời gian không bao giờ ngủ. | Thấp nhờ ngủ chờ an toàn. | **Cực thấp**: Chỉ thức giấc khi đến giờ chạy hoặc khi có tác vụ mới nạp vào. |
| **Độ tin cậy đa luồng (Robustness)** | Kém. Dễ xảy ra race condition. | **Kém**: Chỉ sử dụng duy nhất 1 luồng xử lý nền. Nếu 1 tác vụ chạy bị lỗi hoặc chạy quá lâu (ví dụ nghẽn I/O) sẽ làm **tất cả các tác vụ phía sau bị trễ lịch**. | **Tuyệt vời**: Luồng quản lý lập lịch tách biệt hoàn toàn với Thread Pool thực thi tác vụ, đảm bảo thời gian chạy độc lập chính xác. |
| **Xử lý ngoại lệ (Exception Handling)** | Tự viết. | Kém. Nếu 1 tác vụ ném ra RuntimeException không được bắt, luồng Timer duy nhất sẽ **bị chết hoàn toàn**, làm tê liệt hệ thống. | **Tốt**: Thread Pool nội bộ tự động cô lập và xử lý các Exception riêng lẻ của từng tác vụ. |

## ⚠️ Common Gotchas (Câu hỏi đào sâu từ interviewer)

### 1. Tại sao cơ chế "Đánh thức sớm" (Leader-Follower / Early Wakeup) thông qua lệnh `available.signal()` lại vô cùng quan trọng khi nạp tác vụ mới?
* **Trả lời**: Đây là câu hỏi kiểm tra kỹ năng tư duy bất đồng bộ xuất sắc:
  * **Tình huống**: Giả sử hàng đợi đang có một tác vụ chạy sau 1 giờ nữa. Luồng Worker kiểm tra và thấy `delay = 1 hour`. Luồng quyết định đi ngủ bằng lệnh `awaitNanos(1 hour)`.
  * **Vấn đề**: Ngay sau đó 1 phút, Client lập lịch cho một tác vụ cực kỳ khẩn cấp cần chạy sau **5 giây** nữa. 
    * Nếu ta **không** gọi `available.signal()` khi đưa tác vụ khẩn cấp vào đầu Heap: Luồng Worker vẫn tiếp tục ngủ say sưa suốt 1 giờ nữa mới tỉnh dậy. Lúc này tác vụ khẩn cấp kia đã bị trễ lịch chạy tới 59 phút 55 giây!
  * **Giải quyết**: Bằng cách kiểm tra `if (queue.peek() == scheduledTask)`, ta phát hiện ra tác vụ mới thêm vào có độ ưu tiên cao nhất (chạy sớm nhất). Ta lập tức gọi `signal()` đánh thức Worker Thread dậy. Luồng tỉnh dậy sớm, tính toán lại delay của tác vụ khẩn cấp (5s) và đi ngủ chờ ngắn lại chỉ 5 giây. Đúng giờ chạy chính xác!

### 2. Tại sao chúng ta cần đưa ExecutorService (`CachedThreadPool`) vào bộ lập lịch để thực thi Runnable thay vì chạy trực tiếp `runnable.run()` trên luồng của bộ lập lịch?
* **Trả lời**:
  * Nếu ta gọi trực tiếp `firstTask.runnable.run()` trên luồng lập lịch chính (Scheduler Thread): 
    * Luồng lập lịch sẽ bị **khóa chặt** để thực thi logic nghiệp vụ của tác vụ đó (ví dụ tác vụ thực hiện gọi API mạng mất 10 giây).
    * Trong suốt 10 giây đó, luồng lập lịch bị nghẽn không thể kiểm tra, không thể ngủ chờ, không thể đánh thức cho bất kỳ tác vụ nào khác. Mọi tác vụ có lịch chạy rơi vào khoảng thời gian 10 giây đó đều bị trễ giờ hàng loạt.
  * **Khắc phục**: Việc chuyển giao tác vụ cho `ExecutorService` thực thi đảm bảo luồng lập lịch chính giải phóng tức thì (Non-blocking) để tiếp tục quay lại vòng lặp quản lý thời gian chính xác tuyệt đối.

### 3. Làm thế nào để giải quyết bài toán đồng bộ múi giờ (Timezone) hoặc thay đổi giờ hệ thống (Clock Drift) làm sai lệch giờ chạy của tác vụ?
* **Trả lời**:
  * **Vấn đề**: Sử dụng giờ hệ thống tuyệt đối `System.currentTimeMillis()` có thể bị sai lệch nếu máy chủ thực hiện đồng bộ lại thời gian NTP (Network Time Protocol) gây nhảy vọt hoặc giật lùi giờ hệ thống.
  * **Giải pháp khắc phục**: Ta nên thiết kế bộ lập lịch dựa trên thời gian đơn điệu tăng dần của CPU thông qua hàm **`System.nanoTime()`** (không phụ thuộc vào thay đổi múi giờ hay chỉnh sửa thời gian vật lý của máy chủ). Mọi tính toán delay sẽ được đảm bảo ổn định và chính xác tuyệt đối!
