# Một service deploy version mới phá contract với service khác. Làm sao tránh?

## ⚡ Tóm tắt ngắn (30s)
* **Bản chất**: Trong hệ thống Microservices, các dịch vụ liên lạc với nhau thông qua **API Contract (Giao kèo API)** (REST, gRPC, Schema Kafka). Khi một service nhà cung cấp (Provider) tự ý thay đổi cấu trúc API (đổi tên trường, xóa trường bắt buộc, thay đổi kiểu dữ liệu) mà không báo trước, nó sẽ phá vỡ giao kèo và lập tức **kéo sập** các service tiêu dùng (Consumer). Để ngăn chặn điều này, Senior Engineer sử dụng phương pháp **Consumer-Driven Contract Testing (Kiểm thử giao kèo định hướng bởi bên tiêu dùng)** kết hợp quy tắc **Tương thích ngược (Backward Compatibility)** nghiêm ngặt.
* **Thảm họa thực chiến được giải quyết**:
  1. **Hiệu ứng sụp đổ Domino (Cascading Downtime)**: Team User Service đổi tên trường `user_id` thành `id` trong JSON response. Ngay sau khi deploy lên production, Order Service và Payment Service (do team khác quản lý) đọc trường `user_id` bị nhận giá trị `null`, ném lỗi `NullPointerException` hàng loạt, làm tê liệt tính năng thanh toán đặt hàng trên toàn hệ thống.
  2. **Integration Test chậm và không đáng tin cậy**: Việc dựng toàn bộ hệ thống 50 services lên môi trường Staging để chạy kiểm thử liên thông (End-to-End Test) cực kỳ tốn tài nguyên, chạy rất chậm và thường xuyên bị lỗi ảo (Flaky tests).
* **Quyết định Senior**:
  1. **Triển khai PACT (Consumer-Driven Contract Testing)**: Phía Consumer viết code định nghĩa chính xác những trường và kiểu dữ liệu họ cần từ API của Provider. File giao kèo này (`contract.json`) được đẩy lên **Pact Broker**. Khi Provider build CI/CD, hệ thống tự động bốc file này về chạy verify. Nếu Provider sửa code làm gãy cấu trúc mong muốn của Consumer, CI/CD của Provider sẽ **tự động fail và chặn deploy lập tức**.
  2. **Thiết kế API Tương thích ngược tuyệt đối**: Chỉ thêm trường mới dạng Optional, cấm xóa hoặc đổi tên trường cũ. Nếu bắt buộc phải thay đổi cấu trúc lớn, phải áp dụng **Quy trình Release 3 bước (Expand and Contract)** và duy trì song song phiên bản cũ/mới.
  3. **Tích hợp Schema Registry cho Event-Driven**: Bắt buộc sử dụng Confluent Schema Registry (Avro/Protobuf) cấu hình chế độ tương thích `BACKWARD` hoặc `FULL` để chặn đứng event phá cấu trúc ngay từ tầng gửi tin.

## 🔍 Chi tiết bản chất thực chiến: Consumer-Driven Contract Testing hoạt động ra sao?

Consumer-Driven Contract Testing (ví dụ sử dụng framework **PACT**) dịch chuyển việc phát hiện lỗi tương thích API từ môi trường Production về môi trường Local/CI thông qua quy trình sau:

```
[BƯỚC 1: CONSUMER TẠO CONTRACT]
Consumer viết Test -> Sinh ra file 'order_user_contract.json' -> Đẩy lên Pact Broker
                                                                         │
                                                                         ▼
[BƯỚC 2: PROVIDER VERIFY TRONG CI/CD]
User Service (Provider) build code -> Tải file Contract từ Pact Broker về -> Chạy Verify Test ngầm
                                                                         │
                    ┌────────────────────────────────────────────────────┴─────────────────────────────────┐
                    ▼ (Thành công - Khớp contract)                                                         ▼ (Thất bại - Phá vỡ contract 💥)
         [Cho phép Deploy lên Prod]                                                             [CI/CD FAIL - Chặn đứng Deploy!]
```

### 1. Quy tắc Thiết kế API Tương thích ngược (Robustness Principle - Postel's Law)
> *"Hãy khắt khe trong những gì bạn gửi đi, và hãy linh hoạt trong những gì bạn nhận về."*
* **Phía Provider (Gửi đi)**: Khi nâng cấp API, nếu muốn đổi tên trường `phone` thành `phoneNumber`, hãy trả về cả hai trường cùng lúc trong phiên bản mới để các consumer cũ chưa kịp nâng cấp vẫn đọc được trường `phone` bình thường.
* **Phía Consumer (Nhận về)**: Khi parse JSON nhận từ API, tuyệt đối **không được parse toàn bộ Object một cách mù quáng (cấm dùng strict object mapping)**. Chỉ parse đúng những trường mình cần dùng. Việc Provider thêm 10 trường mới vào API không được làm ảnh hưởng đến Consumer cũ (Sử dụng `@JsonIgnoreProperties(ignoreUnknown = true)` trong Jackson).

### 2. Chiến lược 3 Bước thay đổi Contract an toàn (Expand and Contract Pattern)
Khi bắt buộc phải thực hiện một thay đổi phá vỡ tương thích (Breaking Change), Senior áp dụng quy trình 3 bước không downtime:
* **Bước 1: Mở rộng (Expand)**: Deploy phiên bản mới hỗ trợ song song cả cấu trúc cũ và cấu trúc mới (ví dụ: hỗ trợ cả API `/v1/users` và `/v2/users`).
* **Bước 2: Di cư (Migrate)**: Yêu cầu toàn bộ các team quản lý Consumer service cập nhật code để chuyển sang gọi cấu trúc mới (`/v2/users`).
* **Bước 3: Thu hẹp (Contract)**: Sau khi đảm bảo 100% consumer đã chuyển đổi (giám sát qua log traffic), tiến hành xóa bỏ hoàn toàn cấu trúc cũ (`/v1/users`) an toàn.

## 💻 Code thực chiến: Viết Pact Provider Verification Test trong Spring Boot

Dưới đây là cách triển khai một test case bên phía **Provider (User Service)** để tự động kiểm tra xem code của mình có phá vỡ giao kèo mà bên **Consumer (Order Service)** yêu cầu hay không.

### 1. File Contract do Consumer sinh ra và lưu trên Pact Broker (Mô phỏng JSON)
```json
{
  "consumer": { "name": "order-service" },
  "provider": { "name": "user-service" },
  "interactions": [
    {
      "description": "Yêu cầu lấy thông tin user ID 100",
      "request": {
        "method": "GET",
        "path": "/users/100"
      },
      "response": {
        "status": 200,
        "headers": { "Content-Type": "application/json" },
        "body": {
          "id": 100,
          "username": "senior_engineer",
          "email": "senior@expert.com"
        },
        "matchingRules": {
          "$.body.id": { "match": "type" },
          "$.body.username": { "match": "type" },
          "$.body.email": { "match": "type" }
        }
      }
    }
  ]
}
```

### 2. Viết Provider Test xác thực giao kèo tự động trên CI/CD
```java
import au.com.dius.pact.provider.junit5.HttpTestTarget;
import au.com.dius.pact.provider.junit5.PactVerificationContext;
import au.com.dius.pact.provider.junit5.PactVerificationInvocationContextProvider;
import au.com.dius.pact.provider.junitsupport.Provider;
import au.com.dius.pact.provider.junitsupport.State;
import au.com.dius.pact.provider.junitsupport.loader.PactFolder;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.TestTemplate;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Provider("user-service") // ✅ Tên Provider phải khớp với tên khai báo trong contract
@PactFolder("pacts")      // Đọc contract từ thư mục local (hoặc thay bằng @PactBroker để lấy từ máy chủ tập trung)
public class UserServiceProviderContractTest {

    @LocalServerPort
    private int port;

    @BeforeEach
    void setup(PactVerificationContext context) {
        // Thiết lập mục tiêu chạy test chính là local Spring Boot port vừa start ngầm
        context.setTarget(new HttpTestTarget("localhost", port));
    }

    /**
     * ✅ Test template tự động duyệt qua toàn bộ các API interaction khai báo trong file contract
     * và thực hiện bắn request thật vào local server để so sánh khớp kiểu dữ liệu / trường.
     */
    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void pactVerificationTestTemplate(PactVerificationContext context) {
        context.verifyInteraction();
    }

    /**
     * Thiết lập trạng thái giả định (State Setup) mà bên Consumer yêu cầu trước khi gọi API
     */
    @State("User ID 100 exists")
    public void toUserExistsState() {
        // Code insert mock data user ID 100 vào DB H2 test ở đây để chuẩn bị dữ liệu cho API trả về đúng mong đợi
        log.info("ℹ️ Thiết lập trạng thái test: Mock User ID 100 thành công.");
    }
}
```

## 📊 Bảng so sánh 3 Loại hình Kiểm Thử API Phân Tán

| Tiêu chí | Integration Testing (Kiểm thử tích hợp) | End-to-End Testing (E2E) | Contract Testing (PACT) |
| :--- | :--- | :--- | :--- |
| **Tốc độ thực thi** | Trung bình (`1 - 5 phút`). | Rất chậm (`30 phút - vài tiếng`). | **Cực nhanh** (`vài giây`). |
| **Độ tin cậy (Lỗi ảo)** | Trung bình (Dễ lỗi do database test không sạch). | Kém (Thường xuyên lỗi do nghẽn mạng/môi trường staging sập). | **Tuyệt đối** (Không phụ thuộc vào môi trường hay service khác). |
| **Phát hiện lỗi breaking change** | Muộn (Chỉ phát hiện khi tích hợp chạy chung). | Rất muộn (Chạy ở môi trường Staging cuối cùng). | **Cực sớm** (Phát hiện ngay lúc dev viết code sửa API ở máy local). |
| **Chi phí bảo trì hạ tầng** | Trung bình. | Cực cao (Đòi hỏi duy trì cụm server Staging đầy đủ). | **Cực thấp** (Chỉ tốn 1 máy chủ Pact Broker gọn nhẹ). |

## ⚠️ Common Gotchas & Questions follow-up

### 1. Cạm bẫy "Lấy mẫu thử quá cứng nhắc (Over-asserting / Strict JSON Match)"
* **Vấn đề**: Phía Consumer viết contract yêu cầu so khớp chính xác giá trị tĩnh trả về (ví dụ: bắt buộc trường `status` phải bằng `"ACTIVE"`). Khi Provider thay đổi logic nghiệp vụ làm trường `status` trả về `"SUSPENDED"` (hoàn toàn đúng kiểu String), contract test bị fail oan.
* **Giải pháp khắc phục**: Phía Consumer khi viết contract chỉ nên so khớp **Kiểu dữ liệu (Type-based matching)** (ví dụ: bắt buộc là String, Int, Boolean) hoặc sử dụng **Regex-based matching** thay vì so khớp giá trị cứng (Value matching), trừ các trường hợp đặc biệt như Enum.

### 2. Câu hỏi đào sâu từ interviewer
* **Q: Nếu hai service giao tiếp bất đồng bộ qua Kafka Event chứ không phải REST API. Làm sao ứng dụng Contract Testing để đảm bảo thay đổi cấu trúc Event của Producer không kéo sập Consumer?**
  * *Trả lời*:
    * Với kiến trúc Event-Driven, ta không dùng PACT trực tiếp mà sử dụng **Schema Registry (ví dụ: Confluent Schema Registry)**:
      1. Producer bắt buộc phải định nghĩa cấu trúc Event bằng **Protobuf hoặc Apache Avro Schema**.
      2. Khi Producer gửi event, thư viện sẽ tự động đăng ký schema này lên Schema Registry.
      3. Ta cấu hình luật tương thích trên Registry là **`BACKWARD` compatibility**: Cấm xóa trường cũ, cấm đổi kiểu dữ liệu trường cũ.
      4. Trong CI/CD của Producer, ta chạy plugin kiểm tra schema (ví dụ: `io.confluent:kafka-schema-registry-maven-plugin:compatible`).
      5. Nếu Producer sửa đổi schema vi phạm luật tương thích ngược, build plugin sẽ báo lỗi lập tức và **chặn đứng việc deploy / publish event lỗi**.
