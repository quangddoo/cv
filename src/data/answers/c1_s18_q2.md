# Phân biệt Đảo ngược phụ thuộc (DIP) và Tiêm phụ thuộc (DI) (Dependency Inversion vs Dependency Injection)

## ⚡ Tóm tắt ngắn (30s)
* **Khái niệm**: 
  * **Dependency Inversion Principle (DIP)**: Là một **nguyên lý thiết kế hướng đối tượng** (chữ D trong SOLID). Nó đưa ra hướng dẫn lý thuyết: Mô-đun cấp cao không nên phụ thuộc vào mô-đun cấp thấp, cả hai phải phụ thuộc vào các lớp trừu tượng (Abstractions).
  * **Dependency Injection (DI)**: Là một **mẫu thiết kế (Design Pattern)** hoặc **kỹ thuật hiện thực hóa**. Đây là công cụ kỹ thuật cụ thể giúp triển khai nguyên lý DIP bằng cách chuyển việc khởi tạo phụ thuộc ra ngoài lớp sử dụng và "tiêm" (inject) chúng vào từ bên ngoài.
* **Mối quan hệ**: **DIP là mục tiêu thiết kế (nguyên lý), còn DI là phương tiện để đạt được mục tiêu đó (cách thực hiện).** Cả hai đều thuộc về khái niệm rộng hơn là **Inversion of Control (IoC - Đảo ngược điều khiển)**.

## 🔍 Phân tích chuyên sâu: DIP, DI và IoC

Để hiểu sâu sắc, chúng ta cần phân biệt rõ ba khái niệm thường bị nhầm lẫn này thông qua mô hình phân tầng:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Inversion of Control (IoC)                           │
│        (Khái niệm rộng nhất - Triết lý đảo ngược luồng điều khiển)       │
│                                                                         │
│     ┌───────────────────────────────┐   ┌─────────────────────────┐     │
│     │  Dependency Inversion (DIP)   │   │ Dependency Injection(DI)│     │
│     │  (Nguyên lý thiết kế lý thuyết)│   │  (Kỹ thuật lập trình)   │     │
│     └───────────────────────────────┘   └─────────────────────────┘     │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1. Inversion of Control (IoC)
IoC là một triết lý thiết kế chung giúp chuyển giao quyền điều khiển luồng hoạt động của ứng dụng từ mã nguồn tự viết sang cho một Framework hoặc Container (ví dụ: Spring Framework).
* **Truyền thống**: Mã của bạn quyết định khi nào gọi thư viện, khi nào tạo đối tượng.
* **IoC**: Framework quyết định luồng chạy và gọi lại (callback) mã của bạn khi cần (Triết lý *"Đừng gọi cho chúng tôi, chúng tôi sẽ gọi cho bạn"* - Hollywood Principle).

### 2. Dependency Inversion Principle (DIP)
Nguyên lý DIP tập trung vào sự **lỏng lẻo trong liên kết (Loose Coupling)** giữa các thành phần thông qua 2 quy tắc:
1. Các mô-đun cấp cao (chứa business logic lõi) không nên phụ thuộc vào các mô-đun cấp thấp (database, network, file helper). Cả hai nên phụ thuộc vào abstractions (Interface).
2. Abstractions không nên phụ thuộc vào chi tiết. Chi tiết nên phụ thuộc vào abstractions.

### 3. Dependency Injection (DI)
DI là một mẫu thiết kế cụ thể nhằm hiện thực hóa IoC và DIP. Thay vì để một lớp tự khởi tạo các phụ thuộc của nó thông qua từ khóa `new`, các phụ thuộc đó sẽ được cung cấp từ bên ngoài. Có 3 kiểu tiêm phổ biến:
* **Constructor Injection**: Tiêm qua hàm khởi tạo (Khuyên dùng nhất).
* **Setter Injection**: Tiêm qua hàm setter.
* **Field/Interface Injection**: Tiêm trực tiếp vào trường (thường sử dụng reflection).

## 💻 Code Example: Phân biệt qua mã nguồn Java

### ❌ Vi phạm cả DIP và DI (Tight Coupling)
Lớp cấp cao `NotificationService` trực tiếp tự khởi tạo và phụ thuộc chặt chẽ vào lớp cấp thấp cụ thể `GmailSender`.

```java
// Lớp cấp thấp (Low-level detail)
public class GmailSender {
    public void send(String message) {
        System.out.println("Gửi Gmail: " + message);
    }
}

// Lớp cấp cao (High-level module)
public class NotificationService {
    // VI PHẠM DI: Tự khởi tạo phụ thuộc bằng 'new'
    // VI PHẠM DIP: Phụ thuộc trực tiếp vào class cụ thể (GmailSender) thay vì Interface
    private GmailSender sender = new GmailSender();

    public void sendNotification(String message) {
        sender.send(message);
    }
}
```
* **Hệ quả**: Nếu muốn chuyển đổi sang gửi qua `SmsSender` hoặc `TelegramSender`, ta phải mở file `NotificationService` để sửa lại code. Không thể mock `GmailSender` để viết Unit Test cô lập cho `NotificationService`.

### ✔️ Áp dụng DIP và DI (Loose Coupling)
1. Tạo một Interface làm cầu nối trừu tượng (**Áp dụng DIP**).
2. Cung cấp đối tượng cụ thể từ bên ngoài thông qua Constructor (**Áp dụng DI**).

```java
// 1. Khai báo Interface trừu tượng (Abstraction) - Áp dụng DIP
public interface MessageSender {
    void send(String message);
}

// Các chi tiết triển khai cụ thể phụ thuộc vào Abstraction
public class GmailSender implements MessageSender {
    @Override
    public void send(String message) {
        System.out.println("Gửi Gmail: " + message);
    }
}

public class SmsSender implements MessageSender {
    @Override
    public void send(String message) {
        System.out.println("Gửi SMS: " + message);
    }
}

// 2. Lớp cấp cao chỉ tương tác qua Abstraction - Áp dụng DIP & DI
public class NotificationService {
    // Đạt DIP: Chỉ phụ thuộc vào Interface
    private final MessageSender sender;

    // Đạt DI: Nhận phụ thuộc từ bên ngoài thông qua Constructor (Constructor Injection)
    public NotificationService(MessageSender sender) {
        this.sender = sender;
    }

    public void sendNotification(String message) {
        sender.send(message);
    }
}
```

## 📊 Bảng so sánh chi tiết: DIP vs DI vs IoC

| Tiêu chí | Inversion of Control (IoC) | Dependency Inversion Principle (DIP) | Dependency Injection (DI) |
| :--- | :--- | :--- | :--- |
| **Phân loại** | **Triết lý / Cách tiếp cận rộng** (Design Paradigm) | **Nguyên lý thiết kế** (Design Principle - Chữ D trong SOLID) | **Mẫu thiết kế / Kỹ thuật** (Design Pattern / Technical Pattern) |
| **Mục đích** | Đảo ngược quyền kiểm soát luồng thực thi hệ thống cho framework. | Giảm độ kết dính (Decoupling) giữa các module bằng cách đảo ngược hướng phụ thuộc. | Hiện thực hóa DIP bằng cách loại bỏ mã tự khởi tạo `new` bên trong class nghiệp vụ. |
| **Cách hoạt động** | Framework (như Spring) quản lý vòng đời và gọi mã của lập trình viên. | Định nghĩa các `Interface` / `Abstract Class` làm ranh giới giữa các tầng. | Cung cấp phụ thuộc thông qua Constructor, Setter hoặc Annotation. |
| **Ví dụ thực tế** | Spring Container quản lý vòng đời của Beans thay vì người dùng tự gọi `main`. | `OrderService` chỉ tương tác với interface `PaymentProcessor`. | `new OrderService(new PaypalProcessor())` hoặc `@Autowired`. |

## ⚠️ Common Gotchas (Câu hỏi phỏng vấn đào sâu)

### 1. Có thể áp dụng Dependency Injection (DI) mà không tuân thủ Dependency Inversion Principle (DIP) hay không?
* **Trả lời**: **Có thể.** Đây là một hiểu lầm cực kỳ phổ biến.
  * Ta hoàn toàn có thể "tiêm" (DI) một đối tượng cụ thể trực tiếp vào lớp sử dụng mà không thông qua bất kỳ Interface hay lớp trừu tượng nào.
  * *Ví dụ*:
    ```java
    public class NotificationService {
        private GmailSender gmailSender; // Class cụ thể, không phải Interface (Vi phạm DIP)
        
        // Vẫn áp dụng DI thông qua Constructor
        public NotificationService(GmailSender gmailSender) {
            this.gmailSender = gmailSender; 
        }
    }
    ```
  * Cách làm này đạt được DI (dễ viết unit test bằng mock hơn), nhưng **vi phạm DIP** vì module cấp cao vẫn dính chặt vào chi tiết lớp cụ thể `GmailSender`. Nếu đổi sang `SmsSender`, ta vẫn phải sửa lại signature của Constructor.

### 2. Sự nguy hại của Field Injection (`@Autowired` trên Field) là gì? Tại sao Constructor Injection luôn được Spring khuyến nghị hàng đầu từ bản 4.3 trở đi?
* **Trả lời**: Mặc dù `@Autowired` trực tiếp lên Field trông rất gọn gàng, nhưng nó có 3 nhược điểm chí mạng:
  1. **Khó viết Unit Test**: Khi test không dùng Spring Boot Container (Plain Unit Test), bạn không thể tiêm phụ thuộc vào field `private` ngoại trừ việc phải lạm dụng Reflection. Với Constructor Injection, ta chỉ cần gọi `new NotificationService(mockSender)` cực kỳ sạch sẽ.
  2. **Vi phạm tính Immutable (Bất biến)**: Field được tiêm bằng `@Autowired` không thể khai báo là `final`. Phụ thuộc có thể bị thay đổi vô tình sau khi đối tượng đã khởi tạo xong. Với Constructor, ta có thể khai báo `private final MessageSender sender;`.
  3. **Không phát hiện được Circular Dependency lúc khởi động**: Constructor Injection giúp Spring phát hiện lỗi phụ thuộc vòng tròn (Circular Dependency) ngay lập tức khi ứng dụng khởi động (sẽ ném ra ngoại lệ). Field Injection chỉ phát hiện lỗi này khi runtime khi một phương thức cụ thể được gọi, gây rủi ro crash hệ thống trên production.
