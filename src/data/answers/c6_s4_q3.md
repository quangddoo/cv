# Phân tích và cải thiện complexity — Tối ưu theo constraint
## ⚡ Tóm tắt ngắn (30s)
* Định nghĩa n và các kích thước input trước khi đếm work.
* Phân biệt loop, sort, number of states, data structure cost và auxiliary space.
* Chỉ tối ưu khi constraint cần; bảo vệ correctness/readability sau tối ưu.

---

## 🔍 Cách trả lời từng bước
### 1. Đặt biến và model
Tôi nói n là số phần tử, m là số cạnh/chuỗi thứ hai hoặc k là top-k. Nếu input là graph, O(V+E) khác O(n); nếu parse string Unicode, “character” có thể khác code unit. Model rõ giúp tránh Big-O giả.

### 2. Đếm repeated work
Tôi xem mỗi phần tử vào stack/map bao nhiêu lần, có nested loop thực sự độc lập không, sort có dominates không, và DP có bao nhiêu state/transition. Với hash map, tôi nói average-case và assumption; với tree, nêu height.

### 3. Tối ưu theo bottleneck
O(n²) có thể đổi thành lookup O(1), sort + scan, prefix sum, monotonic stack, heap hoặc DP memoization. Tôi không đổi sang structure khó debug nếu n nhỏ hoặc constraint cho phép.

### 4. Re-check implementation
Sau tối ưu, tôi test duplicate/edge case, phân tích memory, cache locality/constant factor khi relevant và xác nhận code khớp claim.

---

## 💻 Ví dụ trả lời / worked example
Với two-sum, brute force thử mọi cặp là O(n²), space O(1). Nếu n lớn và không yêu cầu giữ thứ tự đặc biệt, tôi dùng map value → index: với mỗi x, kiểm tra target-x đã thấy chưa rồi lưu x. Mỗi phần tử xử lý một lần, average O(n) time, O(n) space.

Tôi nói rõ worst-case hash collision có thể khác, và nếu input đã sort hoặc có thể sort thì có thể dùng two pointers O(n log n) do sort, O(1) extra tùy requirement. Nếu interviewer yêu cầu trả về original indices và không được mutate input, map là lựa chọn phù hợp hơn.

Điểm quan trọng không phải luôn chọn O(n), mà là chọn theo constraint và contract.

## 📊 Follow-up interviewer có thể hỏi
| Follow-up | Hướng trả lời mạnh |
| :--- | :--- |
| Space có tính output không? | Nói rõ auxiliary space và output space. |
| Hash map có luôn O(1) không? | Nói average-case, assumption và alternative nếu cần. |
| Có thể đổi time lấy space không? | Nêu trade-off và memory limit. |
| Tối ưu nữa được không? | Xem constraint, lower bound và constant factor trước khi complexity. |

---

## ⚠️ Common Mistakes & Pro Tips
1. **Không nói O(n) nhưng dùng sort/substring ẩn.**
2. **Không quên cost của recursive stack.**
3. **Không nhầm average với worst case.**
4. **Không hy sinh proof và readability cho optimization không cần thiết.**

**Mục tiêu của câu trả lời:** cho thấy cách suy nghĩ có cấu trúc, ownership cá nhân, khả năng định lượng impact và sự trung thực về trade-off cũng như giới hạn của solution.
